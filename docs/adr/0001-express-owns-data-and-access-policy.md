# ADR-0001: Express владеет базой и политикой доступа, Next только показывает UI

Сейчас политика доступа вычисляется в трёх местах. Express делает это в `services/rbac`, в `middleware/auth/session.ts` и в проверках по строкам ролей. Next делает это в `app/web/lib/auth/server/getMeData.ts`, у которого свой пул `pg` и своя проверка JWT. `getServerMe` на каждом запросе выбирает между HTTP к Express и этой копией. Одно и то же правило приходится чинить в двух приложениях, а пулы соединений с PostgreSQL удваиваются.

## Решение

- **База, токены и права живут только в `app/server`.** Обращения к PostgreSQL, выпуск и проверка JWT и вычисление эффективных прав есть только там. Эффективные права считаются одним модулем от ролей и overrides. Все проверки Express и `/api/auth/me` идут через него.
- **Next ходит только в Express.** `app/web` получает текущего пользователя и его права по HTTP из `/api/auth/me` и только проверяет готовый список прав. В `app/web` нет `pg`, `jsonwebtoken`, `DATABASE_URL` и `AUTH_JWT_SECRET`.
- **`packages/rbac` остаётся словарём.** В нём реестр ролей, доменов и действий. Второго алгоритма вычисления прав рядом с серверным не появляется.

## Рассмотренные варианты

Отклонён перенос API в route handlers или server actions Next. В Express 103 обработчика, которые пришлось бы переносить без выигрыша. У Express уже есть обычная точка запуска, а на VPS с Docker Compose отдельный контейнер API естественен.

## Последствия

- Удаляются `getMeData`, `app/web/app/api/auth/me/route.ts` и пул `pg` в Next.
- Server rendering должен уметь обновлять сессию через refresh, иначе короткие access-токены (план 003) будут выкидывать пользователя на логин. Для этого нужен один модуль веб-сессии: кто текущий пользователь, 401 → refresh → retry, редирект на логин.
- UI берёт гейты маршрутов из тех же прав, что проверяет Express. Своих обходов `isAdmin` и проверок по строкам ролей в React нет.
