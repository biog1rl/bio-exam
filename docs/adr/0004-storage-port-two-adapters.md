# ADR-0004: Хранилище файлов: один интерфейс, два адаптера

Развилка «Supabase или локальный диск» сейчас живёт не в модуле хранилища, а в маршрутах: `routes/docs/assets.ts`, `routes/users/avatar.ts` и `routes/tests/index.ts`. Пути в них считаются вручную через `fs`. Режимы ошибок расходятся: без Supabase `readFile` молча возвращает `''`, а запись бросает исключение. Web разбирает URL Supabase регуляркой (`lib/image-signed-url-cache.ts`). Для переезда на VPS нужно локальное хранилище с тем же контрактом.

## Решение

- **Одна точка доступа.** Модуль хранилища — единственное место, через которое идёт работа с файлами.
- **Два адаптера.** Supabase используется сейчас, локальный том нужен для VPS.
- **Логика внутри модуля.** Нормализация ключей, проверка, что путь не выходит за корень (containment), правило «ключ → URL» и единые режимы ошибок живут в модуле.
- **Маршруты** не трогают `fs` и не считают пути.
- **Web** получает готовые URL от API и не знает, как разложены файлы в хранилище.
- **Тесты.** Один контрактный набор тестов прогоняется на обоих адаптерах.

## Кто читает пространство

| Пространство | Кто читает                                                         | Как отдаётся                                                                                      |
| ------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `images/`    | любой вошедший (картинки вопросов и медиатека)                     | общий прокси, ссылка `storageUrl`                                                                 |
| `avatars/`   | любой вошедший                                                     | общий прокси, ссылка `storageUrl`                                                                 |
| `topics/`    | любой вошедший, только ключи `…/assets/…`                          | общий прокси, ссылка `storageUrl`                                                                 |
| `answers/`   | владелец сессии; после сдачи ещё проверяющие по `canReviewAttempt` | только отдельный маршрут раздачи фото, никогда общий прокси; `storageUrl` для него бросает ошибку |

Правило записано в коде таблицей `NAMESPACE_READERS` (`app/server/src/services/storage/keys.ts`): новое пространство без записи в ней не компилируется, `isServableImageKey` и `storageUrl` выводятся из неё.

## Обработка фото и память

Правило приёма изображения живёт в одном модуле `app/server/src/services/assets/image-intake.ts` (`acceptImage` с профилем). Через него идут фото ответа, медиатека, встроенные картинки вопросов и аватар.

| Настройка                      | Значение                                                                                                                                                                                           |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Размер файла                   | фото ответа до 10 МБ; медиатека и аватар до 5 МБ                                                                                                                                                   |
| Тип                            | по сигнатуре буфера, заголовок `Content-Type` и имя файла не учитываются; фото ответа и медиатека — JPEG, PNG, WebP; встроенные картинки и аватар — ещё GIF; нет сигнатуры — 400, другой тип — 415 |
| HEIC                           | не принимается: 415 с отдельным текстом у фото ответа                                                                                                                                              |
| Лимит пикселей                 | 50 млн во всех профилях; проверка по заголовку до декодирования (413) и `limitInputPixels` в sharp                                                                                                 |
| Фото ответа                    | длинная сторона 2560 px, WebP q82, миниатюра 400 px WebP q75                                                                                                                                       |
| Медиатека, встроенные картинки | длинная сторона 1920 px, WebP q85                                                                                                                                                                  |
| Аватар                         | исходник перекодируется в формате сигнатуры (JPEG q90, WebP q90, PNG, GIF), кроп 256 px PNG от выпрямленного исходника                                                                             |
| Поворот и метаданные           | `autoOrient()` во всех профилях; EXIF, GPS, XMP и ICC в результат не попадают                                                                                                                      |
| sharp                          | `sharp.cache(false)`, `sharp.concurrency(1)` при загрузке модуля                                                                                                                                   |
| Ограничитель                   | один на процесс: одновременно `IMAGE_INTAKE_CONCURRENCY = 1` обработка, очередь `IMAGE_INTAKE_QUEUE_LIMIT = 8`; при полной очереди фото ответа получает 503, остальные профили ждут                |

Буфер запроса держится в памяти до ответа; клиент шлёт фото по одному, уменьшенным JPEG до 2560 px.

### Замер

Скрипт `app/server/src/scripts/photo-memory-bench.ts`: синтетические входы, каждый случай в отдельном процессе, пик RSS — прирост над базой процесса, опрос каждые 5 мс, профиль фото ответа. Запуск: `yarn workspace @bio-exam/server tsx src/scripts/photo-memory-bench.ts` (в образе API — `node dist/scripts/photo-memory-bench.js`), флаги `--series <n>`, `--dir <каталог>` для реальных снимков, `--out <каталог>` для записи результата.

Машина разработчика: macOS arm64, Node 24.17.0, sharp 0.35.5, libvips 8.18.7. Пик RSS в МБ / время в мс.

| Вход                                              | Файл, МБ | 1 обработка                           | 2 подряд (concurrency 1) | 2 одновременно (concurrency 2) |
| ------------------------------------------------- | -------- | ------------------------------------- | ------------------------ | ------------------------------ |
| JPEG 4,9 МП (2560×1920, как шлёт клиент)          | 3,1      | 87 / 603                              | 114 / 1125               | 193 / 577                      |
| JPEG 12 МП, Orientation 6 и 8                     | 7,5      | 84 / 615                              | 104 / 1223               | 182–186 / 625                  |
| JPEG 48 МП, Orientation 6 и 8                     | 30,1     | 69 / 698                              | 89 / 1385                | 149–151 / 705                  |
| PNG 24 МП однотонный, Orientation 6 и 8           | 0,3      | 59 / 252                              | 79 / 500                 | 134 / 258                      |
| PNG 48 МП однотонный, Orientation 6 и 8           | 0,6      | 74–75 / 394                           | 95–96 / 785              | 165–166 / 408                  |
| PNG 49 МП однотонный                              | 0,6      | 63 / 228                              | 91 / 453                 | 149 / 238                      |
| WebP lossless 48 МП однотонный, Orientation 6 и 8 | 0,003    | 308 / 338                             | 308 / 649                | 597–614 / 350                  |
| WebP q80 48 МП с шумом, Orientation 6             | 23,2     | 276 / 1472                            | 312 / 2852               | 602 / 1455                     |
| PNG 64 МП однотонный                              | 0,8      | отказ 413 по заголовку, 0,7 МБ / 2 мс | —                        | —                              |

Серия из 30 обработок JPEG 12 МП подряд при concurrency 1: RSS процесса после обработок держится в диапазоне 194–255 МБ и после 30-й равен 217 МБ, без роста ступенькой; среднее 612 мс на фото, около 98 фото в минуту.

- Пик растёт примерно линейно с числом одновременных обработок. JPEG декодируется в уменьшенном масштабе и дешевле прочих форматов; WebP 48 МП декодируется целиком и даёт худший случай — около 310 МБ на одну обработку.
- `IMAGE_INTAKE_CONCURRENCY = 1`: пара при concurrency 2 вдвое быстрее, но её пик на WebP 48 МП — около 600 МБ, выше предела 200 МБ на пару.
- Очередь 8: ждущие задачи держат только буферы запросов, до 80 МБ при файлах по 10 МБ.
- Образ API (Linux): замер выполняет пользователь командой `node dist/scripts/photo-memory-bench.js` в отдельном контейнере того же образа с лимитом памяти контейнера API, серией и реальными снимками (`--dir`); лимит памяти контейнера решает пользователь по замеру.

## Последствия

- Переезд на VPS сводится к включению второго адаптера.
- Защита от выхода за корень (план 006) и потоковый ZIP (план 008) реализуются один раз внутри модуля.
