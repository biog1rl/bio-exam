# 011. Углубление модулей: архитектурный обзор

Дата: 2026-10-02. Код: `ebf9e65`, ветка `master`.
Статус: TODO. Решения, на которые опирается план: [ADR-0001](../docs/adr/0001-express-owns-data-and-access-policy.md) – [ADR-0005](../docs/adr/0005-decompose-by-concept.md).

Обзор охватывает горячие точки за последние 40 коммитов: прохождение теста и разбор попытки, авторинг тестов, auth, слой запросов, пользователей и поиск. Исследование шло только чтением кода. Номера строк взяты из отчётов исследования; перед планированием фазы их нужно перепроверить. Факты, перепроверенные вручную, отмечены ✓.

Словарь обзора: **модуль** (интерфейс плюс реализация), **глубокий модуль** (много поведения за маленьким интерфейсом), **шов** (место, где живёт интерфейс), **адаптер** (конкретная реализация на шве), **локальность** (изменения и баги сосредоточены в одном месте).

## 2. Кандидаты на углубление

### C1. Модуль шаблона вопроса, общий для web и server (Strong) → ADR-0002

- **Файлы.**
  - Server: `lib/tests/{scoring,question-type-resolver,question-types}.ts`, `schemas/tests.ts`.
  - Web: `components/tests/{QuestionInput,TestRunner}.tsx`, `attempt-review/{attempt-review-utils.ts,QuestionAnswerReview.tsx}`, `admin/tests/types/index.ts`, `QuestionEditorPageClient.tsx`, `test-editor/test-editor-utils.ts`.
- **Проблема.** Поведение шаблона описано примерно в 11 местах двух приложений, и копии разошлись (D2, D5).
  - Валидация ключа выполняется в четырёх местах и в двух словарях: по ключу типа и по `uiTemplate`.
  - Web повторно вычисляет вердикты по каждой части ответа, хотя сервер уже считает ошибки.
  - Только web правили коммиты `ebf9e65`, `3aa452a` и `a51b673`. Только сервер правил `04c621c`.
- **Решение.** Пакет `packages/exam-core` с адаптером на каждый шаблон. Адаптер отвечает за форму ключа, форму ответа, «отвечено ли», нормализацию, ошибки и баллы, вердикты по частям.
- **Тесты через интерфейс.** Таблица на каждый шаблон: (ключ, ответ) → оценка и вердикты, плюс инвариант «все части верны ⇔ ошибок 0».
- **Пересечения.** Нет. План 004 оценку явно исключает.

### C2. Оценённая попытка и её вид для каждого зрителя (Strong) → ADR-0005

- **Файлы.**
  - Server: `routes/tests/public.ts:695-903` (submit), `routes/tests/index.ts:2601-2730` (разбор у администратора), `lib/tests/submit-result.ts`.
  - Web: `lib/tests/types.ts:56-114`, `components/tests/AttemptReview.tsx`, `QuestionAnswerReview.tsx`, `TestRunner.tsx:745-770`.
- **Проблема.**
  - Попытка хранит урезанный вид для студента, а разбор у администратора достраивает её текущими ключом и вопросами (D1).
  - Правило скрытия ключа web угадывает в четырёх местах.
  - Тип результата объявлен шесть раз. При чтении результаты не проверяются по схеме (`unknown[]` с приведением типа).
  - Статус вопроса считается в двух местах и не совпадает при `points === 0`.
- **Решение.** При submit сохраняются факты оценки: ключ, по которому оценивали, ошибки и вердикты по частям. Вид для студента с ключом, студента без ключа и администратора строится при чтении в одном модуле.
- **Тесты через интерфейс.** Ключ, исправленный после сдачи, не меняет разбор. Три вида одной попытки.
- **Пересечения.** План 004 задаёт транзакцию submit. Этот кандидат выполняется **вместе** с 004, потому что меняет то, что транзакция записывает. Данные для старых попыток нужно перенести отдельной миграцией (решить при планировании).

### C3. Содержимое вопроса на сервере (Strong) → ADR-0005

- **Файлы.**
  - `routes/tests/index.ts`: `/save` (1456-1512), POST (1764-1812), PATCH (1890-1939), settings (1619-1645), move (2118-2170), delete (2231-2243).
  - `routes/tests/public.ts:60-95`, `services/storage/storage.ts`, `services/search/question-documents.ts`.
- **Проблема.** Вопрос состоит из пяти частей, и каждый из примерно 9 обработчиков собирает их сам. Части: строка в БД, версии ключа, файлы промпта и пояснения, документ поиска, путь от slug.
  - Пути переносятся тремя разными способами, PATCH slug темы не переносит их вообще.
  - Порядок вопросов поддерживается четырьмя разными способами.
  - Два блока чтения у администратора совпадают байт в байт.
  - `settings.json` пишется и нигде не читается.
  - GET-экспорт с `withAnswers` записывает `answer_keys.json` в хранилище.
- **Решение.** Один модуль отвечает за жизненный цикл вопроса (создать, править, перенести, удалить, прочитать), включая согласованность БД и файлов и непрерывный порядок.
- **Тесты через интерфейс.** Операции на реальной БД плюс in-memory адаптер хранилища, с проверкой, что БД и файлы согласованы. Отдельно: переименование slug и сбой записи файла.
- **Пересечения.** План 010 (нарезка роутера идёт после этого модуля, ADR-0005), план 008 (ограниченная параллельность загрузки промптов в одном месте).

### C4. Шов хранилища с двумя адаптерами (Strong) → ADR-0004

- **Файлы.** Server: `services/storage/storage.ts`, `routes/docs/assets.ts`, `routes/users/avatar.ts`, `routes/tests/index.ts:2303-2350`, `app.ts:89`. Web: `lib/image-signed-url-cache.ts`, `components/tests/MdxRenderer.tsx`.
- **Проблема.**
  - Развилка Supabase или локальный диск живёт в маршрутах.
  - Режимы ошибок расходятся: без Supabase `readFile` молча возвращает `''`, а запись бросает исключение.
  - Web разбирает URL Supabase регуляркой.
  - Картинки промптов лежат в общем `images/`, поэтому ZIP теста их не включает, а медиатека может удалить картинку, которая ещё используется.
- **Решение.** Один интерфейс хранилища и два адаптера: Supabase и локальный том. Нормализация ключей и защита от выхода за корень живут внутри модуля.
- **Тесты через интерфейс.** Один контрактный набор на оба адаптера, плюс тесты на выход за корень (traversal).
- **Пересечения.** План 006, план 008 (ZIP), `plans/beget-migration.md` §3.2.

### C5. Политика эффективных прав (Strong) → ADR-0001

- **Файлы.**
  - `packages/rbac/src/rbac.ts:20-40`.
  - Server: `services/rbac/rbac.ts:62-141`, `middleware/auth/session.ts:82-100`, `requirePerm.ts`, `routes/auth/me.ts:24-31`.
  - Web: `lib/auth/server/getMeData.ts`, `AuthGuard.tsx:62`, `admin/layout.tsx`.
- **Проблема.**
  - Роли раскрываются тремя разными алгоритмами. Версия из пакета учитывает `inherits`, серверная не учитывает.
  - В одном запросе Express проверки по строкам ролей видят роли из БД и JWT, а `requirePerm` только из БД.
  - D4.
  - `AuthGuard` пропускает администратора мимо любых прав, есть ещё четыре ручные проверки `isAdmin`.
  - `/admin/**` в UI закрыт правами `rbac.*`, а Express пускает к тестам по `tests.*`.
- **Решение.** Один модуль на сервере: роли + overrides → эффективные права. У модуля шов на загрузке грантов (адаптеры Drizzle и in-memory). Все проверки Express и `/auth/me` идут через него.
- **Тесты через интерфейс.**
  - Роль снята после выдачи токена.
  - Запрет из БД, наложенный на администратора.
  - `inherits`.
  - `/auth/me` и `requirePerm` дают одинаковый ответ.
- **Пересечения.** План 003 (шаги 2, 6), план 010 (шаг 4).

### C6. Модуль веб-сессии (Strong) → ADR-0001

- **Файлы.** `app/web/lib/auth/{getServerMe,fetchMe,refresh,authMePayload,loginRedirect,sessionCookie}.ts`, `lib/api-fetch.ts`, `proxy.ts`, `components/providers/AuthProvider.tsx`, `AuthGuard.tsx`, `app/providers.tsx`, `AppLayout.tsx`, `app/api/auth/me/route.ts`.
- **Проблема.**
  - Двойной `AuthProvider` (D3).
  - Refresh с повтором запроса реализован дважды с разными условиями: `apiFetch` срабатывает на 401, `fetchAuthMe` на ответ 200 с `ok:false`.
  - Редирект на логин собирается тремя способами.
  - Server rendering не делает refresh (D8).
  - `API_ORIGIN` одновременно задаёт маршрутизацию на этапе сборки и выбирает адаптер во время работы.
- **Решение.** Один модуль на web отвечает за то, кто текущий пользователь (при server rendering и на клиенте), за цепочку 401 → refresh → retry и за редирект на логин с callback. Адаптеры: HTTP к Express и fake для тестов. Адаптер через `pg` удаляется.
- **Тесты через интерфейс.**
  - Server rendering при истёкшем access-токене и живом refresh-токене.
  - Несколько одновременных 401 дают один refresh.
  - Неудачный refresh ведёт на логин с callback.
- **Пересечения.** Планы 003, 010, `beget-migration.md` §3.4.

### C7. Жизненный цикл попытки на клиенте (Worth exploring) → ADR-0005

- **Файлы.** `app/web/components/tests/TestRunner.tsx`, `components/tests/telemetry.ts`, `app/server/src/lib/tests/telemetry.ts`.
- **Проблема.**
  - `TestRunner` держит 15 `useState`, 5 `useRef`, 8 `useEffect` и 17 обращений к localStorage.
  - Фаза попытки вычисляется заново в трёх местах.
  - При пересдаче приходится вручную сбрасывать 5 refs, 9 setters и 3 ключа. Ровно это чинил коммит `29563ff`.
  - Тесты покрывают редьюсеры, а оба бага телеметрии были в эффектах.
  - Слияние телеметрии скопировано между web и server.
- **Решение.** Резать по жизненному циклу: фазы × события. Модуль отвечает за формат черновика, телеметрию и сброс. Шовы: хранилище, API, часы, видимость вкладки.
- **Тесты через интерфейс.** Последовательности событий с fake clock:
  - пересдача;
  - скрытая вкладка не накапливает время;
  - ответ на Q2 в окне debounce не теряет Q1 (баг из плана 005).
- **Пересечения.** Это способ выполнить план 005 (шаги 1, 3) и план 010 (шаг 3, заменён ADR-0005), а не отдельная работа.

### C8. Типизированные запросы по доменам и справочник пользователей (Worth exploring)

- **Файлы.** `app/web/lib/{api-fetch,fetcher,swr-config}.ts`, `lib/tests/api.ts` (образец нужной формы), `components/users/*`, `components/groups/GroupSheet.tsx`, `admin/users/[id]/page.tsx`, `app/server/src/routes/users/index.ts`.
- **Проблема.**
  - В коде 17 локальных fetcher'ов примерно пяти разных форм, часть из них не проверяет `ok` и не передаёт credentials.
  - `swrConfig` и `swrOptions` нигде не импортируются.
  - `apiFetch` возвращает сырой `Response`.
  - Отдельного интерфейса поиска пользователя нет (D7).
  - Server-страницы ходят в Express двумя путями: через `API_ORIGIN` и через самовызов `absoluteUrl`.
- **Решение.** Повторить форму `lib/tests/api.ts` для users и groups поверх одного модуля запросов, который отвечает за 401, ответы с ошибкой и некорректный JSON. На стороне Express добавить поиск пользователя по id или login.
- **Пересечения.** План 007 (шаг 1, только клиентская часть).
