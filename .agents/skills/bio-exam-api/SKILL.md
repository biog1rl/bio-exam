# bio-exam api

Express владеет данными и политикой доступа (`docs/adr/0001-express-owns-data-and-access-policy.md`). Правило декомпозиции по понятиям: `docs/adr/0005-decompose-by-concept.md`.

## Доступ

- Права пользователя: `requestAccess(req)` и `hasPermission(req, key)` в `app/server/src/services/access-policy/index.ts`, один расчёт на запрос.
- Доступ к объекту решают только функции `app/server/src/services/access-policy/scope.ts`: `canReadTest`, `canWriteTest`, `canWriteTopic`, `canReviewAttempt`, `canReadUser`, `canManageCatalog`, `canManageGroup`, `canManageStudent`, `canAssign`, `canAssignMany`, `canAssistSignIn`, `canReadAnswerPhoto`, `hasGlobalZone`; фильтры списков `testScope`, `groupScope`, `userScope`. Новая проверка объекта добавляется туда, а не в маршрут.
- Чтение теста без `Request`: `canUserReadTest(userId, testId)` из `app/server/src/services/access-policy/scope.ts` (фабрика `createUserTestRead` в `scope-rules.ts`) - то же правило, что `canReadTest`: `tests.read`, при `zone.all` любой тест, иначе тема теста в зоне. Им пользуется правило слота фото, у ссылки загрузки пользователя в запросе нет.
- `requirePerm` и `requirePermKey` (`app/server/src/middleware/auth/requirePerm.ts`) закрывают раздел по ключу права; объектные маршруты проверяют доступ функциями `scope.ts`, а не `requirePerm`.
- Решения по строке роли (`'admin'`, `roles.includes(...)`) запрещены, разрешено только право из `@bio-exam/rbac`: это держит `scripts/auth-no-role-string-checks.test.mjs`.
- Пункты бокового меню: `GET /api/sidebar` требует сессию и отдаёт только пункты, которые пользователь может открыть (`canOpenPath` из `packages/rbac/src/sections.ts`); запись проходит схему `app/server/src/routes/sidebar/schema.ts` — адрес только `/…` или `http(s)://`.
- Настройки графиков: `GET /api/settings/charts` открыт любому вошедшему, `PUT` требует `settings.manage` (`app/server/src/routes/settings.ts`). Схемы и значения по умолчанию — `app/server/src/lib/charts/config.ts`: при чтении испорченное поле заменяется значением по умолчанию, запись проверяется строго; хранится одна строка `chart_settings` с `configs` (jsonb) по ключу графика.
- Адрес темы не может совпадать со статическими страницами банка (`RESERVED_TOPIC_SLUGS` в `packages/rbac/src/sections.ts`): `POST`/`PATCH /api/tests/topics` отвечают 400. Новая статическая страница прямо под `/admin/tests/` добавляется в этот список.

## Роли и зона учителя

- Роли `admin`, `teacher`, `user` («Ученик») в `packages/rbac/src/roles.ts`; персонал `STAFF_ROLE_KEYS`, роль ученика `STUDENT_ROLE_KEY`. Право `zone.all` (домен `zone` в `packages/rbac/src/domains.ts`) есть у `admin` и снимает ограничение зоной.
- Зона пользователя без `zone.all`: закреплённые разделы (`teacher_topics`) и группы, где он владелец (`student_groups.owner_id`). Тесты и попытки зоны - тесты и попытки этих разделов, ученики - участники этих групп.
- Зону читает загрузчик `ZoneLoader` (`app/server/src/services/access-policy/zone-loader.ts`) внутри `createAccessScope` (`app/server/src/services/access-policy/scope-rules.ts`): заново на каждом запросе, с мемоизацией на `Request` (`WeakMap`), без кэша между запросами. Ошибка загрузчика или проверки права пробрасывается, запрос без `req.authUser` получает `false` или пустую зону.
- `canReadAnswerPhoto(req, photoId)`: владелец сессии фото читает всегда; проверяющий - только когда у сессии есть `attempt_id`, через `canReviewAttempt`; субъект (`answerPhotoSubject` загрузчика зоны) - строка `answer_photos` с `test_sessions.user_id` и `attempt_id`.
- Формула функции шва: нет права действия → `false`; `zone.all` → `true`; иначе объект в зоне. `canManageCatalog` = `tests.write` и `zone.all`. `canAssign` и пакетный `canAssignMany` требуют `tests.manage_assignments`, тест в разделе зоны и ученика своей группы. `canAssistSignIn` с `zone.all` требует `users.edit`, без него - `canManageStudent`.
- Списки: грубый гейт `requirePerm` в регистрации и фильтр зоны `testScope`, `groupScope` или `userScope` (`{ all: true }` или идентификаторы). Пустая зона - пустой список. Объектный маршрут без `requirePerm` первой строкой вызывает функцию шва: отказ - 403 до поиска объекта, затем 404.
- Ветвление «администратор или учитель» в маршруте - только `hasGlobalZone(req)`; литерала `zone.all` вне `app/server/src/services/access-policy` нет.
- Ученик - роль ученика, других ролей нет, allow-строк `rbac_user_grants` нет. Правило записано один раз SQL-фрагментом `studentOnlyFilter`.
- Таблицы зоны пишут только функции `app/server/src/services/access-policy/zone-store.ts`: `setTopicTeachers`, `setGroupOwner`, `releaseZone`; для показа - `topicTeachers`, `groupOwners`, `zoneOwnerCandidates`. Признаки ролей `ownsZone` и `groupMember`: `roleTraits` и `loadRoleTraits` в `app/server/src/services/access-policy/role-traits.ts`.
- Охранный тест `scripts/teacher-zone-guards.test.mjs`: таблицы зоны и `zone.all` только в шве, инвентарь маршрутов с их функциями шва. Новый маршрут доступа к объекту зоны добавляется в инвентарь теста.

## Вход и сессии

- Сессии входа: `app/server/src/services/session/index.ts` - `openSession`, `rotateRefreshToken` (исходы `rotated`, `reused` в окне `REFRESH_REUSE_WINDOW_MS`, `replay` с отзывом сессии, `rejected`), `revokeSession`, `revokeUserSessions`, `endSession`, `loadSessionUser`.
- Повтор израсходованного refresh-токена разбирает `classifyRepeat` под блокировкой строк преемников и сессии: преемник уже использован или предъявлен отозванный токен живой сессии → `replay`; повтор в окне или повторная выдача в окне → `reused` (только access); иначе ответ ротации считается потерянным: неиспользованные преемники отзываются, выдаётся новый refresh (`rotated` с `regranted: true`, событие `refresh_regrant` в журнале).
- Куки: `app/server/src/services/session/cookies.ts`; токены: `app/server/src/services/session/tokens.ts`; разбор сессии в запросе: `app/server/src/middleware/auth/session.ts`; маршруты: `app/server/src/routes/auth`.
- Ограничение попыток входа: `app/server/src/services/login-throttle`.

## Попытка теста

- `app/server/src/services/attempt-sessions` (вход `index.ts`): доступ (`checkAttemptAccess`, `findVisibleTest`, `findVisibleTestBySlug`, `isAssignedOrPrivileged`, `visibleTestsFilter`); команды `startAttemptSession(pair)`, `saveSessionDraft(pair, sessionId, draft)`, `submitSession(pair, request)` (`commands.ts`) сами решают, когда финализировать просроченную сессию, и отвечают исходом словаря `SessionOutcome` (`outcome.ts`); финализация `finalizeSessionByDeadline(sessionId, owner?)`, `findSessionsDueForFinalization`, `closeStaleOpenSessions` (`deadline.ts`); окно фото `photoUploadWindow`, `uploadWindowRefusal`, `uploadWindowState` (`upload-window.ts`); `databaseNow`, `DEADLINE_FINALIZE_MAX_AGE_HOURS` (`sessions.ts`). Шаги `precheckSubmit`, `submitAttempt`, `closeSessionAsExpired` внутренние (`submit.ts`), в `index.ts` их нет.
- Маршрут переводит исход в HTTP одной функцией `sendSessionOutcome(res, route, outcome, viewer)` в `app/server/src/routes/tests/public.ts` (`route`: `start`, `draft`, `fate`, `submit`); новый исход добавляется в словарь и в эту функцию, а не в обработчик.
- Просроченная сессия теста с лимитом сдаётся сервером по черновику: `finalizeSessionByDeadline`, источник `deadline`, `submitted_at` - конец таймера (`started_at` плюс лимит), пустой черновик закрывает сессию `expired` без попытки. Давность (D-21): сдаются только сессии, у которых дедлайн плюс льгота прошли не раньше `DEADLINE_FINALIZE_MAX_AGE_HOURS` (24 ч), более давние закрываются `expired`, `draft_answers` остаётся. Просрочку везде считает `sessionExpired(limit, marginSeconds)` из `sessions.ts` - ленивые пути, задача и давность берут одну формулу.
- Ошибка данных при финализации закрывает сессию `expired` и пишется в лог; временная ошибка базы (`isTransientDbError` из `app/server/src/lib/db-errors.ts`) пробрасывается и повторяется. Ленивая финализация идёт на `/start`, PATCH черновика, `/submit` и чтении судьбы.
- Судьба сессии: `GET /api/tests/public/tests/:id/sessions/:sessionId` отдаёт `open | submitted | expired` по `SessionFateSchema`. Ответ `/submit` после серверной сдачи - 409 `ATTEMPT_ALREADY_SUBMITTED` с `submitSource: 'deadline'`, `uploadClosesAt`, `serverNow`, `attempt`; одно тело «сдано» для судьбы и 409 строит `submittedBody`.
- Окно фото: `tests.photo_upload_window_minutes` (0-120, по умолчанию 15), `test_attempts.upload_closes_at` считает база в той же вставке, что попытку. `photoUploadWindow` решает на `clock_timestamp()` базы и вызывается сервисом фото в транзакции после `FOR UPDATE` сессии; отказ - 422 `UPLOAD_WINDOW_CLOSED` или `UPLOAD_WINDOW_NONE` с `uploadClosesAt`, текст ученику строит web по коду.
- Фото ответа: `app/server/src/services/answer-photos` - единственный, кто строит ключи `answers/…`. Принимает ли слот фото, решает одна функция `readPhotoSlot(executor, place)` (`app/server/src/services/answer-photos/slot.ts`) от места `AnswerPhotoPlace` (`owner: { testId, userId }`, `sessionId`, `questionId`), а не от `Request`: владелец активен (`users.is_active`), `checkAttemptAccess` с `canUserReadTest` (назначение или право чтения теста), сессия принадлежит владельцу, вопрос из теста сессии с шаблоном `open`; ответ - `{ kind: 'refused', reason }` (`test_missing`, `not_assigned`, `slot_missing`, `user_inactive`) или `{ kind: 'slot', test, rule, window }` с правилом вопроса (`allowPhotos`, `maxPhotos`) и сырым состоянием окна. Части доступа ходят через глобальный `db`, поэтому `readPhotoSlot(db, …)` вызывается до транзакции, под блокировкой не вызывается. `placeOfSession(executor, sessionId, questionId)` строит место по владельцу сессии.
- `uploadAnswerPhoto(place, photoId, buffer, via)` идемпотентна по клиентскому `photoId` (та же сессия и вопрос → `existing` без обработки и без проверки слота, другие → `conflict` 409), затем `readPhotoSlot(db)` (отказ → `missing`, окно → 422, `allowPhotos = false` → `forbidden` 409 `ANSWER_PHOTO_FORBIDDEN_MESSAGE`); под `FOR UPDATE` сессии через `tx` повторяются окно, правило вопроса и счёт, лимит - `max_photos` вопроса (409 с `answerPhotoLimitMessage(max)`). Источник `via` (`AnswerPhotoSource`: `session` или `link`) пишется в `answer_photos.uploaded_via`. sharp в транзакции не вызывается, при отказе свои файлы удаляются. `deleteAnswerPhoto` - `refused` (слот не принимает), `absent` с `count` (фото нет в слоте), `deleted` с `count`; строка удаляется при открытом окне, файлы - после коммита. `removeUserAnswerPhotos(userId)` удаляет файлы фото ученика до строки пользователя (`DELETE /api/users/:id`). `readAnswerPhotoFile(photoId, variant, slot?)` строит ключ из строки базы и с `slot` отдаёт только фото этого слота.
- Маршруты фото под сессией - `app/server/src/routes/tests/session-photos.ts`, монтируется как `/tests/public` после маршрутов ученика: `PUT` и `DELETE /api/tests/public/tests/:id/sessions/:sessionId/questions/:questionId/photos/:photoId` (PUT - multipart с полем `file`, 201 новое, 200 повтор, тело `{ photo, count }`; DELETE - `{ count }`, отказ слота и отсутствие фото - 404 `{ error: 'Фото не найдено' }`), `GET …/questions/:questionId/photos` - `{ photos }`. Отказы слота: 404 `Test not found`, 403 `Тест не назначен`, 404 `Ответ для фото не найден`. Тела ответов - схемы `AnswerPhoto*` из `@bio-exam/exam-core`. Ограничитель `photoBodyGate`, `sendUploadOutcome`, `sendDeleteOutcome`, ответ 503 с `Retry-After` и заголовки раздачи фото - один модуль `app/server/src/routes/answer-photo-intake.ts` для маршрутов под сессией и по ссылке. Помощники тестов `answerPhotoPath` и `putAnswerPhoto` - `app/server/src/test-support/attempt-world.ts`.
- Раздача фото: `GET /api/answer-photos/:photoId/:variant` (`app/server/src/routes/answer-photos.ts`, `variant` из `ANSWER_PHOTO_VARIANTS`: `thumb`, `full`) - WebP с `Cache-Control: private, no-store`, `nosniff`, `Cross-Origin-Resource-Policy: same-origin`; нет доступа, нет фото, неизвестный вариант и нет файла дают один и тот же 404 `{ error: 'Фото не найдено' }`.
- `app/server/src/services/scored-attempt`: оценка (`scoreSubmission`), хранимые факты, чтение результата (`readAttemptView`, `readAdminAttemptView`) и вид попытки (`buildAttemptView`); он же отвечает за итог попытки.
- Итог считает `computeAttemptOutcome` и `projectionOf` из `packages/exam-core/src/outcome.ts`: статус проверки `none`, `pending` (есть открытый вопрос без оценки, итог `NULL`) или `graded`. Проекцию пишет единственный писатель `materializeAttemptOutcome` (`app/server/src/services/scored-attempt/outcome.ts`), хранение проекции сверяет с пересчётом `reconcileOutcomes` там же.
- Читатели берут поля результата только через `attemptResultColumns` (Drizzle) и `attemptResultSql` (сырой SQL с алиасом) из `app/server/src/services/scored-attempt/columns.ts`, не из фактовых столбцов. Агрегаты (средний балл, «пройдено», график) условием `review_status <> 'pending'` явно исключают попытки на проверке.
- Сдача и черновик отвечают `ANSWERS_INVALID`: на сдаче 422, на черновике 400, тело несёт `reason` (`foreign_question`, `short_text_too_long`, `open_text_too_long`, `unknown_question_type`) и `limit`. Пределы ответов - `packages/exam-core/src/answer-limits.ts`.
- Вопрос ученику собирает `studentQuestionView` (`app/server/src/routes/tests/student-question-view.ts`) по белому списку полей: ключ и пояснение в ответ ученику не попадают.
- Шесть шаблонов вопросов: `single_choice`, `multi_choice`, `matching`, `short_text`, `sequence_digits`, `open`. Тип `open` засеян неактивным, оценивает его учитель (0-3 балла); сервер запрещает включить его, переписать его правило и создать кастомный тип с шаблоном `open`. Запрет живёт в `app/server/src/routes/tests/admin/question-types.ts`, запрет правила для теста - в `validateScoringRuleTemplateCompatibility` из `app/server/src/routes/tests/admin/shared.ts`; их снимают при включении открытых вопросов (фаза 17).
- `testAttempts.results` читается только в `app/server/src/services/scored-attempt`; маршруты попытки не читают `answer_keys` и назначения напрямую: это держит `scripts/attempt-integrity-guards.test.mjs`.
- Маршруты: `app/server/src/routes/tests/public.ts` (ученик); дашборд, список попыток и разбор попытки у персонала - `app/server/src/routes/tests/admin/attempts.ts`.

## Ссылка загрузки фото

- Ссылка-способность: телефон без входа добавляет и удаляет фото одного слота `(session_id, question_id)`. Токен - `randomBytes(32).toString('base64url')` (43 символа), в базе только sha256 hex. Токен ходит только заголовком `X-Upload-Token` (`UPLOAD_TOKEN_HEADER`), в пути, query и теле API его нет.
- `app/server/src/services/upload-links/index.ts` - единственный писатель `answer_upload_links`. `issueUploadLink(place)`: `readPhotoSlot(db)` до транзакции, затем `FOR UPDATE` сессии, окно и правило вопроса через `tx`; активных ссылок слота не больше `UPLOAD_LINKS_PER_SLOT` (3), новая выдача гасит самую старую (`revoked_at = now()`), строки не удаляются. `resolveUploadLink(token)` ищет по уникальному хешу; `uploadLinkSlot(link)` решает живость; `readUploadContext(scope)` отдаёт контекст вопроса; `touchUploadLink(linkId, log)` пишет `last_used_at`.
- Живость ссылки считается на каждом запросе по текущей базе: токен 43 символа base64url (иначе отказ без запроса в базу); `revoked_at IS NULL`; `created_at` не старше 24 часов; ссылка, выданная до сдачи (`created_at < submitted_at`), недействительна; затем `readPhotoSlot(db)` - любой отказ слота и окно `session_closed` дают недействительную ссылку, закрытое окно или окна нет - 422 тела `uploadWindowRefusal`.
- `uploadTokenRequired` (`app/server/src/middleware/uploadTokenRequired.ts`) читает только заголовок `x-upload-token`: `req.authUser` не читает, `requestAccess` не вызывает, путь и тело не читает. Живой ссылке ставит `req.uploadScope = { linkId, sessionId, questionId }`; маршруты берут место через `placeOfSession`. Недействительная ссылка - 404 `{ error: UPLOAD_LINK_INVALID_MESSAGE }` (`sendInvalidUploadLink`) с одним телом для всех причин и без заголовков `X-RateLimit-*`. После ответа ниже 400 пишет `last_used_at` не чаще раза в 30 с; ошибку записи `touchUploadLink` перехватывает и пишет в журнал, ответ не меняется.
- Лимиты внутри `uploadTokenRequired`: `upload-ip` 3000/мин на IP до поиска токена; `upload-unknown` 600/мин на IP для неизвестного, отозванного и старого токена; `upload-link` 120/мин на `linkId` найденной ссылки. Выдача - `upload-link-issue` 10/мин на `userId`. Отказ - 429 общего `errorHandler` с `Retry-After`.
- Выдача: `POST /api/tests/public/tests/:id/sessions/:sessionId/questions/:questionId/upload-link` в `app/server/src/routes/tests/session-photos.ts` под `sessionRequired`: 201 `{ token, uploadClosesAt, serverNow }` с `Cache-Control: no-store`; отказы слота как у маршрутов фото, 422 окна, 409 `ANSWER_PHOTO_FORBIDDEN_MESSAGE`.
- Маршруты ссылки - `app/server/src/routes/upload/index.ts`, монтируется как `/upload` после `/answer-photos`: `GET /api/upload/context` (`UploadLinkContextSchema`), `GET /api/upload/photos` (`{ photos }`), `PUT /api/upload/photos/:photoId` (multipart, `uploaded_via = 'link'`, ответы как у PUT под сессией, отказ слота - 404 недействительной ссылки), `DELETE /api/upload/photos/:photoId` (любое фото своего вопроса; фото нет в слоте - 200 `{ count }`), `GET /api/upload/photos/:photoId/thumb` (только миниатюра своего слота, чужое или нет - 404 `{ error: 'Фото не найдено' }`). Полноразмерных фото по ссылке нет, `canReadAnswerPhoto` ссылку не пускает.
- Заголовок `req.headers["x-upload-token"]` стоит в `LOG_REDACT_PATHS` (`app/server/src/lib/logger.ts`).
- Новый маршрут ссылки добавляется только в `app/server/src/routes/upload` под `uploadTokenRequired`. Охрану держит `app/server/src/routes/upload/upload.test.ts`: строки `/api/upload/` инвентаря идут через `uploadTokenRequired` без `sessionRequired`, вне них `uploadTokenRequired` нет, каждый маршрут под `sessionRequired` на один заголовок живого токена отвечает 401.

## Проверка открытых ответов

- Служба `app/server/src/services/answer-reviews`: `saveAnswerReview` (оценка учителя) и `recordNoAnswerReviews` (оценка 0 «нет ответа» без проверяющего). Обе в одной транзакции под `FOR UPDATE` попытки (`lockAttemptForReview` поверх `lockAttemptFacts` из `scored-attempt`, чтение `testAttempts.results` остаётся там) вставляют строки `answer_reviews`, собирают последние оценки, вызывают `materializeAttemptOutcome` и при итоге `graded` пишут уведомление `attempt.graded` (`recordAttemptGraded`, ключ дедупликации на попытку).
- `POST /api/tests/admin/attempts/:attemptId/questions/:questionId/review` (`app/server/src/routes/tests/admin/reviews.ts`), тело `OpenReviewRequestSchema` из `@bio-exam/exam-core`, ответ `OpenReviewResponseSchema`. Порядок отказов: `canReviewAttempt` 403, схема тела 400, нет попытки 404, своя попытка 403 `OWN_ATTEMPT`, окно открыто 409 `REVIEW_NOT_READY`, вопрос не открытый вопрос этой попытки 404.
- Чтение: `readAdminAttemptView` кладёт в каждый открытый вопрос `open` (`text`, `photos`, `review`, `referenceText`); `readAttemptView` для ученика после `graded` отдаёт `review` и `referenceText`, до итога `explanationText` открытого вопроса скрыт. Фото попытки читает `listAttemptAnswerPhotos` (`services/answer-photos/attempt-photos.ts`) по `attempt_id` или сессии попытки.
- Задача `no-answer-reviews` (раз в 60 с, батч 50 попыток): `findNoAnswerCandidates` находит открытые вопросы `pending`-попыток с закрытым окном без текста, фото и оценки; повторный прогон ничего не меняет. После авто-0 тот же проход зовёт `notifyReviewPending` для готовых `pending`-попыток без события; из `closeUploadWindow` в той же транзакции вызывается `recordReviewPending` (`answer-reviews/review-pending.ts`, по пути файла, чтобы не было цикла через `notifications`). Событие `attempt.review_pending` (продюсер `recordAttemptReviewPending`, ключ на попытку, получатели без повтора) получают администраторы с `zone.all` и учителя, владеющие группой ученика и имеющие тему теста в зоне (`attemptReviewers` в `access-policy`); не ученик, при расчёте без открытых вопросов без оценки и текста/фото события нет.

## Уведомления

- Модуль `app/server/src/services/notifications`, вход `index.ts`; про `Request` не знает: права на объект ему передаёт маршрут.
- Запись - `recordNotification` и `recordNotifications` (`record.ts`), только внутри транзакции причины (`NotificationTx`): откат причины откатывает событие. Повтор той же причины (`dedupe_key` у получателя) поднимает `ref_seq` и `last_event_at` той же строки и снова делает её непрочитанной, второй строки нет.
- Каналы доставки - `DELIVERY_CHANNELS` в `channels.ts` (сейчас один, `inbox`); каждое событие получает строку `notification_deliveries` по каждому каналу в той же транзакции.
- Производитель `test.assigned` (`app/server/src/services/notifications/producers/test-assigned.ts`): `addAssignments` (`app/server/src/routes/tests/assignments.ts`) для всех трёх путей назначения в одной транзакции вставляет назначения и вызывает `recordTestAssigned` только для вставленных строк и только для видимого теста (опубликован, тема активна). Назначение на черновик события не создаёт.
- Публикация: `updateTestSettings` (`app/server/src/services/question-content/relocate.ts`) при переходе `is_published` из false в true в своей транзакции вызывает `recordTestPublished`: событие всем уже назначенным с тем же `dedupe_key`. Включение темы событий не создаёт.
- Таблица видов - `kinds.ts`: на вид запись с текстом строки и обработчиком `open`. Неизвестный вид показывается как «Новое уведомление», его `open` отвечает `NO_ACCESS`. Новый вид - запись в `kinds.ts` и производитель в транзакции причины.
- Маршруты `app/server/src/routes/notifications.ts`: `GET /api/notifications` (курсор, `limit` до 50), `GET /api/notifications/unread-count`, `POST /api/notifications/read-all`, `POST /api/notifications/:id/read`, `GET /api/notifications/:id/open`. Все читают и меняют только события текущего пользователя (`ownedBy` в `read.ts`).
- `open` отмечает событие прочитанным и заново проверяет доступ: обработчик вида в `kinds.ts` вызывает `checkAttemptAccess` из `attempt-sessions`, а `canReadTest(req, testId)` ему передаёт маршрут. Ответ - `{ href }` или 403 `{ error: 'NO_ACCESS' }` без данных объекта.

## Фоновые задачи

- Модуль `app/server/src/services/background-jobs`: `createBackgroundJobs({ log })` отдаёт `register`, `start`, `stop`, `runNow`, `names`. Прогон держит замок `pg_try_advisory_xact_lock(11011, hashtext(имя))` в отдельной транзакции, работа идёт другими соединениями пула; занятый замок - отчёт `{ skipped: 'locked' }`.
- Стартуют задачи только из `app/server/src/index.ts`, в колбэке `listen`; тест или скрипт запускает задачу через `runNow` или `yarn workspace @bio-exam/server jobs:run <имя>` (код 75 - замок занят, 1 - неизвестное имя).
- Задачи (`jobs.ts`): `finalize-deadlines` раз в 30 с, батч 50, запас 60 с после льготы, давность 24 ч, предел прогона 20 с, память сбоев 10 мин; отчёт `{ stale, due, finalized, expired, other, failed, timeBounded }`. `reconcile-outcomes` только по `runNow`, чинит проекцию попыток со статусом `none`, оценки берёт из `loadLatestScores`; `no-answer-reviews` раз в 60 с, отчёт `{ candidates, reviewed, graded, notified, failed }`.
- Остановка: `createShutdown` в `app/server/src/lib/shutdown.ts` - прекращает приём соединений, ждёт запросы и задачи до `SHUTDOWN_DRAIN_MS` (25 с), затем закрывает пул; повторный сигнал завершает процесс кодом 1.

## Маршруты тестов

- `/api/tests` собирает `app/server/src/routes/tests/index.ts`: только импорты, `Router()`, `router.use(...)` по порядку и `export default router`, без обработчиков и импортов базы, `drizzle-orm`, хранилища и `services/question-content`. Это держит `scripts/tests-router-composition.test.mjs`.
- Маршруты персонала - суброутеры `app/server/src/routes/tests/admin/`, один файл на понятие: `topics.ts`, `tests-list.ts`, `question-types.ts`, `scoring-rules.ts`, `tests-by-slug.ts`, `question-drafts.ts`, `tests-core.ts`, `questions.ts`, `tests-delete.ts`, `export.ts`, `attempts.ts`. В файле локальный `const router = Router()`, полные пути от `/api/tests` и `export { router as <имя>Router }`; общие помощники - `app/server/src/routes/tests/admin/shared.ts`. Новый суброутер монтируется в `index.ts`, иначе падает `scripts/tests-router-composition.test.mjs`.
- Назначения теста - `app/server/src/routes/tests/assignments.ts`, монтируется как `/:testId/assignments` между `export.ts` и `attempts.ts`. Маршруты ученика - `app/server/src/routes/tests/public.ts`, монтируется в `app/server/src/routes/index.ts` после `/tests`.
- Порядок `router.use(...)` значим: `GET /:id` с `validateUUID` отвечает 400 на любой односегментный путь, зарегистрированный после него (`/topics`, `/question-types`, `/scoring-rules`). Порядок держит снимок `app/server/route-inventory.txt`: после правки маршрута или middleware снимок перегенерирует `routes:inventory` (`node scripts/with-test-db.mjs -- yarn workspace @bio-exam/server routes:inventory`), перенос без изменения поведения проверяет `routes:inventory --check`.
- ZIP-экспорт: обработчики `app/server/src/routes/tests/admin/export.ts` вызывают `prepareTestArchive` или `prepareTopicArchive`, доставку делает `sendArchive` из `app/server/src/routes/tests/export-response.ts` поверх `streamArchive` и `archiveToBuffer` из `app/server/src/services/question-content/export.ts`. Потоковое ядро архива - `app/server/src/services/storage/zip.ts`. Файлы `app/server/src/routes/tests` не импортируют `services/storage`.

## Содержимое вопроса и файлы

- `app/server/src/services/question-content`: создание и правка вопроса (`createQuestion`, `updateQuestion`), чтение (`readAdminTest`, `readQuestionMarkdown`), перенос и переупорядочивание, удаление, экспорт архива, индекс ссылок на картинки (`indexQuestionAssets`, `assetUsage`), сверка хранилища (`reconcileStorage`). Маршруты содержимого вызывают этот модуль.
- Файлы - только через `storage()` из `app/server/src/services/storage/index.ts`: модуль `StorageModule` поверх порта `StorageAdapter` (`app/server/src/services/storage/port.ts`). Адаптеры: `local`, `supabase` и `memory` в `app/server/src/services/storage/adapters`; `memory` работает только при `BIO_EXAM_ISOLATED_ENV=1`, `supabase` в этом режиме запрещён (`docs/adr/0004-storage-port-two-adapters.md`).
- Ключи живут в пространствах `images/`, `topics/`, `avatars/`, `answers/` (`app/server/src/services/storage/keys.ts`). Кто читает пространство, задаёт таблица `NAMESPACE_READERS` там же (`images` и `avatars` - любой вошедший, `topics` - вошедший, только файлы `assets/`, `answers` - владелец и проверяющие); правило и причины - раздел «Кто читает пространство» в `docs/adr/0004-storage-port-two-adapters.md`. Файлы `images/`, `topics/`, `avatars/` отдаются маршрутом `storageUrl(key)` → `/api/docs/assets/proxy?path=...`; `answers/` через `storageUrl` и общий прокси не идёт (`storageUrl` бросает ошибку, прокси и `/signed` отвечают 400), его раздают только `GET /api/answer-photos/:photoId/:variant` и миниатюры своего слота по ссылке `GET /api/upload/photos/:photoId/thumb`.
- Приём изображения - один модуль `app/server/src/services/assets/image-intake.ts`: `acceptImage(buffer, profile)` с профилями `IMAGE_PROFILES` (`answerPhoto`, `mediaLibrary`, `inlineImage`, `avatar`). Тип решает сигнатура файла, а не `Content-Type`; лимит `IMAGE_MAX_PIXELS` (50 МП) проверяется по заголовку до декодирования; поворот по EXIF, выход WebP без метаданных (аватар хранится в исходном формате), миниатюра только у фото ответа. Отказы `ImageRejectedError`: 400 (тип не распознан, файл повреждён), 413 (больше лимита пикселей), 415 (распознанный, но не принятый профилем тип; у фото ответа HEIC получает `HEIC_MESSAGE`), 503 `IMAGE_BUSY_MESSAGE` только у фото ответа, когда ограничитель (`IMAGE_INTAKE_CONCURRENCY` 1, очередь `IMAGE_INTAKE_QUEUE_LIMIT` 8) занят. `sharp.cache(false)` и `sharp.concurrency(1)` ставятся при загрузке модуля.
- Приём файла из формы - `singleFileUpload({ field, maxBytes })` в `app/server/src/middleware/upload.ts`: превышение размера - 413 «Файл больше N МБ», сломанная форма - 400 «Не удалось прочитать файл из запроса».
- Замер памяти обработки фото - `app/server/src/scripts/photo-memory-bench.ts`; в образе API запускается как `node dist/scripts/photo-memory-bench.js` (`--series`, `--dir`, `--out`), результаты - раздел «Обработка фото и память» ADR-0004.
- Маршруты не импортируют `fs`, не собирают литералы ключей `topics/` и `avatars/`; `app/server/src/routes/tests` работает с файлами через `app/server/src/services/question-content`, без прямого импорта хранилища: это держит `scripts/storage-no-private-access.test.mjs`.

## exam-core как контракт HTTP

- Шаблоны вопросов, оценка, схемы ответов, сессии и результата попытки, коды ошибок сдачи живут в `packages/exam-core/src` (`docs/adr/0002-shared-exam-core-package.md`). Тело запроса сервер разбирает схемой оттуда (`SaveAttemptDraftRequestSchema`, `SubmitAttemptRequestSchema`, `SUBMIT_ERROR_CODES`), web берёт оттуда те же схемы и типы. Контракт ссылки загрузки - `packages/exam-core/src/answer-photos.ts`: `UploadLinkIssueResponseSchema`, `UploadLinkContextSchema`, `UPLOAD_TOKEN_HEADER`, `UPLOAD_LINK_INVALID_MESSAGE`.
- Приватные копии логики шаблона в `app/web` и `app/server/src` ловит `scripts/exam-core-no-private-copies.test.mjs`.
- Пакет потребляется из `packages/exam-core/dist`: `yarn test` и `yarn typecheck` собирают его сами, перед отдельным `yarn workspace @bio-exam/server test` после правки пакета нужен `yarn workspace @bio-exam/exam-core build`.
