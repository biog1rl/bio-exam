## Phase Boundary

Студент начинает, сохраняет черновик и сдаёт только назначенный ему тест (или тест, к которому у него есть право по текущей БД). Одна сессия даёт одну попытку, submit атомарен и идемпотентен, черновик сохраняется без потери полей. При submit сохраняются факты оценки, разбор строится из них при чтении, и правка ключа после сдачи не меняет разбор (D1).

- **Сессия попытки (план 004).** Одна проверка «назначен или привилегирован» для чтения теста, старта, черновика, submit и своей истории. Submit принимает явный `sessionId`, проверяет тест, пользователя и состояние сессии. В БД: одна открытая сессия на пару (тест, пользователь), одна попытка на сессию; дубликаты на проде закрываются детерминированно до ограничений. Submit в одной транзакции захватывает сессию, вставляет или возвращает попытку, закрывает сессию и чистит черновик. Один `clientAttemptId` живёт весь цикл повторов. Черновик (ответы и телеметрия) сливается под блокировкой строки.
- **Оценённая попытка (C2, ADR-0005).** При submit на каждый вопрос сохраняются ключ, по которому оценивали, число ошибок и вердикты по частям (через `exam-core`). Вид для студента с ключом, студента без ключа и администратора строит один серверный модуль при чтении; правило скрытия ключа живёт только там. Схема результата объявлена один раз в `exam-core`, результаты читаются через неё без `unknown[]`. Статус вопроса считается в одном месте и совпадает при `points === 0`. Старые попытки читаются через совместимый путь без перезаписи данных.

Требования: ATT-01 … ATT-06, SCORE-01 … SCORE-05 (`.planning/REQUIREMENTS.md:62-75`). Источник: `plans/004-attempt-session-integrity.md`, `plans/011-architecture-deepening.md` §1 D1, §2 C2, ADR-0005, ADR-0002 (контракты в пакете), ADR-0001 (доступ решает Express). Находки N1 и R2 фазы 3 закрываются здесь.

Видимое поведение меняется:
- неназначенный пользователь без права `tests.read` получает 403 на старт, черновик, submit и свою историю по тесту (N1);
- submit требует `sessionId` и `clientAttemptId` для всех тестов; повтор с тем же `clientAttemptId` возвращает тот же ответ, вторая отправка той же сессии с другим `clientAttemptId` получает 409 (раньше создавалась вторая попытка);
- просроченная открытая сессия теста с лимитом закрывается, и студент может начать заново (сейчас он застревает на 422 навсегда);
- разбор администратора показывает ключ на момент сдачи, а не текущий (D1);
- вопрос с 0 баллов показывается «Без оценки» и в `TestRunner`, и в разборе администратора.

Что НЕ входит:
- Клиентский модуль жизненного цикла попытки, формат WAL, debounce, сброс при пересдаче, разбиение `TestRunner` — Phase 6 (LIFE-01 … 05). Фаза 5 меняет в `TestRunner` только контракт отправки и чтение вида (D-11, D-18).
- Изменение правил оценки (PROJECT.md Out of Scope; `REQUIREMENTS.md:165`); баллы старых попыток не пересчитываются (Phase 3 D-06). STOP плана 004 «атомарность требует менять правила оценки» не срабатывает.
- Новая страница разбора старых попыток для студента, лимит попыток, скрытие ключа до дедлайна — функциональность сверх «назначен или привилегирован» (PROD-02).
- Нарезка роутера, типизированные запросы на web, самовызов `absoluteUrl` на странице разбора — Phase 8 (DECOMP-*, HTTP-*).
- Снимок содержимого вопроса (формулировка, варианты) на момент сдачи; legacy `TestScoringRules` (Phase 3 D-19).

Миграция с данными: SQL бэкфилла дописывается в сгенерированный файл вручную, `migrations-manifest.json` пересчитывается, бэкфилл проверяет отдельный DB-тест с заранее вставленными строками.

Новые миграции разрешены, применённые не правятся, следующий номер после 0021. Комментарии в коде не пишутся. Доки по-русски.

### Доступ к попытке (ATT-01)
- **D-01 [авто]: одно правило «назначен или привилегирован».** Функция модуля сессий попытки (D-12): тест виден (опубликован, тема активна), затем пользователь проходит, если у него есть право `tests.read` (`hasPermission`, как в Phase 4 D-04) или строка в `test_assignments` для пары (тест, пользователь). Всё читается из БД на каждом запросе, без кэша сверх мемоизации запроса. Порядок ответов как сейчас: тест не виден → 404, не назначен → 403 `{ error: 'Тест не назначен' }`. Других источников доступа (группы, роли по строкам) правило не знает: назначение группы уже раскладывается в строки `test_assignments` (`routes/tests/assignments.ts:65-92`).
- **D-02 [авто]: где применяется.** Одна функция вместо двух инлайн-копий (`public.ts:302-316`, `:408-420`) и вместо отсутствующих проверок:
  - `GET /topics/:topicSlug/tests/:testSlug`, `GET /tests/:id` — как сейчас, через функцию;
  - `POST /tests/:id/start` — сейчас проверяет только `isPublished` (`public.ts:576-581`), начинает проверять и активность темы;
  - `PATCH /tests/:id/sessions/:sessionId/answers` — сейчас не проверяет тест вовсе (`public.ts:651-662`);
  - `POST /tests/:id/submit`;
  - `GET /tests/:id/attempts/me`, `GET /tests/:id/chart-data` — сейчас не проверяют ни назначение, ни существование теста (`public.ts:477-568`). Критерий 1 говорит о «reading … an attempt». Видимого эффекта нет. Web вызывает их в трёх местах: `DashboardClient.tsx:194` (только по тестам из `GET /tests`, где у роли `user` уже только назначенные), `TestLandingPageClient.tsx:69`, `:84`, `:119` и `start/TestPageClient.tsx:24` (после чтения теста, которое у неназначенного уже 403).
  Списки (`GET /tests`, `GET /topics/:slug/tests`) фильтруют назначенные тесты join'ом, как сейчас. Разбор администратора остаётся под `requirePerm('tests', 'read')`. Снятие назначения посреди попытки: следующий PATCH и submit получают 403, черновик остаётся в строке сессии.

### Сессия, submit и черновик (ATT-02 … ATT-05)
- **D-03 [авто]: контракт submit.** Путь `POST /api/tests/public/tests/:id/submit` не меняется (инвентарь маршрутов для DECOMP-01 тот же). Тело: `{ sessionId: uuid, clientAttemptId: uuid, answers, telemetry? }`; `sessionId` и `clientAttemptId` обязательны для всех тестов, с лимитом и без. Сессия должна принадлежать этому тесту и пользователю. Ответы:
  - 400 — нет `sessionId` или `clientAttemptId`, тело не по схеме;
  - 403 — не назначен (D-01);
  - 404 — тест не виден, сессия не найдена, чужая или закрыта как `superseded` (без различения; клиент сохраняет WAL и снимает `sessionKey`);
  - 409 `ATTEMPT_ALREADY_SUBMITTED` с `attemptId` — сессия уже сдана с другим `clientAttemptId` (D-09); заменяет `TIME_EXPIRED_ALREADY_SUBMITTED`;
  - 422 `TIME_EXPIRED` — сессия с лимитом просрочена на входе (`precheckSubmit`, D-05) или закрыта как `expired`;
  - 200 — вид попытки (D-15), и при первой отправке, и при повторе.
  Схема конверта объявляется в `exam-core` рядом со схемой вида (ADR-0002).
- **D-04 [авто]: модель открытой сессии.** В `test_sessions` добавляются `closed_at timestamptz NULL` и `close_reason text NULL` с CHECK (`'expired'`, `'superseded'`). Открыта = `submitted_at IS NULL AND closed_at IS NULL`. `submitted_at` по-прежнему значит «сдана», `attempt_id` по-прежнему пишется. Время считается часами БД (`now()` в транзакции), как и `started_at` (`DEFAULT now()`). Льгота `GRACE_PERIOD_MINUTES = 2` остаётся.
- **D-05 [авто]: просроченная сессия теста с лимитом.** Просрочена — открыта, у теста есть `time_limit_minutes` и прошло больше лимита плюс льгота.
  - `/start` закрывает такую сессию (`close_reason = 'expired'`) и в той же транзакции открывает новую. Сейчас `/start` возвращает просроченную сессию снова (`public.ts:584-597`), клиент сразу получает 422, и тест больше не начать.
  - Submit в просроченную сессию закрывает её как `'expired'` и отвечает 422 `TIME_EXPIRED`; попытка не создаётся. Это прежнее «hard reject» (`public.ts:737-742`).
  - Автосдачу черновика на сервере не делаем: она создала бы попытку, которую студент не отправлял.
  - Черновик закрытой сессии не удаляется.
  - PATCH черновика таймер не проверяет: сохранение в открытую сессию безвредно.
- **D-06 [авто]: миграция 0022 — ограничения и чистка (ATT-03).** Одна миграция, только добавляет:
  1. колонки D-04;
  2. `test_attempts.session_id uuid NULL` с FK на `test_sessions(id)` `ON DELETE SET NULL`;
  3. чистка дубликатов: в каждой группе (тест, пользователь) с несколькими открытыми сессиями остаётся самая новая (`started_at DESC, id DESC`, ровно та, которую сейчас берут `/start` и submit, `public.ts:584-587`, `:722-725`); остальные закрываются (`closed_at = now()`, `close_reason = 'superseded'`); строки и черновики не удаляются;
  4. частичный уникальный индекс `(test_id, user_id) WHERE submitted_at IS NULL AND closed_at IS NULL`;
  5. частичный уникальный индекс `test_attempts(session_id) WHERE session_id IS NOT NULL` («одна попытка на сессию»).
  Старым попыткам `session_id` не проставляется (остаётся NULL): обратная ссылка `test_sessions.attempt_id` у них уже есть, а неоднозначность закрывать незачем. Уникальность на `test_sessions.attempt_id` не вводится: текущий submit ставит один `attempt_id` всем открытым сессиям пары (`public.ts:873-883`), и на проде такие строки возможны. Политика детерминирована. STOP плана 004 срабатывает только если подсчёт на проде (`<specifics>` п. 2) покажет то, что политика не покрывает. Чистку проверяет DB-тест на `test_*` с заранее вставленными дубликатами (Phase 4 04-03).
- **D-07 [авто]: атомарный `/start`.** В одной транзакции: открытая сессия пары берётся с `FOR UPDATE`; если она просрочена — закрывается (D-05); если открытой нет — `INSERT … ON CONFLICT DO NOTHING` по частичному индексу D-06 и повторное чтение. Ответ `SessionInfo` не меняется (`sessionId`, `startedAt`, черновик). Параллельные старты дают одну открытую сессию.
- **D-08 [авто]: транзакция submit.**
  1. Предпроверка без блокировок: доступ (D-01), сессия существует и принадлежит паре. Уже сданная сессия сразу уходит в путь идемпотентности (D-09), без оценки.
  2. Оценка вне транзакции: вопросы, карта типов, активные ключи, тексты пояснений из хранилища → факты через `exam-core` (D-13). Чтение хранилища в транзакции держало бы блокировку строки на время сетевых запросов.
  3. Одна транзакция:
     - `SELECT … FOR UPDATE` сессии;
     - повторная проверка состояния без условия по времени: сдана → D-09; закрыта как `expired` → 422; закрыта как `superseded` → 404. Просрочку решает только проверка на входе, иначе оценка в конце льготы давала бы 422;
     - `INSERT` попытки с `session_id`, `client_attempt_id`, фактами и `results_version = 2`;
     - `UPDATE` сессии: `submitted_at = now()`, `attempt_id`, черновик `NULL`; обновляется ровно эта сессия, а не все открытые сессии пары, как сейчас (`public.ts:873-883`).
  4. После commit — вид из сохранённой строки (D-15).
  Вторая параллельная транзакция ждёт блокировку, после commit первой видит сданную сессию и уходит в D-09. Если ключ поменяли между оценкой и транзакцией, фактом остаётся ключ, по которому оценили.
- **D-09 [авто]: идемпотентность и `clientAttemptId`.**
  - Сессия уже сдана, и `clientAttemptId` совпадает с сохранённым → 200 с видом из сохранённой попытки. Он совпадает с первым ответом, пока не изменили `showCorrectAnswer` теста (D-15).
  - `clientAttemptId` другой → 409 `ATTEMPT_ALREADY_SUBMITTED` с `attemptId` (вторая вкладка, устаревший клиент).
  - Уникальный индекс `(user_id, client_attempt_id)` (миграция 0009) остаётся. Конфликт по нему с попыткой другой сессии → 409 тем же кодом.
  - Клиент создаёт `clientAttemptId` один раз на сессию, хранит его вместе с закэшированной сессией (`sessionKey` в localStorage) и повторяет при ручной отправке, автосдаче и повторе после перезагрузки. Удаляет после успеха, при пересдаче и при смене `sessionId`. Сейчас он создаётся заново на каждый вызов (`lib/tests/api.ts:123`).
- **D-10 [авто]: атомарный черновик (ATT-05).** PATCH в одной транзакции:
  1. `SELECT … FOR UPDATE` открытой сессии с проверкой теста и пользователя;
  2. слияние в коде: ответы по ключу вопроса, телеметрия — `mergeTelemetryMaps` из `exam-core`, той же функцией, что при submit;
  3. `UPDATE`.
  Слияние телеметрии берёт максимум по полям, обычный `jsonb ||` его не повторяет, а SQL-функция стала бы второй копией правила. Оптимистичная версия потребовала бы повторов на клиенте. Закрытая или сданная сессия → 404, как сейчас (`public.ts:660-662`). Параллельные PATCH ответов на разные вопросы и телеметрии не теряют полей.
- **D-11 [авто]: клиент в фазе 5 — только контракт.**
  - `lib/tests/api.ts`: отправка принимает `{ sessionId, clientAttemptId, answers, telemetry }` и возвращает вид (D-16).
  - `TestRunner` перед отправкой убеждается, что сессия есть. Ветка «`/start` не удался — работаем без сессии» (`TestRunner.tsx:252-280`) больше не может сдать тест: отправка сначала повторяет `/start`.
  - `TestRunner` обрабатывает 403, 409 и 422 по UI-SPEC. 409 показывает существующий диалог (`TestRunner.tsx:911-936`) с обобщённым текстом. 422 сообщает, что время вышло и ответы не засчитаны, и даёт начать заново.
  - Закэшированная сессия и WAL сбрасываются, если `/start` вернул другой `sessionId`.
  - Модуль жизненного цикла, формат WAL и сброс пересдачи — Phase 6; `TestRunner` в фазе 5 не перестраивается.

### Оценённая попытка и виды (SCORE-01 … SCORE-04)
- **D-12 [авто]: серверные модули.** Два модуля в `app/server/src/services` по образцу `access-policy`:
  - **сессии попытки:** правило D-01, `/start`, черновик, транзакция submit, идемпотентность;
  - **оценённая попытка:** факты при submit (D-13), вид для зрителя (D-15), совместимое чтение старых попыток (D-19).
  Маршруты `public.ts` и разбор администратора (`routes/tests/index.ts:2603-2735`) только делегируют. Пути, middleware и порядок маршрутов не меняются, новых маршрутов нет. Модуль оценённой попытки — единственное место, где читаются `test_attempts.results` и `answer_keys` ради разбора.
- **D-13 [авто]: факты оценки на вопрос (SCORE-01).**
  - `questionId`, `template`, `metric` — шаблон и метрика, по которым оценивали;
  - `points`, `earnedPoints`, `isCorrect`, `mistakes`;
  - `key` — копия значения активного ключа в каноничной форме (Phase 3 D-10) — и `keyVersion` — версия строки `answer_keys`;
  - `verdicts` — части из `computeVerdicts`;
  - `userAnswer`, `explanationText` — пояснение по-прежнему снимается при сдаче.
  Баллы и вердикты считаются одним вызовом пакета от одного ключа, ответа и метрики. Инварианты: число единиц ошибок в вердиктах равно `mistakes`, `isCorrect` ⇔ `mistakes === 0`. Позже факты не пересчитываются. Ключ копируется значением: вопрос может быть удалён, и его версии ключа уйдут каскадом. Правила оценки не меняются: `scoreQuestionByType` уже возвращает `mistakesCount`, `computeVerdicts` уже есть.
- **D-14 [авто]: хранение — миграция 0023 (SCORE-05, отдельная).**

### Требует подтверждения пользователя (фазу не блокирует)
1. **Контракт submit и порядок выкатки (D-03, D-09, D-11, D-25).** `sessionId` и `clientAttemptId` обязательны для всех тестов. Вторая отправка той же сессии с другим `clientAttemptId` получает 409 вместо второй попытки. Коды 409 `ATTEMPT_ALREADY_SUBMITTED` и 422 `TIME_EXPIRED`; `TIME_EXPIRED_ALREADY_SUBMITTED` уходит. Вкладка, открытая до деплоя, получит 400 и восстановится перезагрузкой, поэтому деплой в тихое окно: web, сразу за ним server, откат парой server → web (D-25). Read-only перед выкаткой:
   ```sql
   SELECT count(*) AS active_open_sessions
   FROM test_sessions
   WHERE submitted_at IS NULL
     AND coalesce(draft_updated_at, started_at) > now() - interval '3 hours';
   ```
2. **Чистка дубликатов открытых сессий (D-06, STOP плана 004).** В каждой паре остаётся самая новая открытая сессия, остальные закрываются как `superseded`; данные не удаляются. Read-only:
   ```sql
   SELECT count(*) AS groups, coalesce(sum(n - 1), 0) AS extra_open
   FROM (
     SELECT test_id, user_id, count(*) AS n
     FROM test_sessions
     WHERE submitted_at IS NULL
     GROUP BY test_id, user_id
     HAVING count(*) > 1
   ) d;

   WITH ranked AS (
     SELECT id, test_id, user_id, draft_updated_at,
            row_number() OVER (PARTITION BY test_id, user_id ORDER BY started_at DESC, id DESC) AS rn
     FROM test_sessions
     WHERE submitted_at IS NULL
   )
   SELECT count(*) AS older_with_fresher_draft
   FROM ranked old
   JOIN ranked keep ON keep.test_id = old.test_id AND keep.user_id = old.user_id AND keep.rn = 1
   WHERE old.rn > 1
     AND old.draft_updated_at IS NOT NULL
     AND (keep.draft_updated_at IS NULL OR old.draft_updated_at > keep.draft_updated_at);

   SELECT count(*) AS attempts_shared_by_sessions
   FROM (
     SELECT attempt_id FROM test_sessions
     WHERE attempt_id IS NOT NULL
     GROUP BY attempt_id HAVING count(*) > 1
   ) x;
   ```
   Если `older_with_fresher_draft > 0`, у кого-то более свежий черновик лежит в старой сессии. Он не теряется (строка остаётся), но к нему больше не будет доступа из приложения; решить до деплоя.
3. **Просроченные сессии теста с лимитом (D-05).** `/start` закрывает просроченную сессию и открывает новую; submit после лимита и льготы — 422 без попытки, черновик остаётся в строке. Автосдачи на сервере нет. Сейчас такие студенты не могут пройти тест заново. Read-only:
   ```sql
   SELECT count(*) AS stuck_expired_sessions
   FROM test_sessions s
   JOIN tests t ON t.id = s.test_id
   WHERE s.submitted_at IS NULL
     AND t.time_limit_minutes IS NOT NULL
     AND s.started_at < now() - make_interval(mins => t.time_limit_minutes + 2);
   ```
4. **Доступ к попытке (D-01, D-02).** Привилегия — право `tests.read`, как у чтения теста. Снятие назначения посреди попытки: черновик и submit получают 403. История и график по тесту для неназначенного тоже 403. Оценка того, сколько попыток уже сделано без назначения (верхняя граница: назначение могли снять позже):
   ```sql
   SELECT count(*) AS attempts_without_assignment
   FROM test_attempts a
   WHERE NOT EXISTS (SELECT 1 FROM test_assignments x WHERE x.test_id = a.test_id AND x.user_id = a.user_id)
     AND NOT EXISTS (SELECT 1 FROM user_roles ur WHERE ur.user_id = a.user_id AND ur.role_key = 'admin');
   ```
5. **Видимость ключа при чтении (D-15).** Ключ в виде студента скрывается или показывается по текущей настройке `showCorrectAnswer` теста; сам ключ — всегда сохранённый при сдаче. Администратор после правки ключа видит в разборе старых попыток прежний ключ (D1).
6. **Старые попытки без перезаписи (D-19, SCORE-05, R2).** 264 попытки (замер 2026-09-26) не переписываются. Ключ берётся из сохранённого `correctAnswer` или из версии `answer_keys` на момент сдачи. Вердикты показываются только если пересчёт совпадает с сохранёнными баллами; иначе — ключ и сохранённый статус без вердиктов. Ключ неизвестен → пометка в разборе. Read-only:
   ```sql
   WITH items AS (
     SELECT a.id, a.submitted_at, (r->>'questionId')::uuid AS question_id,
            coalesce(jsonb_typeof(r->'correctAnswer'), 'null') <> 'null' AS key_stored
     FROM test_attempts a
     CROSS JOIN LATERAL jsonb_array_elements(a.results) r
     WHERE jsonb_typeof(a.results) = 'array'
   )
   SELECT
     count(*) FILTER (WHERE key_stored) AS key_stored,
     count(*) FILTER (WHERE NOT key_stored AND EXISTS (
       SELECT 1 FROM answer_keys k WHERE k.question_id = items.question_id AND k.created_at <= items.submitted_at
     )) AS key_from_history,
     count(*) FILTER (WHERE NOT key_stored AND NOT EXISTS (
       SELECT 1 FROM answer_keys k WHERE k.question_id = items.question_id AND k.created_at <= items.submitted_at
     )) AS key_unknown
   FROM items;

   SELECT count(DISTINCT a.id) AS attempts_with_key_changed_after_submit
   FROM test_attempts a
   CROSS JOIN LATERAL jsonb_array_elements(a.results) r
   JOIN answer_keys k ON k.question_id = (r->>'questionId')::uuid
   WHERE jsonb_typeof(a.results) = 'array'
     AND k.version > 1
     AND k.created_at > a.submitted_at;
   ```
   Второй запрос — сколько разборов администратора сейчас показывают не тот ключ (D1). Для R2 — запрос из `03-11-SUMMARY.md:115`. Скрипт перевода старых строк в версию 2 — отдельное решение.

   ```sql
   SELECT jsonb_typeof(results) AS kind, count(*) FROM test_attempts GROUP BY 1;

   SELECT k, count(*)
   FROM test_attempts a
   CROSS JOIN LATERAL jsonb_array_elements(CASE WHEN jsonb_typeof(a.results) = 'array' THEN a.results ELSE '[]'::jsonb END) r
   CROSS JOIN LATERAL jsonb_object_keys(CASE WHEN jsonb_typeof(r) = 'object' THEN r ELSE '{}'::jsonb END) k
   GROUP BY 1 ORDER BY 1;
   ```
