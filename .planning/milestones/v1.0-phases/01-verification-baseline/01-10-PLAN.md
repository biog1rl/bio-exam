    - findLockfileViolations(['yarn.lock', 'bun.lockb', 'npm-shrinkwrap.json', 'bun.lock']) returns all three, sorted

    - a path such as 'docs/package-lock.json.md' is not a violation (exact basename match only)
    - existingPaths(['yarn.lock', 'package-lock.json'], (p) => p === 'yarn.lock') returns ['yarn.lock'], so findLockfileViolations of that result is [] (a tracked file that is deleted from the worktree and not staged is not a violation)
    - existingPaths(['yarn.lock', 'package-lock.json'], () => true) returns both paths, so findLockfileViolations of that result is ['package-lock.json'] (a lockfile that exists on disk is still flagged)
    - existingPaths(['yarn.lock'], (p) => p !== 'yarn.lock') returns [], so findLockfileViolations of that result reports the missing root yarn.lock (a deleted yarn.lock is still caught)
  </behavior>
  <action>
Implements PROJECT D-07 / VER-04.
1. `scripts/check-lockfile.mjs` (zero deps, ESM). Export `findLockfileViolations(paths)`: it returns the sorted list of forbidden basenames (`package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`) found anywhere, plus a `missing: yarn.lock` entry when the exact path `yarn.lock` is absent. Also export `existingPaths(paths, exists)`, which returns the paths for which the injected predicate `exists(path)` is true (the injection lets the node:test cases run without a git repository). The CLI runs from the repository root, collects paths with `git ls-files --cached --others --exclude-standard`, so tracked and unignored files count while `node_modules` stays out through `.gitignore`, and then passes them through `existingPaths(paths, fs.existsSync)` before `findLockfileViolations`. The filter is required because `--cached` still lists a tracked file that was deleted from the worktree and not staged (`git ls-files --deleted` lists it too), and step 3 below leaves exactly that state. Filtering on disk existence is the smaller fix than subtracting the `--deleted` list, and it also covers a deleted `yarn.lock`. It prints `check-lockfile: OK` or one line per violation and exits 1.
2. `scripts/check-lockfile.test.mjs` with `node:test` and `node:assert/strict` for the behaviour list.
3. Delete `package-lock.json` from the working tree with a plain `rm`. The user commits the deletion; do not stage it. In the SUMMARY, tell the user that `NEXT_IGNORE_INCORRECT_LOCKFILE` in their local `app/web/.env` is now obsolete and may be removed by them. Do not edit `.env` files.
