# Phase 4 — UI Design Contract

> Узкий контракт на четыре поверхности, которые фаза меняет в видимом тексте и поведении: ответ 429 на странице логина, вид «нет доступа» для разделов `/admin`, поведение при истёкшей или отозванной сессии, действия «Завершить все сеансы» и «Снять ограничение входа» в карточке пользователя. Режим автономный, вопросов пользователю не задавалось. Решения выбраны по существующей дизайн-системе и решениям D-01…D-24 из `04-CONTEXT.md`; где спека потребовала бы ответа пользователя, стоит пометка **[авто] требует подтверждения**. Фаза не вводит ни новых компонентов `components/ui`, ни новых цветов, ни новых токенов, ни npm-пакетов.

## Поверхность 1. Страница логина: ответ 429 и тексты ошибок (D-11, D-15)

Файл: `app/web/app/(internal)/login/LoginPageClient.tsx`. Вёрстка карточки, поля, плейсхолдеры `Login` и `Пароль`, текст кнопки `Войти` не меняются (на них опираются `e2e/tests/auth.spec.ts` и `auth.setup.ts`).

Фокус экрана: строка ошибки под полями сразу над кнопкой `Войти`. Больше на экране ничего не меняется, поэтому взгляд идёт от полей к причине отказа и к выключенной кнопке.

### Контракт ответа

Express при блокировке отвечает 429 с заголовком `Retry-After` (целое число секунд) и телом `{ error }`, одинаково для существующих и несуществующих логинов (D-11). Запрос идёт на тот же origin через rewrite, заголовок доступен `fetch`. Новых полей в теле не вводится, web читает только заголовок. **[авто] требует подтверждения** (альтернатива — поле `retryAfterSec` в теле, это расширение API).

Web выбирает текст по коду ответа, а не по строке `error` с сервера: английские строки `lib/constants.ts` (`Invalid credentials`, `Account is not activated`, `Too many requests…`) на странице больше не появляются. Серверные строки в этой фазе не меняются. **[авто] требует подтверждения** (альтернатива — перевести `ERROR_MESSAGES` на сервере; это меняет ответы API для всех клиентов).

### Тексты

| Ситуация | Текст строки ошибки |
|----------|---------------------|
| Пустой логин или пароль (проверка на клиенте, запрос не уходит) | `Пожалуйста, введите логин и пароль` (как сейчас) |
| 400 | `Пожалуйста, введите логин и пароль` |
| 401 | `Неверный логин или пароль` (как сейчас в запасном тексте) |
| 403 (аккаунт не активирован) | `Аккаунт не активирован. Обратитесь к администратору.` |
| 429 с корректным `Retry-After` | `Слишком много неудачных попыток входа. Попробуйте через {время}.` |
| 429 без `Retry-After` или с нечисловым значением (в том числе HTTP-дата) | `Слишком много неудачных попыток входа. Попробуйте позже.` |
| 5xx и любой другой неуспешный код | `Не удалось войти. Попробуйте ещё раз.` |
| Сеть недоступна (`fetch` бросил) | `Не удалось связаться с сервером. Проверьте соединение.` |
| Конец ожидания 429 (только для скринридера) | `Можно снова войти.` |
| Кнопка показа пароля, `aria-label` | `Показать пароль` / `Скрыть пароль` (сейчас по-английски) |
| Кнопка `Войти` во время отправки | видимо `LoaderComponent`, доступное имя `Вход…` (`<span className="sr-only">`) |

Текст `Сессия не установилась. Обновите страницу и попробуйте снова.` удаляется: после входа страница делает полную навигацию без повторного `/api/auth/me` (D-15). Число оставшихся попыток не показывается ни в одном состоянии: оно раскрывало бы, существует ли логин.

### Формат `{время}`

Чистая функция рядом с модулем веб-сессии, табличный тест. Без склонения: сокращения `с` и `мин` грамматичны при любом числе.

| Секунд | Вывод |
|--------|-------|
| 1 | `1 с` |
| 45 | `45 с` |
| 59 | `59 с` |
| 60 | `1 мин` |
| 61 | `1 мин 1 с` |
| 125 | `2 мин 5 с` |
| 900 | `15 мин` |

Правило: меньше 60 — `{s} с`; иначе `{m} мин`, и если остаток секунд больше 0, через пробел `{s} с`. Секунды без ведущего нуля.

### Поведение 429

| Шаг | Поведение |
|-----|-----------|
| Ответ 429 с `Retry-After = N` | строка ошибки показывает текст с `{время}`; кнопка `Войти` выключена (`disabled`), её текст остаётся `Войти`; поля остаются активными, введённые значения не стираются, фокус не перемещается |
| Пока идёт ожидание | `{время}` в видимом тексте обновляется раз в секунду от момента получения ответа (`Date.now() + N * 1000`, остаток округляется вверх) |
| Ввод в поле `Пароль` | строка 429 не исчезает и кнопка не включается (сейчас любой ввод вызывает `setError('')`; для 429 это исключение) |
| Изменение поля `Login` (нормализованное значение отличается от того, на котором пришёл 429) | ожидание на клиенте снимается: строка ошибки скрывается, кнопка включается; решение примет сервер. Причина: ограничение действует на пару (логин, IP), другой логин может быть свободен |
| Остаток дошёл до 0 | строка ошибки скрывается, кнопка включается, фокус не перемещается, для скринридера один раз звучит `Можно снова войти.` |
| 429 без `Retry-After` | текст `…Попробуйте позже.`, кнопка не выключается, таймера нет; повторная попытка снова получит ответ сервера |
| Перезагрузка страницы во время ожидания | состояние ожидания не сохраняется (ни `localStorage`, ни cookie); форма активна, следующая попытка получит 429 с актуальным остатком без проверки пароля на сервере |

Разметка строки ошибки при 429 (доступность: видимый текст тикает, но не перечитывается скринридером каждую секунду):

```tsx
<p className="text-sm text-destructive">
	<span aria-hidden="true">{`Слишком много неудачных попыток входа. Попробуйте через ${formatWait(remaining)}.`}</span>
	<span role="alert" className="sr-only">{`Слишком много неудачных попыток входа. Попробуйте через ${formatWait(initial)}.`}</span>
</p>
```

Остальные ошибки логина выводятся в той же `<p className="text-sm text-destructive">`, которая получает `role="alert"` (сейчас у строки ошибки нет live-области). Сообщение `Можно снова войти.` — `<span role="status" className="sr-only">`, существует до следующего ввода.

### Загрузка страницы логина (D-15)

| Состояние | Поведение |
|-----------|-----------|
| `me` из контекста `AuthProvider` есть (сессия действует) | вместо формы по центру `LoaderComponent className="size-6 animate-spin"` (как сейчас), `router.replace(callback)`; запроса `/api/auth/me` из браузера нет |

## Поверхность 2. «Нет доступа» для разделов `/admin` (D-17)

### Вид

Нет права на раздел → `notFound()` в серверном layout поддерева. Пользователь видит существующую страницу `app/web/app/not-found.tsx` без изменений: заголовок `404-error`, `PAGE NOT FOUND`, `Ну такой страницы нет вообще, либо кто-то что-то сломал`, кнопка `Вернуться назад`. Вид неотличим от несуществующего адреса: роль `user` не узнаёт, что раздел есть. URL в адресной строке не меняется, редиректа нет. **[авто] требует подтверждения** (альтернативы: отдельный экран «Нет доступа» — новый текст и новая вёрстка; `forbidden()` — экспериментальный `authInterrupts` в Next 16.3.8).

Вложенные `not-found.tsx` под `/admin` не создаются: `notFound()`, брошенный в layout, обрабатывает граница родительского сегмента, вложенный файл не сработал бы. `app/not-found.tsx` не меняется (английские подписи остаются, перевод не входит в фазу).

### Карта «раздел → право» (из D-17, одна на модуль веб-сессии)

| Префикс | Право |
|---------|-------|
| `/admin/tests/**`, `/admin/attempts/**` | `tests.read` |
| `/admin/users/**` | `users.edit` |
| `/admin/groups/**` | `groups.manage_groups` |
| `/admin/settings/rbac/**` | `rbac.read` |
| `/admin/settings/**`, `/admin/sidebar/**` | `settings.manage` |
| `/admin` (корень) | любое из перечисленных |
| `/profile/[id]` (страница назначений, не под `/admin`) | `tests.manage_assignments` (проверка в странице) |
| `/admin/users/[id]` | два гейта: layout `/admin/users/**` требует `users.edit`, сама страница перед редиректом на `/profile/<login>` — `tests.manage_assignments` |

### Состояния

| Состояние | Поведение |
|-----------|-----------|
| Право есть | раздел рендерится как сейчас |
| Права нет, переход по ссылке или прямой URL | серверный layout раздела вызывает `notFound()` до рендера. Корневой `app/layout.tsx` оборачивает `{children}` в `AppLayout`, поэтому `app/not-found.tsx` рендерится внутри `children` гарда контента (`AuthGuard` с `redirectTo`). Гард контента без права на раздел не прячет содержимое: рендерит `children` (то есть 404) и один раз вызывает `router.refresh()`. Гарды сайдбара и шапки раздел не проверяют, сайдбар и шапка остаются |
| Права нет у роли `user` на корне `/admin` | 404 вместо нынешней пустой области под шапкой (сейчас `AuthGuard` с `requireAny={['rbac.read','rbac.write']}` рендерит `fallback = null`). Видимое изменение для `user`, следует из D-17 |
| Право снято, пока пользователь сидит в разделе (обновлённый `me` пришёл из опроса или возврата на вкладку) | гард контента продолжает рендерить `children` и один раз на изменение набора прав вызывает `router.refresh()`; серверный layout отвечает `notFound()`, и 404 приходит в те же `children`. До ответа сервера виден прежний экран раздела; данные раздела защищает Express. Новых текстов нет. **[авто] требует подтверждения** (альтернатива — оставить пустую область, как сейчас при `fallback = null`) |
| Сессии нет | не «нет доступа», а редирект на логин (Поверхность 3) |
| Ошибка БД прав (`/api/auth/me` отвечает 5xx, D-02) | `getServerMe` бросает ошибку, а не возвращает пустые права или `null`; страница уходит в существующий `app/error.tsx`, а не в 404 и не на логин. Вид `error.tsx` фаза не меняет. **[авто] требует подтверждения** (сейчас ошибка превращается в `null` и ведёт на логин) |

Обход `isAdmin` в `AuthGuard` и проверки `roles.includes('admin')` в web удаляются (D-17, D-21); для роли `admin` видимый результат не меняется.

### Контракт для e2e (D-23)

Проверка «раздел `/admin/users` недоступен роли `user`»: после `page.goto('/admin/users')` URL остаётся `/admin/users`, виден текст `PAGE NOT FOUND`, заголовка `Пользователи` и таблицы нет. HTTP-статус ответа в контракт не входит (зависит от стриминга layout).

## Поверхность 3. Истёкшая или отозванная сессия (D-13, D-14, D-16)

Фокус: у этой поверхности почти нет вида. Действующая сессия обновляется незаметно; кончившаяся ведёт на форму логина с возвратом туда, где пользователь был.

| Ситуация | Что видит пользователь |
|----------|------------------------|
| Access истекает через 60 с, вкладка видима (D-16) | ничего: refresh в фоне, ни лоадера, ни тоста |
| Возврат на вкладку после истечения access (D-16) | ничего: refresh сразу при `visibilitychange`, содержимое не перерисовывается заново |
| Серверная страница с истёкшим access и живым refresh (D8, D-14) | страница открывается как обычно, без промежуточного перехода на `/login` |
| Серверная страница, refresh не удался (сессия отозвана, refresh истёк, replay) | `proxy.ts` очищает cookie и редиректит на `/login?callbackUrl=<путь с query>` |
| Серверная страница, access ещё жив, но сессия отозвана (RSC получил 401) | тот же редирект на `/login?callbackUrl=…` |
| Клиентский запрос через модуль сессии получил 401, single-flight refresh не удался | модуль делает полную навигацию на `/login?callbackUrl=<текущий путь>` функцией D-13. Тост перед навигацией не показывается: он не переживёт перезагрузку |
| Несколько запросов одновременно получили 401 | один refresh на вкладку; при неудаче — одна навигация на логин |
| Выход в другой вкладке (событие `logout` в `localStorage`) | как сейчас: `me` становится `null`, `AuthGuard` уводит на `/login?callbackUrl=…` |
| Деактивация или «Завершить все сеансы» администратором | на следующем запросе или фоновой проверке — тот же редирект на логин |
| После повторного входа | полная навигация на `callbackUrl`; `TestRunner` восстанавливает ответы из WAL и показывает существующий `toast.info('Сессия восстановлена')` |

Страница логина после такого редиректа выглядит как при обычном входе: без баннера и без пояснения «сессия завершена», параметр причины в URL не вводится. **[авто] требует подтверждения** (альтернатива — `reason=session_ended` в URL и строка `Сессия завершена. Войдите снова.` над формой; это новый параметр в функции редиректа D-13 и в `proxy.ts`).

Текст `AuthExpiredError` остаётся единственным: `Сессия истекла. Пожалуйста, войдите снова.` (`lib/api-fetch.ts`, переходит в модуль сессии). Он виден только там, где вызывающий код показывает `err.message` до того, как навигация на логин завершилась.

Несохранённые данные форм (редактор вопроса, `EditUserDialog`) при навигации на логин теряются. На логин ведёт только отказ refresh (ответ 401); сбой сети или сервера при refresh навигации не вызывает, пользователь остаётся на странице, клиент повторяет refresh. Отказ refresh случается при отзыве (выход, смена пароля на другом устройстве, деактивация, действие администратора, replay), после 30 дней бездействия и после потери ответа ротации (оборванная навигация, перезагрузка во время холодного старта, RSC-prefetch): в последнем случае выход наступает примерно через 15 минут, в том числе посреди работы (CONTEXT `<specifics>` п. 4). **[авто] требует подтверждения.**

### Смена пароля (D-08)

В `profile/ProfileClient.tsx` успех смены пароля остаётся `toast.success('Пароль успешно изменен')` и получает описание `{ description: 'На других устройствах нужно войти заново.' }`: остальные сеансы завершены, текущий продолжает работать. **[авто] требует подтверждения.**

## Поверхность 4. Карточка пользователя: «Завершить все сеансы» и «Снять ограничение входа» (D-08, D-12)

### Где

`app/web/components/users/dialogs/EditUserDialog.tsx`. Это карточка пользователя в админке: её открывает кнопка `Pencil` в строке `/admin/users` (`UserRowItem`, только при `users.edit`) и страница назначений `/profile/<login>` (`UserProfileAssignmentsPage`). Новые маршруты Express («завершить все сеансы», «снять ограничение входа») требуют `users.edit`. Из списка `/admin/users` диалог и так открывается только при `users.edit`; со страницы `/profile/<login>` он доступен при `tests.manage_assignments`. Поэтому блок «Сеансы и вход» рендерится только при `can('users','edit')`; без этого права блока нет (для текущих ролей `admin` и `user` вид не зависит от этого условия). Если право снято, пока диалог открыт, сервер отвечает 403 — строка «403 во время действия» в таблице ниже. **[авто] требует подтверждения** (альтернатива — кнопки на странице `/profile/<login>` вне диалога; тогда их не видно из списка пользователей).

Новый блок «Сеансы и вход» стоит после строки «Персональные права пользователя» и перед строкой ошибки диалога:

## UI Considerations

Доступность: строка ошибки логина получает `role="alert"`; тикающее время 429 скрыто от скринридера (`aria-hidden`), а начальный текст объявляется один раз через `sr-only` с `role="alert"`; конец ожидания озвучивается `role="status"`. Пиктограммы кнопок — `aria-hidden`, смысл несёт подпись. Выключенная кнопка на своём аккаунте объясняется через `Tooltip` на обёртке `<span>` (выключенная кнопка сама фокус не получает; известное ограничение того же приёма, что у `Права…`). Тосты sonner озвучиваются его собственной live-областью.
