## Deviations from Plan

### Решения исполнителя (автономно)

1. **`studentOnlyFilter` живёт в `zone-loader.ts`, `zone-store.ts` его реэкспортирует.** План: определить в `zone-store.ts` и импортировать в загрузчик. `zone-store.ts` импортирует значение `db` (исполнитель по умолчанию), а `vitest.config.ts` сервера задаёт `BIO_EXAM_ISOLATED_ENV=1`: модуль, импортирующий `db` без `TEST_DATABASE_URL`, падает. Так чистый `scope.test.ts` с `createInMemoryZoneLoader` остался бы зависим от базы. Правило по-прежнему написано один раз; `zone-store.ts` его отдаёт (`store.studentOnlyFilter` используется в DB-тесте).
2. **`role-traits.test.ts` поднимает тестовую базу** (`startAuthApp('test_role_traits')`, динамический импорт после неё): `role-traits.ts` импортирует `db` для `loadRoleTraits(executor = db)`, а проверка deny в `rbac_role_grants` требует базы.
3. **`canManageGroup` с `zone.all` тоже проверяет существование группы** (must_haves «группы нет → false»); behavior «с zone.all на любую существующую → true» выполнен.
4. **Новые функции без `req.authUser`** отвечают `false` / `{ all: false, groupIds: [] }` / предикат «всё нет», не вызывая `check` (продовый `hasPermission` без пользователя отклоняется).
5. **Id не в формате UUID** загрузчик Drizzle и функции `zone-store.ts` считают несуществующими (пусто, `null`, `false`) без запроса: иначе PostgreSQL ответил бы ошибкой приведения типа (500).
6. **`setTopicTeachers` и `releaseZone`** выполняются в `executor.transaction(...)`: с `db` — атомарно, внутри транзакции маршрута — точкой сохранения (DB-тест отката `releaseZone` в транзакции).
7. **`nonStudentUserIds` и `ineligibleTeacherGroupMembers`** относят несуществующие id к не ученикам (`notStudent`); деактивированный не ученик попадает только в `notStudent`.
8. **`topicTeachers` и `groupOwners`** сортируют учителей по `users.name`, затем `id`; `groupOwners` возвращает записи только для существующих групп.
