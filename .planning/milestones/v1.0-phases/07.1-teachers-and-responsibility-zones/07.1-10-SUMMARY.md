# Phase 07.1 Plan 10: Приглашения по зоне учителя, помощь со входом через шов, признаки ролей Summary

## Для web-планов 07.1-15 и 07.1-16

### `POST /api/auth/invites`

Тело: `{ userId?, login?, firstName?, lastName?, roleKey?, groupId? }` (`groupId` — uuid). Гейт `requirePerm('users','invite')` прежний.

Новый пользователь (нет `userId`):

| Кто | Условие | Ответ |
| --- | ------- | ----- |
| любой | тело не проходит схему | 400 `{ error: 'Bad request', details }` |
| любой | логин не по `LOGIN_RE` | 400 `{ error: 'Login is invalid' }` |
| без `zone.all` | `roleKey` задан и не `user` | 403 `{ error: 'Forbidden' }` |
| без `zone.all` | нет `groupId` | 400 `{ error: 'Group is required' }` |
| без `zone.all` | группа не своя или не существует | 403 `{ error: 'Forbidden' }` |
| без `zone.all` | ок | 200 `{ inviteLink, userId }`, роль `user`, член группы, `created_by` = приглашающий, `is_active` false |
| `zone.all` | нет `roleKey` | 400 `{ error: 'Role is required' }` |
| `zone.all` | `roleKey` не из `ROLE_KEYS` | 400 `{ error: 'Unknown role' }` |
| `zone.all` | `groupId` задан, группы нет | 404 `{ error: 'Group not found' }` |
| `zone.all` | ок | 200 `{ inviteLink, userId }`, при `groupId` — член группы |

Во всех отказах пользователь не создаётся.

Повторная ссылка (`userId`):

| Кто | Условие | Ответ |
| --- | ------- | ----- |
| без `zone.all` | `roleKey` задан и не `user` | 403 `{ error: 'Forbidden' }` |
| любой | пользователя нет | 404 `{ error: 'User not found' }` |
| без `zone.all` | не ученик своей группы (`canManageStudent`) | 403 `{ error: 'Forbidden' }` |
| любой | `isActive` | 409 `{ error: 'Пользователь уже активен: приглашение выдаётся только неактивному пользователю' }` |
| без `zone.all` | неактивен, но `activated_at` не NULL | 409 `{ error: 'Ученик уже активировал приглашение. Новую ссылку выдаёт администратор' }` |
| `zone.all` | нет `roleKey` и роли в БД | 400 `{ error: 'Role is required' }` |
| любой | ок | 200 `{ inviteLink, userId }`, прежние приглашения пользователя удалены |

### `DELETE /api/users/:id/login-throttle`, `POST /api/users/:id/sessions/revoke`

Невалидный id — 400, без сессии — 401, `canAssistSignIn` ложно — 403 `{ error: 'Forbidden' }`, пользователя нет — 404 (только у `zone.all` + `users.edit`; учителю — 403), ок — 200 `{ ok: true, cleared }` / `{ ok: true, revoked }`.

### `GET /api/rbac/roles`

`{ roles: Array<{ key, name, order, grants, ownsZone: boolean, groupMember: boolean }>, overrides }`. На миграциях по умолчанию: `admin` `{ ownsZone: false, groupMember: false }`, `teacher` `{ true, false }`, `user` `{ false, true }`. Признаки считаются с учётом переопределений роли в `rbac_role_grants`.

## Deviations from Plan

### Решения исполнителя (автономно)

1. **Строка `admin POST /invites missing group`.** В behavior Task 1 есть «несуществующая группа у администратора → 404, пользователь не создан», а в матрице строки не было. Добавлена; группа проверяется SELECT до транзакции, поэтому «сбой вставки членства» до транзакции не доходит.
2. **Проверка текста 409 в строке `teacherA POST /invites userId deactivated`.** must_haves задают текст; строка теперь проверяет и `error`.
3. **Порядок проверок повторной ссылки без `zone.all`:** `roleKey` ≠ `user` → 403 до чтения пользователя (по решению «roleKey проверяется до транзакции»), затем 404 → 403 `canManageStudent` → 409 активному → 409 активировавшему. Учителю роль из БД не подставляется.
4. **Существующие комментарии `invites.ts` сохранены.** «Назначаем роль пользователю» стоит над безусловной вставкой роли. «Если перегенерируем ссылку…» и «Проверяем, что roleKey есть…» перенесены вместе со своей логикой в ветку `zone.all` повторной ссылки. Новых комментариев нет.
5. **oxfmt переформатировал `login-throttle.ts` и `sessions.ts`:** без `requirePerm` регистрация уместилась в одну строку, тело обработчика сдвинулось на уровень. Логика та же, что в плане. Отдельного коммита форматирования не нужно: это одна правка поведения.

Других отклонений нет. Решения пользователя соблюдены: без `zone.all` повторная ссылка выдаётся только при `activated_at IS NULL`, иначе 409 с текстом из плана; `roleKey` проверяется до транзакции в обеих ветках; учитель снимает блок входа и завершает сеансы ученикам своих групп.
