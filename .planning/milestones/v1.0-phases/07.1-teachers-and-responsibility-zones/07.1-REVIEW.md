## Critical Issues

### CR-01 [BLOCKER]: Учитель перехватывает неактивированную учётку ученика другого учителя или админа

**Files:**
- `app/server/src/services/access-policy/zone-store.ts:198`
- `app/server/src/routes/groups/index.ts:40-46`, `:236-238`, `:294-300`
- `app/server/src/routes/auth/invites.ts:139-159`, `:184`
- `app/server/src/routes/tests/assignments.ts:84-91`

**Issue:** `ineligibleTeacherGroupMembers` считает «деактивированным» только `!isActive && activatedAt !== null`. Приглашённый, но ещё не активировавший ссылку ученик (`isActive=false`, `activatedAt=null`) проходит проверку состава группы учителя по UUID. Решение пользователя разрешает добавлять в свою группу **активного** ученика: `/api/groups/candidates` и `/api/users/directory` тоже отдают только `isActive=true`. Прямой `memberIds` это ограничение обходит. Дальше `POST /api/auth/invites {userId}` для учителя проверяет только `canManageStudent` (ученик в группе запрашивающего) и `activatedAt === null`. Строка `invites.ts:184` удаляет все прежние ссылки пользователя и выдаёт новую тому, кто её запросил.

UUID чужого приглашённого учитель получает штатно. `GET /api/tests/:testId/assignments` отдаёт `userId` каждой строки назначения на тест его раздела, а `login` прячет только за `inScope`. Раздел может быть закреплён за несколькими учителями (D-06), админ тоже назначает тесты раздела.

**Сценарий (воспроизведён):**
1. Учитель A приглашает ученика P в свою группу G и назначает ему тест `tX` раздела X. Раздел X закреплён и за учителем B.
2. B: `GET /api/tests/{tX}/assignments` → 200, в ответе `userId` P.
3. B: `POST /api/groups { name, memberIds: [P] }` → 201.
4. B: `POST /api/auth/invites { userId: P }` → 200, `inviteLink` у B, ссылка A удалена.
5. B принимает ссылку со своим паролем. Учётка P у B, настоящий ученик войти не может, у A ссылка мертва.

То же работает с любым неактивированным учеником, которого пригласил админ и назначил на тест раздела B.

**Fix.** Вариант в рамках принятых решений («добавляет любого **активного** ученика»): учитель добавляет в группу только активных. Проверку ставить в ветку учителя (`teacherMemberViolation` в `routes/groups/index.ts`), а не в общую `ineligibleTeacherGroupMembers`. Общую функцию вызывает и админский `PATCH /api/users/:id/group` (`users/index.ts:328`), и админ должен по-прежнему класть приглашённого в группу учителя.
```ts
// ineligibleTeacherGroupMembers отдаёт третий список, teacherMemberViolation его отклоняет
if (!row.isActive && row.activatedAt === null) pending.push(userId)
```
Своего нового ученика учитель по-прежнему кладёт в группу сразу через `POST /api/auth/invites` (`invites.ts:135`). Этот путь `teacherMemberViolation` не проходит, поэтому сценарий D-17 не ломается. Строку матрицы `teacherA POST /api/groups member invited 201` переписать на 400 и добавить сквозную строку из пунктов 1–4 с ожиданием 400 на шаге 3 в `teacher-zone-groups.matrix.test.ts`.

Дополнительное сужение, **требует подтверждения пользователя**, так как меняет D-17: повторную ссылку без `zone.all` выдавать только своему приглашённому.
```ts
if (!global && u.createdBy !== req.authUser!.id) return res.status(403).json({ error: 'Forbidden' })
```
`users.created_by` — след приглашающего по D-26. Тогда ученику, которого пригласил админ и положил в группу учителя, новую ссылку выдаёт только админ. Строка матрицы: `teacherB POST /invites {userId: чужой приглашённый в группе B}` → 403 в `teacher-zone-invites.matrix.test.ts`.

### CR-02 [MAJOR]: Групповое назначение теста обходит `tests.manage_assignments` и назначает не-учеников

**File:** `app/server/src/routes/tests/assignments.ts:121-156`

**Issue:** До фазы маршрут стоял на `requirePerm('tests','manage_assignments')` (`63259c0`). Теперь он проверяет только `canWriteTest` и `canManageGroup`. Ни одна из этих функций не смотрит `tests.manage_assignments`, поэтому deny-переопределение этого права (Phase 4 D-02, действует и на админа) обходится. Одиночное назначение через `canAssign` при этом корректно отвечает 403. Кроме того, вставляются все `user_groups` группы без `studentOnlyFilter`. Не-ученики попадают в группу учителя по CR-03, и им тоже назначается тест. `canAssignMany` их бы отсеял.

**Сценарий (воспроизведён):** учитель с deny `tests.manage_assignments`, закреплён за X, владеет группой с учеником S:
- `POST /api/tests/{tX}/assignments { userId: S }` → 403;
- `POST /api/tests/{tX}/assignments/group/{g}` → 200 `{ assigned: 1 }`.

**Fix:** обе проверки шва остаются (D-14), право проверяется до чтения состава, вставляются только участники, которых пропускает предикат назначения.
```ts
if (!(await canWriteTest(req, testId)) || !(await canManageGroup(req, groupId))) {
	return res.status(403).json({ error: 'Forbidden' })
}
if (!(await hasPermission(req, 'tests.manage_assignments'))) return res.status(403).json({ error: 'Forbidden' })
const members = await db.select({ userId: userGroups.userId }).from(userGroups).where(eq(userGroups.groupId, groupId))
const memberIds = members.map((m) => m.userId)
const allowed = await canAssignMany(req, [testId], memberIds)
const values = memberIds.filter((id) => allowed(testId, id)).map((userId) => ({ testId, userId, assignedBy: adminId }))
```
`hasPermission` экспортирует `services/access-policy/index.ts`, это проверка права, а не строки роли. Пустая группа у пользователя без права даёт 403, иначе `assigned: N`. В `teacher-zone-tests.matrix.test.ts` добавить строку с профилем «учитель + deny `tests.manage_assignments`» → 403 и строку «в группе учителя есть не-ученик → ему тест не назначен».

### CR-03 [MAJOR]: Инвариант «в группе учителя только ученики» обходится двумя путями записи, а чтение отдаёт учителю карточки персонала

**Files:**
- запись: `app/server/src/routes/auth/invites.ts:99-107`, `:135-137`; `app/server/src/routes/users/index.ts:257-281`
- чтение: `app/server/src/services/access-policy/scope-rules.ts:131-132`; `zone-loader.ts:104-113`; `routes/users/index.ts:124-126`; `services/search/database-search.ts:256-262`; `routes/tests/assignments.ts:44-54`

**Issue:** D-18 требует, чтобы в группе учителя были только ученики. `routes/groups` (`ownerViolation`, `teacherMemberViolation`) и `PATCH /api/users/:id/group` (`joinsTeacherGroup`) это проверяют. Но:
- `POST /api/auth/invites` с `zone.all` принимает любой `roleKey` и любой `groupId`, проверяет только существование группы. Новый админ или учитель попадает в группу учителя.
- `PATCH /api/users/:id` со сменой роли ученика на «Учитель» или «Администратор» не убирает его из групп учителей. `EditUserDialog` при этом сохраняет роль и группы двумя независимыми запросами, и второй проверяет только *новые* группы.

На чтении фильтр по «только ученик» есть лишь в `studentIdsInOwnedGroups`: назначения, повторная ссылка и помощь со входом защищены. `canReadUser` → `isMemberOfOwnedGroup`, `GET /api/users` (`userScope`), `searchUsers` и `login` в списке назначений берут любого участника группы. В итоге учитель видит логин, email, телефон, telegram, дату рождения и роли администратора или другого учителя. Это шире решения «полная карточка ученика своих групп».

**Сценарий (воспроизведён):**
- админ: `POST /api/auth/invites { roleKey: 'admin', groupId: G }` → 200;
- админ: `PATCH /api/users/{s} { roles: ['teacher'] }` для ученика из G → 200;
- учитель A: `GET /api/users` → строки `["zz_adm_in_g",["admin"]]`, `["zzrev_user5",["teacher"]]` с контактами;
- учитель A: `GET /api/users/{s}/test-assignments` → 200.

**Fix:**
1. На чтении в шве: `isMemberOfOwnedGroup` с `studentOnlyFilter(userGroups.userId)`, тот же фильтр в zone-фильтре `GET /api/users` и в `searchUsers`. Это одна функция модуля зоны: `studentsOfOwnedGroupsFilter(groupIds)`. Тогда даже испорченный состав группы ничего не раскрывает.
2. На записи. В `invites.ts` при `global && groupId` прочитать владельца (`groupOwners`) и при `owner !== null && roleKey !== STUDENT_ROLE_KEY` ответить 400 `STAFF_IN_TEACHER_GROUP`. В `PATCH /api/users/:id` при смене ролей, если пользователь перестаёт быть только учеником, в той же транзакции убирать его из групп учителей. Это новая функция модуля зоны рядом с `releaseZone`, например `evictFromOwnedGroups(tx, userId)` в `zone-store.ts`. Читать `student_groups.owner_id` прямо в `routes/users` нельзя: это сломает охранный тест D-29 (`scripts/teacher-zone-guards.test.mjs`). Альтернатива — отвечать 409 со списком групп.

После пункта 1 ученик с любым `allow`-грантом пропадёт и из списка учителя. Поэтому вопрос критерия «ученик» из CR-10 нужно решить вместе с этой правкой.

Строки матрицы: `admin POST /invites roleKey admin groupId G` → 400; `teacherA GET /api/users` после повышения ученика из G → строки нет; `teacherA GET /api/users/{повышенный}/test-assignments` → 403.

```ts
canAssistSignIn: async (req, studentId) => {

```

### CR-08 [MINOR]: Два понятия «персонал» расходятся, а поиск попыток персонал не исключает

**Files:**
- `packages/rbac/src/roles.ts:56-58` (`STAFF_ROLE_KEYS`, статично из реестра);
- `app/server/src/services/access-policy/role-traits.ts:22-26` (`ownsZone` из реестра и `rbac_role_grants`);
- `app/server/src/routes/tests/index.ts:1520-1523`, `services/question-content/remove.ts:177-189`, `routes/users/index.ts:379-384`;
- `services/search/database-search.ts:337-348`.

**Issue:** Статистика, список попыток, запрет удаления теста (D-25) и `GET /api/users/:id/test-attempts` считают персоналом роли с флагом `staff`. Освобождение зоны (D-24) смотрит на `ownsZone` с учётом переопределений роли в БД. CONTEXT D-24 говорит про флаг `staff`. Повышение учителя до админа освобождает зону, что разумно, но расходится с текстом решения. Глобальный поиск попыток у учителя (`searchAttempts`) не исключает попытки персонала, и учитель находит там свои предпросмотры и попытки коллег по разделу, которых нет в `/admin/attempts`. Бывший учитель, понижённый до ученика, начинает считаться учеником задним числом: его старые предпросмотры попадают в статистику и блокируют удаление теста.

**Fix:** в `searchAttempts` для ветки персонала добавить тот же `not exists (… role_key = any(STAFF_ROLE_KEYS))`. В README/CONTEXT записать, что D-24 реализован через `ownsZone`. Предпросмотры при понижении — принять как известное поведение или помечать попытки признаком `by_staff` при создании.

### CR-11 [MINOR]: Гонка освобождения зоны с закреплением раздела и сменой владельца

**Files:** `app/server/src/routes/users/index.ts:247-282`; `app/server/src/routes/tests/index.ts:314-343`; `app/server/src/routes/groups/index.ts:281-315`; `app/server/src/services/access-policy/zone-store.ts:143-153`

**Issue:** `isZoneOwnerCandidate` читает `users.is_active` и роли без блокировки (READ COMMITTED). Если `PUT /topics/:id/teachers` или `PATCH /api/groups/:id { ownerId }` идёт одновременно с деактивацией или снятием роли учителя, `releaseZone` удаляет то, что было до вставки, а вставка коммитится после. Деактивированный учитель остаётся владельцем раздела или группы. При повторной активации зона «возвращается», а D-24 обещает обратное. Если роль снята, а владение группой осталось, бывший учитель через CR-04 сохраняет помощь со входом.

**Fix:** в `isZoneOwnerCandidate` при вызове с транзакцией брать `SELECT … FROM users WHERE id = $1 FOR SHARE`, а в `PATCH /api/users/:id` — `FOR UPDATE` строки пользователя до `releaseZone`. Тогда операции сериализуются по строке учителя.
