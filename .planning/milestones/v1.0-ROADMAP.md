# Roadmap: bio-exam

## Overview

Milestone 1 "Надёжная основа" turns a working but unverified production codebase into a reliable one. It starts with one trustworthy gate (`yarn verify`, Vitest, CI, one lockfile, restored Drizzle metadata), then closes the reachable dependency advisories, then deepens the code into the modules fixed by ADR-0001...0005: `exam-core` for question templates, a single Express-owned auth and session boundary, atomic assigned-only attempts with a stored scored-attempt view, a client attempt-lifecycle module, one storage module with two adapters plus a question-content module, and finally typed client requests, editor-runtime fixes, proven performance wins and the admin router split. All eight defects D1-D8 from `plans/011-architecture-deepening.md` are closed along the way.

Phase order is fixed by plan 011 section 4 and the user's mandate. Eight phases are intentional even though `config.json` says `granularity: standard` (4-6): the order follows hard dependencies, and folding phases would merge unrelated risk areas. Do not collapse them in a later review. Phases 3 and 4 are independent of each other (3 needs only Phase 1; 4 needs Phases 1 and 2) and Phase 7 needs only Phases 1 and 4, but phases execute in numeric order. Phase 8 lists Phase 5 as well as plan 011's "4, 7": ADR-0005 (locked) requires both the question-content module (Phase 7) and the scored-attempt module (Phase 5) before the admin router split. Phase 8 is the heaviest (15 requirements in four groups); split it into plans per group (requests, runtime, performance, decomposition) at planning time.

Cross-cutting rules (from ADR-0003 and the user's working agreements):
- From Phase 1 on, `yarn verify` green locally and in CI is a precondition for closing every phase.
- Phases 3-8 start each ADR-module change with characterization tests that go through the module's interface.
- Code intelligence is CodeGraph: `codegraph impact` before editing a symbol, `codegraph affected` over the diff. Agents never commit.

### Phase 4: Authentication and web session

**Goal**: Access is decided in one place (Express) from current DB state, sessions are short-lived and revocable, and the web only shows what Express says.
**Depends on**: Phase 1, Phase 2
**Requirements**: AUTH-01, AUTH-02, AUTH-03, AUTH-04, AUTH-05, AUTH-06, AUTH-07, AUTH-08, AUTH-09, AUTH-10, AUTH-11, AUTH-12
**Success Criteria** (what must be TRUE):
  1. After an admin removes a user's role or the password changes, the user's very next request reflects it, and logging out invalidates the access token (no 30-day window), shown by integration tests.
  2. Two concurrent refresh calls produce exactly one successor token, replaying a used refresh token revokes its family, and a failed transaction sets no access cookie.
  3. Repeated failed logins are slowed by progressive account-plus-IP throttling without locking the real user out for 30 minutes, and an operational recovery path exists.
  4. `/api/auth/me` and `requirePerm` give the same answer for role and user-override cases, the `['admin','teacher']` check no longer silently drops `teacher` (D4), and UI route gates use the same permission list with no `isAdmin` bypass.

Server rendering with an expired access token and a live refresh token renews the session instead of redirecting to login (D8), one `AuthProvider` mounts with a single `/api/auth/me` per load (D3), concurrent 401s trigger one refresh, and `app/web` has no `pg`, `jsonwebtoken`, `DATABASE_URL` or `AUTH_JWT_SECRET` (`getMeData`, the Next `/api/auth/me` route and its pool are deleted).

### Phase 7: Storage and question content

**Goal**: Files go through one storage module with two adapters, a question is created, edited, moved and deleted by one module, and assets and the user directory no longer expose or destroy data they should not.
**Depends on**: Phase 1, Phase 4
**Requirements**: STOR-01, STOR-02, STOR-03, STOR-04, STOR-05, QCON-01, QCON-02, QCON-03, QCON-04, QCON-05, ASSET-01, ASSET-02, PRIV-01, PRIV-02, PRIV-03
**Success Criteria** (what must be TRUE):
  1. One contract suite passes on both the Supabase and the local-volume adapters, inputs such as `../`, encoded traversal, absolute paths and foreign prefixes cannot read, write or delete outside the root, and no route handler touches `fs` or builds a storage path.
  2. Renaming a question's or topic's slug moves its files with it, a failed file write leaves DB and files consistent, question order stays contiguous after move and delete, and editing a question never deletes the old prompt before the new one is written (D6).
