# Requirements: bio-exam

**Defined:** 2026-10-03
**Core Value:** A student's timed test attempt is scored correctly, exactly once, and stays reviewable exactly as it was scored.

Scope: Milestone 1 "Надёжная основа" (v1.0). No PRD exists; IDs are derived from the steps and done-criteria of plans 001-010, the defects D1-D8 and candidates C1-C8 of plan 011, and ADR-0001...0005. Source tags in parentheses point at the originating plan, ADR or candidate.

### Exam core (Phase 3)

- [x] **EXAM-01**: `packages/exam-core` exists as pure TypeScript with `zod` as its only dependency, built like `@bio-exam/rbac`, importing no React, Lexical, Drizzle or Tiptap (ADR-0002)
- [x] **EXAM-02**: One adapter per template (`single_choice`, `multi_choice`, `matching`, `short_text`, `sequence_digits`) owns key shape and authoring validation, answer shape, "answered?", normalization, error count and per-part verdicts for the review screen (ADR-0002; C1)
- [x] **EXAM-03**: Table-driven package tests per template map (key, answer) to score and per-part verdicts and assert the invariant "all parts correct if and only if errors = 0"; they are the reference point for later phases (ADR-0002; C1)
- [x] **EXAM-04**: The question editor, test runner, attempt review and the server (validation on save, scoring on submit) all use `exam-core`; the roughly 11 duplicated template implementations in `app/web` and `app/server` (key validation in four places, two dictionaries by type key and by `uiTemplate`) are removed (C1)
- [x] **EXAM-05**: The attempt-result zod schema and the telemetry merge are declared in `exam-core` and imported by both apps; the web and server telemetry copies are deleted (ADR-0002; C7 overlap)
- [x] **EXAM-06**: D2 closed: `sequence_digits` is scored and reviewed by one metric, so for key `1243` and answer `1234` the server error count and the review verdicts agree; which metric survives is decided at phase discussion with stored historical scores as the constraint (D2)
- [x] **EXAM-07**: D5 closed: the question editor saves a `short_text` question with several accepted variants (`compact_text_in_set`); a failing test reproduces it first because D5 is known only from reading the code (D5)

### Authentication and session (Phase 4)

- [x] **AUTH-01**: One server module computes effective permissions from roles plus overrides, honouring `inherits`, behind a grants-loading seam with a Drizzle adapter and an in-memory adapter; every Express check (`requirePerm`, role checks) and `/api/auth/me` go through it (ADR-0001; C5)
- [x] **AUTH-02**: Current DB roles are authoritative whenever DB enforcement is active: JWT role claims are no longer unioned back, a role removed after token issue takes effect on the next request, and a DB deny overlays admin (plan 003 step 2; C5)
- [x] **AUTH-03**: D4 closed: role-string checks such as `['admin','teacher']` (where `teacher` is absent from `ROLE_REGISTRY`) are replaced by permission checks through the policy module, with the outcome for each affected route pinned by a test (D4; C5)
- [x] **AUTH-04**: Access tokens are short-lived and bound to a revocable server session family/version; logout revokes them, password change and admin revocation are supported, and no compatibility path keeps 30-day bearer access (plan 003 step 3)
- [x] **AUTH-05**: Refresh tokens are single-use and claimed atomically: two concurrent refreshes yield exactly one successor, the successor is committed before cookies are set (a failed transaction sets no access cookie), and replay is detected at family level (plan 003 step 4)
- [x] **AUTH-06**: The hard lockout (five failures lock the account for 30 minutes) is replaced by progressive account-plus-IP throttling on a shared store with an operational recovery path, so a victim cannot be cheaply locked out (plan 003 step 5)
- [x] **AUTH-07**: Server session issuance is consolidated: `readCookie` (three copies) and Set-Cookie merging (three copies) exist once, and refresh keeps the `login` claim (plan 011 section 3, handled in plan 003)
- [x] **AUTH-08**: The Next auth duplicate is removed after `/auth/me` parity tests: `getMeData`, `app/web/app/api/auth/me/route.ts` and the Next `pg` pool are deleted, `app/web` contains no `pg`, `jsonwebtoken`, `DATABASE_URL` or `AUTH_JWT_SECRET`, and CodeGraph confirms no remaining caller (ADR-0001; plan 003 step 6; plan 010 step 4)
- [x] **AUTH-09**: One web-session module owns the current user (server rendering and client), the 401 to refresh to retry chain (several concurrent 401s yield one refresh) and the login redirect with callback, with an HTTP-to-Express adapter and a test fake (ADR-0001; C6)
- [x] **AUTH-10**: D3 closed: `AuthProvider` is mounted once and a page load makes a single `/api/auth/me` request with no bare-`fetch` refresh (D3; C6)
- [x] **AUTH-11**: D8 closed: server rendering with an expired access token and a live refresh token refreshes the session instead of redirecting to login (D8; C6)
- [x] **AUTH-12**: UI route gates use the same permission list Express checks (`/admin/**` is gated consistently with Express), with no `isAdmin` bypass in `AuthGuard`, no manual `isAdmin` checks and no role-string checks in React (ADR-0001; C5)

### Attempt integrity (Phase 5)

- [x] **ATT-01**: One `assigned-or-currently-privileged` authorization, evaluated against current DB permissions, guards read, start, draft and submit; unassigned users receive 403 on every attempt mutation (plan 004 step 1)
- [x] **ATT-02**: Submit requires an explicit `sessionId` and validates test, user and open state; a timed submission without the exact open session is rejected (plan 004 step 2)
- [x] **ATT-03**: DB constraints with migrations enforce one open session per user/test and one attempt per session; existing duplicates are counted and cleaned by a deterministic policy before the constraint lands, and a non-deterministic cleanup is a STOP (plan 004 step 2)
- [x] **ATT-04**: Submit runs in one transaction (claim the exact session, insert-or-get the attempt, close the session, clear its draft) with one client attempt ID persisted for the whole retry cycle; concurrent or retried submits give one attempt and a stable response, and response-loss retry stays idempotent (plan 004 step 3)
- [x] **ATT-05**: Draft answer and telemetry merges are atomic (row lock, versioning or atomic JSONB operations), so concurrent PATCHes lose no fields (plan 004 step 4)
- [x] **ATT-06**: DB-backed concurrency, authorization and time-limit integration tests exist and run under `yarn verify` and CI (plan 004 step 5; ADR-0003)

### Scored attempt (Phase 5)

- [x] **SCORE-01**: At submit the scored-attempt module persists the scoring facts (the answer key used, errors, per-part verdicts, computed through `exam-core`), and the current key is never substituted into an old attempt (ADR-0005; C2)
- [x] **SCORE-02**: The view for student-with-key, student-without-key and admin is built at read time in one server module that is the only home of the key-hiding rule, so web stops guessing it in four places (ADR-0005; C2)
- [x] **SCORE-03**: D1 closed: an answer key corrected after submission does not change the admin review of earlier attempts, proved by a test through the module interface (D1; C2)
- [x] **SCORE-04**: The attempt result is declared once (the `exam-core` schema replaces six declarations) and validated on read with no `unknown[]` casts; question status is computed in one place and agrees at `points === 0` (C2)
- [x] **SCORE-05**: Existing attempts are migrated, or made read-compatible, to the stored-facts shape by a separate migration whose policy is decided at phase planning; old attempts still open in review (C2)

### Draft durability (Phase 6)

- [x] **LIFE-01**: A client attempt-lifecycle module (phases by events: start, answer, navigate, tab hidden/visible, timer tick, submit, retake) owns the local draft format, telemetry and retake reset behind seams for storage, API, clock and tab visibility; `TestRunner` keeps presentation and is not split into four hooks (ADR-0005; C7; supersedes plan 010 step 3)
- [x] **LIFE-02**: The answer write-ahead log is written synchronously on every answer mutation under the existing scoped key, only network synchronization is debounced and pending saves are flushable, so answering Q2 inside the debounce window never loses Q1 and a reload or unmount inside the debounce keeps the latest answer (plan 005 step 1; C7)
- [x] **LIFE-03**: Retake resets all lifecycle state in one place and a hidden tab does not accumulate time, both covered by event-sequence tests with a fake clock (C7)
- [x] **LIFE-04**: Question-editor draft changes are flushed before controlled navigation (back, cancel), pending and error state is shown, and `beforeunload` is armed only while an unsaved write exists, with no duplicate save after a flush (plan 005 step 2)
- [x] **LIFE-05**: Tests cover rapid changes across questions, reload/unmount inside the debounce, failed retry, immediate back/cancel and no duplicate save after flush, and a manual browser check under throttled network confirms the latest answer or draft survives reload and immediate navigation (plan 005 step 3 and verification)

### Storage (Phase 7)

- [x] **STOR-01**: One storage module is the only route to files and exposes one interface with Supabase and local-volume adapters plus an in-memory test adapter; routes do not touch `fs` or compute paths (ADR-0004; C4)
- [x] **STOR-02**: Inside the module live key normalization, containment (`../`, encoded traversal, absolute paths, foreign storage prefixes and symlinks cannot escape the root), the key-to-URL rule and uniform failure modes, with no silent `''` from `readFile` when Supabase is absent (ADR-0004; C4; plan 006 step 1)
- [x] **STOR-03**: One contract test suite runs against both adapters, plus traversal tests (ADR-0004; C4)
- [x] **STOR-04**: Web receives ready URLs from the API; the regex that parses Supabase URLs in web is removed and web does not know the storage layout (ADR-0004; C4)
- [x] **STOR-05**: Prompt images in the shared `images/` are accounted for: test ZIP export includes the images its questions reference, and the media library refuses to delete an image still referenced by a question; exact scope is confirmed at Phase 7 discussion (C4 problem statement)

### Question content (Phase 7)

- [x] **QCON-01**: One server module owns the lifecycle of a question (create, edit, move, delete, read) across its five parts (DB row, answer-key versions, prompt/explanation files, search document, slug path), and the roughly nine handlers in `routes/tests/index.ts` and `public.ts` delegate to it (ADR-0005; C3)
- [x] **QCON-02**: DB and files stay consistent: a slug rename moves the files (including the topic-slug PATCH, which moves none today) and a file-write failure leaves no half state, tested on a real DB with the in-memory storage adapter (C3)
- [x] **QCON-03**: Question order is kept contiguous by one mechanism, replacing the four current ones, across create, move and delete (C3)
- [x] **QCON-04**: D6 closed: a PATCH of a question never deletes the old prompt before the new one is written (D6; C3)
- [x] **QCON-05**: Side effects are cleaned up: the two byte-identical admin read blocks are merged, `settings.json` (written, never read) is removed or given a reader, and GET export with `withAnswers` no longer writes `answer_keys.json` into storage (C3)

### Assets and user-directory privacy (Phase 7)

- [x] **ASSET-01**: Asset upload and delete require an explicit content-management permission and object names are normalized to `images/<generated-name>` (plan 006 step 1)
- [x] **ASSET-02**: Path-traversal, permission-matrix and legacy-path-compatibility tests prove that `../`, encoded traversal, absolute paths and foreign storage prefixes cannot delete a file and that legacy image paths still resolve; a production legacy path outside the normalized namespace is a STOP (plan 006 step 3)
- [x] **PRIV-01**: The ordinary user-directory lookup returns only approved minimal fields (no login, birthdate, phone, email, Telegram, roles or state) and the broad `users.read` list permission is removed from the default `user` role (plan 006 step 2)
- [x] **PRIV-02**: Admin screens keep full details through an admin permission and legitimate selectors are migrated to the minimal DTO; a student workflow that truly needs a sensitive field is reported by caller rather than widening the DTO (plan 006 step 2)
- [x] **PRIV-03**: Permission-matrix and field-level response tests cover both the minimal and the admin directory responses (plan 006 step 3)

### Teachers and responsibility zones (Phase 7.1)

- [x] **TEACH-01**: A teacher sees, creates and edits tests and questions only in topics assigned to them (teacher ↔ topic is many-to-many); a foreign topic, test or attempt by URL returns 403, and lists and search do not show it
- [x] **TEACH-02**: Only an admin creates, edits and deletes topics, assigns teachers to topics and changes shared question types and scoring rules
- [x] **TEACH-03**: A teacher sees attempts of all students on their topics; student cards (including contacts), assignments and groups only for students of their own groups; the teacher clears the login throttle and revokes sessions of their own students; the teacher invites only students, and an invited student lands in the teacher's group
- [x] **TEACH-04**: A student can belong to groups of several teachers; deactivating a teacher moves their topics and groups to admins in the same transaction; a teacher deletes only a test without attempts (409 otherwise)
- [x] **TEACH-05**: Access is decided by `services/access-policy/scope.ts` from permissions and database rows, never by role strings; the access matrix and the repository guard test are green in `yarn verify`, and an e2e teacher scenario is green

### Typed client requests (Phase 8)

- [x] **HTTP-01**: One typed JSON/SWR request module sits on top of `apiFetch` and handles 401 (through the web-session module), non-OK responses and malformed JSON, so `apiFetch` no longer hands a raw `Response` to callers (plan 007 step 1; C8)
- [x] **HTTP-02**: All protected callers (about 17 local fetchers of about five shapes, plus the global and local SWR fetchers) are migrated in bounded groups onto typed per-domain request layers for users and groups in the shape of `lib/tests/api.ts`; dead `swrConfig`/`swrOptions` are removed; callers that intentionally handle 401 differently stay explicit and tested (plan 007 step 1; C8)
- [x] **HTTP-03**: D7 closed: Express offers a user lookup by id or login, and a user outside the first 100 opens from search without a 404 (D7; C8)
- [x] **HTTP-04**: Server pages reach Express one way (`API_ORIGIN`); the self-call through `absoluteUrl` is removed (C8)

- [x] **RT-02**: Debounce callback refs are updated in an effect or layout effect with cancel-on-unmount, toolbar listeners are stable across the ten plugins, and speech-recognition listeners and objects are fully detached on cleanup, each covered by a test (plan 007 steps 2 and 4)
- [x] **RT-03**: Touched animated and editor controls respect reduced-motion preferences (plan 007 step 3)
- [x] **RT-04**: `npx -y react-doctor@latest app/web --verbose --scope full --offline` reports no confirmed error from plan 007 (remaining diagnostics documented with rationale) and the web production build exits 0 (plan 007 verification)

### Proven performance (Phase 8)

- [x] **PERF-01**: Category searches run concurrently while category ordering stays deterministic and permission filtering is preserved (plan 008 step 1)
- [x] **PERF-02**: Prompt downloads use bounded concurrency in one place (the question-content module), preserving fallback order and per-question failure semantics (plan 008 step 2; C3 overlap)
- [x] **PERF-03**: Editor profiles are split and optional plugin groups plus the 324 KB emoji data are lazy-loaded under a measured bundle budget, with editor serialization and toolbar availability unchanged (plan 008 step 3)
- [x] **PERF-04**: Export fetches data set-wise, bounds storage downloads and streams the ZIP with cancellation and backpressure inside the storage module, with output equivalent to today's; a deployed adapter that cannot stream is a STOP with a bounded alternative reported (ADR-0004; plan 008 step 4)
- [x] **PERF-05**: Benchmarks record before/after query count, concurrency ceiling, peak buffer and editor chunk size, and tests prove result and ZIP equivalence (plan 008 verification)

### Teacher-student chats (Milestone 4, `.planning/research/chat/SUMMARY.md`)

- **CHAT-01**: 1:1 teacher-student dialog, one per pair, created lazily; who may write is decided by the access-policy seam (Phase 07.1 zone), either side may start (a student only with their own teacher); no student-to-student messaging; a student who leaves the zone keeps a read-only dialog
- **CHAT-02**: Teacher announcements to an owned group without replies; students answer in their 1:1 dialog
- **CHAT-03**: Writes over HTTP, idempotent by `(sender_id, client_message_id)`; per-chat `seq` assigned under the chat row lock; edits and deletions in the same delta (`version_seq`); `sync` plus `changes?since` restore state after reconnect
- **CHAT-04**: SSE stream with cookie auth, closed at access-token expiry and on session revocation, heartbeat, in-process event bus published after COMMIT; polling fallback
- **CHAT-05**: Up to 5 photos per message (no PDF): client JPEG re-encode without EXIF, server signature check, `sharp` rotate and metadata strip, thumbnail and `thumbhash`, storage port, delivery through the API only to chat members; unattached uploads expire
- **CHAT-06**: "Обсудить попытку/работу" card storing `{type, id}`; the right to open the review is checked on open
- **CHAT-07**: Server-side unread counts; read state visible to the teacher only; teacher quiet hours with a student banner
- **CHAT-08**: Edit own message within 15 minutes with a mark; soft delete only, the administrator sees originals; message length, rate and upload quotas
- **CHAT-09**: Notification events written in the message transaction to the shared v3.0 journal, inbox channel now, per-dialog throttling, deep links `/chats/{chatId}?m={messageId}`
- **CHAT-10**: Envelope encryption of message bodies and photos (AES-256-GCM, per-chat data key wrapped by a master key kept outside the database and its backups, key version and rotation); administrator reads through an explicit action written to an access log; backups encrypted before upload
- **CHAT-11**: Client ready for PWA: IndexedDB outbox with retries, no service-worker caching of chat API or photos, local data cleared on logout; mobile layout at 375px with iOS keyboard handling
- **CHAT-12**: Guards: every chat route goes through the seam (route inventory test), attachment delivery checks membership, e2e of the SSE stream through the proxy
