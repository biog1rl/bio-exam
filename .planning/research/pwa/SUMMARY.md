# Сводка исследования: PWA и push-уведомления (v5.0)

**Проект:** bio-exam. **Домен:** установка PWA и Web Push как канал общего журнала уведомлений; один учитель, около 30 учеников (часто несовершеннолетних), Россия, один Beget VPS. **Исследовано:** 2026-10-06. **Уверенность:** MEDIUM. Код и стек проверены напрямую; доставка из РФ, iOS и Declarative Web Push проверены только по документам.

Источники: `STACK.md`, `FEATURES.md`, `ARCHITECTURE.md`, `PITFALLS.md` в `.planning/research/pwa/`; порядок вех из `.planning/PROJECT.md` (v3.0 фото-ответы и журнал уведомлений, v4.0 чаты, v5.0 PWA и push).

## Краткое резюме

v5.0 не строит новую систему уведомлений. Он добавляет к журналу из v3.0/v4.0 канал `webpush` и оболочку установки.

- **Стек:** одна новая серверная зависимость (`web-push` 3.6.7), ни одной новой зависимости в web.
- **Воркер доставки:** внутри процесса API, это тот же «модуль фоновых задач», что закладывается в v3.0.
- **Отправка и ключ:** отправляет Express (ADR-0001); публичный ключ VAPID отдаёт API, а не `NEXT_PUBLIC_*`.
- **Порядок работ:** сначала спайк (доходит ли push с VPS до FCM/APNs/Mozilla, работает ли установка на iPhone), затем оболочка, затем подписки и тестовый push (журнал не нужен), затем конвейер по журналу и настройки.
- **Принцип:** кабинет остаётся источником правды, push работает «по возможности». Офлайн-прохождения теста и кэша страниц нет: страницы персональные и `force-dynamic`, таймер и оценка живут на сервере.

Главные риски и закрытие:
1. `proxy.ts` редиректит `/sw.js`, манифест и иконки на `/login`. Исправить первым планом.
2. Подписка принадлежит браузеру, а не человеку. Привязываем к `auth_sessions.id` и удаляем внутри `revokeSession` и `revokeUserSessions`.
3. Недоступность push-служб из РФ. Спайк на реальных устройствах в фазе 1, запасной `PUSH_HTTPS_PROXY`.
4. Приватность детей. В payload нет текста, оценок и имён.
5. Выход не должен стирать черновики попыток. Без `Clear-Site-Data: "storage"`.

## Разрешённые расхождения

### 1. Черновики попыток: `localStorage`

Проверено в коде: `app/web/components/tests/attempt-lifecycle/use-attempt-lifecycle.ts:31-39`, `browserAttemptStorage()` возвращает `window.localStorage` с запасным хранилищем в памяти; `storage-keys.ts` строит ключи `test-session-<testId>-<userId>`, `test-answers-wal-…`, `test-frozen-…` и `clientAttemptId`. `indexedDB` в `app/web` не используется. STACK.md в этом пункте ошибается, PITFALLS.md и ARCHITECTURE.md правы.

Следствия:
- очистка при выходе не трогает ключи попыток;
- `Clear-Site-Data: "storage"` запрещён;
- IndexedDB появится только если v4.0 заведёт очередь исходящих сообщений чата. Её ключуют по `userId` и чистят при выходе.

### 2. Сервис-воркер: без обработчика `fetch`

Рекомендация: в v5.0 только `push`, `notificationclick`, `message`. Без `fetch`, без `/offline.html`, без Cache Storage.

Причины:
- Критерии установки Chrome (web.dev, 2024-09) не содержат сервис-воркера. Меню-установка без `fetch` работает с Chrome 108 (мобильный) и 112 (десктоп).
- Без `fetch` не ломаются 236 e2e-сценариев (пять спеков с `page.route`/`setOffline`) и SSE v4.0. Cache Storage пуст по построению, утечки на общем устройстве нет.
- Навигационный обработчик из ARCHITECTURE ради `offline.html` добавляет кэш `static-v1` и код очистки ради страницы, которую Chrome и так показывает.

Остаточная неопределённость: PITFALLS утверждает, что показ `beforeinstallprompt` всё ещё требует `fetch`, STACK этого не подтверждает. Закрывается спайком фазы 1 (DevTools Installability, приходит ли событие на Android Chrome). Запасной вариант, только если событие не приходит: пустой сквозной `fetch` для навигаций (без `respondWith`, без кэша, без `offline.html`).

### 3. Фазы: четыре (A–D из PITFALLS), спайк входит в первую

Соответствие: шаги 0–2 ARCHITECTURE = фаза 1; шаг 3 = фаза 2; шаги 4–5 = фаза 3; шаг 6 и виды уведомлений = фаза 4. «Ворота» не отдельная фаза, а первый план фазы 1, его выполняет пользователь.

### Остальные расхождения

| Тема | Решение |
|---|---|
| `pushsubscriptionchange` | В SW не обрабатываем. Клиент при каждом старте сверяет `getSubscription()` с сервером и `applicationServerKey`. У воркера нет живого access-токена, повтор refresh вне 30 с отзывает сессию. |
| `session_id` подписки | `NOT NULL`, FK на `auth_sessions` с `ON DELETE CASCADE` (в STACK был nullable). |
| Ссылка из уведомления | `navigate` = абсолютный URL от `APP_ORIGIN` + `deep_link` из журнала + `?n=<eventId>`. Страницы-посредника нет. Абсолютность URL и тип `app_badge` проверить на iPhone. |
| Состав payload | Общий заголовок по виду («Работа проверена»), тело «Откройте, чтобы посмотреть». Без имён, оценок, названий тестов, текста. Превью только по включению пользователя (для учеников выкл). |
| Офлайн-оболочка | Не делаем. FEATURES §4.5 (предзагрузка, офлайн-страница) отклонён. |
| Дубли и подавление | Подавление только на сервере: `graceSec` и проверка `read_at` перед отправкой. В SW не подавлять (тихие push отзывают подписку iOS). По SSE-присутствию не подавлять. |
| Строка доставки | Одна `notification_delivery(channel='webpush')` на событие, устройства раскладываются при отправке, `delivered_to uuid[]`. |
| Кэш фото учеников | `private, no-store`. `routes/docs/assets.ts:77` ставит `private, max-age=3600` для картинок вопросов, фото учеников так нельзя. |

## Ключевые выводы

### Стек

Подробности в STACK.md.
- `web-push` 3.6.7 (+ `@types/web-push` 3.6.4) в `app/server`: RFC 8291, VAPID, 0 уязвимостей, работает на Node 24. Закрыт портом `PushTransport` с фейком (шаблон ADR-0004). Запасной вариант: `@block65/webcrypto-web-push`.
- `app/web/app/manifest.ts` (встроено в Next 16): `display: standalone`, `id: '/'`, иконки 192, 512, maskable, `apple-icon.png` 180.
- Ручной `app/web/public/sw.js`, регистрация `{ scope: '/', updateViaCache: 'none' }`, `headers()` в `next.config.ts` для `/sw.js` (`no-cache`).
- Воркер доставки в процессе API: `FOR UPDATE SKIP LOCKED`, аренда строки, опрос 5–10 с, откат. Без `pg-boss`, Redis, `node-cron`.
- Payload Declarative Web Push (`"web_push": 8030`) одним JSON для Safari 18.4+ и для `push`-обработчика остальных браузеров. TTL по виду события, `urgency: normal`, цель менее 1 КБ.
- `GET /api/push/config` отдаёт публичный ключ. Приватный ключ и `VAPID_SUBJECT` в `api.env`, заглушки в `app/server/.env.example`. Ротация ключа обнуляет все подписки, `vapid_key_id` хранить в строке.
- Не брать: Serwist, `next-pwa`, workbox, Firebase SDK, OneSignal, каналы Telegram/MAX/VK/email, отдельный контейнер воркера, `NEXT_PUBLIC_VAPID_*`.

### Функции

Подробности в FEATURES.md.
- **Обязательные:**

  - бейдж из единого серверного счётчика, глубокие ссылки, отметка прочитанного;

- **Отложить:** срок сдачи у назначения и напоминания (у `test_assignments` нет срока); родитель-наблюдатель; дополнительные каналы; офлайн-разбор и офлайн-перезагрузка раннера.

### Архитектура

Подробности в ARCHITECTURE.md. Производитель в одной транзакции пишет событие, строку `inbox` и (если есть подписки и вид разрешён) строку `webpush`. После COMMIT воркер проверяет `read_at`, сессию и `is_active`, строит payload и шлёт по живым подпискам.

Исходы ответа push-службы:
- 404/410: подписка удаляется;
- 400/401/403: ошибка конфигурации, подписку не удалять;
- 429: ждать `Retry-After`;
- 5xx и сеть: повтор с откатом в пределах TTL.

Счётчик непрочитанного один (`count(read_at IS NULL)`). Клик ведёт на обычный маршрут, права проверяет Express.

Компоненты:
1. `services/push`: подписки, политика адресов `endpoint`, порт, payload, планировщик, воркер, уборщик.
2. `routes/push` и `routes/notifications`: под `sessionRequired()`, обновить `route-inventory.txt` и снимок.
3. `services/session`: `revokeSession` и `revokeUserSessions` удаляют подписки сессии в той же транзакции.
4. `public/sw.js`, `PwaRegistrar`, `lib/pwa/*`, `app/manifest.ts`, правки `proxy.ts` и `next.config.ts`.

### Критические подводные камни

Полный список из 21 в PITFALLS.md.
1. `proxy.ts` редиректит файлы PWA на `/login`. Исключить в matcher, добавить тест путей без cookie (200, не 307).
2. Подписка привязана к браузеру. Уникальный `endpoint` с перепривязкой, `session_id NOT NULL`, удаление внутри обеих функций отзыва, проверка живой сессии при отправке, автоподписка запрещена без флага `push-optin:<userId>`.
3. Недоступность FCM/APNs из РФ; «принято» не значит «доставлено». Спайк с устройств и VPS, `PUSH_HTTPS_PROXY`, кнопка проверочного уведомления.
4. Версионный перекос после автодеплоя и ротация refresh. `deploymentId` = sha образа (build-arg на сервере, шаг пользователя). SW не вызывает `/api/auth/refresh` и не ходит в сеть из `push`. Нет `location.reload()` при смене воркера и во время попытки.
5. Приватность и тихие push. Payload без содержимого. Каждый push показывает уведомление. SSRF через `endpoint` закрыт списком хостов (`fcm.googleapis.com`, `*.push.apple.com`, `updates.push.services.mozilla.com`, `*.notify.windows.com`, только https, без userinfo).
6. SW и e2e. Существующим проектам `chromium-desktop`/`chromium-mobile` задать `serviceWorkers: 'block'`. Отдельный проект `chromium-pwa`. Доставку проверять фейком транспорта, CDP `ServiceWorker.deliverPushMessage` и ручным UAT.

## Что v3.0 должна заложить для v5.0

Блокирующих зависимостей нет: в худшем случае v5.0 начнёт с миграции `ADD COLUMN`. Но всё ниже дёшево сделать сейчас и дорого переделывать потом.

**Журнал**
- `notification_event`:
  - поля: `id`, `recipient_user_id`, `kind`, `subject_type`, `subject_id`, `deep_link` (относительный путь, формирует производитель), `collapse_key` (nullable: `review:<attemptId>`, позже `chat:<chatId>`), `params jsonb` (только несекретное), `created_at`, `read_at`, `expires_at`;
  - индексы: `(recipient_user_id, created_at desc)` и частичный по `read_at IS NULL`.
- `notification_delivery`: `event_id` (FK, `ON DELETE CASCADE`), `channel` (`inbox`, позже `webpush`), `status`, `attempts`, `next_attempt_at`, `lease_until`, `last_error`, `sent_at`, `created_at`, `UNIQUE (event_id, channel)`. v3.0 пишет строку `inbox`.
- Реестр «планировщиков канала», вызываемых в транзакции производителя. v3.0 регистрирует только `inbox`, производители о push не знают.
- Таблица умолчаний по видам в коде (`kinds.ts`: `push`, `graceSec`, `ttlSec`, `urgency`, `throttleMin`).
- Идемпотентность производителя: событие по версии ответа и проверки, правка оценки не плодит события.

**Производители событий**
- Обязательно в v3.0:
  - ученику: возврат на исправление, ответ проверен, тест полностью проверен;
  - учителю: ученик сдал ответ, ученик отправил исправленный ответ.
- Рекомендуем добавить в v3.0, а не в v5.0:
  - `test.assigned` при вставке в `test_assignments`, включая назначение группе (до ~30 событий разом);
  - событие «ждут проверки» у учителя с общим `collapse_key`. В FEATURES у v3.0 это производный запрос, события нет.
- Если не войдут, v5.0 добавит их отдельным планом в фазе 4.

**Точки чтения**
- `GET /api/notifications/unread-count` как единственный источник числа для шапки, вкладки и бейджа ОС.
- `POST /api/notifications/:id/read` с проверкой получателя (чужой id даёт 404).
- Колокольчик понимает `?n=<eventId>` и один раз отмечает событие прочитанным.
- Имена маршрутов стабильны.

**Модуль фоновых задач**
- Размещение: общий модуль (например `app/server/src/services/background-tasks/`), не внутри `services/notifications` и не внутри фото. Интерфейс `register(task)` с `runOnce()` и тонким циклом, `start()`/`stop()`.
- Старт только из `app/server/src/index.ts`, никогда из `app.ts` (иначе его получат тесты и контейнер `migrate`).
- Остановка таймеров до `pgPool.end()` в `gracefulShutdown`.
- `pg_try_advisory_xact_lock` или `SKIP LOCKED`, чтобы два экземпляра при выкатке были безопасны.
- Отдельный скрипт-вход по образцу `storage:reconcile`.
- Шина `publish`/`subscribe` после COMMIT.
- Тесты вызывают `runOnce()` напрямую (учесть флейк `57P01`).

**Сессии**
- Все завершения сессии только через `revokeSession` и `revokeUserSessions` (с `tx`), третьего пути не заводить.
- Токены QR-загрузки отделены от сессий и от push.
- Деактивация пользователя должна отзывать сессии, а не только ставить флаг.

**Кэш фото и публичные пути**
- Фото учеников (превью, оригиналы, ответы на открытые вопросы): `Cache-Control: private, no-store`, раздача за авторизацией. Не повторять `max-age=3600` из `assets.ts:77`.
- Страница `/u/<token>` и её API: без кэша, `no-referrer`.
- В `proxy.ts` публичные пути вести одной таблицей (сейчас `/login`, `/invite`). `/u/` добавить туда же. v5.0 допишет туда `manifest.webmanifest`, `sw.js`, `pwa/`, иконки.
- PWA-компоненты (регистрация SW, плашки установки и разрешения) монтируются только в авторизованном layout. Общие провайдеры v3.0 не должны оказаться на публичной странице QR.

**Окружение и клиентское хранилище**
- Ключ сервера `APP_ORIGIN` в `app/server/.env.example`. QR-ссылке v3.0 он нужен сам по себе, v5.0 использует его для `navigate`.
- Клиентское хранилище для фото (черновики, очередь загрузки): ключи по `userId`, точечная очистка при выходе, фото не класть в Cache Storage.
- `notification_settings` (IANA-пояс, часы тишины, `push_preview`, звук) создаёт первая веха, которой они нужны (по плану чатов v4.0). v3.0 не обязана их строить, но не должна занимать имена.
- Для v4.0, фиксируем сейчас: чтение чата ставит `read_at` событиям этого чата в той же транзакции, что и `last_read_seq`. CSP v4.0, если появится, содержит `worker-src 'self'`.

**В runbook сервера (фаза удаления Supabase/Vercel в v3.0)**
- Передача `NEXT_DEPLOYMENT_ID` (sha образа) в сборку web.
- При желании строка Caddy для `/sw.js`.
- Проверка исходящих хостов push, если пользователь уже на сервере.

## Последствия для дорожной карты

Структура: 4 фазы. Нумерацию подставит роадмапер.

### Фаза 1 (A): ворота, оболочка PWA, безопасный сервис-воркер

**Обоснование:** главный риск (доставка из РФ, iOS) нужно закрыть до конвейера. Оболочка не зависит от журнала.

**Включает:**
- план 0 «ворота» (проверки с VPS и устройств, выполняет пользователь);
- правка `proxy.ts` и тест путей без cookie;
- `app/manifest.ts`, иконки (нужен макет от клиента), `viewportFit: 'cover'`, `appleWebApp`, исправление `/favicon.svg`;
- `public/sw.js` без `fetch`;
- `headers()` для `/sw.js`;
- `PwaRegistrar` (после `load`, только в авторизованном layout);
- `deploymentId` и обработка `ChunkLoadError` вне попытки;
- UI установки (`beforeinstallprompt`, инструкция iOS, пункт в меню профиля);
- e2e: проект `chromium-pwa` и `serviceWorkers: 'block'` для остальных;
- рычаг отката `swEnabled` и минимальный аварийный воркер.

**Избегает:** Pitfall 1, 2, 3, 4, 13, 19, 20, 21.

### Фаза 2 (B): подписки, VAPID, привязка к сессии, тестовый push

**Обоснование:** от журнала не зависит, даёт доставку на реальные устройства рано, закрывает риск общего устройства.

**Включает:**
- миграция `push_subscription` (`session_id NOT NULL`, `endpoint_hash` unique, `vapid_key_id`);
- `config/push.ts` (`PUSH_ENABLED=0` по умолчанию, быстрая ошибка в production);
- маршруты `GET /api/push/config`, `PUT`/`DELETE /api/push/subscription`, `GET /api/push/subscriptions`, `POST /api/push/test`;
- политика адресов;
- порт `PushTransport` (web-push и фейк);
- удаление подписок в `revokeSession` и `revokeUserSessions`;
- `PushOptIn`, `DevicesList`;
- реестр очистки при выходе (`AuthProvider.logout` и `/login`);
- ключи VAPID, `.env.example`, runbook.

**Избегает:** Pitfall 5, 6, 7, 9, 16, 17.

### Фаза 3 (C): конвейер по журналу, бейдж, ссылки

**Обоснование:** жёстко зависит от журнала v3.0 и точки каналов. `chat.message` и часы тишины подключаются, когда есть v4.0.

**Включает:**
- планировщик и строки `webpush`;
- воркер: захват, откат, 404/410, 429, дросселирование, `graceSec` и `read_at`, часы тишины по IANA-поясу, предпочтения по видам;
- `notification_settings` и `notification_preference`, если v4.0 их не создала;
- payload Declarative Web Push и обработчик `push`;
- `app_badge`, `setAppBadge`, `BroadcastChannel`, заголовок вкладки;
- `?n=` и отметка прочитанного;
- запуск и остановка из `index.ts` под флагом;
- уборщик;
- ADR-0006.

**Избегает:** Pitfall 8, 11, 12, 14, 15, 17, 18.

### Фаза 4 (D): виды уведомлений, настройки, приёмка на устройствах

**Включает:**
- недостающие производители событий (`test.assigned`, «ждут проверки: N» с группировкой, объявления), если их не дали v3.0/v4.0;
- страница настроек: выключатель, виды, часы тишины, превью, устройства, проверочное уведомление, фраза о доставке;
- сводный push после часов тишины;
- ручной UAT по матрице устройств;
- страница состояния доставки администратору;
- runbook: ключи, `deploymentId`, откат, потеря ключа.

**Избегает:** Pitfall 10, 21.

### Порядок и флаги исследований

- Фазы 1–2 не требуют журнала. Если v5.0 последняя по порядку вех, их всё равно можно вытащить вперёд как спайк риска.
- Фаза 3 привязана к v3.0 жёстко и к v4.0 мягко (SSE, чтение чата, часы тишины).
- Пока `PUSH_ENABLED=0`, фазы выкатываются «тёмными».

**Нужен `/gsd-plan-phase --research-phase`:**
- **Фаза 1:** спайк на устройствах и VPS. Исходящий доступ к push-службам. Приходит ли `beforeinstallprompt` без `fetch`. Установка и вход на iOS. Нет ли второго уведомления в Safari при наличии воркера.
- **Фаза 3:** точная форма Declarative Web Push (`tag`, `mutable`, тип `app_badge`, абсолютный или относительный `navigate`). Синтетический `NotificationEvent` и CDP `deliverPushMessage` в нашей версии Playwright. Поведение двух экземпляров API при выкатке.
- **Фаза 4:** Яндекс Браузер и Android без Google-сервисов. UX-copy плашек.

**Стандартные паттерны, исследование пропустить:** манифест и иконки, правка `proxy.ts`, политика адресов, миграции подписок, очистка при выходе, `PushTransport` с фейком.

## Открытые вопросы

**К клиенту**
1. Макет иконки (192, 512, maskable, 180 для iOS, монохромный бейдж). Сейчас только растровый непрозрачный `public/img/logo.jpg`.
2. Часы тишины для учеников по умолчанию (22:00–07:00 или 21:00–09:00), только для push.
3. Откладывать ли push, пока идёт попытка теста.
4. Нужен ли push «назначен тест» (рекомендуем да) и «ждут проверки: N» учителю (рекомендуем да, с группировкой).
5. Что считать в бейдже: все непрочитанные одним числом (рекомендуем) или раздельно.
6. Срок сдачи у назначения и напоминания (вне v5.0, отдельная веха).
7. Показывать ли название теста в превью (по умолчанию выкл).
8. Юридическая сторона (152-ФЗ): согласие законного представителя, endpoint и ключи подписки как данные устройства. Не исследовано.
9. Правовая форма оператора и мессенджер, где ученики реально отвечают (условие возврата к MAX/VK/почте, не в v5.0).
10. Какие устройства у учеников. Нужны 2–3 реальных для UAT, включая Huawei/Honor и Яндекс Браузер, если есть в классе.

**К пользователю:** адрес для `VAPID_SUBJECT` (`mailto:` или `https:`; SMTP не нужен).

**Проверки-ворота (выполняет пользователь, у агентов нет доступа к серверу)**
1. С VPS и из контейнера `api`: TLS и ответ от `fcm.googleapis.com`, `web.push.apple.com`, `updates.push.services.mozilla.com`, `*.notify.windows.com`. Ожидается 400/401/403/404, не таймаут и не сброс. Сохранить результат и время. При отказе: `PUSH_HTTPS_PROXY`, решение о постоянном прокси отдельно (152-ФЗ).
2. Реальная отправка тестового push из контейнера `api` на Android Chrome (с Google-сервисами) и на iPhone с установленным PWA. Замерить задержку, Wi-Fi и мобильную сеть, ограничения мобильного интернета.
3. iPhone:
   - установка, повторный вход в PWA, разрешение по жесту только в standalone;
   - поведение `navigate` (абсолютный и относительный URL), `app_badge`, `tag`, один показ без дубля;
   - iOS 16.4–18.3, 18.4+ и 26.
4. Android Chrome: установка, приходит ли `beforeinstallprompt` без `fetch`. Яндекс Браузер. Android без Google (ожидаем «push недоступен»).
5. Один браузер, два пользователя подряд: уведомления первого не приходят второму, уведомления закрыты, черновик попытки сохранён.
6. Сервер:
   - `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` в `api.env` (генерация `yarn dlx web-push generate-vapid-keys --json`), копия закрытого ключа офлайн;
   - `NEXT_DEPLOYMENT_ID` в сборке web;
   - `curl -sI https://<домен>/sw.js`;
   - затем `PUSH_ENABLED=1`.
7. Репетиция отката: подмена `sw.js` на минимальный и рычаг `swEnabled`.

| Область | Уверенность | Примечания |
|---|---|---|
| Стек | MEDIUM-HIGH | Версии, аудит и совместимость `web-push` проверены запуском. Формат Declarative Web Push по документам (M). |
| Функции | MEDIUM | Платформы подтверждены первоисточниками. Данных по Учи.ру, Skysmart, Фоксфорду нет, сравнение опирается на Classroom, Duolingo, Сферум. |

| Подводные камни | MEDIUM-HIGH | Часть привязана к строкам кода. iOS и доставка в РФ частично L. |

**Общая уверенность:** MEDIUM.

**Пробелы**
- Доступность push-служб с VPS Beget и доставка на устройства: закрывает план 0 фазы 1.
- Declarative Web Push на устройстве: абсолютный и относительный `navigate`, тип `app_badge`, `tag`, `mutable`, дубль при наличии воркера.
- Нужен ли `fetch` для `beforeinstallprompt` в актуальном Chrome: источники расходятся.
- Отдельность хранилища и cookie iOS-PWA и повторная подписка без повторного запроса: вторичные источники, проверить на устройстве.
- Яндекс Браузер, Android без Google, Mozilla autopush из РФ: не подтверждены.
- Юридическая часть (152-ФЗ): не исследована.
- Создают ли объявления v4.0 события на каждого ученика группы, и войдут ли `test.assigned` и «ждут проверки» в v3.0: решить при планировании v3.0/v4.0.
- Владелец `notification_settings` (v4.0 или фаза 3 v5.0).
- Актуальность списка хостов `endpoint` и проверка размера payload (библиотека её не делает): проверить при установке.
