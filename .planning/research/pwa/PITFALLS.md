# Pitfalls Research: PWA и Web Push для bio-exam (v5.0)

**Домен:** установка веб-приложения на устройство и Web Push как канал доставки журнала уведомлений на Next.js 16 + Express 4 + одном VPS, ученики часто несовершеннолетние, аудитория в России
**Исследовано:** 2026-10-06
**Общая уверенность:** MEDIUM-HIGH (код репозитория и стек проверены напрямую; поведение iOS и доставка в России подтверждены частично)

**Метки уверенности.** `H`: код репозитория, прочитанный напрямую, и дословный текст первоисточника (Next.js docs). `M`: пересказ первоисточника через WebFetch (webkit.org, developer.chrome.com, playwright.dev, MDN) или совпадение двух независимых источников. `L`: один поисковый источник, блоги, форумы, мои выводы без проверки. Seam `classify-confidence` вернул для провайдеров `websearch` и `webfetch` значение LOW (для `websearch` с `--verified` MEDIUM); повышение до H для дословных страниц первоисточника и для кода репозитория — моя оценка, она указана здесь явно. Ссылки на код даны как `путь:строка` на коммит `1962edd` (ветка `dev`).

**Контекст.** v3.0 создаёт журнал событий уведомлений и кабинет, v4.0 добавляет чаты и SSE, v5.0 подключает push как ещё один канал того же журнала. Кабинет остаётся источником правды, push работает «по возможности», payload без текста сообщений, формат Declarative Web Push (`.planning/ROADMAP.md`, `.planning/research/chat/FEATURES-PWA.md` раздел 6). Предыдущее исследование не повторяется: здесь только то, что ломается, как это заметить и в какой фазе закрыть.

**Предлагаемые фазы v5.0** (названия мои, в дорожной карте их ещё нет; на них ссылается вся таблица соответствия в конце):

| Код | Предлагаемая фаза | Содержание |
|-----|-------------------|------------|
| A | Манифест, установка и безопасный каркас Service Worker | manifest, иконки, исключения в `proxy.ts`, заголовки `/sw.js`, SW без кэша данных, `deploymentId`, обновление SW, разделение Playwright-проектов |

## Critical Pitfalls

### Pitfall 1: `proxy.ts` редиректит `/sw.js`, манифест и иконки на `/login`

**What goes wrong:**
Matcher в `app/web/proxy.ts:78` исключает только `api`, `_next/static`, `_next/image`, `favicon.ico`, `robots.txt`, `sitemap.xml`, `uploads`. Публичны только `/login` и `/invite` (`proxy.ts:10-11`). Файлы из `public/` проходят через прокси как обычные маршруты (H, код; M по поведению Next: прокси выполняется для всех совпавших путей, включая статику из `public/`, проверить в e2e). Три последствия:
1. Запрос манифеста `<link rel="manifest">` по умолчанию идёт без cookie. Прокси не видит сессии, отвечает 307 на `/login`. Манифест не загружается: нет установки, нет иконок, нет `start_url`. На iOS Safari подставит скриншот страницы вместо иконки.
2. Запрос обновления `/sw.js` при истёкшей или отозванной сессии получает редирект. Браузер отвергает редирект при загрузке скрипта SW: обновление молча проваливается, у ученика остаётся старая версия SW до следующего входа (M, поведение браузеров по спецификации SW; поймать в e2e).
3. Для вошедшего пользователя с просроченным access-токеном запрос `/sw.js` запускает `refreshForProxy` (`proxy.ts:47-61`), то есть лишнюю ротацию refresh-токена на запрос статического файла.

**Why it happens:**
Матчер писался под страницы и API. Файлы PWA добавляются позже, и их проверка «открывается ли без входа» не входит в обычные сценарии.

**How to avoid:**
Добавить в исключения матчера `sw.js`, `manifest.webmanifest`, каталог иконок (например `icons/`) и `apple-touch-icon`. Добавить их в тест `app/web/proxy.test.ts` и в `e2e/tests/proxy-protection.spec.ts`: запрос без cookie возвращает 200 и нужный `Content-Type`, не 307. Не выносить в исключения ничего, что отдаёт данные пользователя.

**Warning signs:**
Lighthouse или DevTools Application показывает «Manifest: no manifest detected» или иконки с `/login`; в Network `sw.js` отвечает 307; у разных учеников разные версии SW.

**Phase to address:** A. Confidence: H по коду, M по реакции браузера.

### Pitfall 2: SW кэширует HTML или ответы API: утечка между учениками и вечная старая сборка

**What goes wrong:**
Корневой layout объявлен `force-dynamic` и `revalidate = 0` (`app/web/app/layout.tsx:11-12`), AuthProvider получает `initialMe` с сервера. HTML каждой страницы персональный. Если SW кладёт навигационные ответы в Cache Storage (стратегии «stale-while-revalidate» и «offline-first» из шаблонов Workbox и Serwist), то на общем устройстве (планшет класса, телефон родителя) следующий ученик может увидеть оболочку и данные предыдущего. Кроме того, закэшированный HTML обходит SSR-обновление сессии в `proxy.ts`: оно срабатывает только когда запрос дошёл до Next. Тот же риск у `GET /api/*`: список попыток, оценки, фото ответов (v3.0), переписка (v4.0). Кэш по ключу URL не знает, чья сессия.

**Why it happens:**
Стандартные примеры PWA нацелены на офлайн-режим, а не на авторизованное приложение с двумя ролями и общими устройствами. Помощники вроде Serwist дают «рекомендованный» кэш по умолчанию (H по тому, что гайд Next.js отсылает к Serwist только для офлайна).

**How to avoid:**
SW не имеет стратегии кэширования данных вообще. Минимальный SW v5.0: обработчик `push`, `notificationclick`, при необходимости `fetch` только для явного списка неизменяемых URL (`/_next/static/*`, иконки), остальное без `respondWith`. Навигации и `/api/*` всегда идут в сеть. Офлайн-режим для таймерных тестов не предлагать: он противоречит ядру продукта (одна честная попытка, оценка на сервере). Не использовать Serwist с `runtimeCaching` по умолчанию.

```js
self.addEventListener('fetch', (event) => {
	const url = new URL(event.request.url)
	if (event.request.method !== 'GET' || url.origin !== self.location.origin) return
	if (!url.pathname.startsWith('/_next/static/')) return
	event.respondWith(caches.match(event.request).then((hit) => hit || fetch(event.request)))
})
```

Если нужна установка с `beforeinstallprompt` на Chrome, обработчик `fetch` обязан существовать (см. Pitfall 19), но он может быть таким узким.

**Warning signs:**
В DevTools Application, Cache Storage, есть записи с путями страниц или `/api/`; после выхода и входа другим пользователем в шапке на миг видно старое имя; в тестах после деплоя «старые» экраны.

**Phase to address:** A (политика SW), проверка в D на реальном общем устройстве.

### Pitfall 3: версионный перекос после автодеплоя, вкладки и окна PWA живут днями

**What goes wrong:**
Автодеплой на сервере собирает образ `bio-exam-app:<sha12>` и заменяет контейнер `web` (`~/.claude/servers/bio-exam.md`, раздел про приложение и автовыкатку). Старый `/_next/static/<сборка>/…` исчезает. Установленное PWA на телефоне остаётся «открытым» в переключателе приложений неделями; старая вкладка продолжает загружать чанки старой сборки и получает 404 или `ChunkLoadError`, а RSC-запросы старой сборки уходят на новый сервер. Сейчас это уже риск, но редкий. SW с кэшем HTML (Pitfall 2) делает его постоянным: страница из кэша ссылается на несуществующие чанки. Во время замены контейнера Caddy отдаёт 503 `maintenance.html` на 30 секунд; fetch-обработчик, который кэширует любые ответы, закрепил бы страницу обслуживания.

Второй вариант той же беды: «перезагрузить страницу при смене SW» (`controllerchange` → `location.reload()`). Если это произойдёт посреди таймерной попытки, ученик теряет состояние в памяти. Черновик в `localStorage` спасает ответы, но не нервы и не таймер.

**Why it happens:**
У Next.js по умолчанию случайный идентификатор сборки, защита от перекоса включается только с `deploymentId` (H, nextjs.org/docs deploymentId 16.3.8: к URL статики добавляется `?dpl=`, клиент при расхождении делает полную навигацию вместо клиентской). Но Next не маршрутизирует по `?dpl=`: старые файлы по-прежнему должны быть доступны, иначе клиент перезагрузится, а не продолжит работу (H, там же). Dockerfile лежит на сервере вне Git, поэтому передача `NEXT_DEPLOYMENT_ID` при сборке — шаг runbook, а не коммит.

**How to avoid:**
1. Задавать `deploymentId` значением `sha12` образа (build-arg `NEXT_DEPLOYMENT_ID` в сборке на сервере; шаг для пользователя, агент сервер не трогает).
2. Регистрировать SW с `updateViaCache: 'none'`; `sw.js` без HTML-прекэша и без версий кэша: тогда обновлять нечего, SW меняется только при смене его логики, а не при каждом деплое. Не вшивать build id в `sw.js`.
3. Никогда не вызывать `location.reload()` на `controllerchange`. Показывать ненавязчивую плашку «Доступна новая версия» и применять обновление при следующей навигации; во время активной попытки (фаза модуля `attempt-lifecycle`) не показывать вообще.
4. Тосты и `app/error.tsx`: при `ChunkLoadError` один автоматический перезапуск страницы с защитой от цикла (флаг в `sessionStorage`), и только если попытка не идёт.
5. `skipWaiting()` допустим только пока SW без кэша: он не меняет то, как страницы грузятся (web.dev: опасность `skipWaiting`, когда новый SW управляет страницами старой версии, M).

**Warning signs:**
В журнале Caddy и Next всплеск 404 на `/_next/static/` после автовыкатки; сообщения `ChunkLoadError` или «Failed to fetch dynamically imported module» в клиентских ошибках; жалобы «белый экран после обновления».

**Phase to address:** A (`deploymentId`, обновление SW, `error.tsx`), runbook в D.

### Pitfall 4: SW или push-обработчик ходит в API с cookie и ломает ротацию refresh

**What goes wrong:**
Сессия: access-cookie живёт 900 секунд по умолчанию (`app/server/src/config/auth.ts`), refresh-токен ротируется. Повторное предъявление уже использованного refresh-токена допустимо только внутри окна `REFRESH_REUSE_WINDOW_MS = 30_000` (`app/server/src/services/session/index.ts:42`), иначе сервер считает это повтором и отзывает всю сессию (`index.ts:163`, причина `replay`). Если SW (или код в `push`) выполнит запрос к API с просроченным access, получит 401 и сам вызовет `/api/auth/refresh`, а вкладка потом тоже обновит токен позже 30 секунд, пользователя выбросит из системы. Две вкладки уже координируются через `refreshOnce` и `localStorage` (`app/web/lib/session/client.ts`, `AuthProvider.tsx`); SW не может в эту координацию вступить.

**Why it happens:**
Обработчик `push` естественно хочет «подтянуть детали уведомления с сервера» (в этом проекте payload без текста, и текст берётся по API).

**How to avoid:**
SW не вызывает `/api/auth/refresh` никогда. В обработчике `push` нет сетевых вызовов вообще: payload самодостаточен (Declarative-формат с заголовком, телом-заглушкой и `navigate`). Это главный аргумент в пользу Declarative-first, кроме iOS. Переход по клику идёт обычной навигацией через `proxy.ts`, который сам выполнит SSR-обновление сессии. Если когда-нибудь SW должен вызвать API, терпеть 401 и показывать общее уведомление.

**Warning signs:**
В таблице сессий растёт число отзывов с причиной `replay`; жалобы «после уведомления просит войти заново»; в журнале API вызовы `/api/auth/refresh` без `Origin` вкладки.

**Phase to address:** A (политика SW), C (payload без сетевых зависимостей).

### Pitfall 5: подписка привязана к браузеру, а не к человеку: общее устройство и чужие уведомления детям

**What goes wrong:**
`PushSubscription.endpoint` принадлежит браузерному профилю на устройстве, а не пользователю. На планшете класса или семейном телефоне ученик A выходит, ученик B входит. Если сервер хранит подписку за A, уведомления A продолжают приходить на экран блокировки B. Если выход вызвал только `logout`, а подписка осталась, то же самое. Если вход B создаёт новую строку с тем же `endpoint` (уникальный индекс `endpoint` нарушен или не задан), получатся две строки, и устройство получает уведомления обоих.

**Why it happens:**
Подписку воспринимают как «настройку профиля пользователя», а не как «адрес на конкретном устройстве». Выход из аккаунта в проекте уже чистит cookie (`app/server/src/routes/auth/logout.ts`, `clearSessionCookies`), но про push ничего не знает.

**How to avoid:**
1. Таблица `push_subscription`: `endpoint` уникален; при `POST` для существующего `endpoint` строка переназначается текущему пользователю и текущей `session_id` (upsert с перепривязкой).
2. Подписка привязана к `auth_sessions.id`. Воркер доставки отправляет только по подпискам, у которых сессия не отозвана (`revoked_at IS NULL`); `revokeSession` и `revokeUserSessions` (`index.ts:252`, `index.ts:268`) уже существуют, значит выход, replay и отзыв администратором прекращают доставку автоматически без отдельного кода.
3. При явном выходе клиент сначала (пока сессия жива) вызывает `DELETE` привязки по `endpoint`, закрывает показанные уведомления (`registration.getNotifications()` → `close()`), и только потом `POST /api/auth/logout`. Браузерную подписку при этом можно оставить: при следующем входе клиент берёт `getSubscription()` и привязывает её заново, повторный запрос разрешения не нужен. Это надёжнее, чем `unsubscribe()` на iOS, где поведение повторной подписки не проверено (L).
4. Лимит подписок на пользователя (например 5), вытеснение самых старых; обновление `last_seen_at` при каждом запуске приложения; очистка подписок без активности больше 60 дней.

**Warning signs:**
Два пользователя в таблице подписок с одним `endpoint`; жалоба «мне пришло уведомление про чужую работу»; доставка после отзыва сессии в метриках.

**Phase to address:** B. Проверка в интеграционном тесте сервера: выход, перепривязка, отозванная сессия.

### Pitfall 6: очистка при выходе стирает черновики попыток (`Clear-Site-Data: "storage"`)

**What goes wrong:**
Типовой совет «на выходе пришлите `Clear-Site-Data: "cache","cookies","storage"`». Директива `"storage"` выполняет `localStorage.clear()`, удаляет IndexedDB и снимает регистрации SW (M, MDN). В проекте черновики попыток лежат в `localStorage` (`app/web/components/tests/attempt-lifecycle/use-attempt-lifecycle.ts:34`, `browserAttemptStorage()`; в формулировке вехи говорится об IndexedDB, но в коде это `localStorage`), черновики редактора там же (`app/web/lib/drafts/use-question-draft-autosave.ts:27`). Ключ черновика содержит `userId`, то есть чужие черновики не пересекаются; очистка `"storage"` уничтожит неотправленные ответы текущего пользователя (Core Value: ответ не должен пропасть) и заодно снимет SW с подпиской. На общем устройстве противоположная проблема уже существует и не относится к PWA: `localStorage` с черновиками переживает выход.

**How to avoid:**
Не отправлять `"storage"`. Выход очищает точечно на клиенте: `caches.keys()` → удалить (если SW вообще что-то кэширует, см. Pitfall 2 — тогда удалять нечего), закрыть уведомления, отвязать подписку (Pitfall 5), событие `logout` в `localStorage` уже рассылается другим вкладкам (`AuthProvider.tsx:118`). `Clear-Site-Data: "cache"` допустим для HTTP-кэша изображений, но не обязателен; поддержку Safari проверять на устройстве (M: MDN описывает как widely available, с оговоркой «часть директив отличается»). Тот же путь очистки нужен при «тихом» окончании сессии (отказ refresh, `AuthProvider.refresh` получил `me = null`), а не только по кнопке «Выйти»; для него серверная привязка из Pitfall 5 страхует.

**Warning signs:**
Тест «ответ набран, выход, вход, ответ на месте» падает; после выхода пропадает регистрация SW и разрешение на push приходится запрашивать заново.

**Phase to address:** B.

### Pitfall 7: iOS: отдельное хранилище, повторный вход, push только после установки, запрос только по жесту

**What goes wrong:**
- На iOS PWA с главного экрана имеет своё хранилище: cookie, `localStorage`, IndexedDB не общие с Safari (M, источники по iOS 14+, WebKit 13878 о Home Screen web apps; утверждение «SW и CacheStorage общие с Safari» встречается только в старых блогах: L, не опираться). Ученик логинится в Safari, добавляет сайт «На экран Домой», открывает иконку и видит страницу входа. Черновики, начатые в Safari-вкладке, в PWA не видны.
- Push работает только у установленного приложения с манифестом `display: standalone` или `fullscreen` (M, webkit.org/blog/13878). В Safari-вкладке `PushManager` недоступен: определять функциональность по `'PushManager' in window` и `matchMedia('(display-mode: standalone)')`, а не по User-Agent.
- Разрешение запрашивается только из прямого жеста; вызывать `Notification.requestPermission()` и `subscribe()` надо первым действием в обработчике нажатия, не после `await fetch` (M по требованию жеста; точные границы «жеста» в WebKit при цепочке промисов не проверены, L).
- Каждая переустановка PWA даёт новый `endpoint`; старый живёт до ответа 410. У одного ученика копятся «призрачные» подписки.
- iOS 26: «На экран Домой» по умолчанию открывает сайт как веб-приложение (M, heise.de) — больше пользователей окажется в standalone без осознанной установки, режим надо поддерживать полноценно (навигация без адресной строки и кнопки «назад», безопасные зоны).

**How to avoid:**
Мастер установки для iOS: определить платформу и режим; в Safari-вкладке показать шаги «Поделиться → На экран Домой → откройте иконку → войдите заново» с понятным текстом, что вход нужен ещё раз. Кнопку «Включить уведомления» показывать только в standalone. Подписку и привязку выполнять в одном обработчике клика. Не переносить сессию между Safari и PWA «хитрыми» приёмами через токены в URL: это дыра в безопасности для детей, пусть логинятся заново. На каждом запуске PWA отправлять `last_seen_at` и сверять подписку (Pitfall 9).

**Warning signs:**
В аналитике входов много «вход сразу после установки»; ученики пишут, что «уведомления не включаются» из Safari-вкладки; у части пользователей по 3–4 подписки.

**Phase to address:** B (мастер и привязка), D (проверка на iOS 16.4–18.3 и 18.4+ вручную).

### Pitfall 8: Declarative Web Push не то же самое, что классический push; тихие push отзывают подписку

**What goes wrong:**
- Классический push на Safari требует `userVisibleOnly: true` и показа уведомления на каждый push; нарушение приводит к отзыву подписки (M, WebKit 12945; про «три пропуска» ссылается предыдущее исследование, источник dev.to, L). Код SW с условием «если вкладка открыта и видна, уведомление не показывать» убьёт подписку на iOS. Chrome при пропуске покажет служебное «сайт обновился в фоне».
- Declarative Web Push (iOS/iPadOS 18.4, macOS 15.5; M, webkit.org/blog/16535): JSON с `"web_push": 8030`, обязательные непустой `title` и `navigate` (URL перехода), необязательные `body`, `app_badge`. Если SW есть и показал замену, декларативное уведомление отбрасывается, иначе показывается оно и «штрафа за неудачу SW нет». Если JS SW удалён (действие пользователя или ITP), декларативное всё равно покажется, но изменить его нельзя.
- Chrome, Firefox и iOS до 18.4 не понимают декларативный формат сами: SW должен прочитать `event.data.json()`, увидеть `web_push === 8030` и вызвать `showNotification` с теми же полями, а `notificationclick` должен сам перейти по `navigate`. На iOS 18.4+ `tag` не схлопывает уведомления (M, предыдущее исследование) и `navigate` обрабатывает система. Две реализации одного формата дают дубли, если ключ дедупликации не лежит на сервере.
- Заголовки и дополнительные поля формата (`mutable`, тип содержимого сообщения, требования к абсолютному URL в `navigate`) в источниках, которые я прочитал, полностью не описаны: проверить по актуальному тексту WebKit перед реализацией (L).

**How to avoid:**
Один формат payload, один билдер на сервере (`buildPushPayload(event)`), таблица тестов «тип события → payload» и проверка размера (Pitfall 18). SW всегда показывает уведомление, подавление «вкладка видна» делается на сервере (Pitfall 11), а не в SW. Один и тот же SW-путь для платформ без декларативной поддержки. Не полагаться на `renotify`, `tag`, действия-кнопки как на кроссплатформенные.

**Warning signs:**
На iOS после пары недель подписки исчезают (ответы 410 на устройствах, где уведомления не показывались); дубли на устройствах, где SW и система показали по уведомлению; в e2e Chromium-тест проходит, а на iPhone клик не ведёт в нужное место.

**Phase to address:** B (формат подписки и SW-обработчик), C (билдер payload), D (устройства).

### Pitfall 9: ключи VAPID: потеря или смена обнуляет все подписки; публичный ключ запечён в сборку

**What goes wrong:**
Подписка создаётся с `applicationServerKey` (открытый ключ VAPID). Отправка с другим ключом получает 401/403 от push-сервиса, подписку не «починить» на сервере: клиент обязан отписаться и подписаться заново (M, pushpad и w3c/push-api issue 327, поиск; L по деталям отдельных сервисов). Если закрытый ключ потерян вместе с `api.env` (файлы деплоя лежат вне Git, `~/.claude/servers/bio-exam.md`), все подписки всех учеников мертвы одновременно. Ещё две ловушки:
- Гайд Next.js кладёт ключ в `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (H). Переменные `NEXT_PUBLIC_*` вшиваются в клиентский бандл при сборке; образ собирается на сервере, Dockerfile вне Git, без build-arg ключ окажется `undefined`, `subscribe()` упадёт только в production. Смена ключа потребует пересборки.
- Контракт окружения `scripts/check-env-contract.mjs` в `yarn verify` падает, если ключ читается в коде, но не описан в `.env.example` (`app/server/.env.example`, `app/web/.env.example`).

**How to avoid:**
1. Отдавать публичный ключ и его идентификатор из API (`GET /api/push/config` → `{ publicKey, keyId }`), а не из `NEXT_PUBLIC_*`. Тогда пересборка web для смены ключа не нужна.
2. В `push_subscription` хранить `vapid_key_id`. Сервер умеет держать два ключа в переходный период и подписывает по ключу строки.
3. На каждом запуске клиент сравнивает `subscription.options.applicationServerKey` с ключом от API; при расхождении `unsubscribe()` → `subscribe()` с новым ключом и повторная привязка (разрешение уже выдано, повторного запроса быть не должно, проверить на Chrome и iOS, L).
4. Ключи только в `api.env` на сервере, копия офлайн у владельца и в зашифрованном бэкапе, как мастер-ключ чатов (`.planning/research/chat/SECURITY.md`, раздел 9). Записать в runbook.
5. `VAPID_SUBJECT` должен быть корректным `mailto:` или `https:`; некорректное значение известно как причина 403 у APNs для Web Push (L, из опыта сообщества; проверить в фазе).
6. Добавить ключи в оба `.env.example` и проверить `yarn verify`.

**Warning signs:**
Массовые 403 после деплоя; доля успешных отправок падает до нуля при исправном API; в клиентском бандле `undefined` вместо ключа.

**Phase to address:** B (ключи, API, `.env.example`), D (runbook потери и ротации).

### Pitfall 10: доставка в России: два плеча, «принято» не значит «доставлено», устройства без Google

**What goes wrong:**
У Web Push два независимых плеча: (1) VPS → push-сервис (`fcm.googleapis.com`, `web.push.apple.com`, `updates.push.services.mozilla.com`), (2) push-сервис → телефон ученика по мобильной сети. Каждое может ломаться отдельно.
- Android Chrome и другие Chromium-браузеры используют FCM, iOS использует APNs; оба требуют глобального интернета. «Белые списки» мобильного интернета в 2026 году ломали push даже у российских сервисов: Новая газета (28.03.2026) приводит пример MAX с невозможностью доставки push из-за зависимости от иностранной инфраструктуры; RuStore Push работает хуже FCM из-за низкого приоритета фонового процесса (M, дословно прочитано, СМИ).
- Ответ `201 Created` от push-сервиса означает только «принято», не «доставлено»: квитанций доставки у Web Push нет.
- Устройства без Google-сервисов (Huawei после 2019, часть китайских и кастомных прошивок): `pushManager.subscribe()` завершается ошибкой «push service error» или метод недоступен (L, общие источники по FCM в Китае). RuStore Push относится к нативным приложениям и к Web Push отношения не имеет: не планировать.
- Какой push-сервис использует Яндекс Браузер на Android, я не нашёл ни в документации, ни в обзорах (L, пробел). Mozilla autopush из России: доступность не проверена (L).
- С VPS в Санкт-Петербурге доступ к `fcm.googleapis.com` и `web.push.apple.com` не проверялся; на сервер у агента доступа нет.

**How to avoid:**
1. Архитектурное правило уже принято: кабинет источник правды, push необязателен. Закрепить в требованиях: ни один сценарий не зависит от доставки push (например, нельзя делать подтверждение «ученик получил задание» по push).
2. Шаг runbook для пользователя до начала фазы C: с VPS выполнить `curl -sS -o /dev/null -w '%{http_code}\n' https://fcm.googleapis.com/` и то же для `web.push.apple.com` и `updates.push.services.mozilla.com`, сохранить результаты и время; повторить в D из контейнера `api`.
3. Клиент обрабатывает отказ `subscribe()`: фиксирует состояние «push недоступен на этом устройстве», не зацикливает повторы, показывает текст «Уведомления будут только в кабинете».
4. Снимать эффективную доставку: `notificationclick` и показ уведомления отправляют `POST /api/push/ack` (идентификатор события), по нему считается доля «принято → подтверждено» по платформам; без подтверждений из показа нельзя отличить «не дошло» от «не открыли».
5. Кнопка «Отправить тестовое уведомление» в настройках уведомлений: ученик или учитель сами проверяют канал на своём устройстве.
6. Другие каналы (почта, Telegram-бот) не входят в v5.0 (в проекте нет SMTP, решение «только в кабинете»); если нужно, вынести отдельным решением клиента.

**Warning signs:**
Доля подтверждённых показов у Android заметно ниже, чем у iOS; рост ошибок `subscribe()` по User-Agent; таймауты соединения с push-сервисами в журнале воркера.

**Phase to address:** C (учёт подтверждений), D (проверка доступа и устройств).

### Pitfall 11: дубли между кабинетом, SSE и push; несколько устройств; повторы после рестарта

**What goes wrong:**
Одно событие журнала приходит: счётчиком кабинета, по SSE (v4.0) в открытую вкладку, как push на каждое из 1–5 устройств пользователя. Если вкладка видна, пользователь видит его и в интерфейсе, и всплывающим уведомлением. Воркер доставки при падении посреди пакета (автодеплой перезапускает `api`) отправляет часть уведомлений повторно (доставка «минимум один раз»). На iOS `tag` не схлопывает (Pitfall 8).

**How to avoid:**
1. Уникальный ключ `(event_id, subscription_id)` в таблице доставок: повтор невозможен на уровне БД.
2. Отложенная отправка: доставка `webpush` создаётся с `not_before = created_at + 15–20 с`. К моменту отправки воркер проверяет: событие прочитано в кабинете (`read_at`) или у пользователя есть активное SSE-соединение с подтверждением чтения — тогда доставка помечается `suppressed`. Это единственное место подавления; в SW подавлять нельзя (Pitfall 8).
3. Группировка на сервере: пока по диалогу есть непрочитанное и уведомление уже отправлялось, новые события не создают новых push (троттлинг в `FEATURES-PWA.md`, раздел 7, пункт 6).
4. На платформах, где `tag` работает, ставить `tag = notification_event.id` либо `chat:{chatId}`; заголовок `Topic` протокола (RFC 8030) использовать только как дополнение, его поддержка у разных push-сервисов не проверена (L).
5. Отправка после сброса часов тишины (Pitfall 15) сворачивается в одно уведомление «Несколько новых уведомлений».

**Warning signs:**
В таблице доставок несколько строк на пару (событие, подписка); жалобы «приходит дважды»; рост уведомлений сразу после деплоя API.

**Phase to address:** C.

### Pitfall 12: приватность несовершеннолетних на экране блокировки и через внешние push-сервисы

**What goes wrong:**
Текст уведомления виден на экране блокировки устройства, которым часто пользуется семья или класс. «Работа проверена: 1 балл из 3» или «Анна Петровна: ты опять не сдал» раскрывают оценку и отношения с учителем посторонним. Метаданные (время, endpoint) проходят через иностранные серверы FCM/APNs; сам payload шифруется по RFC 8291 и push-сервис его не читает (H, RFC), однако факт и время уведомления видны. 152-ФЗ и согласие законного представителя для переписки несовершеннолетних юристом не проверялись (пробел из `SECURITY.md`).

**How to avoid:**
Заголовок по умолчанию «bio-exam», тело «Есть новое уведомление», без имён, без оценок, без названий тестов; `navigate` = `/notifications/<id>`: идентификаторы без смысла, доступ проверяется сервером при открытии. Расширенное превью только по явной настройке и только для учителей и взрослых ролей; для учеников не включать. Изображения и названия файлов в payload не класть никогда. Не писать значения payload в журнал. В тексте разрешения пояснять, что уведомления без содержания. Вопрос про юридическую сторону передать клиенту (список вопросов `SECURITY.md`, раздел 11).

**Warning signs:**
В билдере payload появляется поле с текстом из БД; в тестах payload строка длиннее 200 байт без причин.

**Phase to address:** C (билдер и тест «payload не содержит данных события»), B (текст запроса).

### Pitfall 13: Service Worker ломает существующие e2e и будущий SSE; тесты push

**What goes wrong:**
В `e2e/tests` пять файлов используют `page.route` или `setOffline` (`answer-durability`, `attempt-slow-network`, `submit-retry`, `teacher-draft-durability`, `question-draft-durability`; считались через `rg`, H). Playwright: если у SW есть обработчик `fetch`, запросы страницы через `context.route()` часто не перехватываются; запросы самого SW перехватываются, запросы обновления скрипта SW через маршруты не пройдут (M, playwright.dev/docs/service-workers). Конфигурация использует `chromium-desktop` и `chromium-mobile` (Pixel 7) только на Chromium, `next start` (H, `e2e/playwright.config.ts`). Как только SW зарегистрируется в production-сборке e2e, тесты медленной сети и повторной отправки молча перестанут управлять сетью. Также обработчик `fetch`, который отвечает на SSE `/api/chat/stream`, может буферизовать поток или обрывать его (L, по общему поведению); EventSource через SW безопасно пропускать без `respondWith`.

WebKit в Playwright не поддерживает SW и push (M); iOS проверять можно только вручную. Настоящий FCM и APNs в CI недоступны.

**How to avoid:**
1. Для существующих проектов `chromium-desktop` и `chromium-mobile` задать `use: { serviceWorkers: 'block' }`, чтобы набор не менялся.
2. Отдельный проект `chromium-pwa` с `serviceWorkers: 'allow'` и узким набором сценариев: манифест и `/sw.js` открываются без входа (Pitfall 1); после входа SW зарегистрирован и не кэширует `/api/*`; событие `push` доставляется через CDP `ServiceWorker.deliverPushMessage` (через `context.newCDPSession`, команда описана в Chrome DevTools Protocol; конкретный рецепт взят из поиска, L), `context.grantPermissions(['notifications'])`; уведомление содержит только заглушку; клик ведёт на нужный маршрут (клик по системному уведомлению скриптом не эмулируется: выносить выбор адреса перехода в чистую функцию и проверять её отдельно, а сам клик проверять вручную); выход снимает привязку подписки.
3. Отправка в push-сервис за портом `PushTransport` с адаптерами «web-push» и «в памяти» (по образцу ADR-0004). `web-push` отправляет только по HTTPS, поэтому локальный поддельный push-сервис в интеграционных тестах проще заменить адаптером, чем поднимать TLS.
4. Юнит-тесты только там, где много вариантов (политика тестов): таблица «код ответа push-сервиса → действие» (201, 400, 401, 403, 404, 410, 413, 429, 5xx), вычисление часов тишины по часовому поясу, билдер payload и его размер. Остальное интеграционные тесты сервера и e2e.
5. Ручной чек-лист устройств (iOS 16.4–18.3, 18.4+, Android с Google, Android без Google) выполняет пользователь.

**Warning signs:**
Тесты `attempt-slow-network` и `submit-retry` зелёные, но не перехватывают запросы; после включения SW растёт время e2e.

**Phase to address:** A (разделение проектов), C (тесты воркера), D (ручной чек-лист).

### Pitfall 14: воркер доставки на сервере 6 ГБ с контейнером `api` на 768 МБ

**What goes wrong:**
Контейнер `api` ограничен 768 МБ, `web` 1 ГБ (`~/.claude/servers/bio-exam.md`). Пользователей мало (на момент переезда 31), поэтому риск не в объёме, а в зависших соединениях: из России запросы к push-сервисам могут висеть без ответа; без таймаута сокеты и обработчики копятся, очередь забивается. Ещё риски: воркер внутри `api` перезапускается автодеплоем посреди пакета; рост таблицы доставок; ответ 429 с `Retry-After`; ограничение Chrome на рассылку для «злоупотребляющих» доменов (1000 сообщений в минуту через FCM, ответ 429; M, helpnetsecurity 2026-08-12) нам не грозит по объёму, но подтверждает, что ответ 429 надо обрабатывать.

**How to avoid:**
1. Воркер в том же процессе `api` (без нового контейнера), опрос таблицы доставок раз в несколько секунд, захват строк `FOR UPDATE SKIP LOCKED` с «арендой» (`locked_until`): упавший процесс освобождает строки сам.
2. Таймаут запроса 10 с, общий `https.Agent` с `keepAlive`, предел параллелизма 5–10, размер пакета небольшой.
3. Автомат повторов по таблице ответов: 2xx — готово; 404/410 — удалить подписку; 400/401/403 — не повторять, пометить `failed` и поднять сигнал (ключи или payload неверны); 413 — ошибка кода, не повторять; 429 — ждать `Retry-After`; сеть и 5xx — экспоненциальная пауза, максимум 5 попыток и не дольше `TTL` сообщения. `TTL` задавать по типу события (оценка и назначение: сутки; чат: час).
4. Автоматический выключатель по хосту push-сервиса: при серии таймаутов приостановить хост на минуты, чтобы не плодить зависшие запросы.
5. Корректное завершение по `SIGTERM`: дождаться текущего пакета (с лимитом), недоставленное остаётся `pending`.
6. Хранение: удалять завершённые доставки старше 30 дней.

**Warning signs:**
Растёт число строк `pending` с `attempts > 2`; память `api` по Beszel подбирается к лимиту; очередь «стоит» после деплоя.

**Phase to address:** C.

### Pitfall 15: часы тишины и часовые пояса

**What goes wrong:**
Сервер работает в Europe/Moscow, ученики живут в 11 часовых поясах. Часы тишины по серверному времени будят ученика в Новосибирске. Жёстко заданное «+3» неверно для остальных. Россия давно без перехода на летнее время, но считать надо через IANA-имя пояса. Выход из тишины даёт шквал накопленных уведомлений. Для учителя (по умолчанию 21:00–09:00, `FEATURES-PWA.md`) и для учеников политики разные.

**Prevention:**
Хранить `time_zone` (IANA) в настройках пользователя, определять по `Intl.DateTimeFormat().resolvedOptions().timeZone`, давать изменить вручную, запасное значение Europe/Moscow. Вычислять окно на сервере в момент создания доставки (`not_before`), события внутри тишины откладываются и сворачиваются в одно. Тесты таблицей: пояса, полночь, окно через полночь.

**Phase to address:** C.

### Pitfall 16: усталость от запросов разрешения и автоотзыв в Chrome

**What goes wrong:**
Браузерный запрос показан сразу при входе: часть детей нажмёт «Блокировать», и повторно показать запрос нельзя, остаётся инструкция по настройкам. Chrome в 2026 году отзывает разрешения у сайтов, с которыми пользователь давно не взаимодействовал, и даёт «отписку одним касанием» (M, helpnetsecurity, 2026-08-12). На iOS запрос возможен только в standalone и по жесту (Pitfall 7).

**Prevention:**
Собственная плашка в контексте («Получать уведомления о проверке работ»), браузерный запрос только после нажатия «Включить». Состояния `default`, `granted`, `denied` и «отложено»; после «Не сейчас» не чаще раза в 14 дней и не более трёх раз. При `denied` показывать, как включить в настройках, и не пытаться запрашивать снова. Не запрашивать при первом входе и не во время активной попытки теста. Обновлять `last_seen_at` при запуске, чтобы подписки неактивных устройств можно было отличить от живых.

**Phase to address:** B.

### Pitfall 17: статусы 404/410 и другие ошибки push-сервиса

**What goes wrong:**
404 и 410 означают, что подписки нет (отписался, очистил данные, переустановил PWA): строку нужно удалить, иначе воркер тратит попытки впустую (M, pushpad). Ответы 401/403 часто означают проблему ключей VAPID, а не одной подписки: удаление по ним сотрёт здоровые подписки при ошибке конфигурации. Событие `pushsubscriptionchange` для автообновления подписки поддерживается неравномерно (L, я не проверял надёжность).

**Prevention:**
Удалять только по 404 и 410. Серия 401/403 по многим подпискам сразу — сигнал администратору и остановка канала, а не удаление. Не рассчитывать на `pushsubscriptionchange`: сверка подписки на каждом запуске приложения (Pitfall 9, пункт 3).

**Phase to address:** C.

### Pitfall 18: размер и состав payload

**What goes wrong:**
`web-push` отклоняет payload больше 4078 байт (L, документация пакета через поиск; RFC 8030 гарантирует 4096 байт, `FEATURES-PWA.md`). Кириллица занимает 2 байта на символ в UTF-8. Для заглушек запас огромен, проблема появляется, когда кто-то добавляет в payload текст события, имена или список вложений.

**Prevention:**
Билдер ограничивает поля (заголовок до 60 символов, тело до 140), тест проверяет размер по таблице всех типов событий, текст не попадает в payload (Pitfall 12 про приватность). Для `web-push` задать явный `TTL` и `urgency`.

**Phase to address:** C.

### Pitfall 19: установка на Android Chrome

**What goes wrong:**
Chrome убрал требование обработчика `fetch` для установки из меню (Chrome 108 на мобильных, 112 на настольных), но логика показа `beforeinstallprompt` его по-прежнему требует (M, developer.chrome.com/blog/update-install-criteria). SW, который нужен только для push, не вызовет баннер установки. Пустой `fetch`-обработчик ради баннера Chrome считает вредным для скорости. Новые критерии 2026 года я не нашёл (L). `beforeinstallprompt` есть только в Chromium; гайд Next.js не рекомендует строить на нём установку (H). Изменение `id` или `start_url` манифеста потом создаёт «второе» приложение.

**Prevention:**
Не строить сценарий установки на `beforeinstallprompt`: показывать кнопку «Установить» только если событие пришло, иначе инструкция (меню браузера, «Добавить на главный экран»). Задать `id`, `scope: '/'`, `start_url`, `display: 'standalone'`, иконки 192 и 512 (включая maskable), `short_name`, `theme_color` и `background_color` сразу в окончательном виде. Если выбран узкий `fetch`-обработчик (Pitfall 2), он годится и для баннера. Не показывать приглашение установить при первом входе и во время попытки.

**Phase to address:** A.

### Pitfall 20: область действия SW, регистрация и обновление

**What goes wrong:**
- Скрипт в `/sw.js` управляет всем сайтом, включая `/api/*`; SW из `/_next/...` получил бы узкую область. Помощники для Turbopack, которые отдают SW через маршрут, требуют заголовок `Service-Worker-Allowed` (L).
- Без `updateViaCache: 'none'` импортируемые скрипты могут кэшироваться до суток (M, web.dev: проверка обновления SW запускается навигацией и событиями вроде `push`, не чаще раза в сутки для функциональных событий).
- В `next.config.ts` нет `headers()`; Caddy вне Git по правилу пользователя. Заголовки `Cache-Control: no-cache` для `/sw.js` лучше задать в `next.config.ts` (проверяемо в репозитории), любые правки Caddy оформлять шагом runbook.
- Регистрация во время `load` и только в production: `next dev --turbopack` с SW даёт трудноуловимые устаревшие ответы.
- Будущая CSP из v4.0 (`script-src` с nonce) блокирует регистрацию SW, если не задан `worker-src 'self'`, потому что `worker-src` по цепочке откатывается на `script-src` (M, спецификация CSP). Нужно согласовать фазы.
- Линтер и форматтер (`oxlint`, `oxfmt`) обрабатывают `public/sw.js`: нужны глобальные `self`, `clients`.

**Prevention:**
Ручной `public/sw.js` (как в гайде Next.js 16.3.8, H), регистрация `{ scope: '/', updateViaCache: 'none' }` в клиентском компоненте после загрузки и входа, `headers()` для `/sw.js`, добавить `worker-src 'self'` в чек-лист CSP v4.0.

**Phase to address:** A.

### Pitfall 21: откат плохого SW

**What goes wrong:**
Скрипт обновления `/sw.js` запрашивается мимо самого SW (M, по спецификации SW; проверить в e2e), поэтому даже сломанный `fetch`-обработчик можно заменить новой версией, если `/sw.js` отдаётся с сервера без редиректа, без долгого кэша и без 5xx (Pitfall 1). Снятие регистрации (`registration.unregister()` или `Clear-Site-Data: "storage"`) удаляет и push-подписку: каждому ученику придётся заново включать уведомления, на iOS открыть приложение. Автообновление «молча» невозможно.

**Prevention:**
Основной путь отката: исправить SW и выкатить (fix-forward). Заранее подготовить «минимальный SW» без `fetch` в качестве аварийной версии. Рычаг на случай полного сбоя: эндпоинт `GET /api/pwa/config` с `{ swEnabled }`, который читает код регистрации; при `false` клиент вызывает `getRegistrations().then(unregister)`. Использовать только если fetch-обработчик реально ломает сайт (цена: потеря подписок). Не применять `Clear-Site-Data: "storage"` (Pitfall 6).

**Phase to address:** A (рычаг и минимальный SW), D (runbook и репетиция).

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Serwist с `runtimeCaching` по умолчанию | Быстро получить «офлайн» | Кэш авторизованных страниц и API (Pitfall 2), версионный перекос (Pitfall 3) | Никогда в v5.0 |
| Публичный ключ VAPID в `NEXT_PUBLIC_*` | Повторяет гайд Next.js | Ключ запечён в сборку, ротация требует пересборки на сервере (Pitfall 9) | Только если ключ никогда не меняется, не рекомендуется |
| Подписка привязана к `user_id` без сессии | Одна колонка | Чужие уведомления на общем устройстве (Pitfall 5) | Никогда |
| Подавление уведомлений в SW при видимой вкладке | Меньше дублей | Отзыв подписки на iOS (Pitfall 8) | Никогда |
| Воркер доставки в отдельном контейнере | Изоляция | Ещё 128–256 МБ и ещё один сервис в compose вне Git | Только если нагрузка выросла на порядок |
| Тест push только через мок транспорта | Быстро, без сети | Не ловит реальные ошибки APNs и FCM | Для CI достаточно, реальная проверка в D |
| Один общий `Cache-Control: private, max-age=3600` для картинок (как в `app/server/src/routes/docs/assets.ts:77`) | Быстрее загрузка | Для фото ответов и чатов (v3.0, v4.0) браузерный кэш общего устройства отдаст чужую картинку | Только для картинок вопросов; для фото учеников `private, no-store` |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| `web-push` (Node) | Ожидать, что 201 означает доставку; не задать таймаут; удалять подписки по 401/403 | 201 = принято; таймаут 10 с; удалять по 404/410; сериал 401/403 = проверка ключей |
| FCM (`fcm.googleapis.com`) | Не проверить доступ с VPS; считать ограничение 1000/мин проблемой | Проба из контейнера `api`, обработка 429 с `Retry-After` |
| APNs Web Push (`web.push.apple.com`) | Некорректный `sub` VAPID; тихие push без показа | Корректный `mailto:`; всегда показывать уведомление (Declarative-формат) |
| Caddy (`~/.claude/servers/bio-exam.md`) | Менять заголовки и кэш `/sw.js` в Caddy и забыть, что файл вне Git | Заголовки в `next.config.ts`, правки Caddy только шагом runbook |
| `proxy.ts` | Забыть исключения для файлов PWA | Исключения в матчере и тесты (Pitfall 1) |
| Журнал событий v3.0 | Писать push-доставку отдельной таблицей событий | Доставка `webpush` как канал в `notification_delivery`; уникальный ключ `(event_id, subscription_id)` |
| Autodeploy | Рассчитывать на то, что клиент всегда на свежей сборке | `deploymentId`, обработка `ChunkLoadError`, нет перезагрузки при активной попытке |
| `check-env-contract.mjs` | Добавить ключи VAPID без `.env.example` | Обновить `app/server/.env.example` (и web, если нужен) до коммита |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Зависшие соединения к push-сервисам без таймаута | Рост памяти `api`, очередь «стоит» | Таймаут 10 с, предел параллелизма, выключатель по хосту | При первой же недоступности FCM или APNs из России |
| Воркер опрашивает таблицу без индекса | Нагрузка на PostgreSQL | Частичный индекс по `(status, next_attempt_at)` для `pending` | Десятки тысяч строк доставок |
| Таблица доставок растёт без очистки | Пухнет БД, дольше резервная копия | Удаление завершённых строк старше 30 дней | Месяцы работы |
| Регистрация SW блокирует первую отрисовку | Хуже LCP на слабых телефонах | Регистрация после `load`; SW мал | Постоянно, заметно на дешёвых Android |
| Шквал после окончания часов тишины | Пик отправок и раздражение | Свёртка в одно уведомление | Утро после массовых событий |
| Предварительное кэширование крупного бандла | Лишний трафик у учеников на мобильной сети | Не делать прекэш; только `/_next/static/` по требованию | Сразу, на медленном мобильном соединении |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Подписка остаётся живой после выхода или отзыва сессии | Чужие уведомления несовершеннолетним на общем устройстве, высокий риск | Привязка к `auth_sessions`, перепривязка по `endpoint`, отвязка при выходе |
| Текст сообщений и оценки в payload | Раскрытие на экране блокировки, высокий риск | Только заглушка, `navigate` с непрозрачным идентификатором |
| SW кэширует `GET /api/*` и HTML | Утечка данных между пользователями общего устройства, высокий риск | SW без кэша данных (Pitfall 2) |
| `endpoint` подписки как секрет в логах | Любой, у кого есть `endpoint` и ключи, может слать push | Не писать `endpoint` и ключи подписки в журнал, хранить `p256dh` и `auth` как данные ограниченного доступа |
| Закрытый ключ VAPID в репозитории или клиенте | Подделка рассылок | Только `api.env` на сервере, запись в `.env.example` пустышкой |
| Перенос сессии Safari в PWA через токен в URL | Утечка сессии ребёнка | Отдельный вход в PWA |
| `Clear-Site-Data: "*"` на выходе | Потеря черновиков, снятие подписок (Pitfall 6) | Точечная очистка |
| Кэш изображений ответов в общем HTTP-кэше устройства | Чужие фото ответов видны следующему ученику | `private, no-store` для фото учеников |

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| Запрос разрешения при первом входе | Ребёнок блокирует, повторно не включить | Своя плашка в контексте, браузерный запрос по кнопке |

## "Looks Done But Isn't" Checklist

- [ ] **Манифест и SW:** часто открываются только у вошедшего пользователя. Проверить: `curl -I` без cookie для `/sw.js`, `/manifest.webmanifest`, иконок возвращает 200, не 307.
- [ ] **Кэш SW:** DevTools Application, Cache Storage пуст после обычной работы, в `/_next/static/` лежит только неизменяемое.
- [ ] **Деплой:** после автовыкатки открытое PWA продолжает работать или сам перезагружается вне попытки; в журнале нет `ChunkLoadError`.
- [ ] **Выход:** подписка отвязана, уведомления закрыты, черновик попытки сохранён, второй пользователь на том же устройстве не получает уведомления первого.
- [ ] **iOS:** проверено на реальном iPhone: установка, повторный вход, включение уведомлений в standalone, пуш с заблокированным экраном, клик ведёт на нужную страницу.
- [ ] **Declarative:** на iOS 18.4+ и на устройстве без декларативной поддержки показывается ровно одно уведомление.
- [ ] **VAPID:** ключи и идентификатор в `api.env` и в зашифрованной копии; `yarn verify` зелёный (контракт окружения).
- [ ] **Доставка из России:** есть сохранённый результат проб с VPS и тестовая отправка на реальный телефон в мобильной сети.
- [ ] **Дубли:** одно событие даёт одно уведомление на устройство; прочитанное в кабинете до отправки не уходит push.
- [ ] **Часы тишины:** проверены для учеников в разных поясах.
- [ ] **Откат:** есть репетиция подмены `sw.js` на минимальный и вывод рычага `swEnabled`.
- [ ] **E2E:** существующие 5 спеков с `page.route` проходят при `serviceWorkers: 'block'`; проект `chromium-pwa` отдельный.
- [ ] **Затронутое Core Value:** попытка с таймером не перезагружается при обновлении SW, ответы сохранены.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| `/sw.js` редиректит на логин | LOW | Добавить исключение в матчер, выкатить; клиенты получат новую версию при следующей проверке |
| Закэширован устаревший HTML | MEDIUM | Выкатить SW без кэша (fix-forward); при необходимости рычаг `swEnabled=false` и снятие регистраций; подписки потеряны только при снятии |
| Потерян закрытый ключ VAPID | HIGH | Сгенерировать новый ключ, обновить `api.env`, новая версия клиента переподписывает при запуске; ученики, не открывшие приложение, не получат push до запуска |
| Подписки массово 403 | MEDIUM | Остановить канал, проверить ключ и `VAPID_SUBJECT`, не удалять подписки, повторить |
| Чужие уведомления на общем устройстве | MEDIUM | Отозвать подписки пользователя, исправить привязку к сессии, при инциденте уведомить клиента |
| Скопилась очередь доставок после сбоя сети | LOW | Остановить хост выключателем, пропустить просроченные по `TTL`, возобновить |
| Плохой SW сломал `fetch` | MEDIUM | Выкатить минимальный SW; если не помогает, снять регистрации рычагом (цена: потеря подписок) |
| Пропали черновики после выхода из-за `Clear-Site-Data` | HIGH | Невосстановимо на клиенте; убрать директиву, сообщить пострадавшим |
| iOS массово отозвал подписки | MEDIUM | Повторная подписка при открытии приложения; пересмотр показа уведомления на каждый push |

## Пробелы

- Какой push-сервис использует Яндекс Браузер на Android и доступность Mozilla autopush из России не подтверждены: проверить на реальных устройствах в фазе D (L).
- Поведение подписки при `unsubscribe()` и повторной `subscribe()` на iOS без повторного запроса разрешения и точные границы «жеста» в WebKit не проверены (L).
- Поведение Safari ITP для установленных PWA (вытеснение хранилища и SW) не проверялось; перенести в ручной чек-лист D (L).
- Полные требования формата Declarative Web Push (заголовки, `mutable`, форма URL в `navigate`) прочитаны не полностью: сверить с текстом WebKit перед реализацией (L).
- Надёжность `pushsubscriptionchange` и поддержка заголовка `Topic` у FCM и APNs не проверялись (L).
- Доступность `fcm.googleapis.com`, `web.push.apple.com` с VPS в Санкт-Петербурге не проверена; нет доступа агента к серверу, проверку выполняет пользователь (runbook D).
- Новые изменения критериев установки Chrome 2026 года не найдены; последний прочитанный источник описывает версии 108 и 112 (L).
- Юридические вопросы 152-ФЗ о согласии законного представителя на уведомления и передачу метаданных через иностранные push-сервисы не исследованы (из `SECURITY.md`).
