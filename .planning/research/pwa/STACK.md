# Technology Stack: PWA и Web Push (v5.0)

**Проект:** bio-exam
**Веха:** v5.0 «PWA и push-уведомления» (будущая; идёт после v3.0 с журналом уведомлений и v4.0 с чатами)
**Исследовано:** 2026-10-06
**Общая уверенность:** MEDIUM-HIGH по стеку и браузерным API (npm, исходники библиотек, nextjs.org, WebKit, запуск в этом репозитории), MEDIUM по доставке из России (нет первичных источников о блокировках push-сервисов, есть косвенные), LOW по альтернативным каналам (условия платформ меняются быстро, источники вторичные).

**Шкала уверенности** (та же, что в `.planning/research/chat/FEATURES-PWA.md`): **H** первоисточник прочитан напрямую или проверено запуском (реестр npm, исходники пакета, nextjs.org, webkit.org, код репозитория); **M** два согласованных вторичных источника или выдержка официального текста без открытия страницы; **L** один вторичный источник, поисковая выдержка, оценка. Шов `classify-confidence` оценивает любой веб-провайдер (`websearch`, `webfetch`) как LOW независимо от содержимого, поэтому шкала выше ведётся вручную и привязана к типу источника.

## Главный вывод

В v5.0 нужна **одна новая серверная зависимость (`web-push` 3.6.7) и ни одной новой зависимости в web**. Манифест даёт сам Next 16 (`app/manifest.ts`), сервис-воркер пишется вручную в `app/web/public/sw.js` (около 100 строк, без сборки), воркер доставки живёт внутри процесса API как тот самый «модуль фоновых задач», который уже заложен в v3.0.

Семь решений, которые определяют дорожную карту:

1. **Сервис-воркер без кэширования страниц и API.** Корневой layout web помечен `force-dynamic`, каждая страница отдаёт серверный HTML за авторизацией, поэтому «оболочка приложения» из precache не даёт офлайна: открыть страницу холодно без сети всё равно нельзя. Офлайн-прохождение теста в v5.0 **не делаем**. Устойчивость уже открытой попытки обеспечивают IndexedDB-черновики из v1.0, а не сервис-воркер. Ядро продукта (таймер на сервере, оценка ровно один раз) не должно зависеть от кэша на устройстве. В сервис-воркере нет обработчика `fetch` (Chrome не требует его для установки, см. §1.4); максимум, что допустимо позже, это статическая страница `/offline` и runtime-кэш `_next/static/*`.
2. **Serwist не берём.** `@serwist/turbopack` 9.5.13 работает с Turbopack (проверен исходник), но нужен только для precache и офлайн-оболочки, которых в v5.0 нет. Фиксируем как путь расширения, версия `9.5.13` строго (линейка `10.0.0-preview` имеет баг внедрения манифеста, serwist/serwist#294). `next-pwa` и `@ducanh2912/next-pwa` не использовать (последние релизы 2022-08-23 и 2024-09-18).
3. **Первое, что сломается: `app/web/proxy.ts`.** Его matcher исключает только `api`, `_next/static`, `_next/image`, `favicon.ico`, `robots.txt`, `sitemap.xml`, `uploads`. Запросы `/manifest.webmanifest`, `/sw.js` и иконок без cookie получат редирект на `/login`: манифест станет невалидным (браузер читает его без учётных данных), регистрация сервис-воркера упадёт (редирект для скрипта воркера запрещён). Это нужно исправить в первом плане вехи, до остального.
4. **Формат push: один payload в формате Declarative Web Push** (`{"web_push": 8030, "notification": {...}}`). Safari 18.4+ (iOS и iPadOS) и 18.5+ (macOS) показывает его сам, без запуска сервис-воркера. Chrome и Firefox его не понимают и отдают `push`-событию сервис-воркера, который читает тот же JSON. Текста сообщений в payload нет.
5. **Отправка из Express (ADR-0001), не из Next.** Библиотека `web-push` 3.6.7: 0 уязвимостей по `npm audit` (2026-10-06), корректно работает на Node 24.17 (проверено запуском), типы `@types/web-push` 3.6.4. Релизов нет с января 2024, но репозиторий жив (коммиты и PR в сентябре-октябре 2026, на main уже лежат типы и переход на WebCrypto, без релиза). Страхуемся тонким портом `PushTransport` (по образцу хранилища из ADR-0004), чтобы замена библиотеки была локальной.
6. **Воркер доставки внутри API, отдельного контейнера нет.** Опрос таблицы `notification_delivery` с `FOR UPDATE SKIP LOCKED`, пробуждение событием после COMMIT (шина v4.0) и опрос раз в несколько секунд как запасной режим. Это тот же «модуль фоновых задач» (таймер в `index.ts` плюс `pg_try_advisory_xact_lock`), что в `.planning/research/STACK.md` §7 для v3.0; `pg-boss` и `graphile-worker` отвергнуты там же и здесь.
7. **Push из России: «по возможности», кабинет остаётся источником правды.** Сам факт доставки FCM, APNs и Mozilla с российского VPS проверяется **спайком в первом плане** (§6). Дополнительных каналов в v5.0 не добавляем (§7): Telegram ограничен Роскомнадзором, MAX и VK требуют юридического оформления, email пока нет смысла без SMTP-провайдера.

### Новая серверная зависимость

| Библиотека | Версия | Где | Назначение | Почему |
|------------|--------|-----|------------|--------|
| web-push | 3.6.7 (npm latest, modified 2024-01-16; проверено) | app/server | Шифрование payload (RFC 8291, `aes128gcm`), VAPID (RFC 8292), HTTP-отправка, генерация ключей | Стандартная библиотека с 3,5 тыс. звёзд, 5 прямых зависимостей (`asn1.js`, `http_ece`, `https-proxy-agent`, `jws`, `minimist`), 0 уязвимостей. Опции отправки: `TTL`, `urgency` (`very-low`, `low`, `normal`, `high`), `topic` (до 32 символов url-safe base64), `headers`, `proxy` (через `https-proxy-agent`), `agent`, `timeout`, `contentEncoding` (H, исходник `web-push-lib.js` прочитан и запущен). Ошибки: `WebPushError` с `statusCode`. Минимальная версия Node 16, у нас 24. |
| @types/web-push | 3.6.4 (devDependency; modified 2026-10-04) | app/server | Типы | Пакет DefinitelyTyped поддерживается. Когда в `web-push` выйдут встроенные типы (уже на main), убрать. |

Проверка совместимости, выполненная для этого документа (H): `generateVAPIDKeys()` возвращает `publicKey` длиной 87 и `privateKey` длиной 43 символа; `generateRequestDetails(..., {TTL, urgency, topic})` формирует заголовки `TTL`, `Urgency`, `Topic`, `Content-Encoding: aes128gcm`, `Authorization: vapid t=..., k=...`; `sendNotification` под `node --pending-deprecation --trace-deprecation` на Node v24.17.0 не печатает предупреждений. Issue #978 («warning in Node 24») на момент проверки к нашему пути вызова отношения не показал.

**Две особенности `web-push`, которые меняют проект (H, проверено запуском):**

- **Заголовок `Content-Type` перезаписывается.** При передаче `headers: {'Content-Type': 'application/notification+json'}` итоговый заголовок остаётся `application/octet-stream`: библиотека выставляет его после шифрования. Это не проблема: для Safari опт-ин в декларативный формат делает ключ `"web_push": 8030` внутри JSON (WebKit blog, черновик W3C Push API), а MIME-тип `application/notification+json` в материалах WebKit и в обзорах назван рекомендуемым, не обязательным (M). Проектировать так, будто заголовка нет.
- **Ограничение размера не принудительное.** Генерация запроса с payload 5000 байт прошла без ошибки, хотя RFC 8030 гарантирует только 4096 байт. Проверку размера (целимся в менее 1 КБ после JSON-сериализации) пишем сами в `PushTransport`.

## 1. Манифест, иконки, установка

### 1.1. `app/manifest.ts`

Формат: `export default function manifest(): MetadataRoute.Manifest` (nextjs.org, H). Маршрут `/manifest.webmanifest`, Next сам добавляет `<link rel="manifest">` (без `crossorigin`, поэтому манифест запрашивается без cookie, см. §1.5).

Рекомендуемое содержимое:

```ts
import type { MetadataRoute } from 'next'

export default function manifest(): MetadataRoute.Manifest {
	return {
		id: '/',
		name: 'bio-exam',
		short_name: 'bio-exam',
		description: 'Подготовка к ЕГЭ по биологии',
		lang: 'ru',
		start_url: '/',
		scope: '/',
		display: 'standalone',
		background_color: '#ffffff',
		theme_color: '#ffffff',
		icons: [
			{ src: '/pwa/icon-192.png', sizes: '192x192', type: 'image/png', purpose: 'any' },
			{ src: '/pwa/icon-512.png', sizes: '512x512', type: 'image/png', purpose: 'any' },
			{ src: '/pwa/icon-maskable-512.png', sizes: '512x512', type: 'image/png', purpose: 'maskable' },
		],
	}
}
```

Значения `name` и `short_name` уточнить в `config/site.ts` (`siteConfig.name`), цвета взять из токенов дизайна. `display: standalone` обязателен для push на iOS (WebKit blog 13878, H). `start_url: '/'` ведёт на страницу под `proxy.ts`: для неавторизованного будет редирект на `/login`, это нормально для запуска приложения (запрос навигации, не манифест).

### 1.2. Иконки

| Файл | Размер | Для чего |
|------|--------|----------|
| `public/pwa/icon-192.png`, `icon-512.png` | 192, 512 | Критерии установки Chrome: 192 и 512 обязательны (web.dev, H) |
| `public/pwa/icon-maskable-512.png` | 512, значимая часть в центральных 80 процентах | Android адаптивная иконка |
| `app/apple-icon.png` | 180 | iOS Home Screen. iOS берёт `apple-touch-icon` и не опирается на иконки манифеста (M), Next добавляет тег сам по конвенции `apple-icon.png` (H) |
| `public/pwa/badge-96.png` | 96, монохром с альфа-каналом | Поле `badge` уведомления в Android (опционально) |

Исходного векторного логотипа в репозитории нет (`public/img/logo.jpg` растровый и непрозрачный). **Нужен макет иконки от клиента или дизайнера**; это нетехническая зависимость, о ней стоит сказать до начала плана. Метаданные в корневом layout ссылаются на `/favicon.svg`, которого в репозитории нет (в git есть только `app/favicon.ico`): при работе над иконками привести в порядок.

### 1.3. Экран запуска (splash)

Android строит его из `background_color` и иконки автоматически. iOS из манифеста его не строит; нужны `apple-touch-startup-image` под каждый размер экрана (M, подтверждается несколькими источниками). **Решение: в v5.0 не делать**, поставить `background_color` равным фону страницы, чтобы вспышка была незаметной. Если клиент потребует, брать одноразовую генерацию на `sharp` для 6-8 размеров и `appleWebApp.startupImage` в метаданных Next; `pwa-asset-generator` не добавлять (L: оценка, на устройствах не проверялось).

### 1.4. Установка и сервис-воркер

- Критерии установки Chrome: `name` или `short_name`, иконки 192 и 512, `start_url`, `display` один из `standalone`/`fullscreen`/`minimal-ui`, HTTPS, нет `prefer_related_applications: true` (web.dev install-criteria, обновлено 2024-09-19, H). Сервис-воркер в списке критериев **нет**, гайд Next.js прямо говорит, что установку можно предлагать без офлайн-поддержки (H). Проверка на практике: DevTools, Application, Manifest, «Installability» (спайк, §10).
- iOS: установка только вручную («Поделиться», «На экран Домой»); `beforeinstallprompt` в Safari нет (nextjs.org docs, H). Нужна своя подсказка «как установить», показываемая только если `navigator.userAgent` iOS и `display-mode: standalone` ложно. В iOS 26 любой сайт, добавленный на домашний экран, по умолчанию открывается как веб-приложение (M, heise), но push по-прежнему требует именно установленного приложения.
- Android Chrome и десктопный Chromium: перехватывать `beforeinstallprompt`, показывать кнопку в настройках. Firefox desktop PWA не устанавливает.

### 1.5. Интеграция с `proxy.ts` (критично)

Расширить matcher в `app/web/proxy.ts`, исключив:

```
manifest.webmanifest, sw.js, pwa/, apple-icon, icon, offline (если появится)
```

Иначе неавторизованный запрос манифеста или `sw.js` получит 307 на `/login` (H: прочитан код). Тест: `proxy.test.ts` уже есть, добавить таблицу путей «не требуют сессии». Через `crossorigin="use-credentials"` обходить не нужно: исключение проще и надёжнее.

### 1.6. Заголовки

`next.config.ts` сейчас не содержит `headers()`. Добавить для `/sw.js`: `Cache-Control: no-cache, no-store, must-revalidate` и `Content-Type: application/javascript; charset=utf-8` (по гайду Next.js, H). При регистрации указывать `{ scope: '/', updateViaCache: 'none' }`. CSP из `helmet` относится только к ответам API (`connectSrc 'self'`); у web CSP нет, так что новой политики для воркера не требуется. Если CSP для web появится позже, воркеру достаточно `default-src 'self'`.

## 2. Сервис-воркер: инструменты и что кэшировать

### 2.1. Выбор: ручной `public/sw.js`

| Вариант | Состояние (проверено) | Вердикт |
|---------|-----------------------|---------|
| Ручной `public/sw.js` | Фиксированный URL, область `/`, нет шага сборки, не зависит от Turbopack | **Брать** |
| `@serwist/turbopack` 9.5.13 (npm modified 2026-10-04) | Исходник прочитан: `createSerwistRoute` отдаёт воркер через Route Handler `app/serwist/[path]/route.ts` (`force-static`, `generateStaticParams`), собирает esbuild при сборке, выставляет `Service-Worker-Allowed: /`; регистрация явная (`SerwistProvider`), URL `/serwist/sw.js`. Peer: `next >=14`, `esbuild >=0.25 <1`, `typescript >=5`; зависимости `@swc/core`, `@serwist/build`, `zod 4.6.5`. Гайд nextjs.org ссылается на него (H) | Не брать в v5.0. Путь расширения, если появится требование к precache и офлайн-оболочке. Закрепить `9.5.13`; `@serwist/next` требует webpack. |
| `next-pwa` 5.6.0 | Последнее изменение 2022-08-23 | Не использовать |
| `@ducanh2912/next-pwa` 10.2.9 | 2024-09-18, автор перешёл на Serwist | Не использовать |
| `workbox-build` 7.4.1 | Жив, но интеграции с Turbopack нет | Не нужен |
| `new URL('../lib/service-worker.js', import.meta.url)` из гайда Next.js | Не проверялось в этом репозитории; при Turbopack путь может оказаться хешированным ассетом под `/_next/static/`, откуда область `/` недоступна без заголовка (L) | Не использовать, держать воркер в `public/` |

Честное ограничение ручного воркера: он **не может сделать precache хешированных `_next/static`**, потому что список файлов известен только сборке. Поэтому «оболочка» без Serwist означает runtime-кэш (stale-while-revalidate для `_next/static/*`) плюс статическая `/offline`. В v5.0 и это не включаем.

Если Serwist всё же понадобится, проверить на `next build`: (а) в корневом layout `dynamic = 'force-dynamic'`, а Route Handler Serwist экспортирует `force-static`: сегментная конфигурация у Route Handler своя, но подтвердить; (б) `esbuild` с нативным бинарём в образе web; (в) `proxy.ts` пропускает `/serwist/*`; (г) в образе Docker сборка web не имеет БД, `generateStaticParams` выполняет esbuild при сборке.

### 2.2. Что кэшировать: решение

| Ресурс | Политика | Причина |
|--------|----------|---------|
| HTML страниц (навигации) | **Не кэшировать**, обработчика `fetch` нет | Серверный рендер за авторизацией, `force-dynamic`; кэш авторизованных страниц на общем школьном устройстве недопустим |
| `/api/*` | **Только сеть** | Попытки, ответы, будущая переписка с ребёнком не должны оседать в Cache Storage (`chat/FEATURES-PWA.md` §6) |
| `_next/static/*` | Не кэшировать в v5.0 (HTTP-кэш браузера справляется: имена с хешем и `immutable`) | Расхождение версий чанков после деплоя при самописном кэше создаёт больше проблем, чем даёт |
| Иконки и `/pwa/*` | HTTP-кэш | Уведомлениям иконки нужны, но воркер их не хранит |
| Офлайн-страница | Не в v5.0 | Без неё Chrome показывает свою страницу «нет сети»; приемлемо |

**Офлайн-прохождение теста: нет.** Причины, привязанные к Core Value («оценка ровно один раз, попытка проверяема так, как оценена»): таймер и сессия попытки управляются сервером, старт и сдача требуют сети, сдача идемпотентна по `clientAttemptId`; офлайн-копия задания и ответов на устройстве создала бы вторую правду. Уже открытую попытку от обрыва связи защищает модуль клиентского жизненного цикла и черновики в IndexedDB (v1.0, фаза 6; e2e «медленная сеть и офлайн» есть). Сервис-воркер здесь ничего не добавляет. Не включать `experimental.useOffline` из Next 16.3 (помечен «не для production», nextjs.org, H): это отдельный слой повторов запросов, не кэш воркера.

**Выход из аккаунта**: удалять подписку этого устройства на сервере (запрос с `endpoint`), вызывать `subscription.unsubscribe()`, очищать `caches` и IndexedDB-черновики прошлого пользователя. Подписка привязана к пользователю; на общем устройстве уведомления предыдущего пользователя не должны приходить следующему.

**Побочная выгода «нет `fetch`-обработчика»:** сервис-воркер не вмешивается в запросы, поэтому Playwright `page.route` в e2e (236 сценариев) продолжает работать как прежде.

### 3.2. Ключи VAPID

- Генерация один раз: `yarn dlx web-push generate-vapid-keys --json` (у Yarn 4 нет `yarn global add`, команда из гайда Next.js не подходит; H).
- Переменные окружения сервера: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (`mailto:` или `https:` URL; Apple отвергает невалидный и `localhost`-subject, в репозитории web-push появилось предупреждение 2026-09-11, M). Все три записать в `app/server/.env.example` только как заглушки: `scripts/check-env-contract.mjs` падает, если код читает ключ без записи в примере, и отвергает значения, похожие на секрет (H, код прочитан). Приватный ключ хранить рядом с `AUTH_JWT_SECRET` на VPS (в окружении Compose), не в БД и не в репозитории; копия офлайн у владельца.
- **Публичный ключ отдаёт API** (`GET /api/push/vapid-public-key`), а не `NEXT_PUBLIC_*`: один источник, нет пересборки web при смене, в web нет окружения push (ADR-0001).
- **Ротация ключа = потеря всех подписок**: подписка привязана к `applicationServerKey`. Относиться к ключу как к постоянному, ротацию не планировать. Потеря ключа = все пользователи подписываются заново.

### 3.3. Параметры отправки

| Параметр | Значение по умолчанию | Обоснование |
|----------|-----------------------|-------------|
| `TTL` | 86400 (сутки); для «назначен тест» до 259200; не более 4 недель (дефолт библиотеки 2419200) | Устаревший push («работа проверена» трёхдневной давности) хуже отсутствия; события живут в кабинете |
| `urgency` | `normal`; `high` только для личных сообщений чата (v4.0) и дедлайнов | `high` пробуждает устройство в режиме Doze; злоупотребление ведёт к понижению приоритета у FCM (M) |
| `topic` | до 32 символов url-safe base64, например хеш `chat:<id>`; для остальных видов не задавать | Заменяет неотправленное сообщение с тем же topic на уровне push-сервиса. Поддержка у сервисов различается (M). iOS игнорирует `tag` уведомления (M, `chat/FEATURES-PWA.md`), поэтому троттлинг на сервере обязателен |

### 3.4. Payload и шифрование

Шифрование: RFC 8291, `aes128gcm`; push-сервис (FCM, APNs, Mozilla, WNS) содержимое не читает (H, RFC, исходник). Лимит 4096 байт по RFC 8030. **Целиться в менее 1 КБ.**

Формат (Declarative Web Push, одновременно читаемый сервис-воркером):

```json
{
  "web_push": 8030,
  "notification": {
    "title": "Работа проверена",
    "body": "Откройте, чтобы посмотреть результат",
    "navigate": "https://<домен>/attempts/<id>",
    "tag": "review.graded",
    "lang": "ru",
    "app_badge": 3,
    "data": { "eventId": "<uuid>" }
  }
}
```

- `web_push` целое число `8030` (WebKit blog, черновик W3C Push API; H). В пересказе доклада WWDC25 встречается «8-0-3-0», это ошибка расшифровки (L).
- Обязательные поля `title` и `navigate` (H, WebKit blog). Использовать **абсолютный** URL в `navigate`; в блоге WebKit пример абсолютный, в одном пересказе доклада относительный (M). Основа: значение `ALLOWED_ORIGIN` (уже есть в окружении сервера) или отдельный ключ, если там список.
- Поле `mutable` не указывать. По черновику W3C и пересказам WebKit: `mutable: true` заставляет Safari запустить сервис-воркер, а без него уведомление показывается напрямую и воркер не запускается (M; в блоге WebKit 2025 описана более ранняя схема с запуском воркера и подменой уведомления, поэтому в воркере всё равно нужна ветка «push сработал, показать уведомление»).
- `app_badge` есть в блоге и объяснении WebKit (поведение Safari, M), в черновике W3C поле не найдено. Считать его возможностью Safari и не опираться на него в других браузерах.
- Заголовок `Content-Type: application/notification+json` библиотекой не выставляется (см. выше); опираться на ключ `web_push`.
- **Текста сообщений, ответов, оценок и имён учеников в payload нет**: только нейтральные заголовки («Новое сообщение от учителя», «Работа проверена»), `navigate` с идентификатором. Превью текста, если когда-нибудь потребуется, только как личная настройка пользователя, выключенная по умолчанию (развилка 5 в `chat/SUMMARY.md`). Без текста push не нарушает аргумент аудита переписки с ребёнком (`chat/SUMMARY.md` §5: возражение касалось пересылки содержимого вовне, а здесь содержимое наружу не уходит).
- **Любой push обязан превращаться в видимое уведомление** (`userVisibleOnly: true`). На iOS после трёх подряд не показанных push Safari отзывает подписку (M, `chat/FEATURES-PWA.md`); декларативный формат это страхует.

### 3.5. Обработчики сервис-воркера (запасной путь для Chrome и Firefox)

```js
self.addEventListener('push', (event) => {
	let payload
	try { payload = event.data ? event.data.json() : null } catch { payload = null }
	const n = payload && payload.notification
	const title = (n && n.title) || 'bio-exam'
	const options = {
		body: n && n.body,
		tag: n && n.tag,
		lang: 'ru',
		icon: '/pwa/icon-192.png',
		badge: '/pwa/badge-96.png',
		data: { url: n && n.navigate, eventId: n && n.data && n.data.eventId },
	}
	const tasks = [self.registration.showNotification(title, options)]
	if (n && typeof n.app_badge === 'number' && self.navigator.setAppBadge) {
		tasks.push(self.navigator.setAppBadge(n.app_badge))
	}
	event.waitUntil(Promise.all(tasks))
})
```

Правила, которые обработчик обязан соблюдать: при любой ошибке разбора всё равно показывать общее уведомление; не делать сетевых запросов в обработчике `push` (бюджет времени на iOS и риск отзыва подписки).

**Клик по уведомлению и переход по ссылке** (`notificationclick`): закрыть уведомление; взять `data.url`; **проверить**, что это URL того же origin (`new URL(url, self.location.origin).origin === self.location.origin`), иначе открыть `/`; `clients.matchAll({ type: 'window', includeUncontrolled: true })`; найденное окно приложения `focus()` и отправить ему `postMessage({ type: 'navigate', url })`, чтобы клиентский роутер перешёл без перезагрузки (метод `client.navigate()` работает только для управляемых клиентов, поэтому он не основной путь); если окна нет, `clients.openWindow(url)`. Всё внутри `event.waitUntil`. Для декларативных уведомлений Safari переход выполняет сам по `navigate`. Права на открываемый объект проверяются сервером при открытии страницы, а не при отправке (`chat/FEATURES-PWA.md` §7 п. 2). После перехода страница сама помечает событие прочитанным.

**Смена подписки.** Событие `pushsubscriptionchange` обрабатывать «по возможности»: воркер не имеет живого access-токена (срок 15 минут, обновление через cookie `refresh_token`), поэтому надёжный путь другой: **клиент при каждом открытии приложения сверяет `registration.pushManager.getSubscription()` с сервером** (`endpoint`, ключи) и при расхождении отправляет новую подписку. Воркер в этом событии только пересоздаёт подписку с прежним `applicationServerKey` и сохраняет её сообщением открытой вкладке или при следующем запуске.

### 3.4a. Подписка на клиенте

- Запрос разрешения только по жесту пользователя (обязательно на iOS, WebKit blog 13878, H) и после своей плашки с объяснением; не при первом входе (`chat/FEATURES-PWA.md` §6).
- `registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })`. Ключ `urlBase64ToUint8Array`, как в гайде Next.js.
- На iOS Safari вне установленного приложения push недоступен: сначала подсказка по установке (§1.4), затем запрос разрешения.
- Декларативный `window.pushManager.subscribe` (без воркера) в Safari 18.4+ существует (WebKit blog, спецификация: PushManager есть у Window и ServiceWorkerRegistration; H), но воркер нужен для Chrome и Firefox в любом случае, поэтому единая схема: регистрировать воркер и подписываться через `registration.pushManager`.

### 3.6. Хранение подписок (набросок, не миграция)

`push_subscription`: `id`, `user_id`, `session_id` (nullable), `endpoint` (unique), `p256dh`, `auth`, `user_agent`, `created_at`, `last_success_at`, `failure_count`, `disabled_at`.

- **Список допустимых хостов `endpoint` при сохранении** (защита от SSRF: сервер сам делает POST на адрес, который прислал клиент): `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com` (и поддомены `*.push.apple.com`), `*.notify.windows.com`. Только `https`, без userinfo, без IP-литералов, порт по умолчанию, длина не более 512 (M: согласуется в нескольких открытых проектах; H в части доменов браузерных push-сервисов по документации и примерам). Список вынести в конфигурацию для тестов.
- Ответы push-сервиса: **404 и 410** подписку удалить; **413** уменьшить payload (баг кода); **429** повтор с учётом `Retry-After`; **400, 401, 403** (в том числе Apple `BadJwtToken` при неверном `VAPID_SUBJECT`) считать ошибкой конфигурации, поднять сигнал, не удалять подписку; сетевая ошибка и 5xx повтор с экспоненциальным backoff в пределах TTL.
- Ключи `p256dh` и `auth` сами по себе без приватного ключа VAPID отправлять не позволяют; отдельное шифрование столбцов не обязательно (M).
- Лимит подписок на пользователя (например, 10) и удаление при выходе, смене пароля и блокировке пользователя (шов отзыва сессий из v1.0).

## 4. Воркер доставки без cron

**Решение: внутри процесса API, отдельного контейнера нет.** Причины: тот же образ и та же БД; нагрузка ввода-вывода (31 пользователь, десятки уведомлений в сутки); уже решено в v3.0 (`.planning/research/STACK.md` §7), чтобы фоновые задачи (очистка фото, outbox, чаты) жили в одном модуле без внешнего планировщика; один компонент меньше в Compose и в деплое.

Механика:

1. `notification_delivery` (канал `webpush`) получает `status` (`pending`, `sending`, `sent`, `failed`, `skipped`), `attempts`, `next_attempt_at`, `locked_until`, `last_error`.
2. Строка создаётся в транзакции события вместе с самим событием, но только если у получателя есть активная подписка и уведомления не заглушены (часы тишины, троттлинг «уже сообщили, пока не прочитано»).
3. Захват: короткая транзакция `UPDATE ... WHERE id IN (SELECT id FROM notification_delivery WHERE status='pending' AND next_attempt_at <= now() ORDER BY next_attempt_at FOR UPDATE SKIP LOCKED LIMIT n) RETURNING ...` с установкой `locked_until`. **HTTP-запросы выполняются вне транзакции.** Зависшие по `locked_until` строки возвращаются в очередь.
4. Параллелизм не более 8 одновременных отправок, `timeout` 10 с; результат записывается отдельной короткой транзакцией.
5. Пробуждение: после COMMIT событие в шине процесса (интерфейс из v3.0, `publish` и `subscribe`); запасной опрос раз в 5-10 с. `LISTEN/NOTIFY` не нужен, пока один процесс API. Тем не менее `SKIP LOCKED` делает запуск двух экземпляров при выкатке безопасным.
6. Backoff: 1 мин, 5 мин, 30 мин, 2 ч, затем отказ; не дольше TTL. Устаревшие по TTL строки переводятся в `skipped`, не отправляются.
7. `gracefulShutdown` в `index.ts` останавливает таймер до `pgPool.end()`. Точка входа воркера экспортируется функцией и отдельным скриптом по образцу `storage:reconcile`, чтобы вынести в свой контейнер строкой в Compose (тот же образ, другая команда), если понадобится (признаки: рост числа получателей, долгие отправки, влияние на задержку API).

**Не брать:** `pg-boss` 12.36.0, `graphile-worker` 0.18.0 (свои схемы и воркеры ради одного канала), `node-cron`, Redis и BullMQ (нет Redis в Compose), `pg-listen` 1.7.0 (последний релиз 2022-05-12).

Тестируемость: `PushTransport` (порт) с реализацией на `web-push` и фейком в памяти; e2e реальной доставки в Playwright невозможна (headless Chromium не получает push от FCM), поэтому доставку проверять серверными интеграционными тестами с фейком, а клиентскую часть e2e: манифест, регистрация воркера, сохранение подписки с подставленным endpoint, `context.grantPermissions(['notifications'])`. Реальная доставка проверяется вручную на устройствах (спайк и UAT).

### 6.2. Спайк в первом плане вехи (обязателен)

Скрипт `push:probe` на VPS и ручная проверка:

1. С VPS: TLS-рукопожатие и ответ на `HEAD`/`POST` без авторизации к `fcm.googleapis.com:443`, `updates.push.services.mozilla.com:443`, `web.push.apple.com:443`, `wns2-*.notify.windows.com` (ожидается 400, 401, 403 или 404, но не таймаут и не сброс).
2. Реальная отправка тестового push на подписку, созданную с реального Android-устройства (Chrome) и реального iPhone (установленное приложение), из контейнера API на Beget. Измерить задержку.
3. То же при мобильной сети у получателя и при Wi-Fi.
4. Если п. 1 или 2 падает: включить `PUSH_PROXY_URL` (опция `proxy` у `web-push` через `https-proxy-agent`) и повторить; решение о постоянном прокси или выносе отправки на хост за границей принять отдельно (это уже вопрос 152-ФЗ, содержимого в payload нет, но endpoint и ключи подписи пользователей относятся к данным).

Критерий выхода из спайка записывается в требованиях v5.0: «push на Android Chrome и iOS PWA доходит с Beget».

## 10. Что проверить на фазах (флаги исследований)

- **Фаза 1 (спайк, обязателен):** доступность push-сервисов с Beget (§6.2); установка на Android Chrome и iOS; регистрация воркера после правки `proxy.ts`; подтверждение, что Chrome предлагает установку без `fetch`-обработчика (Lighthouse или DevTools Installability); поведение `navigate` у Declarative Web Push на реальном iPhone (абсолютный и относительный URL); не появляются ли два уведомления в Safari при наличии воркера; работа `clients.openWindow` и `postMessage` в установленном iOS-приложении.
- **Фаза доставки:** нагрузочная проверка воркера (захват, backoff, зависшие строки); поведение при двух экземплярах API при выкатке.
- **Фаза UX:** тексты плашек и подсказки установки (UX-copy), время и место первого запроса разрешения.
- Стандартные паттерны, глубокое исследование не нужно: манифест, иконки, список хостов endpoint, очистка при выходе.

## Пробелы

- Доступность `fcm.googleapis.com`, `web.push.apple.com`, `updates.push.services.mozilla.com`, `*.notify.windows.com` с VPS Beget и доставка на реальные устройства не проверялись: закрывает спайк (§6.2).
- Какой push-сервис использует Яндекс Браузер (предположительно FCM как Chromium), источника не найдено (L).
- Поведение `navigate` (абсолютный или относительный URL) и `app_badge` у Declarative Web Push проверено только по чтению документов, не на устройстве.
- `Service-Worker-Allowed` и область при регистрации через `new URL(..., import.meta.url)` под Turbopack не проверялись (в плане не нужно, воркер лежит в `public/`).
- Сопоставление `force-static` у роута Serwist с `force-dynamic` корневого layout не проверялось (нужно только если вернёмся к Serwist).
- Юридическая часть (152-ФЗ, согласие на push, endpoint как данные устройства) не исследовалась.
- Макет иконки и текст плашек запрашивает клиент.
