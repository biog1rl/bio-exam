# Сводка исследования: открытые задания с фото и ручной проверкой (v3.0)

**Проект:** bio-exam, веха v3.0 «Открытые задания с фото и ручной проверкой»
**Домен:** подготовка к ЕГЭ по биологии (один учитель, около 30 учеников, несовершеннолетние); новое: открытый вопрос (текст и/или до 5 фото), загрузка с телефона по QR без входа, ручная проверка 0–3 с возвратом, общий журнал уведомлений, хранение фото 1 год, затем вывод Supabase и Vercel
**Исследовано:** 2026-10-06
**Уверенность:** MEDIUM-HIGH (точки интеграции прочитаны в коде на `1962edd`; устройства, память `sharp` на реальных снимках и право не измерены)

Подробности: `STACK.md`, `FEATURES.md`, `ARCHITECTURE.md`, `PITFALLS.md`. Этот файл разрешает расхождения между ними и задаёт порядок фаз. Решения пользователя: `photo-milestone-decisions.md` в памяти проекта и раздел v3.0 в `PROJECT.md`.

## Краткое резюме

Веха добавляет шестой шаблон `open` и три контура: приём фото (компьютер и QR с телефона без входа), ручную проверку (очередь, просмотрщик, оценка 0–3, возврат до 3 раз, история), общий журнал уведомлений. Самое рискованное — согласование с ядром: `test_attempts` хранит процент и `passed` NOT NULL при сдаче, попытка создаётся только при сдаче (а QR и фото нужны во время прохождения), сдача после дедлайна +2 минуты сегодня отклоняется и черновик теряется. Поэтому порядок от модели данных к интерфейсу: проекция результата и перевод читателей → финализация по дедлайну → фото → QR → создание и сдача → проверка.

Почти без новых зависимостей: `sharp`, `multer`, `file-type`, `node:crypto`, порт хранилища, `swr` уже есть; добавляются `qrcode.react` и `react-zoom-pan-pinch` (только страница проверки, `next/dynamic`); `heic-decode` — условно. Неизменяемость: автофакты и версии не переписываются, проверки только добавляются, для списков и агрегатов SQL — пересчитываемая проекция (`review_status`, `final_*`), которую пишет одна функция. Тип `open` засевается с `is_active = false` и включается последним.

Главные риски: потеря текста при фиксации по таймеру (фиксировать в дедлайн + `ATTEMPT_GRACE_PERIOD_MINUTES`), OOM контейнера API 768 МБ (лимит ≈ 50 МП, concurrency 1–2, кэш выключен, семафор), утечка ссылки через логи и общий прокси, «на проверке» как 0 или «Не сдано» в забытом читателе, поломка истории при удалении фото по сроку. Решения владельца сервера (агент их не выполняет): защита деплоя на открытые окна загрузки, лимит памяти контейнера, журнал Caddy.

## Ключевые выводы

### Стек (STACK.md с поправками)

- `sharp` ^0.35.5: `autoOrient()` → resize 2560 → WebP q82, миниатюра 400; `withMetadata()`/`keepMetadata()` не вызывать
- `multer` ^2.4.0, `memoryStorage`, `files: 1`, идемпотентность по клиентскому `photoId`; `MulterError` привести к 413/415/400 (сейчас 500)
- `file-type` 22: тип по сигнатуре, заголовку клиента не доверять
- `node:crypto`: токен `randomBytes(32).toString('base64url')`, в БД `sha256` (паттерн `routes/auth/invites.ts`)
- `swr`: опрос раз в 2,5 с (`refreshWhenHidden: false`, ETag по `revision`); SSE откладывается до v4.0
- Новое: `qrcode.react` 4.2.0 (чёрное на белом, тихая зона 4, и в тёмной теме), `react-zoom-pan-pinch` 4.2.0 закрепить точно (запасная 3.7.0; поворот CSS; с React 19 не проверялось), `heic-decode` 2.1.0 только если в логах 415 по HEIC

- Не брать: `heic2any`, `heic-to`, `browser-image-compression`, `exifr`, ClamAV, `pg-boss`/`node-cron`/Redis, `ws`/Socket.IO, JWT для ссылки, `axios`/`tus`/`uppy`, серверный `qrcode`

### Функции (FEATURES.md и решения пользователя)

**Обязательно:** шаблон `open` (ответ `{text, photoIds[]}`, максимум всегда 3), поле «эталонный ответ и критерии» (проверяющему всегда, ученику после итога попытки — как пояснение), смешанные тесты, пустой ответ нельзя; текст с автосохранением, счётчик «2 из 5», загрузка с компьютера, QR у каждого открытого вопроса, страница телефона со всеми состояниями; заморозка текста по таймеру, окно загрузки (поле теста), время загрузки каждого фото, пометка «после окончания времени»; версии ответа и проверки неизменяемы, итог = последняя проверка, «на проверке» без процента, правки графиков/списков/дашбордов/поиска; очередь с фильтрами раздела и группы, экран проверки (зум, поворот, критерии, 0–3, комментарий, «сохранить и следующий»), проверка версии при сохранении; возврат до 3 раз (без оценки, комментарий обязателен), «Оценить без исправления», история видна обеим сторонам; общий журнал и колокольчик с глубокими ссылками; хранение 1 год с заглушкой. По уточнениям пользователя 2026-10-06 в объёме (в FEATURES были P2): предварительный итог «X из Y» без процента и разбор обычных вопросов сразу; кнопка ученика «Готово, фото загружены»; пересдача во время проверки разрешена.

**Желательно (после запуска):** горячие клавиши `0`–`3`, `j/k`, `Ctrl+Enter`; автосохранение черновика комментария; плитка «Ждут проверки»; счётчик в заголовке вкладки.

**Отложить:** шаблоны комментариев, push (v5.0), обсуждение оценки (чаты v4.0).

**Анти-функции:** блокировка работы, назначение проверяющих, рубрики, второй эксперт, пометки на фото, PDF, оценка ИИ, ротация QR, SMS/почта, нулевой балл по умолчанию, удаление фото учеником после проверки.

### Архитектура (ARCHITECTURE.md)

Новые глубокие модули (ADR-0005): `services/open-answers`, `upload-links`, `image-pipeline`, `notifications`, `background-jobs`. Изменяются `exam-core`, `attempt-sessions`, `scored-attempt`, `storage`, `question-content`, клиентский `attempt-lifecycle`.

1. `open-answers` — слот `(session_id, question_id)` (не `attempt_id`), версии, членство фото, append-only проверки, автомат состояний, очередь, `materializeAttemptOutcome`
2. `upload-links` — токен, `loadUploadContext` по текущей БД, `uploadTokenRequired` (игнорирует `req.authUser`, не вызывает `requestAccess`)
3. `image-pipeline` — `processPhoto(buffer)` без знаний о БД, возвращает буферы, не пишет в хранилище (v4.0 вставит шифрование между обработкой и записью)
4. `notifications` — `recordNotification(tx, …)` только в транзакции, `publishAfterCommit` (в v3.0 пуст)
5. `background-jobs` — таймер из `index.ts`, `pg_try_advisory_xact_lock`, остановка до `pgPool.end()`, `jobs:run`
6. `exam-core` — адаптер `open`, метрика `manual`, `KeyShape='none'`, статус `pending`, `computeAttemptOutcome` (одна формула вместо копии в `facts.ts:139-142`)

Паттерны: слой проверок + проекция; событие в транзакции, публикация после COMMIT; капабилити по состоянию БД; идемпотентность по клиентскому UUID (`photoId`, `deadline:<sessionId>`, `dedupe_key`); `expectedVersionNo` (409).

### Критические риски (PITFALLS.md)

1. Потеря текста при фиксации по таймеру (C1): момент = дедлайн + grace, ленивая + фоновая финализация, `clientAttemptId=deadline:<sessionId>`; клиент не стирает WAL при `already-submitted` без сверки версии черновика
2. Ссылка-способность (C2): токен только в заголовке `X-Upload-Token` (в `redact` pino), область из строки ссылки, `PUBLIC_PREFIXES` с завершающим `/`, страница вне `(protected)`, GET без побочных эффектов
3. Память VPS (C3): API 768 МБ, OOM роняет все сдачи
4. Неизменяемость и «на проверке» в сводках (C4, C5): не обновлять `score_percentage`/`passed`; поведенческий тест по всем читателям
5. Приватность и раздача (C6, C7): `answers/` вне `isServableImageKey`, отдельный маршрут, строка фото не удаляется при очистке (`purged_at`), каскады чистят файлы

## Разрешённые расхождения

| Тема | Решение |
|---|---|
| Лимиты `sharp` | **Берём П1, не STACK:** `limitInputPixels` ≈ 50 МП (вместо 100), `sharp.concurrency(1..2)`, `sharp.cache(false)`, семафор 1–2 на маршруте загрузки, HEIC по одному; порог замера: пик < ≈ 250 МБ на запрос |
| Ссылка-способность | **Вариант ARCHITECTURE (решение оркестратора):** непрозрачный токен `randomBytes(32)`, в БД `sha256`; область — слот `(session, question)`; до 3 активных ссылок на слот (повторная выдача не отзывает старые, иначе перезагрузка вкладки компьютера убивает открытую страницу телефона); URL кэшируется в `sessionStorage` по ключу слота (QR тот же); срок не хранится, вычисляется на каждом запросе по живой БД (`revoked_at IS NULL`, слот и сессия живы, `now() < upload_closes_at` или слот `returned`, пользователь активен, назначение есть); отзыв через `link_epoch`, сдачу, «Готово», отзыв назначения, блокировку; новых env-секретов нет; все отказы — единый 404 «ссылка недействительна». **Отвергнуто:** HMAC от `(slot, epoch)` без хранения (PITFALLS C2) — нужен новый секрет в `check-env-contract`, теряется отзыв одной ссылки |
| Чтение по токену | Только миниатюры слота (через `fetch` с заголовком + `createObjectURL`), `no-store`; полноразмерные по токену не отдавать |
| Фиксация по таймеру | **Дедлайн + `ATTEMPT_GRACE_PERIOD_MINUTES` (П5).** Клиентское поле read-only с дедлайна; серверный приём текста до конца grace; сроки по часам БД (`clock_timestamp()` после блокировки); срок медленной загрузки по началу запроса + запас 30 с; клиент считает остаток от серверных `now`/`windowEndsAt` |
| Rate limit | Основной ключ — хеш токена, IP вторичный и мягкий (П4; школьный NAT); защита от перегрузки — семафор |
| Читатели score | Объединённый перечень ниже; все через один экспорт `attemptResultColumns` |
| `results_version` | **Остаётся 2** (аддитивно: `pending`, `criteriaText`, `promptText`), не 3; CHECK `IN (1,2)` не трогать; откат кода после первой попытки с `open` теряет её чтение (допустимо) |
| Хранение результата | 4 старых столбца = автофакты на момент сдачи; добавляются `review_status`, `final_*`, `graded_at`, `passing_score`, `submit_source`; CHECK `pending ⇔ final_* IS NULL`; миграция сперва заполняет 265 попыток, затем включает CHECK; страховка `jobs:run reconcile-outcomes` |
| Критерии | Снимок `criteriaText`/`promptText` в факт при сдаче (как `explanationText`), без версионирования; ученику показываются только после итога попытки, как пояснение (решение пользователя 2026-10-06) |
| Очистка по сроку | Строка и членство остаются, `purged_at`, заглушка; неоценённый слот пропускается; сироты и черновики несдавших удаляются целиком через 24 ч |
| Кэш фото | **`private, no-store`** (carry-in v5.0; ARCHITECTURE предлагал immutable-год — отвергнуто), `nosniff`, `Content-Type: image/webp`, CORP `same-origin` |
| URL телефона | `/photo-upload/[token]`, префикс с завершающим `/` (`/u` совпал бы с `/users`) |
| Ключи хранилища | `answers/<sessionId>/<questionId>/<photoId>/{full,thumb}.webp` |
| Форма в `answers` | Только строка текста; фото в таблицах |
| Каскады от `users` | См. открытый вопрос 1 |

## Что v3.0 закладывает для v4.0 и v5.0

1. Журнал общий: `notification_events` (+`notification_deliveries`, канал `inbox`), неизвестные `kind` допустимы, одна строка на (получатель, объект) с `ref_seq`, `collapse_key`, `read_at`, `deliver_after`, `next_attempt_at`, `lease_until`, `UNIQUE(recipient_id, dedupe_key)`, `subject_type`/`subject_id` (не URL), точка расширения планировщика каналов; бейдж = число непрочитанных событий. Подробный состав столбцов — `pwa/SUMMARY.md`, раздел «Что v3.0 должна заложить для v5.0»
2. Модуль фоновых задач запускать из `index.ts` (не `app.ts`), таймер с `unref()`, остановка до `pgPool.end()`; место под outbox и чаты
3. Починить graceful shutdown (`server.close` не ждётся, `pgPool.end` сразу) в `app/server/src/index.ts`
4. Владелец refresh на весь браузер через `navigator.locks` (сейчас дедуп только во вкладке)
5. Фото учеников `private, no-store` (сейчас `docs/assets.ts:77` — `private, max-age=3600` для картинок вопросов); пространства хранилища расширяемые (`answers/`, позже `chat/`, оба вне `isServableImageKey`)
6. Новые сущности не каскадятся от `users` (`DELETE users` — жёсткое); файлы чистятся явно (`purgeFilesForSessions`)
7. Черновики попыток в `localStorage` (`use-attempt-lifecycle.ts:34`), не IndexedDB; фото в локальный черновик не класть
8. In-memory лимитер по IP плох за школьным NAT (учтено)
9. Публикация событий только после COMMIT; столбец часового пояса пользователя для будущих часов тишины — по решению на планировании
10. К v5.0, не в v3.0: служебные пути PWA в `proxy.ts` редиректятся на `/login`; у назначения нет срока; `test.assigned` и событие «ждут проверки» — решить при планировании (рекомендация PWA-исследования: добавить в v3.0)

## Последствия для дорожной карты

Нумерация с 9. Техдолг, пересекающийся с новым модулем, идёт в фазу этого модуля. Мобильная кнопка меню исключена (UX-сессия).

### Фаза 9: Основа результата и читатели

**Обоснование:** всё опирается на проекцию и шаблон; перевод читателей безопасен, пока попыток «на проверке» нет (тип неактивен).
**Поставляет:** характеризационные тесты (`scored-attempt`, `submit`, читатели; ADR-0003); адаптер `open`, `manual`, `KeyShape='none'`, `pending`, `computeAttemptOutcome`, схемы в `exam-core`; единый словарь статусов; миграции с 0026 (проекция + заполнение 265 попыток + CHECK, посев `question_types` с `is_active=false`, `criteria_path`, `photo_upload_window_minutes`, `upload_closes_at`, `submit_source`); `attemptResultColumns`; перевод всех читателей; сериализация вопроса без критериев; 4xx вместо 500 на неизвестный тип (старая вкладка); предел длины текста (10–20 тыс. знаков) и фильтр сырых `answers` по вопросам теста (**SEC-04/N3 — предусловие**); приведён в порядок `DashboardClient`.
**Избегает:** C4, C5, M10, M11, m5.
**Проверка:** поведенческий тест «попытка на проверке» по всем читателям (нет процента и «Сдано/Не сдано»); таблица-тест «проекция = пересчёт».

### Фаза 10: Журнал уведомлений и колокольчик

**Обоснование:** независим от 9, параллельно; нужен фазе 15.
**Поставляет:** таблицы со столбцами из раздела carry-in, `recordNotification(tx, …)` с `ON CONFLICT DO NOTHING`, `GET /api/notifications` (курсор), `unread-count`, `read`, `read-all`, эндпоинт «куда вести» с повторной проверкой доступа, колокольчик «9+», обновление при входе/фокусе/раз в 30–60 с; без производителей кроме тестовых.
**Избегает:** C9 (дедуп в БД; «тест проверен» из транзакции последней оценки под блокировкой попытки); получатель без каскада от `users`.

### Фаза 11: Финализация по дедлайну, окно загрузки, фоновые задачи

**Обоснование:** без серверной фиксации у окна загрузки нет опоры; раньше фото и QR; самая трудная часть, затрагивает клиентский модуль ADR-0005.
**Поставляет:** `background-jobs` (`jobs:run`), починенный graceful shutdown; `finalizeSessionByDeadline` (ленивая + фон 30–60 с, идемпотентна, `clientAttemptId=deadline:<sessionId>`, `submit_source='deadline'`, момент дедлайн+grace); заморозка черновика на сервере; `upload_closes_at` (min(сдача, конец таймера)+окно; без таймера — от сдачи; «Готово» ставит `now()`); единая функция «принимается ли фото сейчас»; правка `attempt-lifecycle` (`applySubmitFailure`, `attempt-submit-flow.ts`: «ответ принят, фото можно добавить до ЧЧ:ММ» вместо «ответы не засчитаны», WAL не стирать без сверки версии, серверные `now`/`windowEndsAt`); CR-05, CR-03, SEC-02 (**SEC-02 — предусловие выпуска**); `navigator.locks` для refresh.
**Избегает:** C1, M5, M6, M11.
**Проверка:** серверный тест гонки; e2e с потерей сети до таймера (по образцу `attempt-slow-network.spec.ts`, `submit-retry.spec.ts`); сперва характеризация `lifecycle-submit.test.ts`, `lifecycle-time.test.ts`.

## Решения пользователя по открытым вопросам исследования (2026-10-06)

- Пустой открытый ответ к концу окна: автоматически 0 системной записью «нет ответа», в очередь не идёт, учитель может переоценить.
- Возврат на исправление после финального итога попытки запрещён; исправление оценки только новой записью проверки (история и уведомление).
- Эталон и критерии ученик видит после итога попытки, как пояснение.
- Резервные копии не меняются; формулировка «на сайте год, в зашифрованных резервных копиях до 12 месяцев после удаления».
- Срока на исправление нет; у учителя кнопка «Оценить без исправления».
- Максимум открытого вопроса всегда 3 балла (принято по умолчанию).
