**Домен:** чат 1:1 учитель-ученик и объявления группе на одном VPS: SSE, шина событий, прикладное шифрование, лента сообщений, вложения-фото
**Исследовано:** 2026-10-06
**Общая уверенность:** HIGH по серверной части (SSE через Express 4, Caddy, Next-rewrites, `node:crypto`: проверено запуском в этом репозитории или чтением исходника), MEDIUM по поведению iOS Safari и по Beget (не запускалось), MEDIUM по `@shadcn/react` 0.x (молодой пакет)
**Уровни:** HIGH — запуск в репозитории, чтение исходника или дословный текст официальной документации; MEDIUM — вторичный источник, поисковая сводка или одна проверка; LOW — оценка. Шов `classify-confidence` вернул для `websearch` LOW (MEDIUM при `--verified`), для `webfetch` LOW (и при `--verified`); здесь уровень выше MEDIUM поставлен только там, где факт воспроизведён запуском или прочитан в первоисточнике, и это указано.
**Согласовано с:** `.planning/research/chat/SUMMARY.md` (решения раздела 0 не пересматриваются), `TRANSPORT-STORAGE.md`, `SECURITY.md`, `UI.md`, `.planning/research/STACK.md` (v3.0: пайплайн фото, опрос через SWR, таймер фоновых задач).

## Главный вывод

Для v4.0 **не нужна ни одна новая серверная зависимость**. SSE, шина событий, адаптер `LISTEN/NOTIFY` и прикладное шифрование пишутся на `express` 4.22, `pg` 8 и `node:crypto`, которые уже стоят. В web обязательна одна новая зависимость, уже выбранная в `UI.md`: `@shadcn/react` 0.3.1 (6,4 КБ gzip). Вторая, `idb` 8.0.3 (1,4 КБ gzip), нужна для исходящей очереди в IndexedDB, которую `SUMMARY.md` §6 закладывает в v4.0. Клиент SSE, даты, виртуализация, лайтбокс, композер и серверный пайплайн фото обходятся платформой и тем, что v3.0 уже добавляет.

Пять фактов, которые меняют проектирование:

1. **Next-rewrites в `yarn dev` ломают SSE без `Cache-Control: no-transform`.** `router-server.js` в Next 16.3.8 включает `compression` до прокси rewrites. Проверено запуском `proxyRequest` из установленного Next: ответ `text/event-stream` приходит со `Content-Encoding: gzip`, за 3 с доходит один чанк в 10 байт; с `Cache-Control: no-cache, no-transform` приходит шесть чанков по одному на событие, каждые 0,5 с. Тот же заголовок проверяет `encode` в Caddy (`isEncodeAllowed`, строка `!strings.Contains(h.Get("Cache-Control"), "no-transform")` в `modules/caddyhttp/encode/encode.go`). Одна строка на сервере закрывает и открытый вопрос `TRANSPORT-STORAGE.md` §10 про SSE через Next rewrites, и сжатие в Caddy. Это лучше, чем `compress: false` в `next.config.ts`: работает за любым прокси.
2. **Комментарий `: ping` невидим для `EventSource`.** Клиентский сторожок «поток замолчал» возможен только на событиях с `event:`. Heartbeat делаем именованным событием `hb`, а не комментарием.
3. **Прокси Next в dev отдаёт заголовки ответа вместе с первым телом.** Воспроизведено: апстрим сделал `flushHeaders()` в момент 0, клиент статуса не увидел до первой записи. Сервер обязан писать первое событие (`retry:` + `event: ready`) сразу после `flushHeaders()`, иначе `onopen` не сработает.
4. **`Last-Event-ID` в нашем протоколе не нужен.** Один заголовок не выразит курсоры по нескольким чатам, а правда лежит в `sync` (`TRANSPORT-STORAGE.md` §6.3). Не отправляем `id:`, не строим кольцевой буфер повторов. Это упрощение решения «Last-Event-ID для быстрого пути»: быстрый путь уже даёт `GET /changes?since=`.
5. **Сессионный клиент в web уже есть** (`app/web/lib/session/client.ts`: `refreshOnce()` с исходами `ok | rejected | unavailable`, `keep-alive.ts` обновляет токен по расписанию). Поток чата должен ходить за refresh только через `sessionClient.refreshOnce()`: параллельный свой вызов `/api/auth/refresh` гонится с ротацией refresh-токена. На сервере срок токена уже доступен как `req.authUser.accessExpiresAt` (`middleware/auth/session.ts`), таймер закрытия по `exp` строится без доработок.

## 1. SSE на Express 4: свой модуль, не библиотека

**Выбор: своя реализация, `better-sse` 0.16.1 не брать.**

`better-sse` (MIT, ноль зависимостей, релиз 2025-12-29, совместим с Express, есть сессии, каналы, keep-alive, учёт `Last-Event-ID`) закрывает ровно ту часть, которая у нас тривиальна: формат кадра. Всё сложное в нашем протоколе лежит снаружи библиотеки: реестр соединений с фильтром по актуальному членству, закрытие по `accessExpiresAt`, мгновенное закрытие при `session.revoked`/`user.blocked`, лимит соединений на пользователя, сброс медленных клиентов. Каналы `better-sse` дублировали бы наш реестр, а версия 0.x с одним мейнтейнером добавляет риск без выигрыша. Формат SSE это четыре правила, они помещаются в десять строк.

Контракт модуля (HIGH по спецификации WHATWG и по запускам):

| Пункт | Решение | Причина |
|-------|---------|---------|
| Заголовки | `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache, no-transform`, `Connection: keep-alive` (для HTTP/1.1 к апстриму), `X-Accel-Buffering: no` (безвредно, если прокси когда-нибудь сменят на nginx) | `no-transform` обязателен (факт 1) |
| Старт | `res.flushHeaders()`, затем сразу `retry: <случайное 2000..8000>\n\n` и `event: ready` | Факт 3. Случайный `retry` на каждое соединение даёт джиттер переподключений без кода на клиенте: после выката или `caddy reload` клиенты не приходят одновременно |
| Heartbeat | `event: hb\ndata: 1\n\n` каждые 20 с | Факт 2. 20 с укладываются в `proxyTimeout` Next (30 000 мс по умолчанию, `proxy-request.js:37`, **idle-таймаут**: воспроизведено, поток с интервалом 0,5 с при лимите 1,5 с живёт, поток с интервалом 2,5 с обрывается через 1,5 с) и в `write_idle` Caddy (1 мин, сбрасывается перед каждой записью; документация прямо говорит, что SSE с паузами между записями не затрагивается, пока записи проходят) |
| `id:` | Не отправлять | Факт 4 |
| Закрытие по сроку | Таймер на `req.authUser.accessExpiresAt`: `event: reauth` и `res.end()` | Решение `TRANSPORT-STORAGE.md` §3.1 п. 2. `setTimeout` с запасом под потолок 2^31 мс не нужен: TTL токена ≤ 3600 с |
| Отзыв сессии | Подписка реестра на `session.revoked {sid}` и `user.blocked {userId}`, и **один** общий `setInterval` раз в 60 с, который одним запросом `WHERE id = ANY($sids)` проверяет все активные `sid` | Один таймер на реестр, а не по таймеру на соединение |
| Членство | Фильтр перед каждой отправкой по актуальному списку чатов пользователя, список инвалидируется событиями `member.*` | Решение §3.1 п. 5 |
| Обратное давление | После `res.write()` проверять `res.writableLength`; больше 64 КБ: `res.destroy()` | Клиент переподключится и сделает `sync`: медленный получатель не раздувает память процесса |
| Лимиты | Не более 6-8 потоков на пользователя (старший закрывается), `rateLimiter` на подключение (`keyPrefix: 'chat-stream'`) | Защита от вкладок-сирот и штормов переподключения. Существующий `rateLimiter` уже принимает `keyPrefix` и `clientKey` |
| Очистка | `req.on('close')`: снять из реестра, остановить таймеры | Утечки реестра |
| Сжатие | Пакет `compression` в API **не добавлять** (сейчас его там нет) | Он буферизует SSE |
| Завершение процесса | В `gracefulShutdown` (`app/server/src/index.ts`) перед `server.close()` вызвать `registry.closeAll()` с `event: bye`. Сейчас `server.close()` ждёт открытых потоков, а выход принудительно срабатывает через 5 с | Клиенты уходят на переподключение сразу, с джиттером из `retry:` |
| Логи | `pino-http` пишет запись по завершению ответа, для потока это часы. Подключение и закрытие логировать отдельными записями; тел сообщений в логи не писать никогда | Дисциплина логов (раздел 4) |

Фрагмент для ориентира (форма, не окончательный код):

```ts
export function openSseStream(req: Request, res: Response) {
	res.status(200)
	res.setHeader('Content-Type', 'text/event-stream; charset=utf-8')
	res.setHeader('Cache-Control', 'no-cache, no-transform')
	res.setHeader('X-Accel-Buffering', 'no')
	req.socket.setNoDelay(true)
	req.socket.setTimeout(0)
	res.flushHeaders()
	res.write(`retry: ${2000 + Math.floor(Math.random() * 6000)}\n\nevent: ready\ndata: 1\n\n`)
	return {
		send(event: string, data: unknown) {
			res.write(`event: ${event}\ndata: ${JSON.stringify(data)}\n\n`)
			if (res.writableLength > 65536) res.destroy()
		},
		end() {
			res.end()
		},
	}
}
```

Проверки: Vitest поднимает настоящий HTTP-сервер и читает поток через `fetch` (Node 24 отдаёт `response.body` потоком; полифилл `eventsource` 5.1.2 для тестов не нужен). E2E Playwright: «событие дошло меньше чем за 2 с» через Next rewrites в `yarn dev` и через Caddy в Compose (в `TRANSPORT-STORAGE.md` §10 это требование уже стоит).

## 2. Caddy: конфигурация долгих потоков (проверочный список для пользователя)

Файла Caddy в репозитории нет, он живёт на сервере, у агентов доступа к серверу нет (как в v3.0). Ниже то, что пользователю нужно сверить; версия Caddy на момент исследования 2.11.7 (2026-10-03), закрепить тег образа `caddy:2.11`.

| Параметр | Значение по умолчанию | Что делать | Уверенность |
|----------|----------------------|------------|-------------|
| HTTP/2 до браузера | `protocols h1 h2 h3` включены по умолчанию при TLS | Ничего. Лимит 6 соединений HTTP/1.1 на вкладки тем самым снят. Для HTTP/3 нужен открытый UDP 443 на Beget, иначе браузер откатится на HTTP/2 без потери функциональности | HIGH (документация Caddy) |
| Одновременных потоков на HTTP/2-соединение | 250 в `golang.org/x/net/http2` (`defaultMaxStreams = 250`) | Ничего. Что Caddy это значение не меняет по умолчанию, взято из поисковой сводки | HIGH (константа Go), MEDIUM (отсутствие переопределения в Caddy) |
| `flush_interval` в `reverse_proxy` | Без периодического сброса; `text/event-stream` сбрасывается **немедленно автоматически** | Не задавать. По желанию `flush_interval -1` на маршруте потока как страховка, если Content-Type когда-нибудь изменится | HIGH (документация) |
| `encode` | Совпадение по умолчанию включает `text/*`, то есть и `text/event-stream`; заголовки SSE уходят сразу, тело сбрасывается вместе с каждым сбросом апстрима | Ничего, потому что API шлёт `Cache-Control: ... no-transform`: тогда `encode` ответ не трогает (исходник `encode.go`, строка проверки `no-transform`). Без заголовка поток сжимался бы gzip: работает, но тратит CPU ради десятков байт | HIGH (исходник Caddy master) |
| Таймауты `reverse_proxy` transport (`response_header_timeout`, `read_timeout`, `write_timeout`) | Без таймаута | Не задавать | HIGH |
| `servers { timeouts { write } }` | Без таймаута | Не задавать: это жёсткий предел на весь ответ и убил бы поток | HIGH |
| `write_idle` | 1 мин, сброс перед каждой записью | Оставить; heartbeat 20 с с запасом. Не задавать `min_rate` для записи: документация прямо предупреждает, что для долгих потоков он вреден | HIGH |
| `idle` | 5 мин | Относится к keep-alive между запросами, на активный поток не влияет | HIGH |
| `grace_period` (глобально) | Вечный: старые соединения не обрываются при перезагрузке конфигурации | Поток на старом сервере доживёт до `reauth` (≤ 15 мин при TTL по умолчанию) или до `bye` при перезапуске API. Мгновенного эффекта `caddy reload` на уже открытые потоки ждать нельзя. При желании `grace_period 30s`: клиенты переподключатся сами | HIGH (документация), MEDIUM (применение к SSE: прямо не сказано) |
| `stream_close_delay`, `stream_timeout` | Нет | Не задавать. Документация говорит про «streaming requests such as WebSockets»; для SSE прямо не подтверждено | MEDIUM |
| Журнал доступа Caddy для `/api/chat/stream` | Зависит от настройки | Cookie в журнал не попадают; тела тоже. Ничего специального, в отличие от `/u/<token>` из v3.0 | MEDIUM |

Фрагмент Caddyfile (форма; домен и имена сервисов подставляет пользователь):

```

	handle /api/* {
		reverse_proxy api:4000
	}
	handle {

```

Один `reverse_proxy` на `/api/*` достаточен: отдельный блок для потока нужен только если захочется `flush_interval -1`. Express-приложение уже делает `app.set('trust proxy', 1)`.

**Разработка (`yarn dev`).** Поток идёт через Next rewrites (`app/web/next.config.ts`, `/api/:path*` на `API_ORIGIN`). Достаточно факта 1 и 3 (заголовок `no-transform` и первая запись) и heartbeat 20 с под 30-секундным idle-`proxyTimeout`. `experimental.proxyTimeout` менять не нужно, `compress: false` не нужно. Поток не может живее 30 с без heartbeat, поэтому пропуск heartbeat виден в dev сразу.

## 3. Шина событий в процессе и путь к нескольким процессам

**Выбор: интерфейс `ChatEventBus` с реализацией на `node:events`; библиотеки (`mitt` 3.0.1, `nanoevents` 10.0.0, `eventemitter3` 5.0.4, `tseep` 1.3.1) не нужны.** Выигрыша нет: нужен один `publish` и один `subscribe`.

Ловушка: **не вешать по слушателю на каждое SSE-соединение.** У `EventEmitter` предел 10 слушателей на событие, дальше `MaxListenersExceededWarning` и растущая память. Правильная форма: реестр потоков подписывается на шину **один раз** при старте процесса и сам раздаёт события по `Map<userId, Set<Stream>>` с фильтром по членству.

Правила (из `TRANSPORT-STORAGE.md` §4, подтверждены):
- публикация только **после COMMIT**: `await db.transaction(...)`, затем `bus.publish(...)` вне транзакции;
- событие несёт идентификаторы: `{type, chatId, seq}`; тело сообщения в событие не кладётся (шифрование и размер).

**Путь к нескольким процессам: адаптер на `pg`, без `pg-listen`.**

| Пункт | Решение |
|-------|---------|
| Публикация | `SELECT pg_notify('chat_events', $1)` **внутри** транзакции записи. NOTIFY доставляется только после COMMIT и в порядке коммитов, поэтому «публикация после COMMIT» выполняется самой БД, а локальные подписчики получают событие тем же путём через собственное `LISTEN` |
| Подписка | Одно выделенное `new pg.Client({ keepAlive: true })`, **не из пула**; `client.on('notification')` |
| Нагрузка | Не более 8000 байт; шлём только идентификаторы |
| Разрыв соединения | Переподключение с экспоненциальной паузой; после восстановления адаптер публикует в локальную шину синтетическое `resync`, и каждый поток шлёт клиенту `event: resync`. Правда в таблицах, NOTIFY только будит: пропуск закрывается `sync` |
| Прочие события | `session.revoked`, `user.blocked`, `member.*` идут тем же каналом, иначе второй процесс не закроет чужие потоки |
| Тест | Интеграционный тест с двумя шинами и одной БД из `node scripts/with-test-db.mjs`; пул тестов не использует `LISTEN` |
| Когда строить | Когда появится второй процесс API: выкат «сначала новый контейнер» (старый и новый живут вместе), отдельный воркер уведомлений. Если выкат останавливает старый контейнер до старта нового, окно разрыва покрывается переподключением клиентов и `sync`, и адаптер можно отложить. Ответ зависит от схемы деплоя из v2.0, в этом исследовании она не видна |

`pg-listen` 1.7.0 (последний релиз 2022-05-12) и `pg-pubsub` 0.8.1 (2023-06) не брать: хватает 60 строк, а переподключение лучше контролировать самим. Глобальная блокировка NOTIFY при COMMIT из `TRANSPORT-STORAGE.md` §4 на тысячах сообщений в день не проявляется.

## 4. Envelope-шифрование: `node:crypto`, не libsodium

**Выбор: AES-256-GCM из `node:crypto`.**

Проверено запуском (Node 24.17.0, OpenSSL 3.5.7): шифрование и расшифровка с AAD работают, при другом AAD расшифровка отвергается (`Unsupported state or unable to authenticate data`), обёртка ключа данных ключом-обёрткой работает, `id-aes256-wrap` (AES-KW) доступен, `hkdfSync` доступен, 50 шифрований буфера 2 МБ заняли 28 мс (около 0,6 мс на фото).

| Вариант | Версия | Вердикт |
|---------|--------|---------|
| `node:crypto` AES-256-GCM | встроено | **Выбор.** Стандарт NIST, аппаратное ускорение AES-NI, ноль зависимостей |
| libsodium-wrappers | 0.8.4 (2026-04-19), ISC, 550 КБ unpacked, WASM | XChaCha20-Poly1305 с 192-битным nonce безопаснее при случайных nonce и огромных объёмах. Нам не нужно (см. лимит ниже), цена: WASM-зависимость и инициализация |
| sodium-native | 5.1.0 (2026-05-06), MIT, 18 МБ unpacked, нативный аддон | Нативная сборка под Alpine/Debian добавляет риск выката, которого в v3.0 сознательно избегали |
| @noble/ciphers | 2.4.0 (2026-08-27), MIT, чистый JS | Запасной вариант, если нужен XChaCha без нативного кода. Не нужен |
| tweetnacl | 1.0.3 (2023-04) | Не обновляется, не брать |

**Лимит случайных nonce.** NIST SP 800-38D допускает не более 2^32 шифрований под одним ключом при случайном 96-битном IV. Ключ данных (DEK) у нас на чат: тысячи сообщений за учебный год, на много порядков ниже предела. Условие: **новый nonce на каждое шифрование, в том числе при правке сообщения**; nonce не выводить из счётчика.

**Иерархия ключей (согласуется с `SECURITY.md` §9 и решением пользователя B):**

| Уровень | Хранение | Формат |
|---------|----------|--------|
| KEK (мастер-ключ) | Файл вне БД и вне набора бэкапа: Docker secret `/run/secrets/chat_kek` | JSON `{"current":2,"keys":{"1":"<base64>","2":"<base64>"}}`, 32 случайных байта на версию. Читается один раз при старте; в production при отсутствии файла процесс **не стартует**. Копия офлайн у владельца |
| DEK (ключ данных чата) | Таблица `chat_keys(chat_id, dek_version, kek_version, wrapped_dek)` в БД | 32 случайных байта, обёрнуты AES-256-GCM под KEK, AAD = `chat_id \| dek_version \| kek_version` |
| Тело сообщения | `chat_messages.body_enc bytea` | `[0x01][dek_version u16][nonce 12][шифротекст][тег 16]`, AAD = `chat_id \| message_id`. Самоописываемый конверт: отдельных столбцов `key_version` и `nonce` не нужно |
| Фото | Объект в хранилище (раздел 8) | Тот же конверт, AAD = `chat_id \| attachment_id \| variant` (`full` или `thumb`) |

Ротация (согласуется с `SECURITY.md`): добавить версию KEK, скрипт `chat:rotate-kek` (по образцу `storage:reconcile`) переобёртывает `chat_keys` пачками в транзакции, старый KEK удаляется только после проверки, что все бэкапы старше ротации выведены из обращения или KEK сохранён офлайн. Ротация DEK (перешифрование сообщений) не планируется; `dek_version` в конверте оставляет возможность.

**Ловушки (все обязательны для охранных тестов):**

1. **Закреплять длину тега:** `createDecipheriv('aes-256-gcm', key, iv, { authTagLength: 16 })` и проверка длины входного конверта. Без этого Node принимает укороченный тег.
2. **Не расшифровывать GCM потоком.** Поточная расшифровка отдаёт открытый текст до проверки тега. Фото ≤ 10 МБ расшифровываются целиком в памяти, `final()` до отправки в ответ.
3. **AAD всегда содержит идентификаторы строки**, иначе шифротекст можно переставить в другое сообщение или чат. Тест: конверт из сообщения A не расшифровывается как сообщение B.
4. **Один модуль на границе** `services/chat/crypto`: `sealBody/openBody/sealBlob/openBlob`, `loadKeyring()`. Маршруты и репозитории чата работают только через него. Журнал доступа администратора (`SECURITY.md`) пишется в той же транзакции, что и открытие чужого диалога.
5. **Открытый текст сообщений не попадает в побочные места:** `notification_event` (общий журнал из v3.0) хранит `{kind, chatId, messageId, deep link}`, но не текст и не превью; `pino` не логирует тела запросов чата; ошибки валидации `zod` не печатают введённое значение.
6. **Контракт окружения.** Код читает путь, а не ключ: `process.env.CHAT_KEK_FILE`. В `app/server/.env.example` добавить запись `CHAT_KEK_FILE=<path>`: иначе `scripts/check-env-contract.mjs` падает на шаге `env-contract` в `yarn verify`. Значение-ключ в примере `isUnsafeValue` отвергает (32+ символов base64). Для тестов ключевую связку собирает тестовый помощник в памяти, переменная окружения в тестах не читается; для локальной разработки скрипт `chat:keygen` (по образцу `bootstrap:admin`) создаёт файл вне репозитория.
7. **Docker secrets без Swarm.** Compose доставляет секрет как bind-mount одного файла в `/run/secrets/<имя>` (документация Docker, HIGH). Права берутся с файла на хосте: пользователь процесса в контейнере должен его читать (проверить на сервере, MEDIUM). Файл на хосте держать вне корней, которые попадают в бэкапы томов.
8. **Поиск:** серверного нет (решение пользователя). В схеме `search tsvector` из черновика `TRANSPORT-STORAGE.md` §6.1 не создаётся.

Что шифрование не защищает: root на VPS, XSS, учётку с правом чтения (`SECURITY.md` §9). Здесь это не пересматривается.

## 5. Клиент SSE: нативный `EventSource`

**Выбор: нативный `EventSource` в тонкой обёртке `lib/chat/stream-client.ts`; `@microsoft/fetch-event-source` не брать.**

| Вариант | Версия | Вердикт |
|---------|--------|---------|
| Нативный `EventSource` | платформа, 0 КБ | **Выбор.** Cookie уходят сами (same-origin), автоматическое переподключение в браузере, `retry:` от сервера работает как джиттер. Недостаток: статус ответа недоступен, не-200 закрывает источник навсегда. Он нам не мешает: любое закрытие ведёт к `refreshOnce()` |
| eventsource-parser + `fetch` | 4.1.1 (2026-09-15), MIT, ноль зависимостей, 1,8 КБ gzip | **Резерв.** Нужен, если потребуются HTTP-статусы (например 429 с `Retry-After`), заголовки или видимость комментариев `: ping`. Пишется 60 строк поверх, потому что `ReadableStream` у `fetch` есть во всех целевых браузерах |
| @microsoft/fetch-event-source | 2.0.1, последний релиз npm 2021-04-25 (репозиторий `Azure/fetch-event-source`, push 2026-02-28, 74 открытых issue) | Не брать: де-факто не поддерживается, 1,3 КБ выигрыша над своим кодом не стоят |
| event-source-polyfill | 1.0.31 (2022-08) | Не брать |
| eventsource (Node-полифилл) | 5.1.2 | Только для Node-тестов, в Node 24 тестируем через `fetch`, не нужен |

Протокол клиента (дополняет `TRANSPORT-STORAGE.md` §3.1 п. 4):

1. **Порядок: открыть поток, потом `sync`** (решение из §6.3). События во время `sync` буферизуются.
2. **`reauth`:** сначала `es.close()`, затем `await sessionClient.refreshOnce()`, и только потом новое соединение. Иначе автопереподключение браузера гонится с refresh, получает 401, и по спецификации источник закрывается навсегда. Если `keep-alive.ts` уже обновил cookie, `refreshOnce()` отработает без лишней нагрузки.
3. **Исходы refresh:** `ok` — переподключиться и сделать дельту; `rejected` — `sessionClient.redirectToLogin()`; `unavailable` — пауза с джиттером (1 до 30 с) и повтор.
4. **Сторожок:** если за 50 с не пришло ни одного события (`hb` каждые 20 с), закрыть и переоткрыть соединение. Нужен именно для полуоткрытых соединений мобильного Safari, где `error` не приходит.
5. **`visibilitychange` (в «visible») и `online`:** принудительный `sync`, а если `readyState === CLOSED`, ещё и переоткрытие. Корректность держится на `sync`, не на потоке.
6. **`bye` и `resync`:** `bye` — закрыть и переоткрыть с паузой из `retry`; `resync` — сразу запустить `sync`.
7. **Внедрение зависимостей** (`EventSource`-конструктор, таймеры, `document`) по образцу `lib/session/keep-alive.ts`: в jsdom `EventSource` нет, тесты подставляют фейк.
8. **Выход из системы:** закрыть поток и очистить кэш чатов и очередь IndexedDB (раздел 9; требование `SUMMARY.md` §6).

Отложено (развилка Р2): одно соединение на браузер. Без библиотек: `navigator.locks.request('chat-stream', ...)` (Web Locks) выбирает ведущую вкладку, остальные получают события через `BroadcastChannel`. При включённом HTTP/2 лимит 6 соединений не действует, поэтому пока не нужно. Web Locks и `crypto.randomUUID` работают только в защищённом контексте (раздел 9).

## 7. Даты и время по-русски: без новых библиотек

Проверено запуском: `Intl.RelativeTimeFormat('ru', { numeric: 'auto' })` даёт «сегодня», «вчера», «5 минут назад», «2 часа назад», «1 минуту назад»; `Intl.DateTimeFormat('ru-RU', { day: 'numeric', month: 'long' })` даёт «6 октября»; `Intl.PluralRules('ru')` различает `one/few/many` (1, 2, 5, 11, 21, 22, 25 разобраны верно); `date-fns` 4.1.0 с локалью `ru` даёт «6 октября 2026» и «вчера в 16:00».

| Задача | Решение |
|--------|---------|
| Маркер дня в ленте | `isToday` / `isYesterday` из `date-fns`: «Сегодня», «Вчера»; иначе `format(d, 'd MMMM', { locale: ru })`, с годом, если год не текущий |
| Время у пузыря | `Intl.DateTimeFormat('ru-RU', { hour: '2-digit', minute: '2-digit' })` |
| Время в списке чатов | Меньше часа: `Intl.RelativeTimeFormat` («5 минут назад»); сегодня: часы и минуты; вчера: «вчера»; неделя: день недели; иначе `dd.MM.yy` |
| Группировка по дню | По календарному дню в **часовом поясе браузера**, ключ `yyyy-MM-dd` через `format` |
| «N новых сообщений», «N фото» | `Intl.PluralRules('ru')` в 10-строчном помощнике. `intl-messageformat` числится в `app/web/package.json`, но нигде не импортируется: не использовать |
| Часы тишины (21:00-09:00) | **Считаются на сервере в часовом поясе учителя.** В `app/server/src/db/schema.ts` столбца часового пояса нет: добавить IANA-строку в настройки уведомлений (по умолчанию `Europe/Moscow`, заполняется из `Intl.DateTimeFormat().resolvedOptions().timeZone`). Расчёт: `new Intl.DateTimeFormat('en-GB', { timeZone, hour: '2-digit', hourCycle: 'h23' })` (проверено: Asia/Yekaterinburg для 17:30 UTC даёт 22). `@date-fns/tz` 1.5.0 не нужен |
| Общий тик «5 минут назад» | Один таймер на страницу раз в 60 с (`useSyncExternalStore`), а не таймер на пузырь |

Ловушка Next: относительное время, посчитанное на сервере при SSR, расходится с клиентским и даёт ошибку гидратации. Страницы чата управляются клиентом, форматирование держать в клиентских компонентах после монтирования. Не брать `dayjs`, `moment`, `luxon`, `timeago.js`.

## 8. Вложения: что переиспользуется из v3.0

Принцип: **один серверный пайплайн изображений на оба этапа**, шифрование вставляется между «обработать» и «записать». Это единственное место, где v3.0 нужно подготовить: функция обработки должна возвращать буферы, а не писать в хранилище.

| Элемент v3.0 | Использование в чате | Отличие |
|--------------|----------------------|---------|
| `sharp` 0.35.5: `autoOrient()` → `resize(fit: inside, withoutEnlargement)` → WebP, `limitInputPixels: 100_000_000`, метаданные не сохранять | Тот же вызов | Размеры по решению чата: длинная сторона 2048 px, миниатюра 320 px (`SUMMARY.md` §2); параметры передаются в функцию |
| `multer` `memoryStorage`, `files: 1`, 10 МБ, `fileTypeFromBuffer` (белый список) | Тот же | Один файл на запрос: повтор и идемпотентность по id вложения. Сессионная авторизация вместо токена-способности |
| Клиентский конвейер `createImageBitmap(from-image)` → canvas → JPEG | Тот же хук с параметрами 2048 px, качество 0,85 | `onPaste` на `textarea`: `clipboardData.files` идут в тот же конвейер |
| Порт хранилища `write/read/remove/list` | Пространство `chat` | Ключ `chat/<chatId>/<attachmentId>/{full,thumb}.bin`; `contentType: 'application/octet-stream'` |
| Таймер `runRetention()` + `pg_try_advisory_xact_lock` | Тот же таймер: сироты старше 24 ч (вложение без сообщения), срок хранения | В `storage:reconcile` научить пространству `chat` |
| Ответ 415 на HEIC, `heic-decode` как запасной путь | Общее решение для обоих этапов | Один раз и в одном месте |

Что делать иначе в чате:

1. **Разделить в v3.0 «обработать» и «записать»**: `processPhoto(buffer, options) → { full, thumb, width, height }` без записи в хранилище. Чат вызывает `sealBlob` между этим и `storage().write`. Если v3.0 зашьёт запись внутрь, придётся разбирать код.
2. **Шифрование.** Объект в хранилище хранится как конверт раздела 4; миниатюра и полный размер шифруются отдельно (разные AAD). Раздача через API: проверка участника, чтение, `openBlob`, ответ. Маршрут `X-Accel-Redirect` и `file_server` Caddy для чата исключены (диск хранит шифротекст).
3. **Раздача: `Cache-Control: private, max-age=31536000, immutable`, `X-Content-Type-Options: nosniff`, `ETag` = id вложения.** Не `sha256` открытого файла, как в черновике `TRANSPORT-STORAGE.md` §7: хэш открытого файла в БД позволяет подтвердить, что это известное изображение. Столбец `sha256` в `chat_attachments` не создавать.
4. **`thumbhash` не добавлять.** В v3.0 его нет, а в чате он оставил бы в БД открытым размытый предварительный вид детского фото при «зашифрованных» файлах. Заполнитель делает прямоугольник по `width/height` (хранятся открытыми) со `shimmer` из компонента `attachment`. Если решат оставить: `thumbhash` 0.1.1 (2023-03, MIT, ноль зависимостей, 2 КБ gzip, формат стабилен), шифровать значение тем же DEK. Это отклонение от `SUMMARY.md` §2, которое стоит подтвердить на discuss.
5. **Новое пространство `chat` в `isServableImageKey` не добавлять** (та же ловушка, что и в v3.0, раздел 5): общий прокси `/api/docs/assets/proxy` отдал бы шифротекст любому вошедшему. Охранный тест: прокси по ключу `chat/...` даёт отказ.
6. **`accept`.** `UI.md` предлагает явный список `image/jpeg,image/png,image/webp`, v3.0 выбрал `image/*`, предупредив только против добавления `image/heic`. Для macOS Safari явный список перекодирует HEIC в совместимый формат (по найденным источникам v3.0, MEDIUM), так что сведите оба этапа к одному полю с явным списком. Кнопка «Камера» с `capture="environment"` общая.
7. **Двухшаговая загрузка**: `POST /api/chat/:id/attachments` создаёт строку с `message_id NULL`; сообщение ссылается на `attachmentIds`; число привязанных строк обязано совпасть (`TRANSPORT-STORAGE.md` §6.2 п. 4). Квота байт на пользователя в сутки и `rateLimiter` на загрузку.
8. Размытый вид и размер миниатюры 320 px (около 10-20 КБ после шифрования) отдаются тем же маршрутом, отдельного CDN нет.

## 9. Исходящая очередь, идентификаторы, прочее

- **IndexedDB: `idb` 8.0.3** (хранилище `outbox`, ключ `clientMessageId`, индекс по `chatId` и времени, значения со структурным клонированием `Blob`). `idb-keyval` 6.3.0 (0,75 КБ) не подходит: у него нет индексов, а очередь отправки строго по чату нужна последовательной (`TRANSPORT-STORAGE.md` §8). Повторы как в `lib/drafts/save-queue`: экспоненциальная пауза, повтор по `online` и `visibilitychange`. Background Sync только ускорение в Chromium. Очередь очищается при выходе.
- **Идентификатор клиента.** `crypto.randomUUID()` доступен только в защищённом контексте. В `next.config.ts` в `allowedDevOrigins` стоят `172.18.0.1` и `192.168.50.2`: в разработке по LAN через `http://` функции не будет. Сделать помощник `newClientId()` на `crypto.getRandomValues` (доступен без HTTPS). Web Locks по той же причине в LAN-dev отсутствуют.
- **UUIDv7 не нужен.** `TRANSPORT-STORAGE.md` §6.1 предлагал v7 от приложения (в PG 17 нет `uuidv7()`). Порядок и пагинация держатся на `UNIQUE (chat_id, seq)`, а не на `id`; остальные 16 таблиц используют `defaultRandom()`. Для сотен тысяч строк в год выигрыш v7 в локальности вставки незаметен, пакет `uuid` и свой генератор не окупаются. Идентификатор сообщения: `defaultRandom()`.
- **Схема доступа и идемпотентность** без изменений относительно `TRANSPORT-STORAGE.md` §6; отдельных библиотек не требуют.

## Варианты по условиям

**Если появится второй процесс API (выкат «сначала новый контейнер», воркер уведомлений):**
- включить адаптер `LISTEN/NOTIFY` (раздел 3), включая `session.revoked`, `user.blocked` и `member.*`;
- причина: иначе события, записанные одним процессом, не дойдут до потоков другого.

**Если на реальном iPhone подгрузка истории прыгает:**
- запасной путь `use-stick-to-bottom` 1.1.6 с ручной компенсацией `scrollTop`, либо `@tanstack/react-virtual` с `anchorTo: 'end'`;
- причина: у iOS нет `overflow-anchor`.

**Если нужны HTTP-статусы потока (429 при шторме, пояснение причины отказа):**
- заменить нативный `EventSource` на `fetch` + `eventsource-parser` 4.1.1;
- причина: `EventSource` не показывает статус.

**Если решат вернуть «печатает» или «в сети»:**
- двусторонний канал на `ws` 8.22.0 с тем же протоколом `sync` (развилка Р1 из `TRANSPORT-STORAGE.md`);
- причина: SSE односторонний, а частые кадры от клиента через HTTP POST дороги.

**Если потребуется серверный поиск по тексту:**
- не искать в БД; поиск по уже расшифрованному диалогу в браузере;
- причина: тела зашифрованы (решение пользователя B).

## Что проверить на соответствующих фазах (флаги исследований)

- **Фаза потока:** E2E «событие меньше чем за 2 с» через Next rewrites и через Caddy в Compose; поведение при `caddy reload` и выкате контейнера (шторм переподключений, пауза из `retry:`); потеря потока в фоновых вкладках iOS Safari; обратное давление (медленный клиент) на тесте.
