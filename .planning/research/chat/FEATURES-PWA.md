# Чаты учителя и ученика: функции аналогов и готовность к PWA

**Домен:** переписка учителя и ученика внутри образовательной платформы (ЕГЭ по биологии, ученики часто несовершеннолетние, Россия)
**Дата исследования:** 2026-10-05
**Общая уверенность:** MEDIUM (функции зарубежных аналогов — по выдержкам поиска, их справки отдали 403; техника PWA — по первоисточникам WebKit и Next.js)

Уровни уверенности в файле: **H** — первоисточник прочитан напрямую (webkit.org, nextjs.org, sferum.ru, npm); **M** — выдержки официальных справок через поиск, без открытия страницы; **L** — обзоры, агрегаторы, отзывы.

## 1. Главный вывод

1. Переписка на самой платформе для онлайн-подготовки к ЕГЭ — ожидаемая функция. Крупные школы либо держат чат с куратором в кабинете (Умскул, Skysmart, Фоксфорд), либо отдают переписку в Telegram (100балльный, кураторы-студенты). Второй вариант теряет связь с заданиями и контроль над перепиской с детьми.
2. Все западные K-12 продукты сходятся в правилах для детей: **ученик не пишет ученику**, администратор видит всю переписку, включая удалённую, у учителя есть часы тишины, а групповое общение сделано объявлениями, а не общим чатом. Эти правила стоит взять как есть.
3. Для bio-exam основная ценность — **привязка к учебному объекту**: карточка «обсудить попытку» или «обсудить работу» со ссылкой на разбор. Google Classroom держит личные комментарии внутри задания. Наша схема: чат один на пару «учитель–ученик», а карточки объектов вставляются в него.
4. Уведомления нужно строить вокруг **серверного журнала событий (outbox)**: центр уведомлений в кабинете — основной канал, он же реализует решение v3.0 «только в кабинете». Web Push в v4.0 — дополнительный канал поверх того же журнала. Push в России работает «по возможности»: Chrome ходит через FCM, iOS — через APNs, а при «белых списках» мобильного интернета оба канала могут не работать.

## 3. Предлагаемый набор функций

### Первая версия (MVP)

| Функция | Решение | Аргумент |
|---|---|---|
| Диалог 1:1 учитель ↔ ученик | Один диалог на пару (teacherId, studentId), создаётся лениво при первом сообщении | Привычная модель; карточки объектов вставляются в этот диалог, отдельные диалоги на каждую попытку не нужны |
| Кто может писать | Право на диалог берётся из **шва доступа зоны учителя** (фаза 07.1): ученик состоит в группе учителя или учитель отвечает за раздел, где у ученика есть попытка. Отдельный ACL для чата не заводим | Одно правило доступа на весь продукт; у администратора есть доступ на чтение всех диалогов |
| Кто начинает | Обе стороны. Ученик пишет своему учителю | В отличие от ClassDojo и Remind, где первым пишет учитель: здесь платная подготовка с назначенным учителем, и вопрос ученика — основной сценарий. **Развилка 1** |
| Ученик ↔ ученик | Не делаем ни в каком виде | Общее правило детских систем; снимает модерацию буллинга |
| Ученик вне зоны | Диалог становится «только чтение», не удаляется | Если учителя отключили, зона по решению 11 переходит администратору, и история остаётся у него |
| Карточка «обсудить попытку» | Кнопка в разборе попытки и в карточке ученика у учителя → открывает диалог с прикреплённой карточкой (тест, дата, балл, ссылка на разбор). Права на разбор проверяются при открытии ссылки, а не при вставке | Главное отличие от Telegram; ссылка ведёт в разбор со своей проверкой доступа |
| Текст + фото | До 5 фото на сообщение, только изображения, через модуль хранилища фазы 7 | Сценарий «скинуть фото домашки»; лимит совпадает с v3.0 |
| PDF | Не в MVP. **Развилка 3** | v3.0 исключил PDF для ответов; в чате нужен единый ответ |
| Объявления группе | Учитель → своя группа, без ответов в ленте. Ученик отвечает личным сообщением в свой диалог | Групповой чат противоречит запрету ученик↔ученик; так же устроены Announcements в Seesaw, ClassDojo и Canvas |
| Непрочитанное | Счётчик на сервере (по диалогам и общий), метка «прочитано до» на участника | Один источник для шапки, бейджа PWA и push |
| «Прочитано» | Учитель видит, что ученик прочитал. Ученик статуса прочтения учителем не видит | Модель ClassDojo: на несовершеннолетнего не давит «учитель прочитал и молчит». **Развилка 2** |
| Часы тишины учителя | Настройка учителя: интервал и дни. Вне интервала ученик видит баннер «Учитель ответит в рабочее время», сообщение отправляется, уведомления учителю копятся | ClassDojo, Seesaw, Remind; защищает единственного учителя |
| Редактирование | Своё сообщение — 15 минут, с меткой «изменено»; администратор видит исходный текст | Обычная практика плюс аудит |
| Удаление | Только мягкое: участник видит «сообщение удалено», администратор — оригинал. Учитель не удаляет сообщения ученика | ClassDojo: удалённое видно администратору; учитель не стирает следы |
| Аудит администратора | Чтение любого диалога, отметка в журнале о просмотре | Переписка взрослого с ребёнком на платформе компании |
| Лимиты | Текст ~4000 символов; ограничение частоты (например, 30 сообщений в минуту на пользователя); фото по правилам v3.0 (размер, типы) | Защита от спама и случайных вставок |

### Вторая очередь

| Функция | Почему не в MVP |
|---|---|
| Кнопка «пожаловаться» → очередь администратора | При одном учителе и аудите администратора пользы мало; нужна при росте. **Развилка 4** |
| Поиск по сообщениям | Почти не нужен при паре диалогов на ученика; полнотекстовый поиск PostgreSQL `tsvector` с русской конфигурацией — позже |
| Вложение PDF | Если клиент разрешит (развилка 3) |
| Закреплённое сообщение в диалоге | Для «правил работы» или плана подготовки |
| Ответ с цитатой | Удобно, но не критично |
| Шаблоны ответов учителя | Ускоряют работу одного учителя на многих учеников |
| Видимость для родителей | В проекте нет роли родителя; при её появлении — режим наблюдателя, как в ClassDojo для 6–8 классов |
| Экспорт переписки администратором | ClassDojo и Seesaw его делают; нужен при спорах |

### Не делаем

| Функция | Аргумент |
|---|---|
| Звонки, видео, голосовые | Пользователь исключил звонки. Голосовые сообщения у несовершеннолетних не проверить и не найти поиском; хранение аудио — новый тип персональных данных |
| Ученик ↔ ученик, групповой чат с ответами учеников | Нужна модерация буллинга; все детские аналоги это запрещают |
| Исчезающие сообщения | Противоречат аудиту переписки взрослого с ребёнком |
| Жёсткое удаление пользователем | По той же причине. Удаление по сроку хранения выполняет система, не пользователь |
| Стикеры, GIF | Шум, внешние источники контента |
| Реакции | Спорно. Одна реакция «👍 принято» снимает часть сообщений «ок, спасибо», но выглядит как оценка. Не в MVP; при запросе — одна фиксированная реакция-квитанция |
| Перевод | Аудитория русскоязычная |
| Email-дайджест | В проекте нет SMTP-канала; противоречит v3.0 «только в кабинете». При планировании проверить, есть ли почтовая отправка |
| Пересылка в Telegram или VK | Выносит переписку с ребёнком за пределы аудита |
| Индикатор «печатает…» и статус «в сети» | Требуют постоянного соединения и создают давление; ни один из детских аналогов их не выделяет |

## 4. Граница с v3.0 (проверка открытых заданий)

Правило: **комментарий к проверке — часть результата, сообщение в чате — разговор**.

| | Комментарий проверки (v3.0) | Сообщение в чате |
|---|---|---|
| Где живёт | Поле записи проверки ответа, по одной на каждую пересдачу (до 3), с версиями | Диалог учитель ↔ ученик |
| Кто пишет | Только проверяющий, вместе с оценкой 0–3 | Обе стороны |
| Где видно | В разборе попытки, в истории версий ответа, в очереди проверки | В чате |
| Ответ на него | Нельзя: ветки обсуждений внутри проверки нет | Обычный |
| Меняется ли | Фиксируется вместе с оценкой | Правка 15 минут |

Связь односторонняя: в разборе проверенной работы есть кнопка «Обсудить с учителем» (у учителя — «Написать ученику»). Она открывает диалог с вставленной карточкой `attempt` или `review` (идентификатор попытки, вопроса и версии ответа). Так не появляются две похожие сущности: в v3.0 не делаем ветку комментариев под ответом, в чате не делаем оценку.

Общие механизмы:
- **Фото.** Фото домашки в чате и фото ответа в v3.0 используют один модуль хранилища (фаза 7, ADR-0004), одни лимиты и одну политику хранения (год; **развилка 7** — та же ли политика для чата). Фото из чата нельзя «перекинуть» в ответ на открытое задание: ответ сдаётся через тест, иначе ломается учёт пересдач.
- **Уведомления.** Событие «работа проверена» (v3.0) и «новое сообщение» (чат) пишутся в одну таблицу событий, и центр уведомлений в кабинете показывает оба. Если чаты придут после v3.0, таблица уже будет; если v3.0 строит её «только для проверки», нужно сразу делать её общей (см. раздел 6).

## 5. Уведомления до PWA

Решение v3.0 «уведомления только в личном кабинете» расширяется без противоречия: кабинет и есть канал.

| Механизм | В MVP | Комментарий |
|---|---|---|
| Счётчик непрочитанного в шапке и сайдбаре | ✓ | С сервера: `GET /chats/unread` возвращает сумму и разбивку; обновляется при входе в чат и по живому каналу |
| Счётчик во вкладке (`document.title` = «(3) bio-exam») | ✓ | Дёшево, работает везде |
| Favicon с точкой | По желанию | Минимальная стоимость |
| Звук | Выключен по умолчанию, включается в настройках | Звуки без спроса на уроке или ночью нежелательны |
| Центр уведомлений (колокольчик) | ✓, общий с v3.0 | Список событий: сообщение, проверка, назначение теста |
| Живое обновление | ✓ | Транспорт (SSE или опрос) — **развилка 8**, здесь не исследовался. Чат должен работать и при обычном опросе раз в 15–30 с |
| Notification API без push (вкладка открыта) | Нет | Требует того же запроса разрешения, что и push; сделать один раз в v4.0 |
| Email-дайджест | Нет | См. «Не делаем» |

### Ключевые факты

- **iOS.** Push приходит только в установленное PWA (16.4+). Подписка — через `pushManager.subscribe({ userVisibleOnly: true })`; разрешение запрашивается только по жесту пользователя. **Тихие push запрещены**: если три раза не показать уведомление, Safari отзывает подписку. Поэтому каждый push обязан превратиться в видимое уведомление, даже если дочитать детали с сервера не удалось (M).
- **Declarative Web Push** (Safari 18.4+ на iOS/iPadOS, macOS 15.5) — push-сообщение с готовым JSON уведомления: `{"web_push": 8030, "notification": {"title", "navigate", "body"?, "app_badge"?, ...}}`. Браузер показывает его сам, без сервис-воркера. Если сервис-воркер есть и успел показать замену, она вытесняет декларативное уведомление; если не успел, показывается декларативное. Подписаться можно через `window.pushManager` без сервис-воркера (H). Для нас это **страховка от отзыва подписки** на iOS и бесплатный бейдж (`app_badge` = общий счётчик непрочитанного). Формат payload лучше сразу делать декларативным, а браузеры без поддержки обработают его сервис-воркером.
- **Шифрование.** Полезная нагрузка шифруется по RFC 8291 (aes128gcm) ключами подписки; push-сервис (FCM, APNs, autopush) её не читает. Библиотека `web-push` делает это сама. Объём — около 4 КБ после шифрования (RFC 8030 гарантирует 4096 байт), поэтому в payload кладём идентификаторы и короткий текст.
- **Что класть в payload.** Транзит защищён; риск — **экран блокировки** и общее устройство (телефон родителя, планшет класса). Рекомендация: заголовок — «Сообщение от учителя Анны Петровны» (или «от ученика Иванова И.»), тело по умолчанию — «Откройте, чтобы прочитать», `navigate`/`data.url` = `/chats/{chatId}?m={messageId}`. Превью текста — личная настройка, выключенная по умолчанию для учеников. **Развилка 5.** Фото и имена файлов в payload не кладём никогда.
- **Группировка.** `tag = "chat:{chatId}"`, `renotify: true` на Chromium. На iOS `tag` не работает, поэтому сыпать уведомления на каждое сообщение нельзя: на сервере нужен **троттлинг** (не больше одного push на диалог за N минут, пока получатель не прочитал диалог).
- **Клик.** `notificationclick` → `clients.matchAll({type: "window", includeUncontrolled: true})` → если вкладка с приложением есть, `client.focus()` и `client.navigate(url)` (или `postMessage` для клиентского перехода); иначе `clients.openWindow(url)`. Для декларативного push то же делает `navigate`.
- **Офлайн-отправка.** Background Sync есть только в Chromium. Делаем универсально: очередь неотправленных сообщений в IndexedDB на клиенте с `clientMessageId` (UUID) и повтором при `online`/фокусе, а Background Sync — только ускорение там, где он есть. Сервер принимает повтор идемпотентно.
- **Кэширование сервис-воркера для чатов.** Статика и оболочка — precache и cache-first. API чатов и сообщений — **network-only** или network-first без долговременного кэша: переписка с ребёнком не должна оседать в Cache Storage общего устройства. Фото — только по подписанным ссылкам с коротким сроком, не кэшировать. После выхода из аккаунта очищать кэши и IndexedDB.
- **Запрос разрешения.** Не при первом входе. Сначала своя плашка с объяснением («Получать сообщения от учителя, даже когда сайт закрыт»), показанная в контексте: после первого отправленного или полученного сообщения или в настройках уведомлений. Браузерный запрос — только по нажатию «Включить» (web.dev Permission UX, M). На iOS плашка сначала объясняет установку на экран «Домой»: в Safari-вкладке push недоступен.
- **Share Target.** Сценарий «поделиться фото из галереи в bio-exam» работает только на Android в установленном PWA. На iOS его нет, поэтому основной путь — кнопка «Прикрепить» с `accept="image/*"` (камера или галерея на выбор системы).

Push отправляет **Express** (владелец данных по ADR-0001), а не server actions Next.js, как в гайде. Подписки хранятся в PostgreSQL и привязаны к пользователю и сессии; при ответе push-сервиса 404/410 подписку удаляем.

### Риск доставки в России

Chrome и Яндекс Браузер на Android доставляют Web Push через FCM, iOS — через APNs. Публикации 2026 года о «белых списках» мобильного интернета показывают, что при их включении push от FCM и APNs может не доходить даже у российских сервисов (L, ситуативно). Отсюда правило: **push — канал «по возможности»**. Источник правды — центр уведомлений и счётчик в кабинете; ни одна функция не должна зависеть от доставки push. Исходящие соединения с VPS на `fcm.googleapis.com`, `web.push.apple.com` и `updates.push.services.mozilla.com` проверить на этапе v4.0.

## 7. Что заложить в архитектуру чатов уже сейчас

1. **Журнал событий уведомлений (outbox) как отдельная сущность.** Таблица `notification_event` (id, recipient_user_id, kind: `chat.message` | `review.graded` | `test.assigned`, subject_type/subject_id, deep_link, created_at, read_at), которую центр уведомлений читает напрямую. Таблица `notification_delivery` (event_id, channel: `inbox` | `webpush`, status, attempts, last_error). Событие пишется **в той же транзакции**, что и сообщение. В v4.0 добавляется воркер канала `webpush`, схема не меняется. Эту же таблицу использует v3.0.
2. **Стабильные идентификаторы для deep link.** UUID диалога и сообщения; маршрут `/chats/{chatId}?m={messageId}` с проверкой доступа на сервере при открытии; у карточек вложений — типизированная ссылка `{type: "attempt" | "review", id}`, а не готовый URL.
3. **Идемпотентная отправка.** Клиент генерирует `clientMessageId` (UUID), уникальный индекс `(sender_id, client_message_id)`; повтор возвращает уже созданное сообщение. Модуль попыток (фаза 5) уже использует эту технику.
4. **Единый серверный счётчик непрочитанного.** `chat_participant.last_read_message_id` (или `last_read_at`) и запрос суммы. Один эндпоинт питает шапку, заголовок вкладки, `app_badge` в декларативном push и `setAppBadge` в сервис-воркере.
5. **Настройки уведомлений пользователя** уже в MVP: часы тишины (для учителя), звук, превью текста. Push в v4.0 читает те же поля.
6. **Троттлинг на уровне события**: «есть непрочитанное в диалоге, о котором уже сообщили» → новое событие доставки не создаём. Это понадобится для iOS, где `tag` не схлопывает уведомления.
7. **Права через шов доступа зоны**, как в фазе 07.1: `canChat(viewer, studentId)` и чтение для администратора, с охранным тестом, как у зон учителя.
8. **Хранение и удаление**: мягкое удаление сообщений, фото через модуль хранилища с тем же сроком, что в v3.0; журнал просмотров диалогов администратором.

## 8. Развилки для решения клиента

1. Может ли ученик первым написать учителю, или, как в ClassDojo, диалог открывает только учитель? (Рекомендация: может.)
2. Показывать ли ученику, что учитель прочитал сообщение? (Рекомендация: нет; учителю статус ученика — да.)
3. Разрешить ли PDF в чате, если для ответов v3.0 PDF запрещён? (Рекомендация: нет в MVP.)
4. Нужна ли кнопка «пожаловаться» в первой версии или достаточно аудита администратора? (Рекомендация: вторая очередь.)
5. Показывать ли текст сообщения в push-уведомлении (экран блокировки)? (Рекомендация: нет по умолчанию, включается пользователем.)
6. Часы тишины — личная настройка учителя или общая для платформы? (Рекомендация: личная, по умолчанию 21:00–09:00.)
7. Срок хранения фото и переписки в чате — тот же год, что для фото v3.0?
8. Живое обновление: SSE через Express или опрос? (Требует отдельного исследования транспорта и nginx на VPS.)
