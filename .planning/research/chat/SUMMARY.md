# Чаты учителя и ученика: сводка исследования

**Дата:** 2026-10-05
**Источники:** `UI.md` (интерфейс), `TRANSPORT-STORAGE.md` (транспорт, хранение, вложения), `SECURITY.md` (шифрование, право РФ), `FEATURES-PWA.md` (функции аналогов, готовность к PWA). Ссылки и уровни уверенности — в исходных файлах.

## 0. Решения пользователя (2026-10-05)

- **Место:** отдельный этап v4.0 «Чаты учителя и ученика» после v2.0 и v3.0; PWA — v5.0. В карте клиента этап IV «Чаты», «Приложение» — V.
- **Защита:** вариант B (раздел 4): TLS, журнал доступа администратора, шифрованные бэкапы, envelope-шифрование тел сообщений и фото. Серверного поиска по тексту нет. Сквозное шифрование отвергнуто.
- **Группа:** объявления учителя группе без ответов; ученики отвечают в личный диалог.
- **Кто начинает:** обе стороны; ученик пишет только своему учителю.
- **По умолчанию до discuss этапа:** SSE без «печатает» и «в сети»; «прочитано» видит только учитель; часы тишины 21:00–09:00; правка 15 мин, мягкое удаление; до 5 фото без PDF; push без текста.

## 1. Место в плане

- Этап идёт после v2.0 (Beget VPS) и v3.0 (задания с фото), перед PWA.
- До переезда чат невозможен: Express работает на Vercel как serverless-функция (`app/server/vercel.json`, `maxDuration: 30`), долгий поток событий там не держится.
- От v3.0 этап берёт пайплайн фото (порт хранилища на локальном томе, лимиты, срок хранения) и центр уведомлений в кабинете. Журнал событий уведомлений v3.0 делает общим, а не только для проверки.
- PWA подключается к готовому журналу событий как новый канал доставки, схему чатов не меняет.

## 2. Архитектура (рекомендация)

- **Свой модуль в Express, без готового чат-сервера.** Matrix/Synapse избыточен (федерация, AGPL, 1–2 ГБ ОЗУ). Rocket.Chat требует MongoDB replica set и ограничен 50 пользователями в Starter. Mattermost Team Edition с v11 ограничен 250 пользователями. Zulip занимает почти весь VPS. Любой из них — второй источник правды о пользователях и зоне учителя.
- **Доступ.** Через шов `services/access-policy`: учитель ↔ свой ученик (зона фазы 07.1), администратор читает любой диалог с записью в журнал доступа. Переписки ученик ↔ ученик нет.
- **Запись.** Все изменения (отправка, правка, удаление, прочтение) идут обычными HTTP-запросами. Идемпотентность по `UNIQUE (sender_id, client_message_id)`, как у `clientAttemptId`.
- **Порядок и синхронизация.**
  - У каждого чата свой счётчик `chats.last_seq`, номер выдаётся под блокировкой строки чата. Внутри чата порядок `seq` совпадает с порядком коммитов.
  - `version_seq` у сообщения: правки и удаления попадают в ту же дельту `GET /api/chat/:id/changes?since=`.
  - Глобальный `bigserial` как курсор отвергнут: значение выдаётся до коммита, читатель пропускает строки.
  - Клиент сначала открывает поток, затем вызывает `sync`.
- **Живое обновление: SSE** на `/api/chat/stream`.
  - Авторизация теми же cookie (`EventSource` не умеет свои заголовки).
  - Поток закрывается при истечении access-токена (по умолчанию 900 с) и сразу при отзыве сессии.
  - Клиент вызывает `/api/auth/refresh` и переподключается.
  - Heartbeat раз в 20 с.
  - На прокси: `proxy_buffering off`, HTTP/2 до браузера (лимит 6 соединений HTTP/1.1).
  - Деградация к опросу `sync` раз в 20–30 с.
  - `ws` нужен, только если появятся «печатает» и «в сети»; Socket.IO не нужен.
- **Рассылка.** Шина в памяти процесса за интерфейсом, публикация только после COMMIT. Адаптер `LISTEN/NOTIFY` — при втором процессе API. Redis и отдельная служба realtime не нужны: сотни соединений занимают десятки МБ.
- **Вложения.**
  - Клиент: `createImageBitmap` → canvas → JPEG ≤ 2048 px; EXIF и GPS не покидают устройство.
  - Сервер: `multer` → `file-type` (белый список) → `sharp` с `.rotate()` до ресайза, без сохранения метаданных, миниатюра 320 px и `thumbhash` → порт хранилища. Все три пакета уже в зависимостях.
  - Двухшаговая загрузка: вложение без сообщения, неприкреплённые удаляются через 24 ч.
  - Раздача через API с проверкой участника и `Cache-Control: private, immutable`.
  - HEIC: `sharp` и Chrome его не декодируют. Пользователь получает понятную ошибку, тяжёлый декодер подключается только по итогам UAT.
  - До 5 фото на сообщение, PDF нет; это совпадает с v3.0.
- **Уведомления.**
  - Журнал событий `notification_event` (получатель, вид, объект, deep link, `read_at`) и `notification_delivery` (канал `inbox` сейчас, `webpush` в PWA). Событие пишется в транзакции сообщения.
  - Троттлинг: пока диалог не прочитан, новое событие доставки не создаётся. На iOS `tag` не схлопывает уведомления.
- **Данные (набросок, не миграция):**
  - `chats`: `direct_key` — одна пара на диалог, `last_seq`;
  - `chat_members`: `last_read_seq`;
  - `chat_messages`: `seq`, `version_seq`, `client_message_id`, `kind` (`text`/`photo`/`attempt_ref`/`system`), мягкое удаление;
  - `chat_attachments`.
  Непрочитанное вычисляется запросом, не хранится. Схема — в `TRANSPORT-STORAGE.md` §6 с двумя поправками по решениям пользователя: столбца серверного поиска (`tsvector` по `body`) нет, потому что тело шифруется; вид чата `group` заменяется каналом объявлений без ответов.

- **Официальные компоненты shadcn/ui** (с 2026-06-26): `message-scroller`, `message`, `bubble`, `attachment`, `marker`, плюс `empty`, `item`, `spinner`. Поведение прокрутки — headless `@shadcn/react` 0.3.1 (MIT, peer `react >=19`, проверено по npm). Компоненты:

  - Утилиты `scroll-fade-*` и `shimmer` скопировать в `globals.css`, весь `shadcn/tailwind.css` не импортировать.

- **Мобильная вёрстка 375 px:**
  - список диалогов и диалог — отдельные маршруты `/chats` и `/chats/[id]`;

- **Не проверено:** подгрузка истории без прыжка на iPhone (CSS `overflow-anchor` в iOS нет). Нужен ранний спайк.

## 4. Шифрование

- **Telegram, облачные чаты:** сервер хранит переписку и может её прочитать, история на любом устройстве. Модель хранения применима. Протокол MTProto не нужен: TLS 1.3 изучен лучше, у MTProto опубликованы атаки (Albrecht et al., S&P 2022).
- **Telegram, секретные чаты, а также Signal, WhatsApp, MLS, Matrix (сквозное шифрование):** неприменимы.
  - Привязка к устройству либо отдельный протокол истории с PIN. Ученик на школьном компьютере всякий раз «новое устройство», история при потерянном ключе пропадает.
  - Администратор не видит переписку взрослого с ребёнком.
  - В вебе сервер может подменить JS.
  - Ст. 10.1 ч. 4.1 149-ФЗ: обязанность ОРИ передавать ФСБ данные для декодирования при E2E невыполнима. Прецедент — штраф Telegram в 2017 году и решение о блокировке в 2018-м.
  - Образовательные сервисы (ClassDojo, Remind, Google Classroom, Сферум/Max) E2E для текста не делают.
- **Варианты для нас:**
  - **A.** TLS 1.3 + HSTS, строгий CSP, доступ по зоне, журнал доступа администратора, бэкапы шифруются до отправки в S3 (`age` или restic). Текст в БД открытым. Кража дампа БД раскрывает всю переписку.
  - **B.** A + прикладное envelope-шифрование тел сообщений и файлов.
    - Механика: AES-256-GCM, AAD = `chat_id || message_id`; ключ данных на чат хранится в БД, обёрнутый мастер-ключом; мастер-ключ — Docker secret вне БД и вне бэкапа, копия офлайн у владельца; есть `key_version` и ротация переобёрткой.
    - Защищает от кражи дампа или бэкапа, от SQL-инъекции на чтение, от копии БД у разработчика.
    - Не защищает от root на VPS, взлома учётки, XSS.
    - Ломает серверный поиск по тексту. Поиск в MVP не нужен, позже — поиск в браузере по загруженному диалогу.
  - **C.** E2E на MLS. Многие недели работы, конфликт со ст. 10.1, школа переписку не видит.

## 5. Функции

- **MVP:**
  - диалог 1:1 на пару «учитель–ученик», создаётся лениво; если ученик выходит из зоны, диалог только для чтения;
  - текст до ~4000 символов и до 5 фото;
  - карточка «обсудить попытку/работу»: в сообщении хранится `{type, id}`, право на разбор проверяется при открытии;
  - непрочитанное с сервера: шапка, сайдбар, заголовок вкладки;
  - «прочитано» видит учитель, ученик статуса учителя не видит;
  - часы тишины учителя (по умолчанию 21:00–09:00) с баннером для ученика;
  - правка своего сообщения 15 мин с меткой; удаление только мягкое, администратор видит оригинал;
  - лимиты частоты и размера.
- **Вторая очередь:** жалоба на сообщение, поиск, ответ с цитатой, закреплённое сообщение, шаблоны ответов учителя, экспорт для администратора, наблюдатель-родитель (роли родителя в проекте нет).
- **Не делаем:**
  - звонки, видео, голосовые;
  - ученик ↔ ученик и групповой чат с ответами учеников;
  - исчезающие сообщения и жёсткое удаление пользователем;
  - стикеры, GIF;
  - «печатает…» и «в сети»;
  - пересылку в Telegram/VK;
  - email-дайджест (SMTP в проекте нет).
- **Граница с v3.0:** комментарий проверки — часть результата: пишется вместе с оценкой, у каждой пересдачи свой, ответа на него нет. Из разбора кнопка «Обсудить с учителем» («Написать ученику») открывает диалог с карточкой работы. Фото из чата не становится ответом на задание.

## 6. Под PWA закладывается сразу

- Журнал событий уведомлений с каналами, общий с v3.0; событие в транзакции сообщения; троттлинг.
- Постоянные ссылки `/chats/{chatId}?m={messageId}` с проверкой доступа при открытии.
- Исходящая очередь в IndexedDB (`Blob` фото, `clientMessageId`, повтор по `online`/фокусу). Background Sync — только ускорение в Chromium.
- Один серверный счётчик непрочитанного для шапки, вкладки, `app_badge` и `setAppBadge`.
- Настройки уведомлений пользователя (часы тишины, звук, превью текста) уже в MVP; push в PWA читает те же поля.
- **Для этапа PWA:**
  - Push без текста по умолчанию: «Сообщение от учителя …», текст подгружается после открытия. Фото и имена файлов в payload не кладутся.
  - Payload в формате Declarative Web Push (Safari 18.4+): защищает от отзыва подписки на iOS после трёх непоказанных уведомлений и даёт бейдж.
  - Сервис-воркер не кэширует API чатов и фото; кэши и IndexedDB очищаются при выходе.
  - Свой `public/sw.js` + `web-push` по гайду Next.js 16; Serwist — только при офлайн-оболочке; `next-pwa` заброшен.
- **Риски PWA:** push в России доставляется «по возможности» (FCM, APNs, «белые списки» мобильного интернета), основной канал — центр уведомлений в кабинете. Push-службы Google, Apple и Mozilla — внешняя зависимость, решение на этапе PWA.

## 7. Право РФ (не юридическая консультация)

- **ОРИ** (149-ФЗ ст. 10.1): чат формально делает платформу организатором распространения информации.
  - В реестр включают по уведомлению или по требованию РКН.
  - Хранение в РФ: содержание 6 месяцев, метаданные 3 года с 01.01.2026 (срок метаданных — по одному источнику, уверенность средняя).
  - Передача ФСБ данных для декодирования; СОРМ.
  - КоАП 13.31: штрафы от 0,1 до 6 млн руб., блокировка при систематических нарушениях.
- **152-ФЗ:**
  - Локализация (ст. 18 ч. 5, с 01.07.2025): хранить ПД граждан РФ в базах за рубежом запрещено. Это касается текущей схемы Vercel + Supabase, а не только чатов.
  - Согласие на обработку ПД — отдельным документом (с 01.09.2025).
  - Уведомление РКН нужно обновить на переписку и фото.
  - Уровень защищённости УЗ-4 (УЗ-3 при сведениях о здоровье).
  - Утечка: сообщить в РКН за 24 ч, о результатах расследования — за 72 ч; штрафы по 420-ФЗ от 1 тыс. субъектов.

## 9. Дополнение 2026-10-06: стек и ловушки

Источники: `STACK.md` и `PITFALLS.md` в этой папке (стек проверен запуском в репозитории; ловушки сверены с кодом на `1962edd`). Разделы 0–8 остаются в силе; ниже уточнения.

### Стек

- Новых серверных зависимостей нет: SSE, шина, адаптер LISTEN/NOTIFY и envelope-шифрование на `express` 4.22, `pg` 8 и `node:crypto` (AES-256-GCM, KEK в Docker secret, DEK на чат, конверт `[ver][dek_ver][nonce][ct][tag]`). `better-sse`, `pg-listen`, libsodium не брать.
- В web: `@shadcn/react` 0.3.1 (лента без виртуализации, резерв `@tanstack/react-virtual`) и `idb` 8.0.3 для исходящей очереди. Около 8 КБ gzip на маршрутах чата.
- SSE через Next rewrites в dev сжимается в один чанк без `Cache-Control: no-cache, no-transform`; этот же заголовок отключает `encode` в Caddy. `compress: false` не нужен. `proxyTimeout` Next 30 с — heartbeat 20 с.
- Caddy (конфиг на сервере): `flush_interval` для `text/event-stream` автоматический, HTTP/2 по умолчанию; nginx-специфичные советы из `TRANSPORT-STORAGE.md` к нашему прокси не относятся.
- Ключ шифрования: код читает `CHAT_KEK_FILE` (путь), запись нужна в `app/server/.env.example`.

### Главные ловушки

- **Ротация refresh:** окно повтора 30 с, дедуп refresh только во вкладке. Поток SSE с закрытием по `exp` умножит refresh и может отозвать сессию. Нужен владелец refresh на весь браузер (`navigator.locks`) — закладывается в v3.0; переподключение сначала, refresh только после 401.
- **Нативный `EventSource` не видит HTTP-статус** (401/429/502 одинаковы); STACK оставляет `EventSource` с пробой через `apiFetch`, PITFALLS предлагает fetch-поток — решить на discuss.
- **Выкатка = шторм переподключений:** graceful shutdown в `app/server/src/index.ts` не ждёт `server.close()` (чинится в v3.0), пул 20 соединений, лимитер в памяти по IP (школьный NAT).
- **Чтение собеседника:** `sync` с `last_read_seq` обоих участников раскроет ученику, что учитель прочитал; своё сообщение двигает `last_read_seq` по `known_seq` клиента.
- **`DELETE /api/users/:id` жёсткий и каскадный:** таблицы чата не каскадить от `users`.
- **Журнал доступа администратора:** условие «действующий не участник», а не «роль админ» (`zone.all`).
- **Публикация после COMMIT:** `revokeSession(..., tx?)` работает внутри чужих транзакций — нужна очередь after-commit.
- **KEK:** проверка канарейкой при старте, бэкапы без KEK, репетиция восстановления с офлайн-копией.
- **Согласие 14–17 лет:** в схеме хранения согласия нет (только nullable `users.birthdate`).

### Отклонения от разделов 2–6 (подтвердить на discuss v4.0)

1. `thumbhash` убран: открытое размытое превью детского фото в БД при шифрованных файлах; заполнитель по `width/height`.
2. Лайтбокс — просмотрщик v3.0 (`react-zoom-pan-pinch`) вместо `yet-another-react-lightbox`.
3. Без `id:`/`Last-Event-ID`: курсоры по нескольким чатам через `changes?since=`.
4. Heartbeat как `event: hb`, а не комментарий.
5. Первичные ключи `defaultRandom()` вместо UUIDv7; порядок держит `seq`.
6. Без `sha256` открытого файла во вложениях; ETag = id вложения.
7. `accept`: явный список типов, свести с v3.0.
8. Кнопка «пожаловаться» и очередь админа — в MVP; смысл часов тишины (баннер и отложенный push или запрет отправки учителю ночью); хранить зашифрованную историю правок для администратора; поведение диалога при смене владельца группы.

### Что закладывает v3.0

Graceful shutdown, общий модуль фоновых задач, журнал уведомлений с одной строкой на (получатель, объект) и `ref_seq`/`collapse_key`/`deliver_after`, ограничители `sharp`, `processPhoto()` возвращает буферы, расширяемые пространства хранилища, `navigator.locks` для refresh, отсутствие каскада от `users`. Подробно — `../SUMMARY.md`, раздел «Что v3.0 закладывает для v4.0 и v5.0».
