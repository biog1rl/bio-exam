# Чаты учителя и ученика: ловушки и подводные камни

**Домен:** встроенный чат 1:1 «учитель — ученик» (много несовершеннолетних) в работающей экзаменационной платформе: Express 4 + Drizzle + PostgreSQL 17, Next.js 16, один Beget VPS (4 CPU / 6 ГБ / 80 ГБ), Docker Compose, Caddy, локальный том, собственные JWT-сессии с ротацией refresh.
**Дата:** 2026-10-06
**Общая уверенность:** MEDIUM–HIGH. Утверждения о коде репозитория проверены чтением файлов (HIGH). Поведение Caddy проверено по официальной документации (HIGH). Поведение мобильных браузеров и школьных сетей взято из вторичных источников и практики (MEDIUM/LOW, помечено). Право РФ: сводки, не юридическая консультация (MEDIUM).
**Метки:** `[HIGH]` код репозитория или первоисточник; `[MEDIUM]` вторичный источник или согласованные выводы; `[LOW]` предположение, нужна проверка спайком.

**Что НЕ повторяется.** Решения из `SUMMARY.md`, `TRANSPORT-STORAGE.md`, `SECURITY.md`, `UI.md` приняты как данность. Здесь только то, что может сломаться при их реализации в этой кодовой базе, как это заметить и в какой фазе v4.0 закрыть. Фазы v4.0 ещё не созданы; ниже рабочая нарезка, роудмап может её переименовать:

## Критические ловушки

### C1. Рефреш при повторном подключении потока: потерянный ответ, шторм refresh, гонка вкладок

**Что идёт не так.** По решению поток закрывается на `exp` access-токена, клиент вызывает `/api/auth/refresh` и переподключается. В коде это опаснее, чем выглядит.
- Окно повторного использования refresh-токена всего 30 с (`REFRESH_REUSE_WINDOW_MS = 30_000`, `app/server/src/services/session/index.ts`) `[HIGH]`. Внутри окна повтор со старым токеном получает ответ `reused`: только новый access-cookie, **без нового refresh** (`routes/auth/refresh.ts`). После окна повтор старого токена считается `replay` и **отзывает всю сессию** (все вкладки и устройства этой сессии выходят). Это зафиксировано тестами `refresh-rotation.test.ts` (`rot_replay_late`).
- Если ответ победившего запроса потерян (мобильная сеть, iOS убил страницу посреди fetch, переход между Wi-Fi и LTE), в cookie-хранилище остаётся использованный T1. Повтор через 31 с и позже убивает сессию. Раньше такой запрос случался раз в ~14 минут на устройство. Реконнекты потока добавляют ещё один refresh на каждую вкладку каждые 15 минут и на каждую сетевую ошибку.
- Дедупликация refresh в вебе только внутри вкладки: `pendingRefresh` в `createSessionClient` (`app/web/lib/session/client.ts`). В `app/web` нет `BroadcastChannel` и `navigator.locks` (поиск по коду пуст) `[HIGH]`. N вкладок на экзаменационной платформе после перезапуска API шлют N параллельных refresh с одним токеном; окно 30 с это прощает, но не прощает ни медленную сеть, ни очередь запросов в браузере.
- `createKeepAlive` обновляет access за 60 с до `exp`, только когда вкладка видима (`keep-alive.ts`, `schedule.ts`). Серверный таймер потока считается от `exp` в момент подключения. Видимая вкладка уже обновила токен через keep-alive, а поток всё равно закроется по старому `exp` и вызовет второй refresh через минуту.
- Cookie доступа живёт ровно `accessTokenTtlSec` (`cookies.ts`): после `exp` браузер перестаёт его отправлять, и повтор подключения приходит вообще без cookie, то есть как 401 `[HIGH]`.

**Почему так выходит.** Дизайн «закрыть поток на `exp`, клиент сам делает refresh» не учитывает, что refresh в этом проекте не идемпотентен после 30 с, а cookie общие для вкладок, тогда как координации между вкладками нет.

**Как избежать.**
1. Событие `reauth` и закрытие потока: клиент **сначала просто переподключается** (cookie мог обновить keep-alive или другая вкладка). Refresh только после ответа 401 на переподключение, и только через общий `sessionClient.refreshOnce()` / `apiFetch`, а не отдельным вызовом из модуля чата.
2. Один владелец refresh на браузер: обернуть `performRefresh` в `navigator.locks.request('bio-exam-session-refresh', ...)` и после получения блокировки сверить, не обновил ли токен соседняя вкладка (время последнего успешного refresh в `localStorage`/`BroadcastChannel`). Это правка модуля сессии из v1.0 (`app/web/lib/session`), она улучшает и экзаменационный сценарий, а не только чат. Править через `codegraph impact` и юнит-таблицы `keep-alive.test.ts`/`client.test.ts` (там действительно много вариантов).
3. Серверный таймер потока пересчитывать от актуального `exp` при каждом повторном подключении, не держать по токену дольше 15 минут. Закрывать за 5–10 с до `exp` со случайным сдвигом, чтобы N вкладок не закрывались в одну секунду.
4. Не лечить потерянный ответ в `rotateRefreshToken` в рамках чата (инвариант безопасности v1.0). Если на UAT воспроизведётся «выбрасывает на логин после сна телефона», решать отдельным изменением сессий, а не обходом в чате.

**Признаки.** В логах API растёт `refresh_replay` (сервер уже пишет `event: 'refresh_replay'`); жалобы «выкинуло из системы» у учеников на телефоне; два refresh с одной сессии с интервалом менее секунды.

**Фаза:** V4-B (модуль потока и клиент), правка `app/web/lib/session` — отдельным планом внутри V4-B до включения потока. Метрику `refresh_replay` завести в V4-B.
**Уверенность:** HIGH по коду; MEDIUM по вероятности (мобильные сети).

### C2. `EventSource` не показывает статус ошибки: 401, 429, 502 неразличимы

**Что идёт не так.** Любой ответ не 200 закрывает `EventSource` насовсем без повтора, а `onerror` отдаёт пустой `Event` без кода [WHATWG, HIGH]. Клиент не может отличить «токен истёк» (нужен refresh) от «API перезапускается» (502 от Caddy), «лимит» (429) и «сервер перегружен» (503). План «ошибка → refresh» превращает каждый 502 во время выкатки в refresh, а каждый 401 после `exp` в бесконечные переподключения без refresh (нативный `EventSource` повторяет запрос с теми же просроченными cookie).

**Как избежать.**
- Выбрать одно из двух. (а) Читать поток через `fetch` + `ReadableStream` (свой парсер на ~60 строк или `@microsoft/fetch-event-source`): виден статус, можно разобрать 401/429/5xx. Cookie уходят так же (`credentials: 'include'`), `Last-Event-ID` не нужен (источник правды `sync`). (б) Оставить `EventSource`, но после любой ошибки делать зонд через `apiFetch('/api/chat/sync?probe=1')`: он уже содержит 401 → refresh → повтор, а статус зонда решает, ждать или менять режим на опрос.
- Рекомендация: **(а)** `fetch`-поток. Тот же код даёт `AbortController` для закрытия при `visibilitychange` (C5) и чёткие ветки 401/429/5xx.
- Если оставлен нативный `EventSource`: после чистого закрытия сервером (ответ 200, поток завершён) браузер переподключается сам через `retry` мс **без джиттера**. Отдавать в первой строке потока `retry: <случайное 2000–15000>` отдельно для каждого соединения.

**Признаки.** В логах Caddy и API пачки 502/401 с одного клиента каждые 3 с; клиент «висит» после выкатки до перезагрузки страницы.
**Фаза:** V4-B. **Уверенность:** HIGH (спецификация, MDN, практика).

### C3. Выкатка: SIGTERM не завершает потоки, шторм переподключения, истощение пула БД

**Что идёт не так.** Автодеплой из master пересоздаёт контейнеры web/API (`plans/beget-migration.md`, «recreate web/API с healthcheck»), без перекрытия. Что видно в текущем коде:
- `app/server/src/index.ts`: `gracefulShutdown` вызывает `server.close()` без ожидания, сразу `pgPool.end()`, затем `process.exit(0)` через 5 с. План переезда прямо отмечает эту ошибку и требует исправления (строка про graceful shutdown, раздел 3) `[HIGH]`, но в коде она осталась. `server.close()` не закрывает открытые потоки SSE, они остаются подвешенными до SIGKILL; запросы в полёте после `pgPool.end()` падают.
- Docker ждёт `stop_grace_period` (по умолчанию 10 с), затем SIGKILL. Все ~300–450 потоков обрываются в одну секунду.
- Пока новый контейнер поднимается (Node 24, импорты, миграции), Caddy отвечает 502 по умолчанию. Затем сотни клиентов с одинаковым экспоненциальным шагом приходят одновременно и делают `sync` (+ `changes` на каждый чат). Пул БД: `PG_POOL_MAX` по умолчанию 20, `connectionTimeoutMillis` 5 с, `statement_timeout` 10 с (`app/server/src/db/index.ts`) `[HIGH]`. Очередь за соединением превышает 5 с, пользователи видят 500, повторяют, нагрузка растёт.
- Лимитер частоты в памяти по IP (`middleware/rateLimiter.ts`): сброс при перезапуске; а за школьным NAT один IP у целого класса. Если лимитер повесят на `/api/chat/*`, 429 на переподключении превратится в «закрыто насовсем» (C2).

**Как избежать.**
1. До v4.0 (в v3.0, техдолг) исправить `gracefulShutdown`: остановить приём, разослать всем потокам финальное событие `event: bye` с `retry` со случайным значением, закрыть потоки, дождаться активных запросов (с общим потолком), затем закрыть пул; `stop_grace_period` в Compose больше потолка.
2. Caddy: `reverse_proxy` с `lb_try_duration 10s` и `lb_try_interval 250ms`: запросы, не нашедшие апстрим, ждут, а не получают 502 `[HIGH, Caddy docs]`. Для потока это превращает короткий рестарт в «подвисание» вместо шторма отказов. Конфигурация Caddy лежит вне репозитория (`deploy/` на сервере), поэтому проверка через runbook, а не через `yarn verify`.
3. Клиент: джиттер на **первом** повторе (0–5 с), далее 1→30 с с полным джиттером; не стартовать `sync` до открытия потока и не более N одновременных `sync` с сервера (семафор на уровне маршрута).
4. Один массовый эндпоинт `sync`, который возвращает дельты по всем чатам пользователя за один запрос (карта `chatId → known_seq` в теле), вместо `changes?since` на каждый чат. Одна пачка запросов на переподключение, а не N.
5. Ограничивать ключом **user id**, а не IP (`rateLimiter` уже принимает `clientKey`), особенно для `sync`, чтения и отправки: школьный NAT.
6. Нагрузочная проверка: скрипт держит 400 потоков, перезапускает контейнер API, измеряет время до восстановления и процент 5xx. Порог приёмки: все клиенты синхронизированы за 60 с, ни одной ошибки пула.

**Признаки.** В логах `timeout exceeded when trying to connect` сразу после деплоя; всплеск `sync` в первую минуту; потоки после деплоя не возвращаются.
**Фаза:** исправление `gracefulShutdown`: **v3.0 (техдолг)**; остальное V4-B. **Уверенность:** HIGH (код и документация Caddy).

### C4. Буферизация, сжатие, таймауты и лимит соединений: dev, e2e и production идут разными путями

**Что идёт не так.**
- В `yarn dev` и в `yarn e2e` `/api/*` идёт через Next rewrites (`app/web/next.config.ts`), в production `/api/*` обслуживает Caddy напрямую. Next по умолчанию включает `compress: true`; сжатый `text/event-stream` может копиться в буфере кодировщика (известное поведение, обсуждение vercel/next.js #48427, MEDIUM). Тест зелёный в одном окружении и ничего не доказывает про другое.
- Caddy сам не мешает: `reverse_proxy` немедленно сбрасывает ответы `text/event-stream`, а `encode` не сжимает SSE `[HIGH, Caddy docs]`. Директивы nginx из `TRANSPORT-STORAGE.md` (`proxy_buffering off`, `proxy_read_timeout 1h`) к Caddy неприменимы. Что реально может сломать: глобальные `servers { timeouts { write_timeout ... } }` в Caddyfile (убьёт поток), собственный `compression` в Express (в `app.ts` его нет, не добавлять), HTTP/3 на сетях, где режут UDP (автоматический откат на h2).
- Лимит 6 соединений HTTP/1.1 на домен остаётся в `yarn dev`, e2e (`http://127.0.0.1`) и при любой отладке без TLS. 6 вкладок с чатом исчерпывают пул браузера, обычные `fetch` встают в очередь, интерфейс «зависает». На production с h2 это не проявляется.
- Корпоративные и школьные фильтры, мобильные операторы: прозрачные прокси, которые буферизуют или обрывают долгие ответы `[LOW, нужно проверить на UAT в реальной школьной сети]`. Здесь решает только полный деградационный путь на опрос.

**Как избежать.**
1. Заголовки потока: `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no` (безвредно для Caddy, нужно, если впереди появится nginx), `res.flushHeaders()` и **немедленная первая запись** (`retry:` + комментарий) сразу после заголовков.
2. `next.config.ts`: не полагаться на rewrites для потока. Либо `compress: false` для dev-цепочки, либо в dev обращаться к потоку напрямую на `API_ORIGIN`. Фиксируется решением в V4-B и проверкой «событие дошло за < 2 с» в e2e **и** в smoke-проверке прод-цепочки (`curl -N` через Caddy в runbook выкатки: первое событие за 2 с, heartbeat за 25 с).
3. Не снимать `compress` со всего Next «на всякий случай»: в production `/api/chat/stream` идёт мимо Next, в dev и e2e для него нужен отдельный обход (пункт 2).
4. Деградация к опросу `sync` раз в 20–30 с, если за 45 с не пришёл ни heartbeat, ни событие (поток «жив», но молчит из-за буфера). Переключение автоматическое, видно в интерфейсе («обновляется с задержкой»).
5. Предел потоков на пользователя (5) и на процесс (1000), по превышению 503 с `Retry-After`.
6. Решение Р2 из `TRANSPORT-STORAGE.md` (поток на вкладку + HTTP/2) принять, но для dev/e2e сделать выбор ведущей вкладки не обязательной оптимизацией. Минимум: одна вкладка не держит более одного потока, закрытие при скрытии (C5) снимает давление на лимит.

**Признаки.** События приходят пачкой раз в 30–60 с; `yarn dev` «замирает» при 4–6 вкладках; в логах Caddy `context deadline exceeded` на потоке.
**Фаза:** V4-B (заголовки, деградация), V4-F (e2e сквозь цепочку и smoke runbook). **Уверенность:** HIGH по Caddy и коду, MEDIUM по Next и школьным сетям.

### C5. Фоновые вкладки и мобильные браузеры: «живой» поток, который на самом деле мёртв

**Что идёт не так.** iOS Safari приостанавливает JS и сеть в фоновой вкладке; `EventSource` остаётся в `readyState = 1`, `onerror` не вызывается, а TCP-соединения уже нет [MEDIUM, server-sent-events.com и практика]. Chrome замораживает фоновые вкладки. Клиент считает себя подключённым, ждёт события, а они потеряны. Таймеры heartbeat-контроля на клиенте тоже заморожены.
Дополнительно: `keep-alive.ts` специально не обновляет сессию в скрытой вкладке; чат в скрытой вкладке с живым потоком вынужден делать refresh при `reauth` (C1).

**Как избежать.**
- Правило из `TRANSPORT-STORAGE.md` «корректность только через `sync` при `visibilitychange` и `online`» развернуть в конкретику: при `hidden` закрывать поток через 30–60 с (не сразу, чтобы быстрые переключения не дёргали сеть); при `visible`, `pageshow` (в том числе из bfcache), `online`, `focus` открывать поток заново **и затем** вызывать `sync` (порядок «сначала поток, потом sync»).
- Серверная проверка «клиент жив»: если heartbeat-комментарий не подтверждён ничем, это не страшно (запись в мёртвый сокет вызовет `close`), но клиент должен иметь **таймер молчания** (нет байтов 45 с → пересоздать поток), и этот таймер сам проверять по реальным часам (`Date.now()`), а не по счётчику тиков.
- Для скрытых вкладок обновлять счётчик непрочитанного опросом раз в 60 с (`GET /api/chat/unread`) вместо живого потока. До PWA/Web Push (v5.0) это единственный источник уведомлений вне открытой вкладки.
- Убрать `beforeunload`/`unload`-обработчики для чата; использовать `pagehide`.

**Признаки.** «Сообщение пришло только после того, как я переключился на другую вкладку и вернулся»; счётчик в заголовке вкладки отстаёт.
**Фаза:** V4-B (клиентский транспорт); проверка на живом iPhone — V4-F (e2e на Chromium этого не покажет). **Уверенность:** MEDIUM.

### C6. Контракт `seq`/`sync`: события теряются в местах, которых нет в схеме

**Что идёт не так.** Основной контракт описан верно (блокировка строки чата, `version_seq`, поток до `sync`). Но пропуски рождаются вокруг него.
1. **Публикация после COMMIT, а вызов из вложенной транзакции.** `revokeSession(sessionId, reason, tx?)` и `revokeUserSessions(..., tx?)` принимают чужую транзакцию (`services/session/index.ts`); `rotateRefreshToken` вызывает отзыв при `replay` внутри своей транзакции. Если событие `session.revoked` публиковать внутри функции, оно уходит до COMMIT: поток закрывается, клиент переподключается, строка сессии ещё выглядит живой, поток снова открывается и живёт до ближайшей 60-секундной перепроверки (по плану). То же для события членства.
2. **Падение процесса между COMMIT и `bus.publish`.** Сообщение есть, события нет; клиенты узнают о нём только при следующем переподключении (до 15 минут при закрытии на `exp`).
3. **Членство и зона.** Права на чат выводятся из живого состояния зоны (`canManageStudent` через `studentIdsInOwnedGroups`, `ownerId` группы nullable). Зона меняется минимум в трёх местах: `setGroupOwner`/`releaseZone` в `zone-store.ts`, прямые правки `user_groups` в `routes/users/index.ts`, деактивация и жёсткое удаление пользователя. Кэш членства потока, инвалидируемый «событиями `member.*`», будет пропускать то, что изменили в обход этих событий.
4. **Буфер «событий во время sync» без предела** и без дедупликации по `(chatId, version_seq)`.
5. **`Last-Event-ID` как «быстрый путь»**: `id: chatId:seq` у потока по многим чатам не может выражать несколько курсоров; реализация воспроизведения из памяти теряется при перезапуске.

**Как избежать.**
- Шина с очередью «после коммита»: функции, принимающие `tx`, не публикуют сами, а кладут событие в список, привязанный к транзакции верхнего уровня; список сбрасывается после `await db.transaction(...)`. Для `session.revoked` достаточно и надёжного дублирования: перепроверка строк сессий **одним запросом** на все потоки раз в 30–60 с.
- Отказаться от `Last-Event-ID` и повторного воспроизведения; не ставить `id:` у событий. `sync` — единственный путь восстановления.
- Сигнал согласования: раз в 60–120 с поток шлёт `event: tick` с картой `chatId → last_seq` пользователя (один пакетный запрос на все потоки). Клиент, видя `last_seq > known_seq`, запускает `changes`. Это лечит потерю события при падении между COMMIT и publish без Redis.
- Право на доставку проверять **политикой на событии**, а не кэшем членства: короткий кэш (≤ 30 с) списка доступных чатов пользователя + событие `zone.changed`, которое публикуют `zone-store` и маршрут пользователей. Документировать верхнюю границу задержки отзыва доступа (≤ 60 с) и закрыть мгновенно только для `session.revoked` и блокировки.
- Контракт клиента: применять событие только если `version_seq` больше известного для этого сообщения; разрыв `seq != known+1` → `changes`. Буфер на время `sync` с потолком (например, 500 событий; при переполнении отбросить и сделать повторный `sync`).
- Тест на серверном уровне (интеграционный): два подключения, отзыв сессии внутри чужой транзакции, откат транзакции (событие не уходит), падение между COMMIT и publish (эмулируется), зона меняется прямым SQL.

**Признаки.** «Сообщение появилось после обновления страницы»; ученик, выведенный из зоны, ещё минуту видит новые сообщения; события `session.revoked` приходят до того, как сессия отозвана в БД.
**Фаза:** V4-B (шина, контракт `sync`, `tick`), доступ по зоне — V4-A. **Уверенность:** HIGH по коду, MEDIUM по сценариям.

### C7. Порядок и дубли: клиент порядок ломает чаще, чем сервер

**Что идёт не так.**
- Клиент сортирует по `created_at`, а не по `seq`: часы телефона уходят, порядок между участниками «прыгает».
- Оптимистичное сообщение вставляется «в конец по локальному времени» (решение из `TRANSPORT-STORAGE.md` §8). После ответа сервера оно встаёт на место по `seq`; если собеседник успел написать между, интерфейс прыгает, а прокрутка у `message-scroller` держит позицию только у нижнего края.
- Тот же `clientMessageId` для **другого** текста (баг клиента: id генерируется один раз на композер и не обновляется после отправки; повтор после правки): сервер молча возвращает прежнее сообщение со статусом 200, пользователь видит «отправлено», а текст не тот.
- Две вкладки читают общий исходящий (IndexedDB v5.0) и отправляют одно и то же: безопасно из-за уникальности, но показывают «ошибку» вкладке, чей запрос отработал как повтор.
- Двойной клик и повтор по `online` без блокировки кнопки.
- Загрузка вложений и сообщение с `attachmentIds`: повтор после частичного сбоя. По плану конфликт идемпотентности обрабатывается до привязки вложений, но если порядок шагов в реализации поменяется, повтор вернёт 409/500 вместо 200.
- Правка и удаление приходят событием раньше, чем клиент получил само сообщение.

**Как избежать.**
- На сервере при конфликте `(sender_id, client_message_id)` сравнивать хеш содержимого (текст, `attachmentIds`, `kind`) с сохранённым: тот же → 200 с существующим сообщением; другой → 409 `client_message_id_reused`. Юнит-таблица не нужна, нужен интеграционный тест.
- На клиенте единственный ключ сортировки `(seq)`, неподтверждённые в отдельной зоне «отправляется» под лентой, без вставки в середину; при подтверждении не двигать прокрутку, если пользователь не внизу.
- Хранилище клиента применяет события идемпотентно: `Map<messageId, {version_seq, ...}>`, обновление только при большем `version_seq`; событие об ещё неизвестном сообщении вызывает `changes`, а не создаёт «призрак».
- Блокировать кнопку отправки на время запроса; новый `clientMessageId` генерировать только после подтверждения или явного «отправить заново».
- Порядок блокировок в одной транзакции: **всегда сначала строка чата**, потом вложения и сообщения (иначе взаимная блокировка при правке и привязке вложений одного чата).

**Признаки.** Двойные пузыри; пузырь «прыгает» при подтверждении; текст не совпадает с отправленным после повтора.
**Фаза:** V4-A (сервер: идемпотентность и порядок блокировок), V4-B (клиентское хранилище). **Уверенность:** HIGH.

### C8. Непрочитанное: дрейф счётчиков и утечка статуса «прочитано» ученику

**Что идёт не так.**
1. **«Свои сообщения сразу двигают `last_read_seq` отправителя»** (`TRANSPORT-STORAGE.md` §6.1). Если пока ученик набирал ответ, пришли сообщения учителя 8–10 (он их не увидел), новое сообщение ученика получает `seq = 11` и сдвигает его `last_read_seq` до 11. Сообщения 8–10 помечены прочитанными, учитель видит «прочитано», ученик ничего не читал. Сдвигать нужно до **известного клиенту `known_seq` на момент отправки** (клиент передаёт его в POST), не до нового `seq`.
2. **Утечка статуса учителя.** По решению ученик статуса учителя не видит. Но `sync` по плану возвращает «`last_read_seq` участников», а событие `read` уходит «другим участникам». Если сериализатор не зависит от роли зрителя, ученик получает `last_read_seq` учителя и в `sync`, и в потоке.
3. **Отметка о прочтении при скрытой вкладке или без прокрутки вниз.** Открытая, но скрытая вкладка помечает прочитанным.
4. **Клиент увеличивает счётчик на каждое событие** и никогда не сверяется с сервером: после пропущенных событий и удалений число расходится.
5. **Несколько счётчиков** (шапка, сайдбар, заголовок вкладки, журнал уведомлений v3.0, потом `setAppBadge`) считаются в разных местах.
6. **Что считается:** сообщения `kind = 'system'`, `attempt_ref` без текста, удалённые и собственные сообщения; «99+» реализовано обрезкой на клиенте, а не `LIMIT` в подзапросе.
7. **Чат в режиме «только чтение»** после выхода ученика из зоны навсегда остаётся «с непрочитанным».

**Как избежать.**
- Одна серверная функция `unreadSummary(userId)` для всех мест; ответы `sync`, `read`, потока `tick` возвращают итоги по чатам. Клиент **заменяет** локальное значение, а не инкрементирует.
- `read` помечается только при `document.visibilityState === 'visible'`, фокусе окна и положении у нижнего края; `GREATEST` на сервере уже защищает от отката.
- Сериализатор `ChatMemberView` строится от роли зрителя: ученик никогда не получает `last_read_seq` учителя; серверный тест на этот инвариант (ученик читает `sync`, `changes`, поток; во всех трёх нет поля).
- Подсчёт: `kind IN ('text','photo')` (и `attempt_ref`, если он должен быть заметен), `deleted_at IS NULL`, `sender_id <> me`; подзапрос с `LIMIT 100`. Для архивных чатов не считать.

**Признаки.** «Прочитано» без открытия чата; число в шапке не совпадает со списком; ученик видит «учитель прочитал».
**Фаза:** V4-D (счётчики, `read`), V4-A (инвариант сериализатора ролей). **Уверенность:** HIGH.

### C9. Дублирование уведомлений с журналом v3.0

**Что идёт не так.** Чат пишет событие журнала в транзакции сообщения (CHAT-09), а непрочитанное чата вычисляется запросом (CHAT-07). Появляются два источника правды.
- Шапка показывает «непрочитанные уведомления (журнал) + непрочитанные чаты», а сообщение чата породило ещё и событие в журнале: счёт удваивается.
- Троттлинг «пока диалог не прочитан, новое событие не создаётся» проверяется по строке `notification_event` с `read_at IS NULL`. Ученик читает чат на другом устройстве, пометка в журнале не снята, новых событий больше нет: уведомления молча пропадают. Обратная гонка: ученик читает до seq N, а новое сообщение N+1 пришло после; чтение гасит событие целиком, сообщение N+1 остаётся без события и без будущего push.
- Часы тишины откладывают push, но не должны откладывать запись события в кабинете.
- Журнал v3.0 проектируется для «работа проверена»; вид события `chat.message` с глубокой ссылкой `/chats/{id}?m={messageId}` попадает в читателей, не знающих такой вид, или в `CHECK`/enum, требующий миграции.

**Как избежать.**
- **Одна строка журнала на пару `(получатель, чат)`**, а не на сообщение: `ref = {chatId}`, `ref_seq = last_seq`, upsert при новом сообщении (`ref_seq` растёт, `read_at` сбрасывается, если `ref_seq > last_read_seq` получателя). Чтение чата в **той же транзакции**, что и сдвиг `last_read_seq`, помечает событие прочитанным только если `ref_seq <= новый last_read_seq`.
- Счётчик для шапки считается из одного источника: чатовые события в общую сумму не входят, сумма = журнал без вида `chat.message` + `unreadSummary`. Либо наоборот. Выбрать в V4-D и зафиксировать в ADR или в плане.
- Троттлинг «не создавать событие» заменить обновлением строки (upsert выше): тогда он не зависит от пометки и гонки.
- Доставка по каналам: `notification_delivery` создаётся с `deliver_after` (часы тишины и временная зона получателя); канал `inbox` доставляется сразу.
- v3.0: вид события хранить как `text` с проверкой на уровне приложения, читатель обязан **терпимо** обрабатывать неизвестные виды (не падать, показывать общий текст или пропускать). Это нужно и ради отката (см. C17).

**Признаки.** После прочтения чата колокольчик всё ещё показывает единицу; у получателя «тишина», хотя сообщения есть; два уведомления на одно сообщение.
**Фаза:** требования к схеме журнала: **v3.0 (планирование сейчас)**; реализация V4-D. **Уверенность:** HIGH (логика), MEDIUM (формы схемы v3.0 пока нет в репозитории).

### C10. Шифрование: потеря и ротация KEK, нечитаемые бэкапы, и места, где открытый текст всё же протекает

**Что идёт не так.**
1. **Потеря KEK = потеря всей переписки.** Бэкапы PostgreSQL (ежечасные, шифруются до отправки в S3) содержат только обёрнутые DEK; без KEK они бесполезны. Если «копия офлайн у владельца» не проверена восстановлением, это не копия. Второй независимый секрет: ключ `age`/restic для бэкапов; оба хранить отдельно от VPS и друг от друга.
2. **KEK окажется в бэкапе или в логах.** Docker secret в Compose без Swarm — это просто файл на хосте (`./secrets/...`, bind mount); если скрипт бэкапа архивирует каталог деплоя, ключ уезжает вместе с данными, а смысл разделения пропадает. Переменная окружения с KEK видна в `docker inspect`, `/proc/<pid>/environ`, дампах.
3. **Тихий небезопасный режим.** Паттерн из `config/auth.ts`: `DEFAULTS.JWT_SECRET` как значение по умолчанию и запрет только в production. Для KEK повторять нельзя: сервис, стартующий без файла KEK и пишущий открытый текст «пока», незаметен.
4. **Старт без KEK после выкатки.** Файл секрета пропал при пересоздании контейнера, API стартует, чат «работает», но расшифровка падает на первом чтении.
5. **Ротация KEK не атомарна.** Переобёртка тысячи DEK идёт долго; промежуточное состояние (часть DEK под v1, часть под v2) требует одновременно загруженных двух версий KEK. Поле `kek_version` должно жить в строке ключа чата, а не в сообщении.
6. **Повторное использование nonce в GCM** катастрофично: у правки сообщения должен быть **новый** случайный 96-битный nonce; детерминированный nonce от `message_id` ломает AES-GCM при первой же правке (NIST SP 800-38D, MEDIUM, источник не открывался). AAD = `chat_id || message_id`: любой скрипт, который пересоздаёт строки с новым `id` (бэкфилл, перенос, восстановление с ремаппингом), делает шифротекст нечитаемым.
7. **Открытый текст в соседних местах**, которые легко пропустить: превью последнего сообщения в `chats` или в `sync`, текст в `notification_event` («Вам написал…»), содержимое push, подписи вложений, `thumbhash` (низкое разрешение самой картинки), `ETag = sha256` открытого файла (раскрывает совпадение файлов и позволяет дедупликацию), логи ошибок валидации с входными данными. Для файлов: расшифровка требует проверки тега до выдачи, значит файл читается в память целиком (≤ 1–2 МБ, допустимо).
8. **Дампы для разработки.** Dev-БД на домашнем сервере получает с production только банк заданий (`local-dev-db`); скрипт обновления должен быть allowlist по таблицам, а не denylist, иначе новая таблица `chat_*` уйдёт на dev.

**Как избежать.**
- Файл KEK монтируется только в контейнер API (`:ro`), путь задаётся ключом `CHAT_KEK_FILE` (в `.env.example` только плейсхолдер, `scripts/check-env-contract.mjs` этого требует); значение никогда не в окружении.
- **Самопроверка при старте:** в БД лежит контрольная запись (канарейка `chat_key_check`: DEK, обёрнутый KEK, и известный открытый текст). API при старте расшифровывает её; не удалось → процесс падает (как `AUTH_JWT_SECRET` в production), healthcheck красный, автодеплой откатывается по digest. Без KEK модуль чата **не** переходит в открытый режим.
- Учение по восстановлению в runbook (C5 из `beget-migration`): чистая машина, дамп БД из S3, ключ бэкапа и **офлайн-KEK**, расшифровка тестового чата. Повторять после каждой ротации и раз в квартал. Критерий готовности V4-E: runbook выполнен человеком, не агентом.
- Ротация: `chat_keys(chat_id, dek_version, wrapped_dek, kek_version)`; скрипт переобёртывает в транзакции на чат, идемпотентен, работает при двух загруженных KEK; старый KEK удаляется только после проверки `SELECT count(*) WHERE kek_version = old = 0` и свежего бэкапа.
- Для сообщений и вложений: новый nonce при каждой записи (включая правку); `message_id` никогда не перегенерируется; миграции чата обязаны быть только аддитивными.
- Таблица «где живёт открытый текст»: превью только в зашифрованном виде или не хранится; события журнала без текста («Новое сообщение от …»); тест: после отправки сообщения `SELECT` по всем таблицам и по `pg_dump` не находит маркерную строку из теста (интеграционный тест «grep по дампу»).
- ETag вложения: хеш шифротекста или непрозрачный идентификатор.

**Признаки.** Старт API без файла секрета не завершается ошибкой; в `pg_dump` читается текст; `kek_version` разный у строк после «завершённой» ротации; восстановление на тестовой машине даёт «bad decrypt».
**Фаза:** V4-A (модуль крипто, самопроверка старта, форма таблиц), V4-E (runbook и учение восстановления, ротация). **Уверенность:** HIGH (логика и код), MEDIUM (детали NIST и Docker secrets).

### C11. Журнал доступа администратора: дыры

**Что идёт не так.** Журнал в `SECURITY.md` описан как «кто, когда, какой диалог, причина». Дыры возникают в реализации.
- Условием записи сделали роль `admin`. В коде доступ учителя к чужим данным определяет право `zone.all` (`hasGlobalZone`, `scope-rules.ts`): учитель с глобальной зоной тоже читает чужие диалоги. Условие должно быть «**актор не участник чата**», а не «роль admin».
- Журнал пишется после ответа (или асинхронно) и теряется при падении; либо пишется «открытие диалога», а `changes`, `sync`, раздача вложений и пагинация истории идут мимо.
- Один вход в журнал на диалог при бесконечном чтении: невозможно ответить «какие именно сообщения читали».
- Журнал изменяем: у API-роли есть `UPDATE`/`DELETE`.
- Экспорт чата, поиск и любой маршрут админки, возвращающий тело сообщений, живут отдельно от основной ручки и не пишут журнал.
- Администратор попадает в `chat_members` и получает SSE-события чужого чата.
- Прямой доступ владельца к БД (`psql`, дамп) невозможно залогировать. Остаточный риск, который надо принять явно.

**Как избежать.**
- Один выделенный сервис `chat-admin-read`: **единственный** путь, на котором не-участник получает расшифрованный текст или файл. Он пишет запись журнала **в той же транзакции до выдачи тела** (отказ записи = отказ чтения, fail-closed). Запись содержит актора, чат, диапазон `seq`, число сообщений, список id вложений, причину (обязательное поле), IP, время; **без текста**.

### C12. Безопасность детей: нежелательный контакт, жалобы, блокировки, часы тишины

**Что идёт не так.** Главный риск такого чата в том, что это канал **взрослый → несовершеннолетний** без видимости для третьего лица. Решения из `SUMMARY.md` (зона, нет ученик↔ученик, журнал админа) нужны, но недостаточны.
- «Жалоба на сообщение» отнесена во вторую очередь. Без неё ребёнку некуда пожаловаться, а у платформы нет и повода открыть журнал доступа: журнал без повода никто не читает. Решение 1:1 канала между взрослым и ребёнком без кнопки жалобы и очереди модерации оставляет самый тяжёлый сценарий незакрытым.
- «Свой учитель» неоднозначен: ученик может состоять в нескольких группах разных владельцев (`user_groups`, `student_groups.owner_id` nullable). При смене владельца группы старый диалог становится «только чтение», создаётся новый, ученик видит раздвоенную историю; учитель, снятый с зоны, не должен писать, а доступ к старому диалогу у него пропадает или остаётся? Решение нужно, иначе поведение определит ветка кода.
- Правка 15 минут «с меткой» без хранения оригинала стирает улики; удаление ученика (`DELETE /api/users/:id`) каскадно сотрёт переписку (C13).
- Обмен контактами уводит разговор за пределы платформы. У пользователя в профиле уже есть `telegram`, `phone`, `email`: убедиться, что чат и справочник пользователей не раскрывают их ученику и учителю дополнительно, чем сейчас.
- **Часы тишины 21:00–09:00** определены как учительские с баннером для ученика. Если цель защитная (взрослый не пишет ребёнку ночью), баннера недостаточно: нужно ограничение **на отправку учителя** (или хотя бы на уведомления ученику). Если цель в отдыхе учителя, достаточно баннера и отложенных push. Это разные продукты. Реализационные ловушки: часовой пояс (в России 11 поясов, контейнер в UTC, колонки `users.created_at` и ряд других в схеме `timestamp` без пояса), вычисление в момент доставки, а не создания, перевод часов не нужен, но IANA-пояс нужен. Любое сравнение «сейчас» — только по часам БД и по полю пояса получателя.
- Фото: ребёнок может прислать неуместное изображение учителю и наоборот; у платформы нет автоматических проверок (решение пользователя), значит, единственная защита — жалоба + возможность администратору скрыть вложение.

**Как избежать.**
1. **Вынести кнопку «Пожаловаться» и очередь администратора в MVP V4-E** (на уровне CHAT-08: пункт меню у пузыря + запись `chat_reports` + экран в админке + скрытие сообщения администратором с сохранением оригинала). Это малый объём по сравнению с рисками. Решение пользователя нужно, потому что оно меняет «вторую очередь».
2. Метаданные без текста для администратора: число сообщений по учителям, ночные сообщения, диалоги с рекордным объёмом, первые сообщения учителя ученику (без чтения тел). Позволяет заметить аномалию без чтения.
3. Определить правило «чей учитель» в одном месте (политика, `direct_key` по паре) и описать смену владельца группы: диалог остаётся с прежним учителем в режиме «только чтение для обеих сторон, администратор видит», новый создаётся лениво.
4. Правка хранит версии: таблица `chat_message_versions` (шифрованное тело, `edited_at`), доступна администратору; клиентам отдаётся только текущая. Удаление мягкое.
5. Часы тишины: хранить IANA-пояс получателя (по умолчанию `Europe/Moscow`), вычислять на сервере по `now() AT TIME ZONE tz`; решение «баннер» против «ограничение» принять до V4-D. Тесты с подменой часов на границах 21:00, 09:00 и в день смены месяца.
6. Ссылки и контакты: отображать текст как есть, не превращать в кликабельные ссылки на внешние ресурсы без `rel="noopener noreferrer nofollow"` и без превью.

**Признаки.** Учитель получил доступ к ученику вне своих групп; жалоб нет, потому что пожаловаться некуда; у отредактированных сообщений нет истории; ночью идут уведомления ученику.
**Фаза:** V4-E (жалобы, модерация, версии правок, регламент), V4-D (часы тишины), V4-A (правило «чей учитель», политика). **Уверенность:** HIGH по логике, MEDIUM по юридическим формулировкам.
**Решение пользователя нужно:** жалоба в MVP; смысл часов тишины.

### C13. Хранение, удаление по запросу, 152-ФЗ, согласие 14–17 лет и жёсткое удаление пользователя

**Что идёт не так.**
- **Жёсткое удаление.** `DELETE /api/users/:id` (`routes/users/index.ts`, строка с `db.delete(users)`) выполняет жёсткое удаление; почти все внешние ключи схемы `ON DELETE CASCADE` или `SET NULL`. Если таблицы чата получат `REFERENCES users ON DELETE CASCADE`, администратор одним кликом сотрёт переписку, а **файлы на томе останутся** (каскада в файловой системе нет): сироты с чужими фото. Одновременно это нарушает хранение 6 мес./3 года, если сервис попадёт в реестр ОРИ.
- **Удаление по запросу и бэкапы.** Отзыв согласия: уничтожение в срок до 30 дней (MEDIUM, law.ru и сводки). Часовые бэкапы содержат удалённое. Сквозное «крипто-стирание» не работает: обёрнутые DEK лежат в тех же бэкапах. Нужна политика: срок ротации бэкапов и запись об этом в согласии/политике.
- **Согласие.** В схеме есть `users.birthdate` (nullable), но **нет поля согласия** и нет формы (поиск по коду пуст). Для детей до 14 согласие даёт родитель; для 14–17 источники расходятся (LOW). «Галочка при первом входе» в чат не доказывает ни факта согласия, ни кто его дал, ни версии текста.
- **Локализация.** Чат не должен стартовать, пока БД и файлы не в РФ. Поскольку v2.0 завершён переездом на Beget, это закрыто для чата; но вывод старой Supabase-копии из эксплуатации в v3.0 (последняя фаза) должен предшествовать включению чата в production: до подтверждённого удаления на старых провайдерах там могут лежать копии ПД.
- **Срок хранения фото 1 год** (v3.0) и срок хранения переписки/вложений чата не совпадают и не определены; задание удаления вложений по `expires_at` может удалить файл, который ещё нужен сообщению.

**Как избежать.**
- Таблицы чата **без каскада от `users`**: `ON DELETE RESTRICT` (или без FK и с проверкой в приложении); удаление пользователя, имеющего диалоги, запрещено (500 вместо тихой потери данных не годится: понятная ошибка 409), вместо него «деактивировать и анонимизировать» после срока хранения. Тест: попытка удаления пользователя с чатом → 409, файлы нетронуты.
- Процедура удаления по запросу: (1) закрыть диалоги (`archived_at`), (2) через срок, определённый юристом, удалить сообщения и файлы заданием, (3) запись в журнал, (4) документально зафиксировать окно бэкапов. Задание **не** использует `storage-reconcile` с удалением сирот для `chat/` (он знает только `topics/`).
- Согласие хранить как данные: `user_consents(user_id, kind='chat', version, given_at, given_by ('student'|'parent'), evidence)`; доступ к чату по наличию действующей записи. Возрастная ветка по `birthdate`; при пустой дате считать «нужен родитель». Формулировка и порядок получения согласия — вопрос юристу (Q5 из `SUMMARY.md`), не решение разработчика.
- Один срок хранения вложений: `expires_at = max(срок сообщения, срок политики)`; удаление вложения только вместе с сообщением по политике.
- До V4-E зафиксировать у клиента и юриста: оператор ПД, срок хранения переписки, нужен ли ОРИ-режим (6 мес./3 года), видят ли родители переписку.

**Признаки.** После удаления тестового ученика в томе остаются файлы чата; нет места, где фиксируется кто и когда дал согласие; не определён срок хранения.
**Фаза:** V4-A (внешние ключи, запрет каскада), V4-E (согласие, удаление, хранение). **Уверенность:** HIGH по коду, MEDIUM–LOW по правовым срокам (нужен юрист).

### C14. Фото: злоупотребление, рост диска, пик памяти на `sharp` и `multer`

**Что идёт не так.**
- Загрузки в проекте идут через `multer.memoryStorage()` (лимиты 5 МБ в `routes/docs/assets.ts`, `routes/tests/admin/assets.ts`, `routes/users/avatar.ts`) `[HIGH]`; по плану чат берёт 10 МБ × до 5 файлов. Класс из 30 учеников присылает фото одновременно: пик 30 × 50 МБ в буферах плюс `sharp` на 12-мегапиксельных кадрах (сотни МБ). В `app/server/src` нет настроек `limitInputPixels`, `sharp.concurrency`, `sharp.cache` `[HIGH]` (по умолчанию `limitInputPixels` ≈ 268 Мпикс: «бомба декомпрессии» допустима). API делит 6 ГБ с PostgreSQL, Next и Caddy.

Быстрая оценка: 150 учеников × 5 фото/день × ~0,4 МБ после пережатия ≈ 300 МБ/сутки ≈ 110 ГБ/год `[LOW, предположение для проверки на реальных данных]`. Квоты обязательны.
- Неприкреплённые вложения чистятся раз в сутки: между очисткой и сообщением ученик успевает залить 100 файлов.
- Раздача: `Cache-Control: private, immutable` + проверка членства; ссылка на фото в `blob`/`img` после выхода пользователя остаётся в кэше браузера на общем школьном ПК (`private` не очищается при выходе).

- Серверный `uploadImage` не вызывает `.rotate()` (замечание `UI.md` §3): фото ложатся боком; пересылка пикселей без метаданных приводит к тому, что ориентация теряется.
- Злоупотребление: неуместные изображения, фото с чужими лицами, картинки с текстом-оскорблением; автоматической проверки нет.

**Как избежать.**
- Общий лимитер для `sharp` (семафор 2 одновременных, `sharp.concurrency(2)`, `sharp.cache(false)`, `limitInputPixels` ≈ 40 Мпикс) и **один файл на запрос** загрузки (так двухшаговый поток уже устроен): память на запрос ≤ 10 МБ. Один пул для v3.0 и чата. Лимит нужен v3.0 (QR-загрузка с телефона) раньше, чем v4.0.
- Квоты: байты и число файлов на пользователя в сутки (например 30 файлов / 25 МБ), общий предел на чат, предел неприкреплённых (например 10 на пользователя), чистка неприкреплённых раз в час.
- Мониторинг диска: предупреждение при 70 % и 85 %, запас под WAL и бэкапы; чат отключает загрузку (503 с понятным текстом), когда свободно меньше порога, **до** того, как диск заполнится.
- `chat/` как отдельное пространство в `keys.ts`, тесты контейнмента на нём (контрактный набор адаптеров уже есть); `storage-reconcile` не трогает `chat/`.
- При выходе пользователя очищать кэши: у фото `Cache-Control: private, no-store` для вложений чата, если школьные ПК обычны (цена: повторная загрузка). Решение в V4-C; либо разрешить кэш и документировать остаточный риск.
- `.rotate()` в серверной обработке чата (обязательное требование из `UI.md` п. 5).
- Жалоба и скрытие вложения администратором (C12).

**Признаки.** Рост использования диска > 1 ГБ/сутки; всплески RSS API при загрузках; `ENOSPC` в логах PostgreSQL.
**Фаза:** лимитер и квоты: **v3.0**; чат-специфика V4-C. **Уверенность:** HIGH по коду, LOW по оценке объёма.

### C15. Память на поток и ресурсы процесса

**Что идёт не так.** Оценка `TRANSPORT-STORAGE.md` (единицы–десятки МБ на сотни потоков) верна по порядку величины (MEDIUM, оценка), но настоящие проблемы не в памяти соединения.
- Таймер на поток (`setInterval` heartbeat, таймер `exp`, таймер перепроверки сессии) × 450 потоков = тысячи таймеров и синхронные выбросы раз в 20 с.
- Реестр потоков хранит `res`; без `req.on('close')` и `res.on('error')` мёртвые ответы остаются в реестре, запись в разрушенный сокет бросает `EPIPE`/`ERR_STREAM_WRITE_AFTER_END`.
- Медленный клиент (туннель, метро): `res.write` возвращает `false`, `res.writableLength` растёт, буфер на поток неограничен.
- `pino-http` создаёт дочерний логгер на каждый запрос и пишет лог при завершении: поток живёт часами, лог один раз; зато строка лога потока при падении содержит заголовки (cookie уже вычищены через `LOG_REDACT_PATHS` `[HIGH]`, но тело сообщения и текст ошибок валидации проверить).
- Перепроверка сессий по 1 запросу на поток в минуту: 450 запросов/мин на пул из 20 соединений ощутимо.
- Глобальный `express.json({ limit: '10mb' })` применяется до маршрутов чата; сообщение ≤ 4000 символов, но предел парсера остаётся 10 МБ.

**Как избежать.**
- Один общий таймер раз в секунду, обходящий реестр (heartbeat и `exp` по полю `nextAt`), без таймера на поток; `exp` отсортирован.
- Перепроверка сессий **одним запросом** `WHERE id = ANY($1)` на все потоки раз в 30–60 с.
- Очистка: `req.on('close')`, `res.on('close')`, `res.on('error')`; сброс потока при `writableLength > 64 КБ`; счётчик потоков в `/healthz`-метрике и в логе раз в минуту.
- Предел 5 потоков на пользователя (новое вытесняет старое), 1000 на процесс.
- Маршруты чата: `express.json({ limit: '16kb' })` на роутере **до** глобального парсера невозможно (он уже сработал в `app.ts`), поэтому ограничить размер проверкой `Content-Length` и zod-схемой, либо зарегистрировать парсер маршрутов чата раньше глобального. Решить в V4-A.
- Лимит памяти контейнера API в Compose (`mem_limit`), чтобы утечка потока не убила PostgreSQL соседа по OOM.

**Признаки.** RSS API растёт монотонно между деплоями; `EPIPE` в логах; размер реестра потоков не падает при закрытии вкладок.
**Фаза:** V4-B. **Уверенность:** MEDIUM.

### C16. Тестирование SSE и двух участников в Playwright и Vitest

**Что идёт не так (с учётом текущей настройки `e2e/playwright.config.ts`).**
- `workers: 1`, `fullyParallel: false`, `retries: 0`; `auth.setup.ts` один раз входит каждым аккаунтом и сохраняет `storageState` `[HIGH]`. Два участника — это **два `BrowserContext`** с разными `storageState` в одном тесте; общий сид и последовательный порядок тестов означают, что сообщения и счётчики **накапливаются** между тестами, и проверки непрочитанного и порядка ломаются от соседних тестов.
- В e2e `ACCESS_TOKEN_EXPIRES_SEC: 3600`: ветка `reauth` не выполняется никогда, а минимум в `parseAccessTokenTtl` равен 60 с (меньше нельзя), то есть живой таймаут в e2e не получить без ожидания минуты.
- Цепочка e2e = `next start` с rewrites по HTTP/1.1 без Caddy: не покажет ни прод-буферизацию, ни HTTP/2.
- Поток держит запрос открытым: `waitForLoadState('networkidle')` не наступает; `page.waitForTimeout` приводит к хрупким тестам; тест «событие пришло < 2 с» сравнивает время на медленном CI.
- Проект `chromium-mobile` (Pixel 7) гоняет те же тесты: удвоение потоков и времени. WebKit/iOS Safari в репозитории не установлен (`playwright install chromium`).
- Рестарт API посреди e2e невозможен (процесс поднимает `webServer`).
- Симуляция обрыва: `context.setOffline(true)` не всегда рвёт уже открытое потоковое соединение (LOW, проверить спайком).

**Как избежать.**
- **Уровни.** Семантика потока (авторизация, `exp`, отзыв, членство, `tick`, порядок, дубли, откат транзакции, шторм после перезапуска) тестируется на сервере интеграционными тестами Vitest: настоящий `http` + `fetch` с `AbortController` читает поток, часы подменяются, БД `test_*` через `scripts/with-test-db.mjs`. Они быстрее и детерминированнее. Playwright — только 4–5 сквозных сценариев: A пишет → B видит < 2 с; обрыв через `page.route('**/api/chat/stream', r => r.abort())` → деградация на опрос → восстановление; скрытие/показ вкладки → `sync`; фото; чат на 375 px.
- Помощник `createChatPair()` в `e2e/fixtures`: свежие пользователь-учитель и пользователь-ученик в зоне (по образцу `seedTeacherZoneWorld` из `test-support`), своя пара на тест; никакого общего диалога между тестами.
- Утверждения: `expect.poll(...)` с потолком 2–5 с, никаких `waitForTimeout`, никаких `networkidle` на страницах чата.
- Тест `reauth`: вариант запуска API с `ACCESS_TOKEN_EXPIRES_SEC=60` в отдельном проекте (раз в прогон, один тест) либо подмена времени на сервере в интеграционном тесте (предпочтительно).
- Смоук-проверка прод-цепочки через Caddy: в runbook выкатки (`curl -N`), потому что e2e её не повторяет.
- Живая приёмка: iPhone (Safari), Android (Chrome), школьный ПК: чек-лист «поток после сна, после смены сети, после блокировки экрана, из bfcache».
- Правило тестов проекта: без хрупких охранников и без юнитов на повторы; для чата юнит-таблицы оправданы только в сериализаторе прав зрителя (C8) и в вычислении часов тишины.

**Признаки.** Тест чата зелёный локально и красный в CI; тесты зависят от порядка; `networkidle` таймаут.
**Фаза:** V4-B (серверные тесты), V4-F (e2e и приёмка). **Уверенность:** HIGH по настройке, MEDIUM по поведению Playwright.

### C17. Миграции и откат

**Что идёт не так.**
- Схема чата аддитивна, но откат автодеплоя («вернуть предыдущий digest», `beget-migration.md`) возвращает **код**, а не БД. Старый API при записях в журнал v3.0 встречает событие нового вида `chat.message` и либо падает при разборе, либо показывает пустую строку.
- KEK-самопроверка (C10) без плана: откат на digest без модуля чата работает, но откат на digest **с** модулем при потерянном секрете валит API.
- Правило проекта: применённые миграции не редактируются, `drop/recreate` — STOP. Ошибка в черновой схеме чата (например, лишний `tsvector search` в `TRANSPORT-STORAGE.md` §6.1, который решением пользователя исключён; `kind IN ('direct','group')` вместо канала объявлений) закрепляется в 0026+ навсегда. `GENERATED ... STORED tsvector` по зашифрованному `body` бессмыслен и раскрывает слова.
- Первичные ключи: PG 17 без `uuidv7()`; UUIDv7 генерирует приложение. Несколько реализаций (клиент, сервер, скрипт) → непредсказуемый порядок и дубликаты.
- `UNIQUE (sender_id, client_message_id)` при `sender_id NULL` (системные сообщения) не защищает: в PostgreSQL `NULL` не конфликтуют.
- Таймстемпы: в схеме проекта много `timestamp` без пояса; в чате использовать `timestamptz` (в наброске так и есть) и не смешивать при JOIN с `users.created_at`.
- `drizzle/meta` и журнал миграций: добавление через `yarn` скрипт проекта и `migrations-manifest.json`; `yarn verify` проверяет цепочку.

**Как избежать.**
- Миграции чата только аддитивные; одна миграция на смысловой шаг (журнал уведомлений видов, ключи, чаты, сообщения, вложения, журнал доступа, жалобы). Схему утвердить на этапе discuss V4-A **после** решения по таблице выше, до первого `drizzle-kit generate`.
- Читатель журнала v3.0 терпим к неизвестным видам (действие для v3.0). Тест: вставить в журнал строку неизвестного вида, API и интерфейс не падают.
- Откат кода без отката схемы: описать в runbook «выключатель чата» (`CHAT_ENABLED=0`): модуль не монтирует маршруты, вкладка скрыта, данные остаются; включение требует успешной самопроверки KEK.
- Один генератор UUIDv7 в `packages/*` или в `app/server/src/lib`, без клиентской генерации идентификаторов сообщений (клиент генерирует только `clientMessageId`).
- Для системных сообщений уникальность по `(chat_id, kind, ref)` или отдельная таблица событий.

**Признаки.** Откат даёт 500 на страницах уведомлений; в схеме остаётся неиспользуемый столбец или индекс, который нельзя убрать.
**Фаза:** V4-A. **Уверенность:** HIGH.

## Умеренные ловушки

### M1. «Ученик пишет только своему учителю» и множественные группы
Ученик в двух группах у двух владельцев получит два диалога; владелец группы `NULL` (`releaseZone`) означает «нет учителя». **Предотвращение:** правило выводится только из `canManageStudent`-эквивалента политики, отдельный `chat-policy` в шве `services/access-policy`, табличный тест по матрице «ученик × группы × владельцы» (как матрицы 07.1). **Фаза:** V4-A.

### M2. Лента и прокрутка на iOS
История вверх без прыжка не проверена на iPhone (`UI.md` §6 п. 2). **Предотвращение:** ранний спайк V4-F на живом устройстве до верстки остальных экранов; запасной путь `use-stick-to-bottom` + ручная компенсация `scrollTop`. Версия `@shadcn/react` без `^`.

### M3. Рост Tailwind и общая вёрстка
Обновление Tailwind до 4.3 может затронуть существующие страницы (`UI.md`). **Предотвращение:** отдельный коммит с `yarn verify` и визуальной проверкой до V4-F; не смешивать с логикой чата. Форматирование отдельным коммитом (правило проекта).

### M4. Объявления группе и ответы
Объявление учителя группе без ответов: ученик отвечает «в личный диалог». Если объявление создаётся как сообщение в каждом личном диалоге, N записей и N событий журнала на одно объявление; редактирование и удаление объявления должны быть согласованы. **Предотвращение:** отдельная сущность `chat_announcements` (один текст, адресаты по группе на момент чтения), а не копии сообщений; уведомление одной строкой на получателя (C9).

### M5. Карточка «обсудить попытку»
В сообщении лежит `{type, id}`, право проверяется при открытии. Ловушка: список чатов и поток показывают название теста и балл попытки в превью без проверки права зрителя; учитель, потерявший зону, видит заголовки. **Предотвращение:** сериализатор карточки проверяет право на каждый ответ; не копировать данные попытки в сообщение (уже решено), и не включать их в превью и журнал.

### M6. Лимиты и модерация текста
Длина ~4000 символов, частота и размер: лимитер в памяти по IP сбрасывается при деплое и ошибочно общий в школе (C3). **Предотвращение:** лимиты по `user id` в БД или в памяти с учётом сброса; для записи в чат 20 сообщений/мин/пользователь, пакетные запросы `sync` ограничены отдельно.

### M7. Dev, CI и данные
Dev-БД на домашнем сервере, e2e и тесты используют `test_*` базы (охрана `assertTestDatabaseUrl`). Чат-таблицы не должны попасть в дампы для dev; тестовый KEK генерируется на лету, а не хранится в репозитории. **Фаза:** V4-A.

### M8. Заголовки CSP и ссылки на файлы
Next и API отдают разные CSP (`helmet` в `app.ts`: `connect-src 'self'`, `img-src ... blob: https:`). Лайтбокс и `blob:`-превью проходят; новая библиотека, подгружающая шрифты или worker-ы, ломается молча. **Предотвращение:** в e2e чата включить проверку консоли на `Content Security Policy` нарушения.

## Мелкие ловушки

- Заголовок вкладки с числом «(3)» без сброса при выходе; на общем ПК остаётся следующему пользователю. Сброс при `logout` и очистка локальных данных (CHAT-11).
- Звук и браузерные уведомления (не push) без запроса разрешения: не добавлять до v5.0.
- `Intl`/`toLocaleString` с локалью по умолчанию контейнера: время сообщений показывать по поясу пользователя, не сервера.
- Эмодзи таблица в бандле редактора вопросов (`yarn editor:budget`): не тянуть её в чат; бюджет бандла маршрутов чата завести так же.
- Ссылки `/chats/{chatId}?m={messageId}`: при отсутствии права открывать нейтральную страницу «нет доступа», не раскрывая существование чата.
- Миграции чата идут после миграций v3.0 в общей цепочке `app/server/drizzle` и `migrations-manifest.json`; номера не резервировать заранее.

## «Выглядит готовым, но нет»

- [ ] **Поток:** работает на `localhost`, не проверен через Caddy → проверить `curl -N` на прод-цепочке, первое событие < 2 с, heartbeat < 25 с.
- [ ] **Деплой:** потоки не переживают рестарт → измерить восстановление 400 клиентов после перезапуска контейнера, ошибок пула нет.
- [ ] **Refresh:** переподключение вызывает refresh → убедиться, что сначала переподключение, а refresh только после 401, один владелец на браузер.
- [ ] **Выход:** отзыв сессии закрывает поток → тест с отзывом внутри внешней транзакции и откатом.
- [ ] **Зона:** вывод ученика из зоны → доставка прекращается ≤ 60 с, чат «только чтение».
- [ ] **Непрочитанное:** сумма в шапке = журнал + чаты без дублей → сверить числа в разных местах интерфейса.
- [ ] **Прочитано:** ученик не получает `last_read_seq` учителя нигде (`sync`, `changes`, поток).
- [ ] **Идемпотентность:** повтор с другим телом → 409, а не молчаливый 200.
- [ ] **Шифрование:** старт без KEK падает; `pg_dump` не содержит маркерной строки; восстановление с офлайн-KEK прошло человеком.
- [ ] **Журнал:** каждый маршрут, возвращающий чужой текст/файл, пишет запись до ответа; таблица неизменяема.
- [ ] **Удаление:** удаление пользователя с диалогом → 409; файлы чата удаляются заданием по политике, не сиротами.
- [ ] **Фото:** семафор `sharp`, `limitInputPixels`, квоты, порог диска; ориентация корректна.
- [ ] **Жалоба:** кнопка есть, очередь администратора есть, скрытие сохраняет оригинал.
- [ ] **Согласие:** запись в БД, кто дал и какая версия; без неё чат закрыт.
- [ ] **Часы тишины:** границы 21:00/09:00 по поясу получателя, не по поясу контейнера.
- [ ] **iPhone/Android:** сон телефона, смена сети, bfcache: сообщения на месте после возврата.
- [ ] **Откат:** журнал v3.0 терпим к неизвестным видам, выключатель `CHAT_ENABLED=0` описан и проверен.

## Действия для v3.0 (планирование идёт сейчас)

Эти пункты стоят дешевле сейчас, чем в v4.0, и не требуют решений по чату:
1. **Исправить `gracefulShutdown`** (`app/server/src/index.ts`): ждать активные запросы, затем закрывать пул, потолок и `stop_grace_period` согласованы (уже записано в плане переезда, но не сделано) (C3).
2. **Журнал уведомлений**: вид события как `text` без `CHECK`/enum, читатель терпим к неизвестным видам; одна строка на `(получатель, объект)` с `ref_seq`/версией и `read_at`; `deliver_after` и канал в `notification_delivery` (C9, C17).
3. **Пайплайн фото**: общий семафор для `sharp`, `limitInputPixels`, один файл на запрос, `.rotate()`, квоты по пользователю, порог диска, чистка неприкреплённых (C14).
4. **Опрос уведомлений** с курсором `since`, а не `limit`, и паузой при скрытой вкладке; тот же клиентский паттерн поток/опрос затем переиспользует чат (C5).
5. **Модуль сессии**: владелец refresh на браузер через `navigator.locks` (C1). Можно сделать в техдолге v3.0, не дожидаясь чата.
6. Пространство ключей хранилища: добавить расширяемость `STORAGE_NAMESPACES` с тестами контейнмента (C14).
7. Завершение Supabase/Vercel (последняя фаза v3.0) **до** включения чата в production (C13).

## Решения, которые стоит подтвердить у пользователя до V4-A/V4-D

Это уточнения прежних решений, не пересмотр:
1. **Жалоба на сообщение и очередь администратора в MVP** (сейчас «вторая очередь»), причина в C12.
2. **Часы тишины**: только баннер и отложенные push, либо ограничение отправки учителем ночью (защитная цель).
3. **Р2**: поток на вкладку принять, но владельца refresh на браузер сделать обязательным; ведущая вкладка для потока остаётся оптимизацией.
4. **Согласие 14–17**: хранить как данные в БД, без согласия чат закрыт; формулировку и порядок определяет юрист.
5. **История правок**: хранить зашифрованные версии для администратора.
6. **Правило смены владельца группы**: диалог остаётся с прежним учителем в режиме «только чтение», новый создаётся лениво.

## Пробелы

- Поведение iOS Safari/Chrome с `fetch`-потоками и bfcache проверялось по вторичным источникам; нужен спайк на устройствах (LOW–MEDIUM).
- Школьные фильтры и операторы: поведение долгих ответов не исследовано, требует приёмки в реальной сети (LOW).
- Передача `Cookie` в запросах из очереди соединений браузера при насыщении пула HTTP/1.1 (устаревший refresh): гипотеза, не проверена (LOW).
- Размер оценки диска (фото в день) нужно заменить измерением на v3.0.
- Правовая часть (срок хранения, согласие 14–17, режим ОРИ) требует юриста; здесь только инженерные последствия.
- Не проверялся реальный Caddyfile на сервере (он вне репозитория): `write_timeout`, HTTP/3, `lb_try_duration` проверить в runbook.
