# Stack Research: открытые задания с фото и ручной проверкой (v3.0)

**Домен:** загрузка фото-ответов (десктоп и телефон по QR без входа), ручная проверка, хранение, уведомления в кабинете
**Исследовано:** 2026-10-06
**Общая уверенность:** HIGH по sharp/HEIC, Caddy, паттерну токенов и сценариям iOS Safari (проверено запуском и первоисточниками), MEDIUM по поведению Android-браузеров с HEIC и по react-zoom-pan-pinch 4.x (новая мажорная ветка, в браузере не запускалась)
**Уровни:** HIGH — запуск в этом репозитории или официальная документация; MEDIUM — вторичный источник или одна проверка на синтетических данных; LOW — оценка без проверки.

## Главный вывод

Новых серверных зависимостей нужно **одна, и то условная**: `heic-decode` (запасной путь для HEIC). Всё остальное закрывается тем, что уже стоит: `sharp` 0.35.5, `multer` 2.4.0, `file-type` 22, `node:crypto`, порт хранилища, `swr` в web. В web добавляются две небольшие библиотеки: `qrcode.react` (QR, 6,2 КБ gzip) и `react-zoom-pan-pinch` (просмотр фото, 14,5 КБ gzip, только на странице проверки, через `next/dynamic`). Сжатие на клиенте, ссылки-способности, плановая очистка и живое обновление пишутся на платформе без зависимостей.

Три факта, которые меняют проектирование (все проверены запуском в этом репозитории):

1. **Готовая сборка sharp 0.35.5 НЕ декодирует HEIC с iPhone.** `sharp.format.heif` объявлен (как AVIF), `metadata()` читает контейнер, но декодирование падает: `heif: Error while loading plugin: Support for this compression format has not been built in: HEVC (a suitable decoder plugin is libde265)`. Состав libvips: `heif 1.23.5`, `aom 3.15.1`, декодера libde265 в сборке нет. Документация sharp не упоминает HEIC вообще, заявлены JPEG, PNG, Ultra HDR, WebP, AVIF, TIFF, GIF, SVG.
2. **Без `autoOrient()` фото с iPhone уйдёт боком.** Sharp по умолчанию удаляет метаданные, включая EXIF-ориентацию, а пиксели при этом не поворачивает. Проверка: JPEG 400x200 с Orientation=6 без `autoOrient()` даёт WebP 400x200 (повернуть забыли), с `autoOrient()` даёт 200x400. GPS и EXIF в обоих случаях удалены. Существующий `services/assets/inline-images.ts` `autoOrient()` не вызывает: для картинок вопросов это нормально, для фото ответов нет.
3. **Секреты и доступ уже имеют готовый паттерн.** Приглашения (`app/server/src/routes/auth/invites.ts`): `randomBytes(24)`, в БД хранится `sha256` токена, публичный маршрут `/invite/[token]` в вебе, путь внесён в `PUBLIC_PREFIXES` файла `app/web/proxy.ts`. QR-ссылка на загрузку с телефона повторяет этот паттерн один в один.

## 1. QR-код

**Выбор: `qrcode.react` 4.2.0, компонент `QRCodeSVG`.** Кодирует URL вида `https://<домен>/u/<token>`. Токен 32 байта в base64url — 43 символа, URL около 70 символов, QR версии 5-6 при уровне коррекции M: хорошо сканируется с экрана ноутбука.

Альтернативы по размеру (измерено esbuild, gzip): `lean-qr` 2.7.4 — 4,2 КБ, `uqr` 0.1.3 — 4,2 КБ, `qrcode.react` — 6,2 КБ. Разница 2 КБ не стоит самописной обёртки под React, поэтому `qrcode.react`. Серверная генерация (`qrcode` 1.5.4) лишняя: добавляет зависимость и запрос, а QR всё равно рисуется из уже известной ссылки.

Требования к отображению (HIGH, из физики сканирования):
- Чёрные модули на белом фоне с тихой зоной не менее 4 модулей **всегда**, в том числе в тёмной теме. Инвертированный QR многие камеры не читают. Цвета не брать из токенов темы.
- Размер не меньше 160 px, `level="M"`, `marginSize={4}`.
- QR лежит на маршруте попытки, не на маршрутах редактора вопросов: `yarn editor:budget` его не проверяет. Размер всё равно держать в голове.

## 2. Фото с телефона: съёмка, HEIC, EXIF, сжатие, загрузка

### 2.1. Атрибуты поля выбора файла

Две кнопки на странице `/u/<token>`:
- «Сделать фото»: `<input type="file" accept="image/*" capture="environment">`.
- «Выбрать из галереи»: `<input type="file" accept="image/*" multiple>` без `capture`.

**`image/heic` в `accept` не добавлять.** Safari 17+ при таком `accept` превращает выбранные JPEG и PNG в HEIC (имя `tempXXXX.heic`, тип `image/heic`): ветка форума Apple 743049, воспроизводится у многих, исправления нет (MEDIUM, форум). Хватает `image/*`.

### 2.2. Что приходит с iOS (проверено по двум источникам)

- **iOS Safari** (и любой браузер на iOS, движок один) при любом значении `accept` отдаёт HEIC уже перекодированным в JPEG. Сторонний источник: Zenn, тест на iOS Safari 604.1 (MEDIUM, один тест, подтверждено обсуждением на Hacker News).
- **macOS Safari**: при `accept="image/*"` или пустом файл остаётся HEIC, при `accept="image/jpeg,..."` перекодируется в первый совместимый формат.

Итог: основной сценарий (iPhone, камера или галерея) HEIC на сервер не приносит. HEIC доходит только с macOS Safari при `image/*`, из «Файлов», с части Android-устройств и с десктопа Windows (MEDIUM, поведение Android-браузеров не проверялось, LOW).

### 2.3. Клиентский конвейер (до отправки)

1. `createImageBitmap(file, { imageOrientation: 'from-image' })` (запасной вариант: `HTMLImageElement` + `decode()`; Safari умеет показывать HEIC и сам, поэтому HEIC с macOS Safari декодируется этим же путём).
2. Отрисовка в canvas, длинная сторона 2560 px (меньше лимита canvas iOS в 16,7 МП), `toBlob('image/jpeg', 0.8)`.
3. Результат около 0,4-1,2 МБ вместо 3-6 МБ с камеры. EXIF и GPS с телефона не уходят вообще.
4. Если декодирование упало (формат неизвестен браузеру, нехватка памяти на 48 МП): отправить оригинал, лимит сервера примет до 10 МБ, сервер перекодирует.
5. Загрузка: один файл на запрос, `PUT /api/.../photos/:photoId`, где `photoId` — UUID, сгенерированный на клиенте (повтор после обрыва не создаёт дубль, как `clientAttemptId`). Повторы с экспоненциальной паузой. Прогресс по загрузке нужен только если захочется индикатора: у `fetch` нет события прогресса, тогда `XMLHttpRequest`, но не `axios`.

Ориентацию клиент не «чинит» вручную: canvas после `from-image` уже даёт верные пиксели, сервер на всякий случай всё равно вызывает `autoOrient()`.

### 2.4. Серверный конвейер (sharp)

```
multer (memoryStorage, files: 1, fileSize: 10 МБ)
  → fileTypeFromBuffer: разрешены image/jpeg, image/png, image/webp, (image/heic, image/heif — см. 2.5)
  → sharp(buf, { limitInputPixels: 100_000_000, failOn: 'error' })
       .autoOrient()
       .resize(2560, 2560, { fit: 'inside', withoutEnlargement: true })
       .webp({ quality: 82 })            // полный размер
  → миниатюра 400 px (.webp({ quality: 75 }))
  → storage().write(key, ..., { contentType: 'image/webp' })
```

- `limitInputPixels` по умолчанию 268 МП (документация sharp, HIGH): занижаем до 100 МП, чтобы «бомба» из сильно сжатого PNG не съела 6 ГБ VPS.
- Формат на выходе WebP, как у картинок вопросов (`images/<sha256>.webp`), единый формат в хранилище.
- Порог 2560 px / q82 подобран под читаемость рукописи при увеличении проверяющим; перед закреплением проверить на реальных фото тетрадных листов (LOW: числа ориентировочные, цель — читаемый почерк при минимуме байт).
- `sharp` по умолчанию обрабатывает параллельно по числу ядер; на 4 vCPU отдельной настройки не требуется.
- Время загрузки фиксируется **сервером** (`uploaded_at timestamptz default now()`), а не EXIF и не клиентом: это «время загрузки каждой фото» для проверяющего.

### 2.5. HEIC на сервере: выбор варианта

| Вариант | Деплой | Решение |
|---------|--------|---------|
| A. Не принимать HEIC, отвечать 415 с понятным текстом | Ничего | **Минимум для первой фазы.** Закрывает iOS-сценарий целиком (см. 2.2). |
| B. `heic-decode` 2.1.0 (WASM libheif-js) → `sharp(raw)` | Только npm-пакет, без правки образа | **Рекомендуемый запасной путь**, включается, если 415 по HEIC появятся в логах или заранее по решению. |
| C. Своя сборка libvips с libde265 (`SHARP_FORCE_GLOBAL_LIBVIPS`) | Правка Docker-образа, сборка sharp из исходников, на Alpine и Debian по-разному | Не брать: образ не лежит в репозитории, патентные условия HEVC, лишний риск выкатки. |
| D. `heic-to` в браузере (WASM libheif, LGPL-3.0) | Бандл 3,2 МБ | Не брать: тяжело для телефона на медленной сети, а iOS и Safari уже перекодируют сами. |
| E. `heic2any` 0.0.4 | — | Не брать: последний релиз 2023-03, не обновляется. |

Проверка варианта B на этой машине (sharp 0.35.5, heic-decode 2.1.0, libheif-js 1.23.5):

```js
const { width, height, data } = await decode({ buffer })
await sharp(Buffer.from(data.buffer, data.byteOffset, data.byteLength), { raw: { width, height, channels: 4 } })
  .autoOrient().resize(2560, 2560, { fit: 'inside', withoutEnlargement: true }).webp({ quality: 82 }).toBuffer()
```

Результат для HEIC 4032x3024, 0,6 МБ (создан `sips`, не снимок iPhone): декодирование 255 мс, всё вместе 440 мс, RSS процесса 307 МБ (MEDIUM: синтетическое содержимое, реальный снимок iPhone с сеткой тайлов декодируется заметно дольше, ориентировочно 1-3 с и 200-400 МБ пика: LOW). Выводы для проектирования: HEIC обрабатывать **не более одного одновременно** (простая очередь `p-limit`-подобная на промисе, без пакета), лимит файла 10 МБ, `limitInputPixels` тот же. Лицензия: `libheif-js` LGPL-3.0, используется на сервере как зависимость npm и не распространяется пользователям, для закрытой платформы это допустимо (оценка, не юридическая консультация: LOW).

HEIC и ориентация: libheif применяет трансформации контейнера (`irot`, `imir`) при декодировании, поэтому `autoOrient()` после `heic-decode` безвреден, но основную работу делает декодер (MEDIUM, проверить на настоящем снимке).

## 3. Живое обновление «телефон → страница на ПК»

**Выбор для v3.0: короткий опрос через SWR, SSE откладывается до v4.0.**

Реализация:
- `GET /api/attempts/:attemptId/questions/:questionId/photos` возвращает список и `revision` (счётчик или `max(updated_at)`). Клиент шлёт `If-None-Match`, сервер отвечает 304 без тела.
- `useSWR(key, fetcher, { refreshInterval: 2500, refreshWhenHidden: false, revalidateOnFocus: true, revalidateOnReconnect: true })`, опрос включён только пока открыта панель QR (то есть пока ссылка живёт).
- Нагрузка: до пары десятков одновременно открытых панелей, один индексный запрос на опрос. Для 31 пользователя пренебрежимо.

Почему не SSE сейчас (решение, с которым можно не согласиться, поэтому причины):
- Это был бы **первый SSE-канал в репозитории**. Из `.planning/research/chat/TRANSPORT-STORAGE.md` §3.1: нужен полный цикл авторизации потока (access-токен живёт 15 минут, переподключение по `reauth`, отзыв сессий, heartbeat). Это отдельная задача на несколько планов, а выгода здесь — выигрыш в 1-2 секунды.
- В том же документе §6.3: **источником правды всегда остаётся запрос `sync`, а поток только будит клиента**. Эндпоинт списка с `revision` и есть этот `sync`. Когда в v4.0 появится шина событий, SSE надстраивается над ним без переделки: опрос превращается в запасной режим при недоступном потоке (это же рекомендует документ про чаты).
- Проверка «SSE через Next rewrites в `yarn dev`» в чат-исследовании осталась открытой и здесь не закрыта.
- Телефон: Safari и фоновые вкладки рвут долгие соединения. Опрос с возобновлением по `visibilitychange` и `online` переживает это без особой логики.

Что сделать сейчас, чтобы позже не переделывать: публиковать события журнала уведомлений **только после COMMIT** и через узкий интерфейс (`publish`/`subscribe` за модулем), даже если подписчика пока нет.

Проверено для будущего SSE (HIGH, документация Caddy): `reverse_proxy` сбрасывает ответы с `Content-Type: text/event-stream` немедленно, независимо от `flush_interval`; `encode` не задерживает SSE-ответы. Пакета `compression` в API нет. Дополнительной настройки Caddy не потребуется. Файла Caddy в репозитории нет, он живёт на сервере.

Уведомления в кабинете: журнал событий читается обычным запросом при открытии кабинета и по `revalidateOnFocus`. Живой канал для них в v3.0 не нужен.

## 4. Ссылки-способности для загрузки без входа

**Выбор: непрозрачный случайный токен + строка в БД, не JWT.**

Таблица (набросок, не миграция): `attempt_upload_links(id, attempt_id, question_id, token_hash, expires_at, revoked_at, created_at)`.

- Токен: `randomBytes(32).toString('base64url')`, в БД `sha256` (hex), как в `invites.ts`. Показывается один раз внутри URL, который кодируется в QR. Для одного вопроса одной попытки активна одна ссылка: повторная выдача отзывает прежнюю.
- Маршрут в вебе: `/u/[token]`, префикс `/u` добавить в `PUBLIC_PREFIXES` в `app/web/proxy.ts` (так сделан `/invite`). Страница отдаёт заголовок `Referrer-Policy: no-referrer`, внешних ресурсов не грузит.
- API: отдельный middleware `uploadTokenRequired()`, **не `sessionRequired`**. Он ищет строку по `sha256(token)`, проверяет `revoked_at IS NULL` и `expires_at > now()` по часам БД, кладёт в `req` область `{ attemptId, questionId }`. Все запросы в обработчиках берут `attemptId` и `questionId` **только из этой области**, а не из пути и тела. Токен передаётся в заголовке (`X-Upload-Token`), чтобы не попадал в логи API запросами к самому API.
- Область прав: добавить фото, удалить своё фото этого вопроса, прочитать миниатюры этого же вопроса. Ничего больше. Отдельные маршруты, отдельные тесты «токен не читает чужое» (охранный тест рядом с инвентарём маршрутов, как в 07.1).
- Срок: `expires_at` = конец окна загрузки (дедлайн таймера + окно, заданное автором теста). Он проверяется на каждом запросе по текущей БД, а не зашит в токен. Это даёт отзыв по текущему состоянию (принцип ADR 0001): повторная выдача QR, сдача попытки, отзыв назначения, блокировка ученика.
- Ограничение частоты: уже существующий `rateLimiter({ keyPrefix, clientKey })`, ключ по хешу токена плюс IP. Лимит числа фото (5) проверять в той же транзакции, что вставка, с блокировкой строки ответа, иначе две параллельные загрузки обойдут лимит.
- Почему не JWT (`jsonwebtoken` уже есть): нельзя отозвать до `exp`, срок окна зашит при выдаче, URL длиннее, значит QR плотнее и хуже сканируется.
- Логи: токен в пути страницы `/u/<token>` попадёт в журнал доступа Caddy и Next, если он включён. Токен живёт не дольше окна и даёт право только добавлять фото к одному вопросу, риск принимаем, но в журнале Caddy путь `/u/*` лучше не писать (проверить на сервере).

## 5. Хранение и раздача фото ответов

- В `STORAGE_NAMESPACES` (`services/storage/keys.ts`: `images`, `topics`, `avatars`) добавить новое пространство, например `answers`. Ключ: `answers/<attemptId>/<questionId>/<photoId>/{full,thumb}.webp`.
- **Это важнейшая точка интеграции.** `isServableImageKey` — белый список (`images/`, `avatars/`, `topics/.../assets`), и общий прокси `/api/docs/assets/proxy` (требует только сессию, без проверки владельца) отдаёт любому вошедшему такие ключи. Новое пространство в список **не добавлять**: фото отдаются только отдельным маршрутом с проверкой владельца попытки или `canReviewAttempt` (шов `services/access-policy/`). Тест: любой залогиненный пользователь, запрашивающий `answers/...` через прокси, получает отказ.
- Порт хранилища (`write/read/exists/remove/copy/list`) достаточен. Presigned-ссылок на локальном томе нет и не нужно. Скрипт `storage:reconcile` научить пространству `answers` (сироты).
- Заголовки раздачи: `Cache-Control: private, max-age=31536000, immutable` (ключ неизменяем), `X-Content-Type-Options: nosniff`.
- Квоты: лимит 5 фото на ответ, 10 МБ на файл, rate limit на загрузку.

## 6. Просмотрщик фото (масштаб и поворот)

**Выбор: `react-zoom-pan-pinch` 4.2.0 + поворот CSS-преобразованием обёртки + `@radix-ui/react-dialog` (уже есть) для полноэкранного режима.**

- Масштаб, перетаскивание, щипок, двойной тап, колесо мыши — готовая библиотека. Это основная работа и основная сложность жестов.
- Поворот на 90 градусов: состояние `rotation` в компоненте, `transform: rotate(...)` на элементе-потомке. Библиотека собственного поворота не имеет (в README слова rotate нет, проверено). **Риск:** поворот потомка может нарушить расчёт границ панорамирования; решение: после поворота пересчитать `centerView`/`resetTransform`, либо поворачивать внешнюю обёртку, а библиотеке отдавать уже повёрнутый блок. Подтвердить в браузере на фазе просмотрщика (LOW).
- Поворот только для просмотра, в данных не сохраняется.
- `yet-another-react-lightbox` 3.32.2 (плагин Zoom, 15,1 КБ gzip): поворота тоже нет, и он тянет собственную модальную оболочку, не нужную рядом с Radix Dialog.
- Нативная реализация на Pointer Events и `motion` (уже есть в web) возможна, но щипок, границы и инерция — это 150+ строк с багами на тач-экранах. Не оправдано.
- Загружать через `next/dynamic` с `ssr: false` только на странице проверки: 14,5 КБ gzip не попадают в первый JS остальных маршрутов.

## 7. Плановая очистка (срок хранения фото 1 год)

Cron и воркера в репозитории нет (проверено: нет `node-cron`, нет цикла фоновых задач, кроме `setInterval` в `middleware/rateLimiter.ts`). **Выбор: функция очистки + запуск таймером в процессе API, без зависимостей.**

- Строка фото получает `expires_at` (по умолчанию `created_at + 1 год`, считается при загрузке). Хранить именно срок, а не вычислять по `created_at`: срок можно будет продлить для спорных работ.
- Функция `runRetention()` в `services/…`: пачками по 100 строк `WHERE expires_at < now()` (и сироты: загружено, но не привязано к ответу, старше 24 ч, как в §7 чат-исследования) → `storage().remove(keys)` → удаление строк. Сначала файлы, потом строки: если удаление файла упало, строка останется, и следующий запуск повторит (удаление отсутствующего ключа безопасно). Журналировать счётчики через `pino`.
- Запуск: из `app/server/src/index.ts` (единственная точка входа процесса; serverless-обёртка `api/` для Vercel таймеры не запускает и до удаления Vercel не нужна). Интервал 1 час, первый запуск через несколько минут после старта.
- Защита от двойного запуска при выкатке с двумя контейнерами: `SELECT pg_try_advisory_xact_lock(<константа>)` внутри транзакции пачки. Использовать **именно транзакционную** версию: сессионная блокировка с пулом соединений `pg` может сняться не на том соединении.
- `gracefulShutdown` в `index.ts` должен остановить таймер (`clearInterval`) до `pgPool.end()`.
- Ту же функцию обернуть скриптом `retention:run` в `app/server/src/scripts/` по образцу `storage:reconcile`: запуск вручную и возможность перейти на cron хоста (`docker compose run`), если понадобится.
- Этот же таймер потом обслуживает воркер outbox уведомлений и чаты (v4.0): место под него закладываем сразу как «модуль фоновых задач», но без внешнего планировщика.

Не брать: `pg-boss` 12.x (MIT, очередь на PostgreSQL: целый слой таблиц и воркеров ради одного суточного задания), `node-cron` 4.6.0 и `croner` 10.0.1 (оба рабочие, но нужны только если появятся cron-выражения; суточный интервал считается таймером). Если cron-выражения понадобятся, брать `croner` (без зависимостей, релиз 2026-10-02).

## Рассмотренные альтернативы

| Рекомендовано | Альтернатива | Когда альтернатива лучше |
|---------------|--------------|--------------------------|
| Опрос через SWR | SSE на шине в памяти | Когда в v4.0 появится канал чатов: тогда фото-событие станет одним из потребителей, опрос остаётся запасным |
| Непрозрачный токен в БД | JWT (`jsonwebtoken`) | Только если отзыв до срока не нужен и БД нельзя трогать; у нас нужен |
| Нативный canvas | `compressorjs` 1.4.0 | Если на реальных телефонах canvas-путь даст сбои (нехватка памяти на 48 МП, старые iOS) |
| `qrcode.react` | `lean-qr` 2.7.4, `uqr` 0.1.3 | Если каждый килобайт на странице попытки критичен (разница 2 КБ) |
| `react-zoom-pan-pinch` | `yet-another-react-lightbox` | Если нужна галерея с листанием и миниатюрами; поворота нет и там |
| Таймер + advisory lock | `croner` 10.0.1 | Когда понадобятся cron-выражения, а не фиксированный интервал |
| `heic-decode` (WASM) | Сборка libvips с libde265 | Практически никогда на этом деплое: образ вне репозитория, HEVC под патентами |

## Варианты по условиям

**Если в журналах API появляются 415 по HEIC (macOS Safari, Android, Windows):**
- включить вариант B (`heic-decode`), очередь по одному, лимит 10 МБ.

**Если на реальных телефонах canvas падает на больших снимках:**
- уменьшать через `createImageBitmap(file, { resizeWidth, resizeHeight })` (поддержку на целевых iOS проверить), либо взять `compressorjs`.

**Если ссылке нужна совместимость с мессенджерами и предпросмотром:**
- у страницы `/u/[token]` отключить индексацию и предпросмотр (`noindex`, `Referrer-Policy`), токен в пути оставить как у `/invite/[token]`.

**Если решат делать живой канал уже в v3.0:**
- взять SSE из чат-исследования целиком (шина после COMMIT, цикл авторизации §3.1), а эндпоинт списка с `revision` оставить запасным.
