# Phase 9 — UI Design Contract

> Узкий контракт на поверхности web, которые фаза 9 меняет в видимом тексте и поведении: все читатели результата попытки учат состояние «на проверке» до того, как такая попытка может появиться (RES-03); фильтр «Проверка» и карточка «На проверке: N» в списке попыток (RES-04, D-09, D-10); предел длины ответа и тексты отказов сдачи (RES-05, D-06…D-08); тип `open` не должен попасть в админские настройки в сломанном или включаемом виде (OPEN-02). Фаза не вводит новых цветов, токенов, npm-пакетов и компонентов `components/ui`.
>
> Решения пользователя из `09-CONTEXT.md` (D-01…D-14) обязательны. Там, где CONTEXT оставил выбор («Claude's Discretion»), выбрано рекомендованное, согласованное с существующим интерфейсом, и помечено **[авто]**. Исходное состояние кода — ветка `dev`, коммит `1962edd`.
>
> Что подтверждено чтением кода и меняет контракт:
> 1. `total_points` попытки включает 3 балла за каждый открытый вопрос (`research/ARCHITECTURE.md`, раздел хранения результата). Поэтому пара `earnedPoints / totalPoints` у попытки на проверке не равна «авто X из Y» из D-01. Нужна отдельная пара автобаллов (раздел «Данные для интерфейса»).

Оба экрана — экраны проверяющего, ученик их не видит. Раздел «Кто что видит» объясняет, какой текст из D-01 и D-02 стоит на каждом экране.

## Данные для интерфейса

Контракт описывает, что должно прийти в web. Имена полей — рабочие, смысл фиксирован; окончательные имена — решение планировщика серверной части.

| Поле | Тип | Смысл |
|------|-----|-------|
| `reviewStatus` | `'none' \| 'pending' \| 'graded'` | `none` — открытых вопросов нет (весь существующий массив); `pending` — есть непроверенный открытый ответ; `graded` — все открытые ответы оценены |
| `scorePercentage` | `number \| null` | итог; `null` ровно при `pending` |
| `passed` | `boolean \| null` | итог; `null` ровно при `pending` |
| `earnedPoints` | `number \| null` | итоговые баллы; `null` при `pending` |
| `totalPoints` | `number` | максимум попытки, включая 3 балла за каждый открытый вопрос |
| `autoEarnedPoints`, `autoTotalPoints` | `number` | баллы автопроверки и их максимум только по не-открытым вопросам (D-01). Присылает сервер, web ничего не суммирует |

Правила:
- «X из Y» одинаковы для ученика и проверяющего: пара `autoEarnedPoints` из `autoTotalPoints`. Различается только подпись: «предварительно» у ученика, «авто» у проверяющего **[авто]**.
- У `none` и `graded` в строке «баллы» стоит `earnedPoints / totalPoints` как сейчас.
- `clampPercent(null)`, `?? 0` и приведение `null` к нулю запрещены на всём пути до экрана (решение вехи). Тип `number | null` заставляет компилятор показать все места.
- Если `autoTotalPoints === 0` (в тесте только открытые вопросы), «X из Y» не показывается: остаётся одна метка «На проверке» **[авто]**.
- В сводке списка: `summary.averageScore: number | null` (`null` — нет ни одной попытки без проверки), `summary.passed` считается без попыток на проверке, новое `summary.pendingTotal` — число попыток на проверке по всей зоне видимости, независимо от фильтров, в том же охвате, что `scopeTotal`.

Вид результата (`attempt-result-view.ts`), один на все читатели:

```ts
type AttemptResultView =
	| { kind: 'pending'; auto: { earned: number; total: number } | null }
	| { kind: 'final'; percent: number; passed: boolean; points: { earned: number; total: number }; teacherChecked: boolean }
```

`auto` равен `null`, когда `autoTotalPoints === 0`. `teacherChecked` истинно ровно при `reviewStatus === 'graded'` (D-03): попытки только с автопроверкой выглядят как сейчас.

## Кто что видит (D-01, D-02) **[авто]**

D-02 относит к «ученику» профиль и шапку разбора, но обе страницы доступны только проверяющему (проверено выше). Подпись выбирается по зрителю, а не по странице: компонент `AttemptReviewLine` принимает `audience: 'student' | 'staff'`.

| Экран | Зритель | Подпись |
|-------|---------|---------|
| Список попыток админа и учителя | проверяющий | `На проверке` + мелко `авто X из Y` (D-01) |
| Разбор попытки (шапка) | проверяющий | то же (D-01) |
| Профиль ученика `/profile/<login>` | проверяющий | то же (D-01) |
| Дашборд, блоки «Последние попытки студентов» | проверяющий | то же |
| `TestRunner`: экран после сдачи и «Мои попытки» | ученик | `На проверке · предварительно X из Y` (D-02) |
| Страница теста: таблица попыток | ученик | то же (D-02) |
| Дашборд ученика | ученик | то же (D-02) |

Если пользователь решит показывать «предварительно» и на экранах проверяющего, меняется одно значение `audience` на вызове, вёрстка не меняется. Если когда-нибудь у ученика появится шапка разбора, она берёт `audience="student"`.

| Role | Value (существующие классы и переменные) | Usage |
|------|------------------------------------------|-------|

| Secondary (30%) | `bg-secondary` (непрозрачный) | метка «На проверке», нейтральная панель результата `TestRunner`, плитки сводки |
| Accent (10%) | `bg-primary text-primary-foreground` | новых мест нет |
| Positive tint | `bg-accent text-accent-foreground` | только отметка «проверено учителем» |
| Destructive | `text-destructive` | только текст отказа в красном баннере, который уже стоит в `TestRunner`; новых красных элементов нет |
| Muted text | `text-muted-foreground` | «авто X из Y», «предварительно X из Y», пояснения |

Accent reserved for (новое в этой фазе), исчерпывающий список:
1. `text-primary` у пиктограммы `Clock3` в плитке «на проверке» (как у пиктограмм остальных плиток сводки);
2. `border-primary` у нажатой плитки «на проверке» (состояние «фильтр включён»; фон при этом `bg-card`, заливки акцентом нет).

Других новых мест с `primary` нет; метки «На проверке» и «проверено учителем» используют `secondary` и `accent`.

Почему «На проверке» не жёлтая и не красно-зелёная: янтарный уже занят словом «Частично» (`getStatusClass('partial')`), зелёный и красный — вердикты «Пройден» / «Не пройден». Попытка на проверке не имеет вердикта, поэтому метка нейтральная: непрозрачная пара `bg-secondary` / `text-secondary-foreground`, пунктирная рамка (`border-dashed`) и пиктограмма `Clock3` как вторые признаки, не только цвет.

Контраст текста, измерен по токенам `globals.css` (OKLCH в sRGB, формула WCAG), порог AA 4,5:1:

| Пара | Светлая | Тёмная | Где |
|------|---------|--------|-----|
| `secondary-foreground` на `secondary` | 9,67 | 14,48 | метка «На проверке» |
| `accent-foreground` на `accent` | 10,45 | 9,95 | «проверено учителем» |
| `muted-foreground` на `card` | 6,05 | 2,06 | «авто X из Y» на карточках списка |
| `muted-foreground` на `bg-secondary/55` поверх `card` | 5,46 | — | подписи в плитках и шапке разбора |
| `muted-foreground` на `secondary` (непрозрачный) | 5,00 | — | пояснение в панели результата `TestRunner` |
| `foreground` на `secondary` | 12,78 | — | текст панели результата |
| `primary-foreground` на `primary` | 5,81 | — | не используется |
| `border-primary` на `card` (рамка нажатой плитки, не текст, порог 3:1) | 5,93 | — | плитка «На проверке» |
| `ring` на `card` (кольцо фокуса, порог 3:1) | 3,44 | — | фокус плитки |

Для сравнения существующая зелёная плашка «Пройден»: 4,72 (`green-700` на `green-50`), красная «Не пройден»: 5,88.

Тёмная тема: измерения выше честные, и они плохи за пределами новых элементов. В `[data-theme='dark']` карточка `--card: var(--color-primary)` получает светло-серый `oklch(0.922 0 0)`, а `--card-foreground` и `--foreground` — белый: `foreground` на `card` даёт 1,21, `muted-foreground` на `card` 2,06. Это существующий дефект палитры, он касается всего приложения и вне этой фазы. Тема при этом недостижима (список в таблице «Design System»). Следствие для фазы: обе новые метки используют непрозрачные парные токены (`secondary` + `secondary-foreground`, `accent` + `accent-foreground`), поэтому проходят AA независимо от того, что под ними. Подпись «авто X из Y» стоит там, где сейчас стоит мелкая строка `X/Y` того же цвета, и наследует её контраст. Исправление палитры тёмной темы в фазу не входит.

Проверка в плане: после реализации измерить контраст меток по вычисленным стилям в браузере (правило проекта), а не по этой таблице.

## Поверхность 1. Общие метки (RES-03, D-01…D-03)

**Фокус:** слова «На проверке», «предварительно X из Y», «авто X из Y» и «проверено учителем» читаются одинаково везде.

### `ReviewStatusChip`

```tsx
<Badge
	variant="secondary"
	className="gap-1 rounded-full border-dashed border-secondary-foreground/40 px-2 py-1 font-medium whitespace-nowrap hover:bg-secondary"
>
	<Clock3 className="size-3.5" aria-hidden="true" />
	На проверке
</Badge>
```

`px-2 py-1` заменяют `px-2.5 py-0.5` исходника (кратно 4); `hover:bg-secondary` отключает затемнение `Badge` при наведении: метка неинтерактивна. Внутри строки-ссылки списка метка не меняется при наведении на строку.

### `TeacherCheckedMark`

```tsx
<span className="inline-flex items-center gap-1 rounded-full bg-accent px-2 py-1 text-xs font-medium whitespace-nowrap text-accent-foreground">
	<BadgeCheck className="size-3.5" aria-hidden="true" />
	проверено учителем
</span>
```

Только с текстом, пиктограмма отдельно не используется. Показывается ровно при `teacherChecked`.

### `AttemptReviewLine`

| Зритель | Разметка | Текст |
|---------|----------|-------|
| `student` | `ReviewStatusChip`, затем `<span aria-hidden="true">·</span>`, затем `<span class="text-xs text-muted-foreground">предварительно {X} из {Y}</span>` | `На проверке · предварительно 5 из 7` |

| `title` | `{тест} · {N}%` | `{тест}` без процента |
| `subtitle` | `{тема} · {ученик} · Сдано \| Не сдано · {дата}` | `{тема} · {ученик} · На проверке · {дата}` |

Совпадение по тексту: процент попытки на проверке в искомую строку не входит, поэтому поиск «85» её не найдёт. Слово из метки (`проверке`) её находит, как слово «Сдано» находит сданные.

## Поверхность 8. Предел длины ответа и отказы сдачи (RES-05, D-06, D-07, D-08)

### Поле краткого ответа

`QuestionInput` для шаблона `short_text`: на `Input` ставится `maxLength={SHORT_TEXT_MAX_LENGTH}` (200, константа из `@bio-exam/exam-core`, общая с сервером, D-06). Поле `sequence_digits` не меняется. Внешний вид, подсказка и ширина (`max-w-xs`) не меняются.

В этой фазе у краткого ответа счётчика нет (D-08): настоящий ответ короче предела на порядок, предел срабатывает почти только при вставке. Вставка длиннее предела обрезается браузером без сообщения; это принятое ограничение этой фазы **[авто]**.

### Правило счётчика (контракт для фазы 14, не строится здесь)

Поле открытого ответа (до `OPEN_TEXT_MAX_LENGTH` = 5 000 знаков) и все последующие поля с пределом следуют одному правилу:

| Что | Правило |
|-----|---------|
| Когда виден | с длины `ceil(0,8 × предел)` (для 5 000 это 4 000), раньше счётчика нет |
| Формат | `{n} / {предел}`, числа с неразрывным пробелом тысяч (`Intl` `ru-RU`): `4 100 / 5 000` |
| Вид | `text-xs text-muted-foreground tabular-nums`, под полем справа |
| На пределе | ввод останавливается (`maxLength`); счётчик получает `text-foreground font-medium`, красного нет (предел — не ошибка, красный зарезервирован за ошибками) |
| Озвучивание | число в живую область не выводится (шум при каждом знаке); при достижении предела один раз озвучивается `Достигнут предел {предел} знаков` через `aria-live="polite"` |
| Связь с полем | счётчик связан через `aria-describedby` |

### Отказы сдачи и черновика (D-07)

Сервер отвечает **422** (тот же статус и форма, что у `TIME_EXPIRED`): тело `{ error: 'ANSWERS_INVALID', reason, limit? }`. Тексты принадлежат web, по образцу `SUBMIT_FLOW_TEXT` и `BANNERS` в `components/tests/attempt-submit-flow.ts`; серверных английских строк пользователь не видит (правило фазы 8). Коды и имена причин — рабочие, решает планировщик.

`classifySubmitFailure` сейчас отправляет любой неизвестный 4xx в `retry` («Не удалось сохранить ответы. Попробуйте еще раз.» с кнопкой «Повторить»): для этих отказов повтор ничего не изменит. Поэтому добавляется вид `answers-invalid` с отдельным баннером; существующие 409, `TIME_EXPIRED`, 403, 404 разбираются раньше и не меняются.

| Причина (`reason`) | Текст баннера | Действие |
|--------------------|---------------|----------|
| краткий ответ или последовательность длиннее предела (`short_text_too_long`) | `Ответ не может быть длиннее 200 знаков. Сократите ответ и отправьте снова.` | нет; кнопка сдачи остаётся доступной |
| текст открытого ответа длиннее предела (`open_text_too_long`) | `Текст ответа не может быть длиннее 5 000 знаков. Сократите ответ и отправьте снова.` | нет; кнопка сдачи остаётся доступной |
| ответ на вопрос, которого нет в тесте (`foreign_question`) | `В ответах есть вопрос, которого нет в этом тесте. Обновите страницу: тест мог измениться.` | `Обновить страницу` |
| неизвестный тип вопроса (старая вкладка) (`unknown_question_type`) | `Один из вопросов больше не поддерживается в этой версии страницы. Обновите страницу.` | `Обновить страницу` |
| ответ не той формы или сверх предела элементов (`answer_shape_invalid`) | `Один из ответов не удалось принять. Обновите страницу и отправьте ответы снова.` | `Обновить страницу` |

Баннер — существующий розовый блок `rounded-lg border border-rose-200 bg-rose-50 p-4` с `role="alert"` и кнопкой `outline sm`; вёрстка не меняется. Числа 200 и 5 000 берутся из констант `exam-core`, а не пишутся в тексте вручную; тысячи — неразрывный пробел. Что после отказа `answers-invalid` модуль попытки возвращается в фазу, где сдача доступна, проверяется в плане (характеризационный тест `lifecycle-submit`).

Автосохранение ответов (черновик, D-07): ограничение поля `maxLength` гарантирует, что очередь отправляет не больше предела; если сервер всё же ответит 4xx, действует существующее состояние строки сохранения («не сохранено» с повтором) без нового текста **[авто]**.

## Поверхность 9. Тип `open` в админских настройках (OPEN-02)

Тип `open` засевается неактивным и включается только в фазе 17. Добавление шаблона `open` в `QUESTION_UI_TEMPLATES` касается трёх админских мест.

| Место | Решение |
|-------|---------|
| «Правила баллов» (`admin/tests/scoring/ScoringSettingsPageClient.tsx`) | **Тип скрыт** **[авто]**: из списка аккордеона исключаются типы с метрикой `manual` (максимум 3 не редактируется, настраивать нечего). Крэш-защита: `TEMPLATE_META` (объект, индексируемый шаблоном) получает запись `open`, а проверка `isMetricAllowedForTemplate` и редактор формулы к `open` не обращаются. Селекторы темы и теста не меняются |
| Список типов вопросов (`admin/tests/question-types/QuestionTypesPageClient.tsx`) | `open` показан как остальные типы, в той же строке пометок (ключ, шаблон, `system`, `disabled`); ссылка `Настроить` остаётся |
| Карточка типа `open` (`question-types/[key]/QuestionTypeDetailsPageClient.tsx`) | переключатель `Активен` — `disabled`, под подписью замещающий текст `Открытые вопросы пока недоступны.` (`text-xs text-muted-foreground`), чтобы тип нельзя было включить раньше фазы 17; вместо редактора формулы начисления — строка `Баллы за открытый вопрос выставляет учитель: от 0 до 3.` Сервер дополнительно отказывает во включении (серверная часть плана) |

В этой фазе не строятся: выбор типа `open` в редакторе вопросов, карточки критериев, раннер открытого ответа.
