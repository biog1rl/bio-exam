# Bio-Exam Server

Express API платформы тестирования Bio-Exam: данные, авторизация и правила доступа живут здесь
(ADR-0001, `docs/adr/0001-express-owns-data-and-access-policy.md`). Web только показывает то, что решил сервер.

Это краткий обзор. Точные маршруты и их параметры не перечислены, потому что они живут в коде и меняются:
смотрите `src/routes/index.ts` и используйте `codegraph explore "<маршрут или символ>"`.

## Области API

Все маршруты, кроме проверки здоровья, лежат под префиксом `/api`.

| Область         | Префикс                           | Назначение                                         |
| --------------- | --------------------------------- | -------------------------------------------------- |
| Авторизация     | `/api/auth`, `/api/auth/refresh`  | вход, выход, текущий пользователь, приглашения     |
| Пользователи    | `/api/users`                      | профили, роли пользователей, аватары               |
| Группы          | `/api/groups`                     | учебные группы и их состав                         |
| Права           | `/api/rbac`                       | роли, выдача и снятие прав поверх реестра ролей    |
| Тесты и попытки | `/api/tests`, `/api/tests/public` | банк вопросов, тесты, назначения, попытки и разбор |
| Поиск           | `/api/search`                     | поиск по вопросам и тестам                         |
| Настройки       | `/api/settings`                   | настройки платформы                                |
| Сайдбар         | `/api/sidebar`                    | пункты меню                                        |
| Документы       | `/api/docs/assets`                | картинки медиатеки через модуль хранилища          |
| Здоровье        | `/healthz/db`                     | проверка соединения с базой                        |

## Правила доступа

- Вход создаёт серверную сессию (`auth_sessions`) и выдаёт две cookie: access-JWT в `SESSION_COOKIE_NAME` и
  refresh-токен в `refresh_token`. Access несёт `sub`, `sid` (id сессии) и `login`, живёт `ACCESS_TOKEN_EXPIRES_SEC`
  секунд (по умолчанию 900, допустимо от 60 до 3600) и принимается только при неотозванной сессии активного
  пользователя.
- Ответы `POST /api/auth/login`, `POST /api/auth/refresh` и `GET /api/auth/me` содержат `accessExpiresAt`: момент
  истечения текущего access в ISO 8601 UTC.
- `POST /api/auth/refresh` принимает refresh-токен один раз и выдаёт новую пару в той же сессии; срок refresh скользящий,
  `REFRESH_TOKEN_EXPIRES_DAYS` дней от последнего обновления. Повтор уже использованного токена в течение 30 секунд,
  пока его преемник не использован, получает только новый access той же сессии. Повтор позже 30 секунд или после
  использования преемника отзывает сессию целиком и отвечает 401.
- Сессию отзывают: выход (`POST /api/auth/logout`), смена пароля (все сеансы пользователя, кроме текущего),
  деактивация пользователя (`PATCH /api/users/:id` с `isActive: false`) и администратор с правом `users.edit` через
  `POST /api/users/:id/sessions/revoke` (все сеансы пользователя). Вместе с сессией отзываются её refresh-токены.
  Причина отзыва записывается в `auth_sessions.revoke_reason`.
- Маршруты, которым нужен пользователь, закрыты `sessionRequired()`, остальные видят сессию через `sessionOptional()`.
- Роли и права читаются из базы на каждом запросе одним модулем `src/services/access-policy`: роли (`admin`,
  `teacher`, `user` в `packages/rbac`) и переопределения в базе. Маршрут требует право `домен.действие` через
  `requirePerm('домен', 'действие')`, например `tests.write` или `rbac.read`. Снятие роли действует со следующего
  запроса и сессию не отзывает. При ошибке базы прав ответ — ошибка, запасного набора прав нет.
- Правила доступа решает только Express (ADR-0001). Проверок прав в web на замену серверным нет.
- Вход ограничивает троттлинг в таблице `login_throttle` (`src/services/login-throttle`). Считаются только неудачи,
  блокировки аккаунта нет. Логин нормализуется `toLowerCase().trim()`, IP берёт `clientIp(req)` (`req.ip` при
  `trust proxy 1`).
  - Пара (логин, IP): первые 5 неудач без паузы, дальше окно 30 секунд, удваивается до потолка. Успешный вход удаляет
    корзину пары.
  - Логин по всем IP: после 20 неудач окно 30 секунд, затем 60 секунд.
  - Ограниченная попытка получает 429 с заголовком `Retry-After` (целые секунды до конца самого длинного окна) и
    одинаковым телом для существующего и несуществующего логина; пароль при этом не проверяется.
  - Счётчик корзины обнуляется, если последняя неудача старше суток; такие строки удаляются при записи.
  - Константа `IP_TRUSTED` в `src/services/login-throttle/progression.ts` равна `false`, пока не проверено, какой IP
    видит Express за rewrite Vercel: корзины «IP по всем логинам» нет, потолок пары 60 секунд. При `IP_TRUSTED = true`
    потолок пары 15 минут и действует корзина по IP (после 50 неудач окно от 30 секунд до 5 минут).

### Роли и зона учителя

- Роли в `packages/rbac/src/roles.ts`:
  - `admin` («Администратор») — все действия доменов `users`, `rbac`, `settings`, `tests`, `groups` и `zone`, в том
    числе право `zone.all`;
  - `teacher` («Учитель») — `tests.read`, `tests.write`, `tests.manage_assignments`, `groups.manage_groups`,
    `users.read`, `users.invite`;
  - `user` («Ученик») — без прав.

  `admin` и `teacher` — персонал (`STAFF_ROLE_KEYS`).

- Право `zone.all` снимает ограничение зоной: с ним действие разрешено на любом объекте, без него — только в зоне
  пользователя. Переопределение `zone.all` в базе действует как любое другое право.
- Зона учителя — закреплённые за ним разделы (таблица `teacher_topics`) и группы, где он владелец
  (`student_groups.owner_id`). Тесты зоны — тесты её разделов, попытки — попытки этих тестов, ученики — участники её
  групп. Таблицы зоны читает и пишет только `src/services/access-policy` (`zone-loader.ts`, `zone-store.ts`).
- Решения о доступе принимают функции шва `src/services/access-policy/scope.ts`: `canReadTest`, `canWriteTest`,
  `canWriteTopic`, `canReviewAttempt`, `canReadUser`, `canManageCatalog`, `canManageGroup`, `canManageStudent`,
  `canAssign`, `canAssignMany`, `canAssistSignIn`, `hasGlobalZone`, а для списков — `testScope`, `groupScope`,
  `userScope`. Ветвление «администратор или учитель» в маршрутах идёт через `hasGlobalZone`, литерала `zone.all` вне
  модуля и тестовых фикстур нет.
- Списки закрыты грубым гейтом `requirePerm` и фильтруются по зоне: `{ all: true }` или идентификаторы разделов и
  групп. Пустая зона даёт пустой список и нулевую сводку. Объектный маршрут без `requirePerm` первой строкой вызывает
  свою функцию шва: отказ — 403 до поиска объекта, затем 404, если объекта нет. Поэтому учитель получает 403 и на
  несуществующий объект, а пользователь с `zone.all` — 404. Маршруты по slug (`/api/tests/by-slug/...`,
  `/api/tests/topics/:slug/export`) при пустой зоне отвечают 403, иначе сначала ищут объект: нет объекта — 404, объект
  вне зоны — 403. Ответы в экспорте (`withAnswers`) отдаются по праву записи раздела (`canWriteTopic`).
- Каталог (создание, правка и удаление разделов, закрепление учителей `PUT /api/tests/topics/:id/teachers`, общие
  типы вопросов, общие правила оценки) решает `canManageCatalog`: `tests.write` вместе с `zone.all`.
- Признаки ролей считает `roleTraits` из `role-traits.ts` по правам роли с учётом переопределений роли в базе:
  - `ownsZone` — роль без `zone.all` с одним из прав `tests.write`, `groups.manage_groups`, `users.invite`. Только
    активный пользователь с такой ролью закрепляется за разделом и назначается владельцем группы;
  - `groupMember` — роль без прав управления (`tests.write`, `tests.manage_assignments`, `groups.manage_groups`,
    `users.read`, `users.edit`, `users.invite`).

  Оба признака отдаёт `GET /api/rbac/roles`.

- Ученик — пользователь с ролью `user`, без других ролей и без allow-переопределений прав (`studentOnlyFilter`).
  Учитель добавляет в свою группу, назначает тесты и приглашает только учеников; администратор не добавляет персонал
  в группу с владельцем-учителем (400).
- Зона освобождается (`releaseZone`: строки `teacher_topics` удаляются, `owner_id` групп становится `NULL`) при
  деактивации пользователя (`PATCH /api/users/:id` с `isActive: false`) и при смене ролей на набор, в котором нет роли
  с признаком `ownsZone`.
- Приглашение `POST /api/auth/invites` без `zone.all`: только роль ученика и обязательная группа, которой управляет
  приглашающий (`canManageGroup`). Повторная ссылка — только своему ученику (`canManageStudent`), который ещё не
  активировал приглашение; активированному — 409.
- Учитель снимает назначения теста только свои; назначения коллеги и администратора — 403. Снятие ограничения входа
  и завершение сеансов (`canAssistSignIn`): с `zone.all` нужно право `users.edit`, без него — только для учеников
  своих групп (`canManageStudent`).
- `DELETE /api/tests/:id` без `zone.all` отвечает 409, если у теста есть попытки учеников; попытки персонала не
  считаются. Сводка `/api/tests/admin/dashboard` и список `/api/tests/admin/attempts` не включают попытки персонала ни
  для кого.

### Снять ограничение входа

- Окна истекают сами, самое длинное при `IP_TRUSTED = false` длится 60 секунд.
- Администратор с правом `users.edit` вызывает `DELETE /api/users/:id/login-throttle`: удаляются все корзины по логину
  пользователя, ответ `{ ok: true, cleared: N }`, повтор безопасен.
- Если ограничен сам администратор, оператор выполняет в консоли базы:

  ```sql
  DELETE FROM login_throttle WHERE login = '<логин в нижнем регистре>';
  ```

### Попытка теста

- Проходить опубликованный тест в активной теме может пользователь, которому тест назначен (`test_assignments`), или
  пользователь с правом `tests.read`. Правило проверяют `canReadTest` и `testScope` из
  `src/services/access-policy/scope.ts`, назначение читает `src/services/attempt-sessions`. Маршруты
  `/api/tests/public/...` не проверяют назначение и права сами. Тест не опубликован или тема неактивна — 404, тест не
  назначен — 403. Списки тестов (`GET /api/tests/public/tests`, `GET /api/tests/public/topics/:slug/tests`) содержат
  только доступные пользователю тесты.
- Разбор попытки `GET /api/tests/admin/attempts/:attemptId` требует право `tests.read` и проверку `canReviewAttempt`
  из того же модуля.
- Список `GET /api/tests/admin/attempts` фильтрует на сервере: `limit` (1…100, по умолчанию 50), `offset`, `q`
  (без учёта регистра по имени ученика, тесту и теме; логин — только при `zone.all`), `topic` (slug), `student`
  (uuid), `from` и `to` (ISO-время, включительно), `status` (`active`, `inactive`, `all`; по умолчанию `all`). Неверный
  параметр — 400. Ответ: `rows`, `total` с фильтрами, `limit`, `offset`, `summary` (`passed`, `averageScore`) по
  отфильтрованному набору, `scopeTotal` и `facets` (`topics`, `students`) по всей зоне без фильтров.
- `POST /api/tests/public/tests/:id/start` возвращает открытую сессию пары (тест, пользователь) или открывает новую
  (`test_sessions`). У пары открыта не больше одной сессии: частичный уникальный индекс `test_sessions_open_uniq` по
  строкам без `submitted_at` и `closed_at`. Ответ: `sessionId`, `startedAt` и черновик.
- `PATCH /api/tests/public/tests/:id/sessions/:sessionId/answers` сохраняет ответ и телеметрию в черновик открытой
  сессии под блокировкой строки. Сданная или закрытая сессия — 404.
- Сессия теста с `time_limit_minutes` просрочена, когда `now()` базы позже `started_at` плюс лимит плюс 2 минуты
  (`ATTEMPT_GRACE_PERIOD_MINUTES` в `@bio-exam/exam-core`). Срок проверяется на момент прихода submit, до оценки:
  долгая оценка не превращает принятую отправку в 422. Просроченная сессия закрывается с `close_reason = 'expired'` при
  submit или при `start`, который затем открывает новую сессию. `close_reason = 'superseded'` у лишних открытых сессий
  пары, закрытых миграцией 0022 (открытой осталась самая поздняя).
- `POST /api/tests/public/tests/:id/submit`, тело `{ sessionId, clientAttemptId, answers, telemetry? }`
  (`SubmitAttemptRequestSchema`). `sessionId` и `clientAttemptId` — обязательные UUID, `clientAttemptId` создаёт
  клиент один раз на отправку. Ответы:
  - 400 — тело не прошло схему;
  - 403 — тест не назначен;
  - 404 — тест не виден, сессии нет у пары или она закрыта как `superseded`;
  - 409 `{ error: 'ATTEMPT_ALREADY_SUBMITTED', attemptId }` — сессия уже сдана с другим `clientAttemptId`;
  - 422 `{ error: 'TIME_EXPIRED' }` — сессия просрочена или закрыта как `expired`;
  - 200 — вид попытки. Повтор с теми же `sessionId` и `clientAttemptId` отвечает 200 с видом уже сохранённой попытки
    и новой не создаёт. На сессию приходится не больше одной попытки: уникальный индекс
    `test_attempts_session_id_uniq`.
- Попытка с `results_version = 2` хранит в `test_attempts.results` факты оценки по вопросу
  (`ScoredQuestionFactSchema`): баллы, `isCorrect`, ответ, ключ на момент сдачи и его версию, вердикты по частям, число
  ошибок и пояснение. Факты считает `scoreSubmission` из `src/services/scored-attempt`.
- Ответ submit и разбор строятся из сохранённой строки: `readAttemptView` для студента (`AttemptViewSchema`) и
  `readAdminAttemptView` для администратора (`AdminAttemptViewSchema`). Вид вопроса содержит статус (`ungraded` при 0
  баллов, `correct`, `partial`, `wrong`), `keyVisible`, `correctAnswer`, `verdicts` и `mistakes`. Студент видит ключ,
  вердикты и число ошибок, когда у теста включён `show_correct_answer`; при выключенном — только вердикты верно
  отвеченного вопроса. Администратор видит ключ всегда, а также ответы и телеметрию. Web берёт статус и ключ только из
  вида, `test_attempts.results` читает только `src/services/scored-attempt`.
- Попытка с `results_version = 1` (значение столбца по умолчанию) хранит `results` в прежней форме
  (`LegacyAttemptResultsSchema`) и читается без перезаписи строки. Ключ берётся из сохранённого `correctAnswer`, иначе
  из версии `answer_keys`, созданной не позже `submitted_at` попытки. Без ключа вопрос показывается без ключа и
  вердиктов. Вердикты пересчитываются, только если пересчёт совпал с сохранёнными баллами и `isCorrect`. Строка, не
  прошедшая схему своей версии, даёт ошибку `AttemptResultsShapeError`.

## Шаблоны вопросов

Тип вопроса задаётся одним из шести шаблонов интерфейса, у каждого своя метрика ошибок. Реестр шаблонов, метрик и встроенных типов и оценка ответа находятся в пакете `packages/exam-core` (`@bio-exam/exam-core`), сервер импортирует их оттуда:

- `single_choice`: один правильный вариант из списка;
- `multi_choice`: несколько правильных вариантов, ошибка считается по расстоянию между наборами;
- `matching`: сопоставление пар, ошибка считается по числу неверных пар;
- `short_text`: короткий текстовый ответ, сравнение без учёта пробелов, допускается набор верных ответов;
- `sequence_digits`: последовательность цифр, ошибки считаются по несовпадениям позиций и разнице длины; перестановка двух соседних цифр в последовательности длиннее трёх цифр считается одной ошибкой.
- `open`: развёрнутый ответ, баллы от 0 до 3 выставляет учитель; тип засеян выключенным, сервер не даёт его включить и менять его правило.

## Хранилище файлов

Модуль `src/services/storage` — единственный путь к файлам хранилища. Модуль проверяет ключ до обращения к драйверу.

### Драйверы

- `local`: каталог на диске из `STORAGE_LOCAL_DIR` (абсолютный путь). Запись атомарная, symlink за пределы
  каталога не проходят.
- `supabase`: бакет Supabase Storage по `SUPABASE_URL` и `SUPABASE_SERVICE_KEY`, имя бакета из
  `SUPABASE_STORAGE_BUCKET` (по умолчанию `main`). Список обходит все страницы, сбои 5xx и сетевые повторяются.
- `memory`: объекты в памяти процесса, только для тестов.

Порядок выбора при первом обращении к хранилищу:

1. `STORAGE_DRIVER=local` — драйвер `local`; без абсолютного `STORAGE_LOCAL_DIR` ошибка конфигурации.
2. `STORAGE_DRIVER=memory` — драйвер `memory` в изолированном режиме тестов (`BIO_EXAM_ISOLATED_ENV=1`), иначе ошибка
   конфигурации.
3. `STORAGE_DRIVER=supabase` или переменная не задана: в изолированном режиме без драйвера — `memory`, а `supabase`
   запрещён; вне изоляции при заданных `SUPABASE_URL` и `SUPABASE_SERVICE_KEY` — драйвер `supabase`.
4. Иначе — ошибка конфигурации. У модуля нет запасного пути на диск.

### Ключи

Ключ — относительный путь из непустых сегментов внутри одного из пространств имён:

- `images/` — картинки медиатеки;
- `topics/` — содержимое вопросов и тестов;
- `avatars/` — аватары пользователей.

Отклоняются ключи с ведущим `/` или `\`, буквой диска, `\`, NUL и управляющими символами, пустыми сегментами,
сегментами `.` и `..` (в том числе после процентного декодирования `%2e%2e`, `%252e%252e`), символами `?` и `#`,
кодированными разделителями `%2F` и `%5C` (на любой ступени декодирования), а также ключи вне пространств имён: имя
бакета (`main/...`), `storage/v1/...`, URL. `%20` и кириллица в ключе допустимы. Адаптер `supabase` кодирует сегменты
ключа в URL запросов чтения, проверки и записи.

### Ключ и URL

- Любой файл хранилища, включая аватар, отдаётся маршрутом приложения `/api/docs/assets/proxy?path=<ключ>` на любом
  драйвере, только вошедшему пользователю. Бакет Supabase приватный, публичные URL бакета не выдаются.
- URL стабилен для одного ключа: ключи неизменяемы, новый файл получает новое имя.

### Ошибки

| Код | Ошибка                    | Когда                                                     |
| --- | ------------------------- | --------------------------------------------------------- |
| 400 | `StorageKeyError`         | ключ некорректен или выходит за корень                    |
| 404 | `StorageNotFoundError`    | нет источника копирования или отдаваемого файла           |
| 409 | `StorageConflictError`    | объект уже есть, запись без перезаписи                    |
| 503 | `StorageUnavailableError` | хранилище недоступно после повторов                       |
| 500 | `StorageConfigError`      | хранилище не настроено или драйвер запрещён в этом режиме |

Чтение отсутствующего объекта возвращает `null`, удаление отсутствующего объекта не ошибка.

### Индекс ссылок на картинки

Таблица `question_asset_refs` хранит пары «вопрос → ключ картинки» из промпта и пояснения. Модуль содержимого
переписывает ссылки вопроса и ставит `questions.assets_indexed = true` в той же транзакции, что и указатели на файлы.

Удаление в медиатеке (`DELETE /api/docs/assets`):

- пока есть вопрос с `assets_indexed = false`, удаление отклоняется: 409
  `{ error: 'Удаление недоступно: ссылки на изображения ещё не проиндексированы' }`;
- картинка в индексе или в черновике вопроса (`question_drafts.payload`) не удаляется: 409
  `{ error: 'Изображение используется в вопросах', usage: { questions, drafts } }`.

```bash
yarn workspace @bio-exam/server assets:refs
yarn workspace @bio-exam/server assets:refs --write
```

- Без флага команда только печатает инвентаризацию: ссылки по формам и пространствам имён, ссылки вне `images/`,
  `topics/*/*/assets/` и `avatars/`, ссылки на ключи, которые не отдаёт маршрут картинок (`nonServable`),
  некорректные ссылки, отсутствующие объекты и указатели на отсутствующий файл. Последняя строка
  `[asset-refs] STOP D-19: …` с ненулевыми числами означает, что до выкатки нужно решение по этим ссылкам.
- С флагом `--write` команда после инвентаризации заполняет индекс для вопросов с `assets_indexed = false` и ставит
  маркер. Уже проиндексированные вопросы не меняются, объекты и строки не удаляются.
- Окружение берётся из `app/server/.env`. Против боевой базы команду запускают отдельной осознанной операцией.

### Сверка хранилища

```bash
yarn workspace @bio-exam/server storage:reconcile
yarn workspace @bio-exam/server storage:reconcile --delete-orphans
yarn workspace @bio-exam/server storage:reconcile --delete-legacy-json
```

- Без флагов команда только печатает отчёт и ничего не пишет: сироты (файлы `.md` под `topics/*/*/questions/*/`,
  которые не читает ни один вопрос: не указатель и не кандидат старых путей промпта и пояснения), свежие сироты
  моложе часа, указатели на отсутствующие объекты, для которых не найден ни один кандидат, сохранённые
  `answer_keys.json` и `settings.json` теста, число объектов под `topics/*/*/assets/` и прочие объекты под `topics/`.
- `--delete-orphans` удаляет только сирот. Сироты моложе часа не удаляются: это может быть правка, указатель которой
  ещё не записан. Перед удалением указатели и кандидаты вопросов перечитываются из базы.
- `--delete-legacy-json` удаляет только `topics/*/*/answer_keys.json` и `topics/*/*/settings.json`.
- Картинки `images/`, `topics/*/*/assets/` и прочие объекты под `topics/` команда не удаляет ни с одним флагом.
- Окружение берётся из `app/server/.env`. Против боевой базы и бакета команду запускают отдельной осознанной
  операцией, сначала без флагов.

### Изолированный режим

В изолированном режиме тестов (`BIO_EXAM_ISOLATED_ENV=1`) загрузки картинок, аватаров и файлов вопросов идут через
тот же модуль хранилища на драйвере `memory` или `local`. Supabase Storage в этом режиме запрещён, запасного пути на
диск у маршрутов нет.

## Запуск и миграции

Команды выполняются из корня репозитория, окружение берётся из `app/server/.env` (пример: `app/server/.env.example`).

```bash
yarn workspace @bio-exam/server dev
yarn workspace @bio-exam/server build
yarn workspace @bio-exam/server start
yarn workspace @bio-exam/server drizzle:generate
yarn workspace @bio-exam/server drizzle:migrate
yarn workspace @bio-exam/server seed
yarn workspace @bio-exam/server bootstrap:admin
```

- `dev` запускает сервер с перезагрузкой, `build` и `start` собирают и запускают `dist`.
- `drizzle:generate` создаёт новую миграцию из `src/db/schema.ts`, `drizzle:migrate` применяет `drizzle/` к базе из
  `DATABASE_URL`. Применённые миграции не редактируются.
- `seed` создаёт роли из `packages/rbac`, `bootstrap:admin` создаёт первого администратора по `ADMIN_BOOTSTRAP_*`.
- Против боевой базы миграции не запускают из разработки: это отдельная осознанная операция.

## Тесты

```bash
yarn workspace @bio-exam/server test
node scripts/with-test-db.mjs yarn workspace @bio-exam/server test
```

Первая команда запускает Vitest. Тестам, которым нужна база, требуется `TEST_DATABASE_URL`: одноразовую базу `test_*`
с ним даёт вторая команда или `yarn verify`. Тесты изолированы (`BIO_EXAM_ISOLATED_ENV=1`): они не читают `.env`, а адрес базы берут только
из `TEST_DATABASE_URL` и принимают лишь локальные базы с именем `test_*`.
